# ТЗ v2 · 02 — Сбор данных (crawling)

> Схема таблиц — `01-database.md` (§7 краулинг, §3 ядро). Живая разведка источника — `research/eis-csv-recon.md`. Опыт v1 (heartbeat, курсор, ценовое дробление) — переносим.

## 1. Принципы

- **Метод забора — переключаемый параметр профиля**, не ветка кода. Один интерфейс, три реализации: `csv` (основной), `html` (запасной, для страниц с JS-рендером), `api` (задел на будущее).
- **HTTP-first.** Для ЕИС и листинг (CSV-экспорт), и детальные карточки (`documents.html`) отдаются server-side и **берутся обычным HTTP-клиентом без сессии** — подтверждено живой разведкой. Headless-браузер для ЕИС не нужен вовсе; он остаётся общим механизмом для будущих площадок с клиентским рендерингом.
- **Идемпотентность.** Повторный забор блока не плодит дублей — дедуп по `source_number` (reg_number) на инжесте.
- **Возобновляемость.** Любой оборванный прогон продолжается с курсора; heartbeat + recovery оборванных (канон v1).

## 2. Source-абстракция

```php
interface SourceMethod
{
    // Собрать блок листинга по курсору. Возвращает сырые строки + метаданные блока.
    public function collectListing(Crawler $crawler, ListingCursor $cursor): ListingBatch;

    // Детали одной закупки (карточка + список документов).
    public function collectDetails(string $sourceNumber, Registry $registry): ProcurementDetails;

    public function isAvailable(): bool;
}
```

- `SourceMethodFactory::make($crawler->source_method)` → конкретная реализация; `makeWithFallback()` — если основной недоступен и задан `fallback_method`, переключается и логирует.
- Реализации: `CsvSourceMethod` (HTTP), `HtmlSourceMethod` (через браузерный сервис, см. §7), `ApiSourceMethod` (заглушка контракта).
- Всё платформо-специфичное (URL-шаблоны, флаги колонок, парсинг карточки) — в адаптере площадки (`Eis\...`), ядро о ЕИС не знает.

## 3. Основной метод — CSV-экспорт (HTTP)

Параметры и поведение сервера зафиксированы разведкой (`research/eis-csv-recon.md`), ниже — сжатый регламент реализации.

### 3.1 Запрос

```
GET /epz/order/orderCsvSettings/download.html
  ?<параметры поиска площадки>      // из crawler.filter: morphology, fz44|fz223,
                                    //   sortBy, sortDirection, publishDateFrom/To,
                                    //   priceFromGeneral/To, okpd2, этапы, регион
  &from=<n>&to=<n+500>              // блок записей
  &<колонкаCsv>=true ...            // набор колонок (crawler.options.columns)
```

- Транспорт: Laravel `Http` через прокси-пул (RU-доступ). Сессия/cookies не требуются; желательны реалистичные `User-Agent`/`Referer`.
- Один endpoint обслуживает и 44-ФЗ (`fz44=on`), и 223-ФЗ (`fz223=on`) — различается флаг реестра и нормализация «способа закупки» (§3.4).

### 3.2 Формат ответа

- `Content-Type: application/download;charset=windows-1251`, `attachment`.
- Кодировка **Windows-1251** → на границе импорта конвертируем в UTF-8 (`iconv`/`mb_convert_encoding`); внутри — только UTF-8.
- Разделитель `;`, кавычки удваиваются (`""`), заголовок на русском. Колонки — только запрошенные, порядок фиксирован. Полный список флагов колонок — в research-файле.

### 3.3 Границы блоков и «тихий cap»

Поведение сервера, критичное для корректности (проверено):

- `from` округляется к границе блока 500; `to` фактически игнорируется — один запрос = **ровно 500 строк**.
- Реальный потолок глубины — около 10 000 строк; **за пределом сервер молча отдаёт последний блок** (тот же контент, без ошибки и без пустого ответа).
- Поэтому обязателен **детект повторного блока**: `crw_fetches.dedup_signature` = первый `reg_number` блока; совпал с предыдущим → достигли cap, стоп. На статус-код полагаться нельзя.

### 3.4 Инжест блока

1. Распарсить CSV → строки.
2. Дедуп внутри скана и против БД по `source_number` — unique-индекс `(registry_id, source_number)` на непартиционированной шапке `prc_procurements` (`01-database.md` §3).
3. Нормализовать «способ закупки»: 44-ФЗ — закрытый справочник (enum); 223-ФЗ — свободный текст по положению заказчика → маппинг-слой + хранение исходной строки.
4. Нормализовать статус через `plt_status_mappings` (сырой → канонический); неизвестный → `unknown` + алерт.
5. Записать через инжест-процессор: новая закупка → `prc_procurements` + ревизия + событие `discovered`; изменённая → сверка `snapshot_hash`, при отличии — новая ревизия + доменные события (`01-database.md` §11 чек-лист).
6. Зафиксировать `crw_fetches` (метрики блока, ссылка на сырой CSV в object storage).

## 4. Режимы обхода

### 4.1 Fresh (свежий поток)

- Расписание: cron профиля (по умолчанию ~30 мин).
- Сортировка `sortBy=UPDATE_DATE, sortDirection=false` (по убыванию обновления).
- Читаем блоки `from=1,501,1001…` **до первого полностью уже известного блока** (все `source_number` виденные и `source_updated_at` не изменился).
- За 30 минут поток обновлений заведомо ≪ 5000 → слепых зон нет **при штатной периодичности**. Сортировка живая — блоки одного скана снимаем подряд, без длинных пауз, с дедупом.
- **Защита от простоя (backlog > cap).** Если fresh-скан не выполнялся дольше обычного (даунтайм воркера/источника), накопленный объём обновлений может превысить cap (§3.3) — и «тихий cap» молча срежет часть, оставив только сигнал детекта повторного блока. Регламент: при срабатывании cap-стопа в fresh-режиме **не** продолжать обычное расписание молча, а поднять флаг «возможен пропуск» и запустить точечный **archive-рескан окна простоя** (по диапазону `source_updated_at` от последнего успешного скана до now, с дроблением как в §4.2). Так пропущенные обновления добираются гарантированно. Метрика «отставание fresh-скана» (05 §3) — триггер этого механизма.

### 4.2 Archive (перекачка истории)

- Идём по дням: `publishDateFrom = publishDateTo = <день>`, сортировка по возрастанию даты.
- Если в дне > лимита выборки — **рекурсивное ценовое дробление** (`priceFromGeneral/priceToGeneral`, бинарное деление интервала), как `priceSplitHook` v1, но цель — выборка ≤ 5000 и качаем CSV, а не HTML-страницы. Стоп-условие рекурсии — минимальный ценовой интервал (лог, если всё ещё переполнено).
- Курсор (`crw_runs.cursor`): текущий день, ценовой стек, номер блока. Возобновление с точки обрыва.
- Назначение архива — обучающий датасет; небольшие потери на краях допустимы.

## 5. Детальная карточка закупки (стадия «детальный анализ»)

Отдельная стадия после листинга: снять **полную карточку** извещения, не только файлы-документы. Структура снята живьём — `research/eis-card-recon.md`. Всё — server-side HTML, **обычный HTTP** без сессии; браузер — только запасной путь.

### 5.1 Вкладки карточки

`GET /epz/order/notice/<тип>/view/<вкладка>.html?regNumber=…`, `<тип>` = способ закупки (`ea20`/`ok20`/`zk20`/`ezt20`…). Шаблоны URL по типам — в `plt_registries.settings`; тип берём из ссылки листинга либо резолвим по `regNumber`.

| Вкладка | Что извлекаем → куда |
|---|---|
| `common-info` | все поля извещения → `prc_procurements` + `prc_eis_details` (ИКЗ-разбор, обеспечение, ЭТП, сроки исполнения, контактное лицо), финансирование по годам → `prc_financing`, роли (заказчик/размещающий/оператор) → `org_procurement_parties`, позиции объекта закупки (ОКПД2/КТРУ) → `prc_items` |
| `documents` | файлы-вложения (`filestore/...`) → `doc_documents` + `doc_versions` |
| `event-journal` | таблица «Дата/Событие» от ЕИС → `prc_events` (даты переходов этапов + факты размещения; **дополняющий** источник, парсинг текстовых строк — риск, `events-results-l2.md` §1; бизнес-данные строим из типизированных сущностей §4 в `01`, журнал — для дат/подтверждения) |
| `supplier-results` (у завершённых) | победитель, предложения участников → `prc_awards` + `prc_bids`; связь с реестром контрактов |

### 5.2 Регламент

- **Триггеры пересъёма** (не только `source_updated_at`): (1) новая закупка; (2) новая редакция (изменился `source_updated_at`); (3) **смена этапа** (`source_status` из листинга) — критично, т.к. публикация протокола/разъяснения/отмены может НЕ двигать `source_updated_at` (разъяснение/протокол не считаются редакцией извещения, `01` §4); (4) периодический ре-скан закупок на завершающихся этапах (`evaluation`/`awarded`) до появления результатов. Иначе `prc_protocols`/`prc_bids`/`prc_awards` рискуют остаться пустыми. Кэш вкладки — по её собственному хэшу контента, не только по дате обновления карточки.
- Каждая вкладка — отдельный под-шаг с идемпотентной записью (upsert по естественным ключам: `prc_items` по позиции, `org_procurement_parties` по `(procurement_id, organization_id, role)`, `prc_protocols` по номеру).
- Организации резолвим по ИНН/ОГРН в `org_organizations` (entity resolution), затем роль-строка в `org_procurement_parties`.
- Протоколы/разъяснения/отмены (`prc_protocols`/`prc_clarifications`/`prc_cancellations`) — из документов и журнала событий; типы для 44-ФЗ закрыты, для 223-ФЗ open-ended.
- Ошибки/ретраи и очередь — как у остальных стадий (`03` §4). Стадия ставит `prc_procurements.detail_fetched_at`.

## 6. Профили, прогоны, устойчивость

### 6.1 Профиль (`crw_crawlers`) и прогон (`crw_runs`)

- Профиль: реестр, режим (`fresh`/`archive`), метод + fallback, фильтр (jsonb), расписание, опции (колонки, лимиты дробления).
- Прогон: инвариант **один `running` на профиль** (частичный unique-индекс); heartbeat на каждом блоке; recovery оборванных по устаревшему `last_heartbeat_at`; курсор для возобновления; `stats` по стадиям.
- Менеджер прогона (аналог v1 `CrawlerRunManager`): `startOrResume` / `heartbeat` / `resetCursor` / `complete` / `fail`.

### 6.2 Вежливость к источнику и надёжность

- **Вежливый темп**: ограниченный параллелизм (единицы одновременных соединений), случайные паузы между запросами (секунды), консервативный лимитер на домен. Конкретные пороги калибруются в тестовом режиме — точные лимиты источника не документированы (research-файл, раздел «Не проверено»).
- **Сетевой доступ**: пул прокси (RU) в таблице `crw_proxies`; креды только там, не в конфигах профилей. Смена узла при недоступности.
- **Ретраи**: экспоненциальный backoff на `429`/`5xx`; отдельно — артефакт `200` с пустым телом (кэш-слой источника) лечится повтором.
- **Smoke-контроль актуальности**: периодический контрольный прогон с известным ожидаемым числом записей; алерт при резком изменении объёма или структуры CSV (смена набора колонок — признак редизайна источника).

## 7. Запасной backend — headless-рендеринг (Node-сервис)

Для площадок, где данные отдаются только после клиентского рендеринга, забор идёт через **отдельный сервис рендеринга страниц** (Node + Playwright) в собственном контейнере. Для ЕИС не задействуется.

### 7.1 Границы и контракт

- PHP — оркестратор (control-plane, Horizon-jobs); Node — исполнитель (execution-plane). PHP **не передаёт произвольный код**; общение — через типизированные задачи (`taskType`), сервис маппит их на версионированные обработчики.
- Асинхронный job-API:

```
POST /v1/jobs        — { taskType, url, options, proxyProfile, timeoutMs, idempotencyKey }
GET  /v1/jobs/{id}   — { status: queued|running|succeeded|failed, ... }
GET  /v1/jobs/{id}/artifacts   — html / файл / метаданные
GET  /v1/health, GET /v1/capacity
```

- `taskType`: `renderPage`, `downloadFile`, `fillForm+submit`, ограниченный набор `extract`-обработчиков.

### 7.2 Пул и изоляция падений

- Пул долгоживущих браузер-слотов (стартово 2–4 на хост, дальше — бенчмарк на реальных страницах); на каждую задачу — свежий контекст, закрытие в `finally`.
- Смерть браузера инвалидирует все его контексты → задачи `failed`/retry; health-probe перед возвратом слота в пул; generation-ID против гонок при рестарте; soft-recycle слота по счётчику задач/памяти.
- Docker: базовый образ `mcr.microsoft.com/playwright`; `--ipc=host` или `shm_size ≥ 1g`; лимит памяти ~1.5–2 ГБ на конкурентный слот; exit-code 137 = нехватка памяти/shm (мониторить).

### 7.3 Сеть, файлы, устойчивость драйвера

- Прокси — на уровень контекста (нативные поля Playwright `server/username/password`), единица ретрая — контекст, не запрос; раздельный health прокси и целевого сайта.
- Скачанные файлы — через **shared volume** между Node-сервисом и PHP-worker'ом (не стримингом в HTTP-ответ): переживает произвольные таймауты крупных файлов, ложится на модель «browser-задачи только в worker-контейнере».
- **Технические детали надёжности и совместимости headless-драйвера — в `research/tz-v2/playwright-service.md`; в ТЗ намеренно не дублируются** (выбор конкретного драйвера — за внутренней абстракцией «browser driver», меняется без правки домена).

## 8. Мост в пайплайн документов

По итогам инжеста закупок диспетчер (аналог v1 `PipelineDispatcher`) отбирает закупки/документы без анализа, ставит их в очередь стадии подготовки документов и помечает статус. Дальнейшая цепочка (скачивание → подготовка → скрининг → извлечение) — в `03-document-pipeline.md`. Диспатч идемпотентен: повтор не создаёт дублирующих анализов (guard по статусу).

## 9. Открытые вопросы / риски

- Точные лимиты частоты источника и порог cap (~10k) недокументированы — калибровать в тесте, заложить мониторинг.
- Стабильность CSV-endpoint и набора колонок между релизами ЕИС — smoke-контроль (§6.2).
- **Стабильность вёрстки HTML-вкладок карточки** (`common-info`/`event-journal`/`supplier-results`) — классы/структура меняются без предупреждения (`card-structure-l2.md` §1, `eis-card-recon.md` §8). Нужен smoke-контроль структуры детальных вкладок наравне с CSV: контрольная карточка с ожидаемым набором блоков, алерт при рассинхроне парсера.
- **Триггер пересъёма детального слоя на события без смены `source_updated_at`** (протокол/разъяснение/отмена). Живой проверкой подтвердить, меняется ли `lastDateChangeCsv` при таких событиях; §5.2 закладывает независимые триггеры (смена этапа + ре-скан завершающихся), но точное поведение поля — открытый вопрос до проверки на реальных данных.
- Шаблоны URL карточек по способам закупки — уточнить при реализации адаптера (хранить в `plt_registries.settings`).
- `api`-метод — отдельная проработка вне текущего MVP; интерфейс `SourceMethod` уже готов принять реализацию. **SOAP int-сервисы ЕИС (`int.zakupki.gov.ru`, `int44-ttls-cert`) как источник чтения реестра не подходят** — это каналы интеграции участника закупки (подача заявок/ЭДО), требуют ГОСТ-крипто и сертификата, старые `int44`/`int223` отключены с 10.2025 (`research/tz-v2/eis-csv.md` §6). Реалистичный кандидат на `api` для массового чтения — раздел «Открытые данные» ЕИС (XML/ZIP-наборы с XSD); прорабатывается при необходимости официального канала вместо CSV-скрейпинга.
