# ТЗ v2 · 00 — Обзор системы

> Статус: рабочая спецификация greenfield-системы. Пакет: `00-overview` → `06-roadmap`.
> Источники решений: интервью с владельцем (см. `plans/tz-v2-crawling-system.md`), живая разведка ЕИС (`research/eis-csv-recon.md`), опыт agelto v1, внешний research (выжимки в `research/tz-v2/`).

## 1. Что строим

Универсальная платформа сбора, отслеживания и AI-разбора закупок:

1. **Сбор** — краулинг реестров закупок (старт: ЕИС zakupki.gov.ru, 44-ФЗ + 223-ФЗ) переключаемыми методами (CSV-экспорт / HTML / API площадки), устойчивый к лимитам выдачи и банам.
2. **Отслеживание** — закупка живёт во времени: редакции извещения, смены статуса/цены/дат, появление и замена документов. Система хранит полную историю и умеет восстановить состояние на любую дату.
3. **AI-разбор документов** — двухступенчатый пайплайн (дешёвый скрининг → полное извлечение) с обработчиком на тип документа (старт: сметы), переключаемыми LLM-провайдерами и накоплением датасета для обучения локальной модели.

Потребитель на горизонте ТЗ — внутренний: операторы (Filament-админка) и датасет для обучения локальной LLM. Публичный API — задел в архитектуре, без детальной проработки.

## 2. Принципы

- **Ядро универсально, площадка — адаптер.** Общие сущности и статусная модель не знают про ЕИС; всё ЕИС-специфичное живёт в адаптере площадки и extension-слое данных (jsonb attributes / extension-таблицы).
- **История — first-class.** Не «текущее состояние с полями», а снапшоты редакций + журнал событий. Апдейт закупки никогда не затирает прошлое.
- **HTTP-first, браузер — last resort.** Листинг — CSV чистым HTTP; детали — HTTP+DOM-парсер; Playwright (отдельный Node-сервис) — только когда без JS не обойтись.
- **Дёшево → дорого.** Скрининг документов минимальным ответом; полный разбор — только кандидатов; context caching; матрица «тип документа × шаг → провайдер».
- **Идемпотентность и воспроизводимость.** Повтор любого job'а не создаёт дублей; сырые артефакты (CSV, документы, ответы LLM) хранятся в object storage — любой этап можно переиграть.
- **Наблюдаемость по умолчанию.** Каждый прогон, каждый блок, каждый LLM-вызов оставляет метрики и след в журнале.

## 5. Ключевые сценарии (система обязана)

1. **Fresh-скан** каждые ~30 мин: CSV-блоки по убыванию даты обновления до первого полностью известного блока; новые закупки → создание, изменённые → новая редакция + события.
2. **Архивная перекачка** года: по дням, при переполнении выборки — дробление по цене; цель — выборка ≤5000 (см. разведку: реальный cap ~10k, тихий).
3. **Детальный слой карточки**: по новой закупке/редакции снять полную карточку (общая инфо + позиции + финансирование + роли + журнал событий + результаты), не только файлы — отдельная стадия HTTP-first (`02` §5).
4. **Новая редакция извещения**: снапшот, диффы → события, переиндексация документов; заменённый документ получает новую версию, старая остаётся.
5. **Документ-путь**: обнаружен → скачан (hash-дедуп) → подготовлен (архив распакован в дочерние, Excel→PDF, изображения) → скрининг (тип) → если смета: полное извлечение → нормализованная смета в БД.
6. **Итоги закупки**: протокол/результаты → победитель, предложения участников, связь с реестром контрактов (`prc_awards`/`prc_bids`).
7. **Смена LLM-провайдера** для шага «полное извлечение смет» через админку, без деплоя; shadow-прогон локальной LLM параллельно Gemini со сравнением.
8. **Новая площадка**: реализация адаптера (Source-методы + маппинг статусов) без миграций ядра.

## 6. Нефункциональные требования

| Аспект | Требование |
|---|---|
| Масштаб | десятки млн Procurement; сотни млн событий/версий — партиционирование с 1-го дня |
| Пропускная | fresh-скан двух реестров ≤ 5 мин; архив — темп ограничен вежливостью к ЕИС, не архитектурой |
| Надёжность | обрыв любого прогона возобновляем с курсора; повторная обработка идемпотентна |
| Стоимость LLM | скрининг ≪ извлечение; context caching обязателен; учёт токенов на каждый вызов |
| Безопасность | прокси-креды вне кода; доступ только через админку с ролями; публичного контура нет |
