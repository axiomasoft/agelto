# Жизненный цикл закупки ЕИС и карта мониторинга

Внешние факты (SOAP API, структура XML, статистика) помечены ⚠️ и требуют проверки на живом ЕИС до реализации.

## 1. Зачем это Agelto

Agelto парсит строительные госзакупки ЕИС и извлекает из смет позиции материалов, чтобы выдавать лиды поставщику. Анализы поднимают существенный продуктовый тезис:

**Реальный покупатель материалов — это победитель закупки (подрядчик), а не заказчик.** Заказчик (госорган) проводит тендер, но материалы по смете будет закупать тот, кто выиграет подряд. Значит лид, выданный на этапе извещения (до известности победителя), может быть **преждевременным**: контакт для продажи материалов — победитель, который определится позже.

Отсюда три прикладных вопроса, на которые текущая система ответить не может:
1. **Когда и где появляется победитель** в жизненном цикле закупки.
2. **Какие статусы означают «работа закончена»** — чтобы не опрашивать мёртвые записи.
3. **Когда «завершённая» закупка снова становится активной** (уклонение, отмена результата ФАС, расторжение, повтор).

> [!note] Это меняет трактовку «лида», поэтому вынесено в [[ADR-002_Winner_Tracking_And_Monitoring|ADR-002]] как предложение, требующее бизнес-валидации. Официальный scope v1 ([[BRD]]) пока не меняется.

## 2. Нормативная база (кратко)

| Закон | Кто проводит | Особенность для парсинга |
|:---|:---|:---|
| **44-ФЗ** | Госорганы, муниципалитеты, бюджетные учреждения | Жёсткая регламентация, стандартизированные статусы и протоколы — пригодно для автоматического чтения |
| **223-ФЗ** | Госкорпорации, АО с госдолей >50%, естественные монополии | Порядок закупки определяет сам заказчик — меньше стандартизации |

Приоритет MVP — **44-ФЗ, строительные аукционы**. 223-ФЗ — после пилота, отдельной реализацией.

## 3. Способы определения поставщика (44-ФЗ) — когда появляется победитель

| Способ | Критерий победы | Где победитель |
|:---|:---|:---|
| Электронный аукцион | Наименьшая цена | Протокол подведения итогов |
| Открытый конкурс (электронный) | Цена + качество | Протокол подведения итогов |
| Запрос котировок (электронный) | Наименьшая цена (НМЦК ≤ лимит) | Протокол |
| Запрос предложений | Наилучшие условия | Протокол |
| Единственный поставщик (ст.93) | Известен заранее | Реестр контрактов напрямую |

Победитель публикуется в **протоколе подведения итогов** (переход закупки в статус «завершена»). Для единственного поставщика — сразу в реестре контрактов.

## 4. Жизненный цикл закупки (44-ФЗ): диаграмма состояний

Сведённая карта (объединены диаграммы обоих анализов). Ветви «возврата к жизни» помечены ⮌.

```
[ИЗВЕЩЕНИЕ ОПУБЛИКОВАНО] ──(правка)──> [ИЗМЕНЕНО ИЗВЕЩЕНИЕ]
        │
        ▼
[ПРИЁМ ЗАЯВОК] ───────────────────────────────► [ОТМЕНЕНА ЗАКАЗЧИКОМ] (терминал)
        │
        ▼
[РАБОТА КОМИССИИ / РАССМОТРЕНИЕ ЗАЯВОК]
        │
        ├── мало/нет участников ─► [НЕСОСТОЯВШАЯСЯ] ⮌ повтор / ед.поставщик
        │
        ▼
[ПОДВЕДЕНИЕ ИТОГОВ]  ★ ПОБЕДИТЕЛЬ ОПРЕДЕЛЁН ★
        │   (ИНН, наименование, итоговая цена, № заявки, дата)
        │
        ├── жалоба в ФАС ─► [ПРИОСТАНОВЛЕНО] ⮌ возврат к рассмотрению / отмена
        ├── победитель не подписал ─► [УКЛОНЕНИЕ] ⮌ контракт со 2-м участником
        │
        ▼
[КОНТРАКТ ПОДПИСАН] ──► [ИСПОЛНЕНИЕ] ──► [ИСПОЛНЕН] (терминал)
                              │
                              └── [РАСТОРГНУТ] ⮌ повторная закупка на остаток
```

Ключ: после узла «подведение итогов» закупка формально может считаться завершённой, но фактически ещё несколько ветвей способны изменить победителя или вернуть закупку в активную фазу — это и есть зона, которую мониторинг должен покрывать.

## 5. Реестр статусов ЕИС (сведённый)

> [!caution] Коды в столбце «Код» — **предлагаемое внутреннее обозначение**, не официальные константы ЕИС (см. §11). Достоверно — русские названия статусов, видимые на карточке/в листинге.

| Статус ЕИС (ru) | Предлаг. код | Когда наступает | Действие Agelto |
|:---|:---|:---|:---|
| Опубликовано / Подача заявок | `active` | Извещение размещено, идёт приём заявок | Парсить документы/сметы |
| Изменено извещение | `amending` | Заказчик правит документацию | Перечитать карточку (триггер — `updatedAt`) |
| Работа комиссии / Рассмотрение заявок | `commission_work` | Срок подачи истёк | Ждать протокол |
| Подведение итогов | `awaiting_winner` | Рассматриваются заявки | **Критично** — ждать протокол итогов |
| **Закупка завершена / Победитель определён** | `winner_found` | Протокол итогов опубликован | ★ **Читать победителя** |
| Несостоявшаяся | `failed` | Нет/мало участников | Отслеживать повторную |
| Отменена заказчиком | `cancelled` | Отзыв до окончания подачи | Архив |
| Отменена ФАС | `cancelled_fas` | Решение ФАС | Архив |
| Приостановлено (ФАС) | `suspended` | Жалоба принята к рассмотрению | Усиленный опрос, ждать решения |
| Уклонение победителя | `winner_evaded` | Победитель не подписал контракт | ★ **Читать 2-го участника** |
| Контракт подписан | `contract_signed` | Контракт размещён в реестре | Зафиксировать, снизить частоту |
| Исполнение контракта | `executing` | Подрядчик выполняет работы | Редкий мониторинг (расторжение) |
| Исполнен | `completed` | Обязательства выполнены | Архив |
| Контракт расторгнут | `terminated` | Расторжение (ст.95) | ★ **Возобновить отслеживание** |

## 6. Маппинг: статус ЕИС → текущий код vs предлагаемый мониторинг

> [!important] Главный разрыв
> Текущие enum'ы `CrawlingStatus` (`Link`) и `AnalysisStatus` (`DocumentAnalysis`) описывают **обработку документов** Agelto, а **не статус самой закупки в ЕИС**. После краулинга статус закупки в ЕИС больше не перечитывается. Поля `OrderMonitoringStatus` и колонок победителя в схеме нет (см. §11, [[Architecture]] §7).

| Слой | Что описывает | Где |
|:---|:---|:---|
| `CrawlingStatus` (pending/processing/completed/failed) | Загрузка документов карточки | `plt_crawler_links.status` |
| `AnalysisStatus` (11 значений) | AI-пайплайн одного документа (стадии 2–4) | `plt_document_analysis.status` |
| `ord_orders.status` (nullable string) | Снимок статуса на момент краулинга, далее не обновляется | `ord_orders` |
| **`OrderMonitoringStatus`** | Статус закупки в ЕИС после краулинга | **отсутствует** → предложено в [[ADR-002_Winner_Tracking_And_Monitoring|ADR-002]] |

## 7. Победитель: где и что извлекать

Победитель фиксируется в **протоколе подведения итогов** (вкладка «Протоколы»/«Итоги» карточки). Поля к извлечению (предлагаемая модель для `ord_orders` / `ord_order_winners`):

- `winner_inn` — ИНН победителя
- `winner_kpp` — КПП (для юрлиц)
- `winner_name` — наименование / ФИО
- `final_price` — итоговая цена контракта (≤ НМЦК)
- `protocol_published_at` — дата протокола
- `protocol_type` — тип (`итоги` / `уклонение` / `несостоявшаяся`)

**Типология протоколов** (⚠️ XML-типы — гипотезы анализа, проверить на живом ЕИС):

| Протокол | Когда публикуется | Что извлекать |
|:---|:---|:---|
| Рассмотрение 1-х частей заявок | До аукциона, след. раб. день | Допущенные/отклонённые (ИНН) |
| Проведение электронного аукциона | ~30 мин после окончания | Ценовые предложения, ИНН лидера |
| **Подведение итогов** | След. раб. день | **Победитель: ИНН, итоговая цена, дата** |
| Об уклонении победителя | След. раб. день | Уклонившийся → переход ко 2-му |
| Заключение со 2-м участником | После уклонения | ИНН нового победителя |
| О признании несостоявшейся | В тот же день | Причина |

> [!caution] ⚠️ Конкретная XML-структура протокола (теги `protocolEF2Data`, `applicationInfo`, `resultStatus=WIN` и т.п.) — внешнее непроверенное утверждение анализа. Перед реализацией парсера проверить реальный ответ ЕИС. Подтверждены кодом только страницы `/common-info.html` и `/documents.html` (используются в `EisCrawlingService`).

## 8. Сценарии «возврата к жизни»

Закупка, формально «завершённая», может потребовать повторного мониторинга.

| Сценарий | Триггер | Предлагаемое действие Agelto |
|:---|:---|:---|
| **Уклонение победителя** | Победитель не подписал контракт в срок; «Протокол об уклонении» | Перечитать карточку при изменении `updatedAt`; обновить победителя на 2-го участника или null; усилить опрос |
| **Обжалование в ФАС** | Участник подал жалобу; закупка приостановлена | Отдельный статус `suspended`; приоритетный перечёт при `updatedAt > submissionEndAt`; возможна смена победителя |
| **Несостоявшаяся → повторная** | Нет/мало заявок; новое извещение (обычно новый `reg_number`) | Хранить в `failed` (не архив); искать связанное извещение по `customer_id` + предмету |
| **Расторжение контракта** | Одностороннее/по соглашению/по суду (ст.95) | Мониторинг записей в `executing`; при расторжении — ждать повторную закупку |
| **Изменение условий / доп.соглашение** | Доп.соглашение (ст.95): цена/объём/срок | Некритично (победитель не меняется), но важно для аналитики |

⚠️ Частота уклонений «3–5% аукционов» — внешняя оценка анализа, не подтверждена.

## 9. Временные рамки (для планировщика опросов)

| Событие | Срок по 44-ФЗ |
|:---|:---|
| Публикация извещения → окончание приёма | ≥7 дней (аукцион), ≥4 рабочих дня (запрос котировок) |
| Окончание приёма → протокол итогов | ≤2 рабочих дня (рассмотрение) |
| Протокол итогов → подписание контракта | ≥10 дней (общий случай), ≥2 дня (запрос котировок) |
| Уклонение → контракт со 2-м участником | ≥10 дней |
| Жалоба в ФАС → решение | ~5 рабочих дней |

Предлагаемое расписание опроса по статусу (из анализа, как ориентир): `active` 4–6 ч · `awaiting_winner` 1 ч · `winner_found` 1 раз/сутки (14 дней) · `executing` раз в 7 дней · `failed`/`cancelled`/`terminated` раз в 3–7 дней · `completed` раз в 30 дней.

> [!caution] ⚠️ Предлагаемые ориентиры мониторинга (внешние, непроверенные)
> - **Freshness победителя** ≤ 2 ч после протокола итогов (отсюда интервал `awaiting_winner` = 1 ч).
> - **Покрытие возвратных сценариев** 100% для `winner_fixed` / `executing` / `completed`.
> - **Retention** истории статусов ≥ 3 года.
> - **Связывание повторной** закупки с исходной ≤ 48 ч (по `customer_id` + предмету).
> - Эвристика открытых парсеров: «дата торгов + 3 раб. дня → опрос итогового протокола».
> - Паттерн Prozorro: cursor-based синхронизация — запрашивать только изменившиеся с последней проверки.

## 10. Доступ к данным ЕИС: HTML vs SOAP API ⚠️

> [!caution] Весь раздел — внешние непроверенные утверждения исходного анализа (Perplexity). Использовать как гипотезу при проектировании, проверить на живом ЕИС.

- Текущая реализация Agelto — **headless-парсинг HTML** zakupki.gov.ru (проверено: `EisCrawlingService`).
- Анализ утверждает: FTP XML-выгрузки закрыты с 01.01.2025; SOAP API сменил домен на `int.zakupki.gov.ru` с 04.10.2025; для организаций — `int44-ttls-cert.zakupki.gov.ru` (ГОСТ + двусторонняя аутентификация).
- SOAP требует токена (физлицо — через Госуслуги) или ЭЦП (организация) + ГОСТ-шифрование (КриптоПро).
- Релевантные методы (по анализу): `getDocsByReestrNumberRequest` (документы по `reestrNumber`=`reg_number`), `getNsiRequest` (справочники). Ответ — `archiveUrl` → ZIP с XML.
- Релевантные `documentType44` (по анализу): `epNotificationEF2020` (извещение), `epProtocolEF22020` (протокол итогов → победитель), `epProtocolEvasion` (уклонение), `epContract`, `epContractTermination`.

**Гибридная стратегия (предложение):** HTML-листинг для обнаружения новых закупок + SOAP по `reg_number` для деталей (протоколы, победитель, контракт). Развилка фиксируется в [[ADR-002_Winner_Tracking_And_Monitoring|ADR-002]].

## 11. Достоверность источника

> [!success] ✅ Проверено по коду (аудит 2026-06-14, сверка с миграциями и классами)
> - Пайплайн стадий 1–4, их код, очереди Horizon, state-машина/лизинг/retry/Telegram-алерты.
> - enum'ы: `AnalysisStatus` (11), `CrawlingStatus` (4), `ProcessStage` (4), `PipelineStage` (3).
> - `EisCrawlingService`: рекурсивное дробление по ценам (стоп при разнице <10000 ₽), архивный/оперативный режимы, `keepStateOnCrash`, `parseAttachments` → `documents.html`, дедуп по `reg_number`, задержки ~3 с.
> - `CrawlingItemDto`: `externalId`, `url`, `subject`, `price`, `publishedAt`, `updatedAt`, `submissionEndAt`, `attachments`.
> - Схема `ord_orders` / `ord_lots` / `ord_purchase_objects` / `ord_customers` (см. [[Architecture]] §7).
> - **Отсутствуют** (подтверждено): поля победителя/контракта, `OrderMonitoringStatus`, таблица `ord_order_winners`, `OrderStatusMonitorJob`, любой парсер протокола. `OrderParsingProcess::run()` — пустая заглушка.

> [!caution] ⚠️ Внешнее, непроверенное (гипотезы Perplexity — проверить на живом ЕИС до реализации)
> - **Коды статусов ЕИС** (`PUBLISHED`, `WINNER_DETERMINED`, `RESULTS_DETERMINATION` …) — предложены анализом, не подтверждены как реальные константы.
> - **SOAP API**: домены `int.zakupki.gov.ru` / `int44-ttls-cert`, закрытие FTP 01.01.2025, смена домена 04.10.2025, токен через Госуслуги, ГОСТ/КриптоПро (весь §10).
> - **XML-структура протоколов**: теги `protocolEF2Data` / `applicationInfo` / `resultStatus=WIN`, коды `documentType44` (§7, §10).
> - **HTML-страницы карточки**: `/protocols.html`, `/complaints.html` (наличие не проверено; `/common-info.html` и `/documents.html` — проверены).
> - **Статистика**: «3–5% уклонений», лимиты Тендерплан (250/10 с, 800/60 с), Prozorro «синк раз в 5 мин».
