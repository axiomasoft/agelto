# Глубокая промт-инженерия — заметки и антипаттерны

> Конкретика формулировок и наследие v1 зеркалятся в Brain по решению владельца D89. Публичная
> версия (композиция промта, версионирование, где искать канонические тексты) —
> `docs/03_Dev/ai/prompts.md`; как писать промт технически — `resources/ai/prompts/README.md`
> (единственный источник, не дублируется здесь).

## 1. Наследие v1 — что перенесено и почему

Тексты промтов v1 существовали ТОЛЬКО в БД v1 (`plt_prompt_rules`) и почти безвозвратно терялись
при подготовке к удалению `Old/`. Приём «PHP-исходник схемы DTO в system instruction» (очищенный
докблоками, `#[Alias]`-словари русских заголовков) перенесён как есть (D2) — двойная фиксация:
constrained decoding (`responseJsonSchema`) гарантирует структуру, а исходник в промте передаёт
модели СЕМАНТИКУ полей (что значит каждое поле, синонимы заголовков в реальных сметах), которую
голая JSON Schema не несёт.

Полный текстовый архив v1-промтов — `plans/EST-AI/research/v1-prompts/` (для сверки при
переформулировке, не для копирования без переосмысления — v1-тексты писались под другую модель
линейки 2.0, отключённую 01.06.2026).

## 2. Известные антипаттерны (research E §2, §5 + v1-наследие)

- **Не просить глубокую вложенность в одном ответе.** Иерархия section→subsection→item в
  structured output хрупкая — упирается в лимиты схемы и `MAX_TOKENS`. Канон: плоский список строк
  с `row_type` (line_item/section_header/subtotal), иерархия собирается на бэкенде.
  `finishReason === MAX_TOKENS` — брак ДО парсинга (структурный вывод НЕ гарантирует валидность
  ответа при обрезании) — лечится меньшим числом строк за один вызов, не «дописыванием скобок».
- **Не просить всю смету одним массивом на сотни строк.** Построчные диапазоны (row-range) или
  окна — не единый вызов на документ целиком.
- **Не полагаться на самооценку confidence модели как на бинарный гейт без буфера.** Скрининг:
  борderline-зона (config, дефолт 0.4–0.6) уходит на ревью/эскалацию, а не молча в `ignored` —
  плохо откалиброванная самооценка LLM топит реальные сметы в тихом «unknown» (D36).
- **Слишком сложная JSON Schema → `400 InvalidArgument`.** Длинные имена полей, большие enum,
  много optional-полей, `format: date-time` — держать схему плоской и лаконичной (research E §2).
- **Диапазон страниц PDF нельзя передать параметром.** Резать документ на бэкенде (`qpdf`) ДО
  загрузки, не полагаться на промт «прочитай только страницы 1-4».

## 3. Composite versioning — почему это критично именно для качества

Поведение модели = промт + модель + JSON-схема одновременно (не промт сам по себе). Смена ЛЮБОГО
из трёх компонентов без фиксации связки делает невозможным воспроизвести, ПОЧЕМУ конкретный
разбор получился таким. `rules_hash` (sha1 финальной системной части) + `prompt_version_set`
(на будущих eval-прогонах) — обязательная привязка при любом сравнении «стало лучше/хуже».

## 4. Fixed-token chunking — почему НЕ используется

Fixed-token нарезка документа рвёт таблицы (~30% потерь строк на границах чанков, research E §5).
Канон — sliding window по СТРАНИЦАМ с overlap 1 страница + carry-over буфер незавершённых строк
(`incomplete_items`) + детерминированный stitcher на бэкенде, не в промте. Дедуп overlap — по
составному ключу (код/наименование/количество/сумма), не по номеру строки (номера у моделей на
двух соседних окнах не гарантированно совпадают).

## 5. Куда смотреть при систематической деградации качества

1. Проверить `ai:cost-report`/`ai:eval:run` — деградация метрик может совпадать с EOL/сменой
   модели маршрута (`economics.md` §1) раньше, чем с промтом.
   `ai:eval:run` на дату этой сессии ни разу не прогонялся на реальных данных боевого eval-набора
   (открытый риск — не путать «промт плохой» с «eval никогда не проверялся»).
2. Посмотреть накопленные коррекции оператора (`prc_ai_corrections`, `is_reusable=true`) — частый
   повторяющийся `reason` по одному `document_type` сигналит, где канонический промт систематически
   недоговаривает, а не где отдельный документ аномален.
3. Не менять канонический текст ad hoc без разметки «зачем» — история правок промта живёт в git;
   без why-аннотации к коммиту следующая правка не понимает, что именно уже пытались чинить
   раньше (тот же антипаттерн, что потерял тексты v1 в БД без истории).

## 6. Связка с обучающим контуром

Раздельное хранение raw/gold + структурированные коррекции (`docs/03_Dev/ai/training-loop.md`,
D15) существуют не только ради UI ревью — это единственный источник данных для (а) диагностики
промта (см. §5) и (б) будущего SFT/DPO локальной модели
(`local-llm-training.md`, P9.4 — задел, обучение вне плана).
