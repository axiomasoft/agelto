## 1. Цель системы

Автоматизировать извлечение коммерческих лидов из государственных строительных закупок (ЕИС) для поставщиков строительных материалов.

**Что система делает:**
1. Непрерывно сканирует ЕИС — скачивает документы тендеров
2. Разбирает PDF и Excel-сметы через AI — извлекает список материалов
3. Сопоставляет позиции смет с номенклатурным каталогом клиента (vector search)
4. Ранжирует совпадения и передаёт готовые лиды в CRM клиента

**North Star Metric:** количество верифицированных лидов, переданных в CRM клиентами за последние 30 дней.

**Что НЕ делает (за рамками v1):**
- Не является торговой площадкой
- Не ведёт переговоры и не формирует КП
- Не анализирует финансовый результат сделки

**Критерий MVP (первый платящий пилот):**
F-CRAWL-1…5 + F-PARSE-1…5 + F-MATCH-1…3, 6 + F-UI-COLL + F-MON-3 (audit trail). Выдача лидов — вручную (без CRM-автоматизации), квоты — вручную. Всё остальное — после пилота.

## 3. User Stories

### Менеджер по продажам (Client / Manager)
- **Как** менеджер, **я хочу** утром открыть дашборд и увидеть список новых тендеров, в сметах которых есть наша номенклатура, **чтобы** не тратить день на ручной поиск по ЕИС
- **Как** менеджер, **я хочу** видеть конкретные строки из сметы, которые совпали с нашим каталогом (название, количество, цена, процент совпадения), **чтобы** быстро оценить интерес к тендеру
- **Как** менеджер, **я хочу** одним кликом отправить лид в CRM с черновиком КП, **чтобы** не копировать данные вручную
- **Как** менеджер, **я хочу** видеть PDF оригинальной сметы с подсветкой найденных позиций, **чтобы** проверить контекст совпадения

### Коммерческий директор (Client)
- **Как** коммерческий директор, **я хочу** настроить каталог нашей номенклатуры (Коллекцию) один раз и больше не думать о настройке, **чтобы** система работала автономно
- **Как** коммерческий директор, **я хочу** видеть аналитику: сколько лидов найдено, сколько передано в работу, по каким позициям чаще всего совпадения, **чтобы** оценивать эффективность канала

### Администратор платформы
- **Как** администратор, **я хочу** управлять AI-инструкциями через интерфейс без деплоя, **чтобы** быстро корректировать качество парсинга при изменении структуры ЕИС

| F-PARSE-2 | Детальное извлечение позиций сметы из PDF: название материала, единица измерения, количество, цена за единицу, ОКПД2 (при наличии). | 🔴 Must Have |

### 4.3 Семантический матчинг

> [!note] Матчинг идёт через внешний эталон ([[ADR-001_Catalog_From_TcenZor|ADR-001]])
> Позиция сметы сопоставляется не напрямую с коллекцией клиента, а через
> **эталонный товар каталога [[TcenZor]]** (категории/эталоны/алиасы/нормативка).
> Эталон — внешний, приходит по API ([[Universal_Catalog_Architecture]]).

| # | Требование | Приоритет |
|:---|:---|:---|
| F-MATCH-0 | Эталонный строительный каталог (категории/эталоны/алиасы/ГОСТ·ОКПД2·КТРУ) синхронизируется из [[TcenZor]] по API в локальную реплику. Матчинг позиции сметы → эталон → коллекция клиента. | 🔴 Must Have |
| F-MATCH-1 | Клиент загружает свою номенклатуру (Коллекцию): SKU, наименование, единица, цена. Валидация импорта: дубли SKU, пустые наименования/единицы, нечисловые цены → отчёт об ошибках, невалидные строки не индексируются. | 🔴 Must Have |
| F-MATCH-2 | Система автоматически строит векторные представления (embeddings) для каждой позиции Коллекции. | 🔴 Must Have |
| F-MATCH-3 | Семантическое сопоставление позиций сметы с Коллекцией: Match Score (0–1), лучший кандидат (топ-1) для каждой позиции. | 🔴 Must Have |
| F-MATCH-3a | Топ-3 кандидата на позицию (выбор менеджером при верификации). | 🟡 Should Have |
| F-MATCH-4 | Hard Constraints Validation: после векторного матчинга — проверка совместимости единиц измерения. Несовместимые пары (т vs м²) получают флаг `unit_mismatch`. | 🟡 Should Have |
| F-MATCH-5 | Ручная верификация: менеджер подтверждает или отклоняет каждый матч. Подтверждённые матчи улучшают качество модели (self-learning). | 🟡 Should Have |
| F-MATCH-6 | Human-in-the-loop: матчи с confidence < 92% не передаются в CRM автоматически — помечаются «Требует проверки» и уходят на премодерацию роли Analyst. Порог настраивается per-клиент. | 🔴 Must Have |
| F-MATCH-7 | Active learning: вердикты верификации (подтверждено/отклонено) сохраняются как размеченная обучающая выборка. Периодичность дообучения / переиндексации — TBD ([[Открытые вопросы (Agelto)]]). | 🟡 Should Have |

| # | Требование | Приоритет |

## 5. Нефункциональные требования

| Требование | Значение |
|:---|:---|
| **Точность матчинга (Accuracy)** | ≥ 92% подтверждённых матчей (цель диплома: 92–95%). Методика: golden dataset из эталонных смет + выборочная ручная проверка N смет/мес. Позиции с confidence < 92% — премодерация (F-MATCH-6). |
| **Скорость AI-скрининга** | Один документ — в течение 5 мин от постановки в очередь (таймауты кода: подготовка 300 сек + скрининг 180 сек, без учёта глубины очереди) |
| **Скорость полного парсинга сметы** | Один документ — в течение 15 мин после скрининга (чанковая обработка по 80 строк) |
| **Скорость матчинга** | Один тендер (~100 позиций) — в течение 30 сек после завершения парсинга |
| **Uptime** | 99% в рабочие часы (пн-пт 8:00–20:00 МСК) |
| **Freshness тендеров** | Новые тендеры из ЕИС — в системе в течение 4 часов |
| **Изоляция данных клиентов** | Коллекции и лиды клиента A не видны клиенту B. ⚠️ Механизм (RLS / tenant_id / схемы) не выбран — см. [[Открытые вопросы (Agelto)]] T4; мультитенантность в коде не начата. |
| **Безопасность PromptRules** | Изменение AI-инструкций только для роли Admin. Версионирование — rollback при деградации качества. |
| **Хранение ПД** | Серверы в РФ, ФЗ-152 (контактные данные ИНН/КПП заказчиков — публичные данные ЕИС, не ПД физлиц). ⚠️ Оговорка: документы тендеров отправляются в Google Gemini API — данные покидают РФ; резолюция обязательна ([[Открытые вопросы (Agelto)]] L3, [[Risk_Register (Agelto)]] R-5). |
| **RPO / RTO** | TBD — целевые значения не определены ([[Открытые вопросы (Agelto)]] T7) |

## 6. Граничные случаи и особые сценарии

| Сценарий | Требуемое поведение |
|:---|:---|
| **ЕИС изменил структуру HTML** | Кроулер перестаёт находить данные → метрика `items_count = 0` за >2 часа → Alert администратору. PromptRules корректируется без деплоя. |
| **Документ — скан без текстового слоя** | Gemini возвращает `has_smeta: false` → задача помечается `ocr_required` → помещается в очередь для LayoutLMv3 (v2). В v1 — логируется, не парсится. |
| **Позиция сметы — нестандартная единица измерения** | Hard Constraints флагирует как `unit_unknown`. Матч остаётся с пониженным Score и пометкой для ручной проверки. |
| **Клиент удалил позицию из Коллекции** | Все исторические матчи с этой позицией сохраняются (soft delete). Новые матчи не создаются. |
| **Тендер снят с публикации на ЕИС** | Статус тендера обновляется при следующем сканировании. Уже переданные в CRM лиды не отзываются — уведомление клиенту. |
| **Gemini API недоступен > 30 мин** | Задачи накапливаются в очереди `parsing`. Администратор уведомляется через Telegram-бот. При восстановлении — автоматический retry. |
| **Коллекция клиента содержит >10 000 позиций** | Векторный индекс строится в фоне (async job). Матчинг запускается только после завершения индексации. Клиент видит статус «Коллекция обновляется». |
| **Матч с confidence < 92%** | Лид не уходит в CRM автоматически: флаг «Требует проверки» → очередь премодерации Analyst (F-MATCH-6). |
| **Превышение квоты / rate limit Gemini** | Задачи остаются в очереди (exponential backoff, до 5 попыток скрининга). При систематическом превышении — алерт администратору и приостановка постановки новых задач. |
| **Сбой стадии пайплайна** | State machine переводит документ в failed-статус (`PrimaryAnalysisFailed` / `EstimateAnalysisFailed` / `Error`), переход логируется, администратор получает Telegram-уведомление. ✅ Реализовано в коде. |
