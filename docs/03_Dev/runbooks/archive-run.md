# Runbook: архивный обход площадки (ЕИС)

## Symptoms

Нужно прогнать площадку ЕИС по историческому диапазону дат (обучающий корпус, повторная заливка
после чистки, контрольный прогон после ремедиации) — не дожидаясь планового «свежего потока».

## Triage

Перед запуском проверить предусловия (`plans/archive/2026.07.31-SYS-INTEGRITY/research/05-change-tracking.md`
§6.1, живо доказаны прогонами P4.7/P4.15):

1. Egress ДО первого запроса к источнику — прокси-скоуп площадки отдаёт RU-адрес
   (`ipinfo.io/json` через тот же узел, что резолвер выдаст на `crawl_listing`/`crawl_detail`).
2. TLS доверие — образ несёт бандл `docker/php/certs/russian-trusted-ca.pem`
   (`docs/03_Dev/crawling-pipeline.md` §«Живые ограничения площадки ЕИС»); если образ пересобирался
   без него — обход упадёт на TLS-рукопожатии до первого прикладного запроса.
3. Сиды площадки применены (`EisPlatformSeeder`, `CrawlerProfileSeeder`) — `select count(*) from
   prc_registries where code='fz44'` и `select count(*) from prc_crawlers` не пусты.
4. Гейты AI-стадий выключены, если прогон не должен тратить деньги: `config('ai.screening.enabled')`
   и `config('ai.extraction.enabled')` — оба `false`.
5. `fresh`-профиль деактивирован (`is_active=false`), если параллельный боевой поток не нужен —
   иначе конкурирует за прокси-узел и троттлинг с архивным обходом.

## Fix (как запустить)

```bash
docker exec agelto_app php artisan crawler:run-archive <crawler_id> --from=<YYYY-MM-DD> --to=<YYYY-MM-DD>
```

- Диапазон дат — включительно, обход идёт по дням публикации; при превышении потолка листинга на
  день (5 000 записей, `docs/02_Workflow/crawling-and-discovery.md`) сканер дробит день по цене
  автоматически.
- Детальная стадия (карточка, документы) запускается ОТДЕЛЬНО и вручную, не через планировщик:

```bash
docker exec agelto_app php artisan crawler:fetch-details <registry_number_or_id>
```

### Что смотреть по ходу и после

- `select count(*) from prc_fetches where proxy_id is null` — обязано быть **0** (весь трафик
  прошёл через прокси, D3).
- `select http_status, count(*) from prc_fetches group by 1` — не должно быть систематических
  403/429/5xx.
- Идемпотентность повтора: повторный прогон того же дня не создаёт вторых ревизий
  (`select count(*) from prc_revisions where revision_number > 1` не растёт).
- Документный/детальный слой не пустой после `fetch-details`: `prc_documents`,
  `prc_document_versions`, непустые `prc_eis_details`, `prc_items`, `prc_financing` — растут.
  Если всё осталось на нуле при формально `completed` прогоне — см. Escalation.

## Rollback

Прогон не пишет данные вне диапазона `--from/--to`; при ошибочном диапазоне — удаление по
`prc_revisions.crawler_run_id` конкретного прогона (единственный надёжный носитель связи «данные ↔
прогон» — НЕ по `registry_id`, он может быть общим с другими прогонами), затем `vacuum full`
затронутых таблиц, если освобождённое место должно быть видно сразу в метриках.

## Escalation

- Прогон `completed`, но детальный слой (`prc_documents`/`prc_eis_details`/`prc_items`) остаётся
  пустым на всех карточках — признак «пришла не та страница» (сторож должен был поймать это в
  `detail_last_error`, см. `docs/03_Dev/crawling-pipeline.md` §«Транспорт детальной стадии»); если
  сторож молчит — это НОВЫЙ дефект, эскалировать разработчику с примером `registry_number`.
  Юнит-тест «не бросил исключение» приёмкой контура не считать — только живые числа.
- Стоп-сигналы (бан прокси-узла, пустой пул, TLS-отказ) — решение о продолжении прогона за
  оператором/владельцем, не автоматический ретрай вслепую.
- Смена набора колонок CSV или полная переверстка карточки между релизами площадки — не чинить «по
  аналогии»: снять актуальную раскладку живой пробой и обновить
  `docs/03_Dev/crawling-pipeline.md`/фикстуры парсеров по факту.
