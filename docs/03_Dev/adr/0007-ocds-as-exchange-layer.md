# ADR 0007: OCDS — exchange/publication layer, а не внутренняя схема

- Status: Accepted
- Date: 2026-07-10
- Источник: `plans/archive/DOMLANG/plan.md` §5 Decision Log, D3; `findings/P1-audit-verification.md` §4.1

## Context

Внешний аудит предложил свою таксономию домена (`Source Intake` / `Notice Enrichment` /
`Estimate Intelligence`), не заметив, что для закупочных данных существует **отраслевой стандарт
словаря** — Open Contracting Data Standard (OCDS).

`RAG:✅ 2026-07-10 «OCDS 1.2: release/compiledRelease/tender/award — отраслевой стандарт?»`
(источники: `standard.open-contracting.org/latest/en/primer/releases_and_records/`,
`link.springer.com/chapter/10.1007/978-3-030-29374-1_19`) фиксирует канон OCDS: `release`
(immutable-снапшот при каждом изменении, ключ `ocid`) · `record` (индекс релизов) · `compiledRelease`
(последнее состояние каждого поля) · `versionedRelease` (история изменений на уровне поля) + секции
`planning`/`tender`/`award`/`contract`/`implementation`.

Проект уже реализовал **изоморф** OCDS, не зная об этом, и это подтверждено кодом:

- `prc_procurements` ≈ `compiledRelease` — последнее известное состояние каждой закупки.
- `prc_revisions` ≈ `versionedRelease` — история редакций извещения на уровне полей.
- `prc_events` ≈ `releases` — **immutable** журнал событий. Подтверждено: таблица
  `prc_events` (`database/migrations/2026_07_04_100013_create_prc_events_table.php`) — append-only
  лог, партиционированный по `occurred_at`, с полями `field`/`old_value`/`new_value`; единственный
  путь записи — `ProcurementStoreRepository::storeEvent()` (`app/Repositories/Procurement/
  ProcurementStoreRepository.php:163`), это чистый `create()` без update-пути. Immutability события
  — предусловие изоморфизма с OCDS `releases` — выполнено.

Критично: `RAG:✅ 2026-07-10` прямо фиксирует, что **OCDS — exchange/publication layer, а не
внутренняя транзакционная схема**. Национальные системы держат свою нормализованную схему и мапят
в OCDS для прозрачности и аналитики; 44-ФЗ/223-ФЗ требуют профилей/расширений поверх ванильного OCDS.

## Decision

OCDS фиксируется как **экспортный контракт (exchange layer)**, а не как внутренняя схема
персистентности. Внутренняя нормализованная схема (`prc_*`) остаётся источником правды; связь с OCDS
выражается **mapping-таблицей** «внутреннее поле ↔ OCDS-путь», которая создаётся в P7.2 как
справочник экспортной поверхности. Этот ADR фиксирует только **принцип**, не саму таблицу: аудитовская
таксономия (`Source Intake`/`Notice Enrichment`/`Estimate Intelligence`) — изобретение словаря там,
где есть отраслевой; но и «переименовать домены в OCDS» неверно — OCDS не персистенс.

## Рассмотренные альтернативы

Перенесены из D-лога (`plan.md` §5, D3) дословно:

- **(а) сделать OCDS primary persistence** — отвергнут (RAG прямо не рекомендует: OCDS —
  публикационный слой, национальные системы держат нормализованную схему и мапят в OCDS).
- **(б) игнорировать OCDS** — отвергнут (интеграции и аналитика ожидают OCDS как поверхность
  публикации закупочных данных).

## Consequences

- Плюс: аналитика/интеграции получают предсказуемую поверхность (release/record/compiledRelease) без
  переписывания внутренней схемы под чужой стандарт.
- Плюс: 44-ФЗ/223-ФЗ-специфика (два номера по 223-ФЗ, реестровый номер, редакции, лоты) остаётся во
  внутренней схеме как профиль поверх ванильного OCDS, а не размывается в общий стандарт.
- Минус (принят осознанно): двойное поддержание — при изменении внутренней схемы mapping-таблицу
  (P7.2) нужно держать синхронной; за это платим осознанно, потому что альтернатива (OCDS как
  персистенс) дороже и не рекомендована RAG.

## Триггер пересмотра

Пересмотреть решение, когда наступит **проверяемое событие**: первый внешний потребитель (интеграция,
дата-портал, регулятор) запросил OCDS-выгрузку (`release`/`record`) **ИЛИ** площадка/регулятор
обязали публиковать данные в OCDS-профиле. Тогда mapping-таблица (P7.2) активируется как боевой
экспортный контракт (эндпоинт/выгрузка), а не остаётся справочной; до этого события внутренняя схема
`prc_*` остаётся единственным источником правды и OCDS-поверхность не материализуется в код.
