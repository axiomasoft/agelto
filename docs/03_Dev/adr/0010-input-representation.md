# ADR: Выбор представления документа на вход LLM extraction

- Status: Accepted
- Date: 2026-07-28
- Источник: план `2026.07.26-EST-TRAIN`, `plan.md` §5 и `phases/P6.md` P6.3

## ⚠ Денежные величины этого ADR — трекинг на момент прогона, не биллинг

Все `cost_micros`, процитированные ниже из отчёта плана `2026.07.26-EST-TRAIN` (`research/12-format-benchmark.md`),
посчитаны СТАРОЙ (заниженной) формулой `PrismGeminiProvider::usageFrom()` — баг игнорирования
`usageMetadata.thoughtsTokenCount` найден и исправлен ПОСЛЕ прогона (D126), исторические цифры
прогона невосстановимы. Для СРАВНЕНИЯ вариантов друг с другом внутри одного прогона это корректно
(систематическое занижение единообразно по всем ячейкам), но НЕ является абсолютной ценой боевого
пайплайна — реальный биллинг Google на дату прогона выше (владелец наблюдал ~$12 факт против ~$2.30
трекинга, D126).

## Контекст

Формат входа, который уходит в LLM на стадии extraction (`pdf`, `pdf_alt`, `text_grid`, `pdf_ocr`,
`text`, `structured_xml` или оригинал версии), до этого ADR был зашит в
`RepresentationResolver::DEFAULT_PRIORITY = [Pdf]` — константой с явным комментарием «правило
выбора по типу источника — P6, D3» (P3.1). Владелец сформулировал вопрос как «что дешевле подавать
в LLM» (`brief/00-brief.md` §«выбор оптимального формата») — D3 требует, чтобы ответом было
ИЗМЕРЕНИЕ, а не инженерная догадка («PDF проще всего»), тем же правилом анти-подгонки, что уже
применялось к потолку OCR (D22) и порогу распознаваемости сетки (D35/D42).

P6.1 построил harness `ai:bench:formats` и зафиксировал критерий победителя ДО данных (дословно):
«побеждает вариант с наименьшей `cost_micros` среди тех, чей `overall.f1` не ниже (лучший f1 по
эталону − 0.02) и `row_coverage` не ниже (лучший row_coverage по эталону − 0.02); при равенстве
цены — меньшее число вызовов; вариант, давший `outcome != succeeded` хотя бы на одном эталоне
подвыборки, победителем быть не может» (план `2026.07.26-EST-TRAIN`, `research/11-format-bench-method.md`).
P6.2 прогнал критерий механически на боевой подвыборке из шести эталонов (`EST-XLS-KS2-001`,
`EST-XLSX-KS2-001`, `EST-XLSX-KS2-003`, `EST-XLSX-LSR-001`, `EST-XLSX-VOR-001`, `EST-GSFX-LSR-001`)
на активном маршруте `gemini-3.5-flash` (финальный прогон v3, после доисправления харнесса —
`maxTokens` 8192→32768, HTTP timeout 30с→150с, см. `research/12-format-benchmark.md`
§1 «Прогресс по попыткам» того же плана).

**Критерий механически не выделил строгого победителя** — у каждого варианта представления
минимум одна дисквалификация на подвыборке из шести эталонов (`research/12` §4). Это ADR-решение
принимает данные P6.2 как они есть — критерий не переписывается задним числом (Code Guidance P6.2/
P6.3, то же правило, что D22/D35/D42).

## Решение

**Действующее представление для `xlsx`/`xls` — `pdf_alt`, с фолбэком на `pdf`.** Формально
`pdf_alt` не строгий победитель критерия P6.1 (единственная дисквалификация — по одному эталону,
`EST-XLSX-KS2-001`), но это единственный кандидат, дисквалифицированный РОВНО одним эталоном, и
причина дисквалификации — техническая (потолок `maxTokens` харнесса на дату прогона), а не качество
представления: тот же эталон дисквалифицирует и `pdf`, только по причине f1. `pdf_alt` дешевле обоих
реальных конкурентов на всех пяти эталонах, где он `succeeded`, и не уступает им по качеству нигде.
Данные указывают в его сторону достаточно однозначно, чтобы принять решение владельца по
рекомендации уходящей сессии P6.2/P6.3, а не откладывать до нового боевого прогона.

`config('ai.representations')`:

```php
'representations' => [
    'policy' => [
        'xlsx' => ['pdf_alt', 'pdf'],
        'xls' => ['pdf_alt', 'pdf'],
        'default' => ['pdf'],
    ],
    'fallback_to_source' => true,
],
```

- `xlsx`/`xls` → `[pdf_alt, pdf]`: резолвер отдаёт `pdf_alt`, если он есть, иначе `pdf`, иначе (при
  `fallback_to_source = true`) оригинал версии.
- `default` → `[pdf]`: ПОВЕДЕНИЕ ДО ЭТОГО ADR не изменено для ЛЮБОГО формата вне подвыборки —
  `gsfx` в карту НЕ добавлен явно (правило ничего не меняет для него: `resolveEffectiveFile()`
  пропускает только PDF/изображение, ни одно представление GSFX не бывает успешным структурно), а
  сканы/`docx`/прочие форматы, которых не было в измеренной подвыборке, идут по `default` —
  молчаливое обобщение с трёх измеренных форматов на все остальные было бы той самой инженерной
  догадкой, против которой написан D3 (Code Guidance P6.3).
- `RepresentationResolver::forLlm()` читает эту карту по расширению исходной версии; сейм
  `$forceKind` (P6.1, D50) сохранён и стоит ВЫШЕ политики: принуждение сильнее политики, политика
  сильнее оригинала. `DEFAULT_PRIORITY`-константа удалена — второй носитель того же факта не
  заводится (D52).

## Последствия

- **Плюс (цена):** `xlsx`/`xls`-документы (доминирующая доля корпуса эталонов) переходят на самое
  дешёвое представление среди измеренных работающих кандидатов — по трекингу прогона на ~28% дешевле
  `default` и ~28% дешевле `pdf` (292 714 против 406 347/509 085 микро-$, см. таблицу выше;
  абсолютные цифры не биллинг, см. предупреждение вверху).
- **Плюс (качество):** медиана f1 на измеренной подвыборке для `pdf_alt` (0.4716) выше `default`
  (0.4326) и разрыв растёт на крупных документах (`EST-XLSX-KS2-003`).
- **Минус, принят осознанно:** правило не строгий победитель формального критерия — `pdf_alt`
  дисквалифицирован одним эталоном по причине, отдельной от качества (`maxTokens` харнесса).
  Если следующий прогон под увеличенным `maxTokens` (≈39520+) покажет, что `pdf_alt` на этом эталоне
  ХУЖЕ по f1/row_coverage, чем `pdf`/`default` — это будет сигналом пересмотреть решение новым D#,
  не тихой правкой.
- **Минус, принят осознанно:** правило распространяется ТОЛЬКО на `xlsx`/`xls` — все остальные
  форматы (включая сканы, где `pdf_ocr`/`text` теоретически могли бы конкурировать) остаются на
  `default = [pdf]`, идентичном поведению до P3.1. Экономика для этих форматов НЕ улучшена этим ADR.
- **Минус производственный:** зависимость от `LibreOfficeConverter` (используется P3.4 для
  `pdf`, теперь и как основной путь `xlsx`/`xls` через `pdf_alt`) — оба представления производятся
  тем же классом инструмента (P6.1, D49: `pdf_alt` — kind под другим `meta.tool`, не второй `pdf`
  цепочки подготовки).

## Когда это решение недействительно

- **Смена линейки моделей активного маршрута** (`extract_*`/`extraction:discovery`) — тарификация
  PDF-страницы качественно другая на `gemini-3.x` (нативный текст PDF не тарифицируется как
  258 токенов/страница, только IMAGE-модальность по тайл-формуле, OQ-4,
  `findings/rag-P6-tokens-2026-07-27.md` того же плана); `FormatBenchRunner` на момент
  этого ADR предсказывает PDF-объём консервативным верхним потолком, НЕ откалиброванным под 3.x
  (Pending Work P6.1, унаследовано).
- **Материальная смена набора промтов** (P7, D54) — критерий P6.1/боевой прогон P6.2 сделаны на
  ЗАФИКСИРОВАННОМ наборе промтов (сегодняшние сиды); версии восьми промтов уже подняты P7.1/P7.2 при
  несуществующем на тот момент ADR — это ДОЛГ D54 (P7.1+P7.2), при появлении этого ADR строка
  «набор промтов изменился → перезамер победителя» фиксируется здесь явно: перезамер обязателен
  ПЕРЕД следующим материальным изменением промтов `extraction:*`.
- **Перегенерация представлений другой версией инструментов** — `meta.tool_version` разошёлся между
  предсказанием/замером и боевой версией `LibreOfficeConverter`/`SpreadsheetStrategy`. Обнаруживается
  сверкой `meta.tool_version` записей `prc_document_representations`.
- **Появление формата, которого не было в подвыборке** (сканы, `docx`, архивы и т.д.) — на них
  правило НЕ распространяется молча: они идут по `default = [pdf]`, и это записано явно в Решении
  выше как факт «не измерено», а не как предположение о качестве.
- **Учёт стоимости пересчитан (D126)** — если сверка реального биллинга Google (follow-up вне P6.3,
  `research/12-format-benchmark.md` Escalation Needed п.2, план `2026.07.26-EST-TRAIN`) покажет, что
  относительный порядок цены `pdf_alt` vs `pdf` vs `default` меняется после точного учёта
  thinking-токенов (маловероятно — искажение пропорционально `completion_tokens`, а не константа,
  `research/12` §«Следствие для этого отчёта», но не доказано измерением) — это тоже повод для
  нового замера, а не правки правила по памяти.

## Утверждение владельца

Владелец (Dmitry Vostrikov) выбрал вариант «принять `pdf_alt` с явной оговоркой» из трёх
альтернатив, предложенных при исполнении P6.3 (2026-07-28, через явный вопрос исполнителя перед
записью правила в конфиг — альтернативы были: (а) принять `pdf_alt` с оговоркой [выбрано], (б)
отложить до нового боевого прогона с увеличенным `maxTokens` (новый апрув денег), (в) зафиксировать
базовую политику D53 как временную). Обоснование выбора — рекомендация уходящей сессии P6.2/P6.3:
дисквалификация `pdf_alt` техническая (харнесс), не про качество представления, и данные по
остальным пяти эталонам подвыборки достаточно однозначны (дешевле, качество не хуже, часто лучше).
