# ADR 0008: provenance — тонкий срез по оспариваемым полям, не 5 уровней на все факты

- Status: Accepted
- Date: 2026-07-10
- Источник: `plans/DOMLANG/plan.md` §5 Decision Log, D4; `findings/P1-audit-verification.md` §2.3

## Context

Внешний аудит предложил пятиуровневую схему доверия к происхождению данных
(`registry-derived` … `validated-derived`) **на все факты** закупки.

`RAG:✅ 2026-07-10 «data provenance/lineage: W3C PROV vs прагматичные колонки»` (источники:
`w3.org/TR/prov-dm/` + PVLDB fine-grained provenance) даёт правило окупаемости: **fact-level
provenance материализуют только там, где ответ должен пережить удаление, ре-агрегацию, дедупликацию
или согласование между источниками.** Если вопрос звучит «какой job/источник произвёл эту запись»
(а не «почему здесь именно это значение») — достаточно coarse-колонок. Fine-grained захват несёт
документированный storage/processing overhead. Рекомендуемый практикой tiered-подход: coarse-lineage
на каждой записи, fact-level — только для 10–20% полей (user-visible / регулируемых / оспариваемых /
model-critical). Пятиуровневая схема аудита на все факты — прямое нарушение этого правила.

Coarse-lineage в проекте **уже существует** и покрывает вопрос «кто произвёл запись»:
`prc_revisions.crawler_run_id` · `prc_fetches.artifact_ref` (сырой CSV) ·
`prc_ai_analyses.{provider,model,rules_hash,cache_id}` · `prc_estimates.raw_result(_ref)` ·
`prc_documents.source_url`.

## Decision

Provenance материализуется **тонким срезом**: fact-level происхождение заводится только для полей,
которые приходят из **≥2 слоёв с расхождением** (значение из реестра ЕИС конфликтует со значением из
карточки/детализации или из AI-извлечения). Пятиуровневая схема `*-derived` на все факты
**отклонена** — это налог на storage/processing без доказанного потребителя. Coarse-lineage
(перечислен выше) остаётся достаточным для всех остальных полей.

Наличие таких конфликтных полей — не предположение, а **предмет доказательства**: research-item P4.1
обязан найти конкретные поля с расхождением между слоями ДО написания кода. Если P4.1 не найдёт
конфликтов — материализация provenance не делается вовсе (фаза P4 закрывается `⛔ Skipped by
decision`), и это легальный исход, а не пропуск работы.

## Рассмотренные альтернативы

Перенесены из D-лога (`plan.md` §5, D4) дословно:

- **(а) 5 уровней `*-derived` на все факты (вариант аудита)** — отвергнут как налог без доказанного
  потребителя.
- **(б) не делать вовсе** — отвергнут, но остаётся исходом P4, если P4.1 не найдёт конфликтов.

## Consequences

- Плюс: storage/processing overhead fine-grained provenance платится только за 10–20% полей, где он
  окупается, а не за весь объём фактов.
- Плюс: coarse-lineage уже покрывает «кто произвёл запись» — новый код нужен только там, где вопрос
  «почему здесь именно это значение» реально возникает (оспариваемое поле).
- Минус (принят осознанно): если позже появится поле, оспариваемое между слоями, но не пойманное в
  P4.1, ему придётся достроить fact-level provenance отдельным срезом — тонкий срез не закрывает
  проблему навсегда, он закрывает её по факту доказанного конфликта.
- Факт: P4.1 конфликтов не нашёл (2026-07-10, `plans/DOMLANG/findings/P4-provenance-proof.md`,
  `ВЕРДИКТ: 0 полей класса R1`). Оба кандидата с write-site'ами в разных слоях отклонены:
  `customer_org_id` — R2 (клоббер-дефект, маршрутизирован в `P5.4`), `status` — R3 (рассинхрон
  материализации, второй слой пишет `prc_events`, не колонку). `P4.2` закрыт `⛔ Skipped by
  decision` — легальный исход этого ADR, provenance не заводится.

## Триггер пересмотра

Пересмотреть решение, когда наступит **проверяемое событие**: факт начал приходить из ≥2 слоёв с
расхождением (реестр ЕИС ↔ карточка/детализация ↔ AI-извлечение дают разные значения одного поля)
**ИЛИ** обучающий контур (`docs/03_Dev/ai/training-loop.md`) потребовал происхождения факта для
gold-снапшота (нужно знать, из какого слоя пришло значение, чтобы зафиксировать его в
`prc_ai_dataset_examples`). До одного из этих событий тонкий срез — достаточная граница.
