# ADR-001: Эталонный каталог приходит из TcenZor, а не строится внутри

## Статус
✅ Принято

## Контекст

Agelto матчит позиции смет ЕИС к товарам. Изначально предполагалось, что Agelto
**сам строит** эталонный слой — «самообучающийся MDM на базе КТРУ/КСР»
(заявлено как конкурентное преимущество в [[02_Competitive_Analysis]]). При этом:

- эталонный MDM в коде **не реализован** (см. [[Architecture_Agelto]] §7.3 — «SQL-проект,
  в коде нет ни таблиц, ни моделей, ни pgvector»);
- параллельно проект [[TcenZor]] строит **универсальный каталог-хаб** с тем же
  слоем (разделы/категории/эталоны/алиасы/нормативка ГОСТ·ОКПД2·КТРУ) — см.
  [[ADR-006_Universal_Catalog_Scope]] (TcenZor);
- оба проекта независимо изобретали один и тот же товарный граф.

Решение владельца: **эталонный каталог — зона TcenZor (хаб)**, Agelto —
потребитель строительного среза по API ([[Universal_Catalog_Architecture]]).

## Рассмотренные варианты

### Вариант A: Agelto строит собственный MDM (исходный план)
- Полный контроль над каталогом и нормативкой.
- ❌ Дублирование с каталогом TcenZor; дважды решается нормализация/алиасы/
  нормативка; MDM так и не реализован — это чистый greenfield-долг.

### Вариант B: Каталог из TcenZor по API ✅
- TcenZor отдаёт строительный срез (категории/эталоны/алиасы/нормативка).
- Agelto хранит локальную реплику/кэш для матчинга смет (у него уже есть
  pgvector-инфраструктура и `client_collections`).
- ✅ Не дублируем товарное ядро; фокус Agelto — сметный матчинг и лиды.

## Решение

1. **Эталонный референс-каталог строительных материалов** (категории/эталоны/
   алиасы/ГОСТ/ОКПД2/КТРУ) **приходит из [[TcenZor]] по API**. Agelto его не
   строит.
2. Agelto хранит **локальную реплику/кэш** строительного среза для матчинга
   (offline-replica как базовый режим; `POST /catalog/match` к TcenZor — опция
   для сложных/редких позиций). Режим — открытый под-вопрос
   [[Universal_Catalog_Architecture]].
3. **`client_collections` остаются в Agelto** — это прайс-листы конкретного
   клиента-поставщика, не эталон. Матчинг: позиция сметы → **эталон TcenZor** →
   позиция коллекции клиента → лид (раньше связывали позицию сметы напрямую с
   коллекцией; теперь через эталонный слой).
4. **Тендеры, сметы, позиции смет (`ord_*`), уведомления, CRM-лиды** остаются
   «дома» в Agelto.

## Последствия

- ✅ Снимается greenfield-долг построения собственного MDM.
- ✅ Единый каталог в экосистеме; алиасы/нормативка ведутся один раз в TcenZor.
- ✅ Фокус Agelto сужается до сильной стороны — парсинг смет + матчинг + лиды.
- ⚠️ **Смена нарратива конкурентного преимущества.** Барьер входа больше не
  «владение самообучающимся MDM», а: (1) качество **сметного матчинга** (парсинг
  неструктурированных PDF/Excel ЕИС), (2) накопленный **golden dataset вердиктов**
  верификации, (3) глубина строительной доменной экспертизы. Это требует правки
  [[02_Competitive_Analysis]] (см. [[Dev_Status]]).
- ⚠️ **Внешняя зависимость от TcenZor** как поставщика каталога: нужен SLA,
  версионирование среза, поведение при недоступности (работа по локальной реплике).
- ⚠️ Нормативка КТРУ/КСР как «эталон при матчинге» (BRD `F-MDM-*`) переезжает в
  потребление вместо построения — правка [[BRD (Agelto)]].
