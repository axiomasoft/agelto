# Архитектура сервиса Agelto Smeta Parser

## 1. Схема конвейера (Pipeline)
Процесс обработки разделен на изолированные этапы, работающие через очереди Laravel (Redis).

| Этап | Механизм | Ответственность | Сетевая политика |
| :--- | :--- | :--- | :--- |
| **S1: Collector** | Job (1 поток) | Сбор ссылок на закупки с ЕИС | Sleep 5-10с, ротация прокси |
| **S2: Indexer** | Job (2 потока) | Сбор ссылок на файлы документов | Rate Limit: 10 зап/мин |
| **S3: Screening** | Job (10 потоков)| ИИ-вердикт: "Это смета?" | Без ограничений (Gemini API) |
| **S4: Parser** | Job (5 потоков) | Извлечение данных в таблицы лотов | Без ограничений |

## 2. Отказоустойчивость
1. **Статусная модель:** Каждая запись в `map_urls` и `map_documents` имеет поля `status`, `attempts` и `next_retry_at`.
2. **Retry Policy:** При ошибке (403, 500, ИИ ошибка) задача уходит в `failed`, инкрементирует счетчик и планирует перезапуск по Exponential Backoff.
3. **Изоляция:** Сбой на этапе анализа ИИ не останавливает сборщик ссылок.

## 3. Мониторинг и Логирование
* **Логи (`sys_logs`):** Хранят детальную историю всех "падений" со стеком ошибок и контекстом (IP прокси, ID документа).
* **Аналитика (`platform_parser_analytics`):** Агрегирует данные в разрезе "День / Парсер". Позволяет видеть:
    - Воронку конверсии: сколько закупок -> сколько файлов -> сколько смет найдено.
    - Процент технического брака (ошибок) на каждой стадии.

## 4. Схема БД (Ключевые таблицы)
* `platform_parsers`: Пресеты фильтров поиска.
* `platform_parser_map_urls`: Реестр найденных извещений.
* `platform_parser_map_documents`: Реестр файлов с результатами ИИ-скрининга.
* `orders` / `order_lots`: Финальные бизнес-данные.
