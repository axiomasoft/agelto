# Runbook: смена S3-провайдера

## Symptoms

Нет прямого симптома — это ПЛАНОВАЯ операционная процедура (владелец решил сменить бакет/провайдера
для документов, эталонов или сырых результатов извлечения), а не реакция на алерт. Три носителя,
которых касается процедура: `prc_document_versions.storage_path`, `prc_ai_fixtures.storage_path`,
`prc_estimates.raw_result_ref` (`disk` — колонка на каждом, `null` = диск по конфиг-ключу на момент
чтения, `research/07-storage-addressing.md` D51).

## Предусловия

- Читать целиком: `research/07-storage-addressing.md` §7–§9 (вердикты и инварианты этой процедуры).
- Единственная точка чтения/записи диска — `App\Services\Storage\FileLocationResolver`; если
  какой-то писатель обходит его конфиг-ключом напрямую — сначала перевести на резолвер (P6.3),
  иначе backfill материализует диск, которым писатель не пользуется.
- До боевого прогона P4.7 носители пусты/малы — шаги 2/4/5 пробегают за секунды; после —
  полноценный чанковый прогон на живых данных (`research/07` §9). Процедура одна и та же в обоих
  случаях, разный только объём.

## Шаги

Десять шагов, у каждого — проверка и точка отката. **Порядок необратим**: шаг 0 обязан пройти до
шага 2 (иначе поколенческое имя попадёт в БД постфактум как миграция данных), шаг 2 — до шага 6
(D51: флип конфига до материализации рвёт адресацию всех исторических записей), шаг 8 — до шага 9,
но НЕ вместе с ним (между ними окно наблюдения — единственная страховка перед необратимым удалением).

### Шаг 0 — переименовать логические имена дисков

Сегодняшние имена (`s3`, `estimates`, `estimates_s3`) нарушают соглашение (D53: имя диска в БД —
логическое и поколенческое, `<роль>_v<N>`, без драйвера/провайдера/региона в строке — иначе смена
`filesystems.php` превращается в миграцию данных). Переименовать здесь — значит поменять ТОЛЬКО
логический ключ диска в конфиге (`config/filesystems.php`, `config/documents.php, config/acquisition.php`, `config/ai.php`,
`.env.example`, тесты), например `s3` → `documents_v1`, `estimates` → `fixtures_v1`. Бакеты и уже
записанные объекты не трогаются.

Почему именно здесь: материализация (шаг 2) пишет в колонку имя, которое конфиг несёт В ЭТОТ
МОМЕНТ. Переименовать после материализации — значит переименовывать уже тысячи строк, то есть
делать данными то, от чего конвенция как раз защищает.

- **Проверка:** `docker compose exec app php artisan test` зелёный; `grep -rn "'s3'\|'estimates'"
  config/filesystems.php config/documents.php, config/acquisition.php config/ai.php` не находит старых ключей вне
  зафиксированного реестра grandfather'ов.
- **Откат:** вернуть прежние ключи в конфигах — данных это не касается.

### Шаг 1 — создать приёмник

Новый бакет, креды/IAM, шифрование, CORS, lifecycle — ДО копирования, чтобы приложение умело
писать в новое место без второй правки схемы.

- **Проверка:** `mc ls` на новом бакете; пробное чтение/запись САМИМ ПРИЛОЖЕНИЕМ (не только
  `mc`) — расхождение прав между `mc`-кредами и credentials приложения не поймать иначе.
- **Откат:** удалить бакет.

### Шаг 2 — материализовать `null`

По каждому носителю с колонкой:

```
docker compose exec app php artisan storage:disk-backfill document-versions --materialize-only
docker compose exec app php artisan storage:disk-backfill fixtures --materialize-only
docker compose exec app php artisan storage:disk-backfill estimate-raw-results --materialize-only
```

Команда проставляет диск, актуальный ПРЯМО СЕЙЧАС (по конфиг-ключу носителя), ни одного объекта не
читая — только `UPDATE` строки. `--from-id` продолжает прерванный прогон с последнего курсора.

- **Проверка:** по каждому носителю `disk IS NULL` = 0 строк.
- **Откат:** `disk = NULL` обратно — значение вычислимо из того же конфиг-ключа, потерь нет.

### Шаг 3 — включить фолбэк-цепочку

Прописать текущее (старое) поколение в `*_fallback_disks`:

- `config('documents.fallback_disks')` — для `document-versions`/`representations`;
- `config('ai.fixtures.fallback_disks')` — для `fixtures`;
- `config('acquisition.raw_fallback_disks')` — для `estimate-raw-results`.

`FileLocationResolver` пробует цепочку, только если объекта нет на диске записи
(`exists() === false`) — сбой самого драйвера не фолбэчит, пробрасывается как есть (P6.4).

- **Проверка:** `docker compose exec app php artisan test --filter=FileLocationFallbackTest`
  зелёный; в логах нет промахов (`Log::warning`) — на этом шаге объекты ещё физически на диске
  записи, промах означал бы дефект конфигурации цепочки.
- **Откат:** очистить `*_fallback_disks` (`[]`).

### Шаг 4 — backfill с верификацией

```
docker compose exec app php artisan storage:disk-backfill document-versions --to=documents_v2
docker compose exec app php artisan storage:disk-backfill fixtures --to=fixtures_v2
docker compose exec app php artisan storage:disk-backfill estimate-raw-results --to=raw_v2
```

Переносит объекты потоком (`readStream`/`writeStream`), чанками; запись обновляется ТОЛЬКО после
совпадения sha256 и размера на приёмнике (ETag не доказательство — только хэш+размер,
`research/07` §6.2, чеклист ловушек). Расхождение не валит весь прогон — строка попадает в отчёт,
код возврата ненулевой, диск строки не обновляется. `--from-id` резюмирует прерванный прогон.

- **Проверка:** нулевой код возврата, ноль расхождений в отчёте; выборочное чтение нескольких
  перенесённых файлов приложением.
- **Откат:** уже скопированные строки продолжают адресоваться и на СТАРОМ диске (диск строки
  ещё старый до подтверждённого совпадения) — переноса «наполовину» без адресации не бывает.

### Шаг 5 — дельта-синк

Повторить РОВНО ту же команду шага 4. Backfill идемпотентен: заново обходит носитель и переносит
только то, что появилось (новые строки, `disk IS NULL`) или изменилось, пока шаг 4 работал —
закрывает окно потери горячих записей, сделанных во время предыдущего прохода (`research/07` §6,
ловушка «горячие записи во время backfill»; dual-write не вводится, синка достаточно).

- **Проверка:** второй прогон печатает ноль скопированных/материализованных — если не ноль,
  повторить дельта-синк ещё раз перед шагом 6.
- **Откат:** тот же, что у шага 4.

### Шаг 6 — флип конфига записи

Переключить конфиг-ключ **записи** на новое поколение: `documents.disk`,
`ai.fixtures.disk`, `acquisition.raw_disk`. Старое поколение ОСТАЁТСЯ в `*_fallback_disks` (шаг 3 не
откатывается здесь).

После флипа перезапустить Horizon-воркеры (`make prod:workers-restart`) — держат конфиг в памяти,
без рестарта продолжат писать на старое поколение дольше веб-слоя.

- **Проверка:** новые записи получают новое имя диска в колонке; чтение исторических строк идёт
  без промахов фолбэка (диск строки — старый, файл там же, где был).
- **Откат:** вернуть конфиг на прежнее поколение и перезапустить воркеры — исторические строки
  продолжают указывать на уже проверенные копии, читаются обоими путями одновременно.

### Шаг 7 — окно наблюдения

Старый бакет остаётся **read-only** и доступным (не удаляется, права на запись снимаются). Следить
за `warning`-промахами фолбэка и ошибками чтения N дней подряд — N назначает владелец по трафику
чтения исторических файлов, не эта процедура.

- **Проверка:** ноль промахов фолбэка за окно наблюдения.
- **Откат:** вернуться к шагу 6 (конфиг записи на старое поколение).

### Шаг 8 — снять фолбэк-цепочку

Очистить `*_fallback_disks` (`[]`) и перезапустить воркеры.

- **Проверка:** полный сюит зелёный; в логах промахов больше нет (фолбэк снят — их и не может
  быть, объекты на новом диске самодостаточны).
- **Откат:** вернуть цепочку из шага 3.

### Шаг 9 — уборка источника

Удалить объекты старого бакета. **Точки отката нет** — поэтому шаг отделён от шага 8 окном
наблюдения (шаг 7) и не сливается с ним: слияние уничтожает единственную страховку процедуры.

- **Проверка:** —
- **Откат:** нет.

## Ловушки, применимые к проекту

- **ETag — не доказательство идентичности** объекта между провайдерами; backfill проверяет только
  sha256 + размер.
- **Дрейф метаданных** — проект не пишет пользовательские метаданные/ACL на объекты, часть ловушки
  не применима; `content-type` копируется потоком без отдельной правки.
- **Троттлинг/retry-штормы** — команда однопоточная и чанковая по построению, отдельного троттлинга
  не требует.
- **Расхождение прав приёмника** — шаг 1 требует пробного чтения ИМЕННО приложением, а не только
  `mc`/консолью провайдера.
- **Версионирование/lifecycle бакета** — delete-маркеры делают источник «полным» при скрытых
  объектах; полнота проверяется по строкам БД, не по листингу бакета.
- **Подписанные URL** cutover не переживают — проект их сегодня не выдаёт, ловушка станет
  применимой только когда появится публичная выдача файлов.
- **Кэши воркеров** — Horizon держит конфиг в памяти весь процесс; рестарт воркеров обязателен
  после шагов 3, 6 и 8, иначе часть трафика ещё какое-то время идёт по старой конфигурации.

## Fix

Сбой на шаге — не чинится молчаливой правкой поведения резолвера/backfill: если проверка шага не
проходит, откат ЭТОГО шага (см. таблицу выше), диагноз причины (обычно — права приёмника, сеть,
незамеченный писатель в обход резолвера), повтор шага. Дефект самого кода резолвера/backfill,
найденный по ходу процедуры, — не эта процедура его чинит: заводить отдельный item/эскалацию, не
трогать шаг наживую.

## Rollback

Откат каждого шага описан построчно выше. Общий принцип: пока не пройден шаг 9 (необратимый),
процедура откатываема на любом шаге без потери адресации — исторические строки либо ещё указывают
на старый диск, либо уже подтверждённо скопированы (совпадение хэша), либо читаются фолбэком.

## Escalation

Промахи фолбэка не исчезают за окно наблюдения (шаг 7), расхождения backfill (шаг 4/5) не
устраняются повторным прогоном, или обнаружен писатель, пишущий диск в обход
`FileLocationResolver`, — эскалация владельцу домена хранения с приложенным отчётом команды
`storage:disk-backfill` и номером шага, на котором процедура остановлена.
