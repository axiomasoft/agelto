## Важные уточнения аудита

**Первое: `egress_id` уже существует.** Он есть в `prc_network_routes`, но текущий набор budget scopes формируется по origin и `route_id`, без общего egress-origin-бюджета. Следовательно, требуется не новая идентичность с нуля, а включение существующей идентичности выхода в авторизацию отправки. [Схема маршрутов](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/database/migrations/2026_10_25_100000_create_prc_process_network_tables.php), [Выбор scopes](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkAuthorityRepository.php)

**Второе: `403` не выделен в транспортном классификаторе.** При отсутствии транспортной ошибки он попадает в общий путь HTTP-ответов с сигналом `Success`; это не доказывает предметный успех парсинга, поскольку ниже есть отдельная проверка адаптера, но транспортная достижимость сейчас явно не отделена от отказа в доступе. [RequestClassifier](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Network/RequestClassifier.php), [AcquisitionValidation](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Acquisition/AcquisitionValidation.php)

**Третье: `sent_at` сейчас нельзя считать точным временем выхода запроса в сеть.** Поле заполняется при регистрации авторизованной попытки, до вызова транспорта; для расследования частоты нужно различать разрешённые отправки и фактически начатые HTTP-вызовы. [Запись авторизации](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkPermitSqlHelper.php), [Вызов транспорта](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Network/OutboundExecutor.php)

## Целевая схема

Предлагаемая архитектура:

```text
Process work + сохранённый checkpoint
                  ↓
Допуск к исполнению с учётом класса трафика
                  ↓
Профиль маршрута, закреплённый для стадии
                  ↓
Проверка health / hold / cooldown
                  ↓
Атомарная проверка применимых бюджетов
  source group → origin → egress-origin → route-origin
                  ↓
Проверка разрешения непосредственно перед отправкой
                  ↓
Один физический HTTP-запрос
                  ↓
Транспортный результат + предметная оценка ответа
                  ↓
Успех / durable defer / recovery / операторский разбор
```

Основные предлагаемые инварианты:

- Количество воркеров и размер пустой базы не увеличивают разрешённую скорость.
- Новый прокси не создаёт дополнительную общую квоту площадки.
- Все повторы, редиректы и диагностические запросы проходят тот же gate.
- Ожидание квоты не считается неудачной попыткой получения данных.
- Отказ координатора не разрешает отправку без лимитов.
- У незавершённой работы сохраняются идентичность, прогресс и причина ожидания.
- Смена маршрута после отказа в доступе не используется как автоматический обход ограничения.

## PR A: диагностика

**Цель:** установить, где именно нарушается ожидаемая интенсивность, не увеличивая нагрузку на ЕИС.

Точки изменения: `NetworkPermitRepository`, `ScheduledAttemptGate`, `OutboundExecutor`, диагностический интерфейс Process. В репозитории уже предусмотрены команды `process:status`, `process:diagnose` и операторские действия Process. [Cheatsheet](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/.ai/guidelines/cheatsheet.md)

### Изменения

- Добавить read-only представление действующей сетевой политики: scope, скорость, burst, параллелизм, версия, cooldown.
- Показывать различие между defaults конфигурации и значениями в БД.
- Разделить события `authorized`, `transport_started`, `finished`.
- Связывать события через `physical_request_id`, work, route, origin и класс трафика.
- Показывать очередь demand, активные permit и их владельцев.
- Отдельно учитывать авторизацию, после которой транспорт не стартовал.
- Проверить внешние HTTP-вызовы вне общего executor архитектурным тестом.

### Приёмка

- По одной работе можно восстановить последовательность всех физических попыток.
- По origin видны интервалы между разрешениями и началами транспорта.
- Неоднозначная попытка не объявляется достоверно отправленной или неотправленной.
- Диагностика не раскрывает proxy credentials, cookies и полные чувствительные URL.

**Результат:** доказательное объяснение текущей проблемы — неверная политика, обход gate, общий внешний IP у независимых систем либо другая причина. До такой проверки нельзя утверждать, что сам GCRA работает неправильно.

## PR B: политика лимитов

**Цель:** управлять ограничениями площадок явно и версионируемо.

Существующая политика уже различает defaults и audited override; её изменение не должно сбрасывать накопленные `tat`, `send_tat` и `not_before`. [Конфигурация](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/config/outbound.php), [Схема бюджетов](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/database/migrations/2026_10_25_100000_create_prc_process_network_tables.php)

### Предлагаемый контракт

| Настройка | Назначение |
|---|---|
| Базовый интервал | Плавная отправка |
| Жёсткий предел окна | Например, запросы за последние 60 минут |
| Burst | Разрешённая кратковременная пачка |
| Max inflight | Одновременные запросы |
| Доли классов | Fresh listing, detail, archive, recovery |
| Cooldown policy | Поведение при ограничениях |
| Версия и происхождение | Default, override, согласованная квота |

### Изменения

- Расширить `OutboundPolicy` и путь материализации бюджетов через `SourceCatalogSync`.
- Отделить потолок политики от будущей адаптивной рабочей скорости.
- Поддержать интервалы реже одного запроса в минуту: часовая настройка не должна искусственно ограничиваться текущим интерфейсом `rate_per_minute`.
- Добавить проверку противоречивых параметров.
- Все изменения проводить с автором, причиной и ожидаемой версией.
- При ужесточении политики инвалидировать несовместимые разрешения через существующую проверку evidence.
- Не вводить «безопасные лимиты ЕИС» без измерений или подтверждённой политики источника.

### Приёмка

- Понижение лимита влияет на ещё не отправленные запросы.
- Повышение лимита не обнуляет cooldown и историю.
- Повторный sync не переписывает операторский override.
- Устаревшая версия изменения отклоняется.

## PR C: общие scopes

**Цель:** учитывать общую площадку и реальный выход в интернет.

Текущий `NetworkAuthorityRepository` централизованно формирует и блокирует budget scopes в установленном порядке; расширение нужно делать именно здесь. [Код](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkAuthorityRepository.php)

### Изменения

- Добавить общий `egress + origin` scope, используя существующий `egress_id`.
- Сохранить `route + origin` для локальных ограничений маршрута.
- Предусмотреть source-group scope для hostname, которые действительно должны делить общую квоту.
- Не объединять разные hostname по догадке: принадлежность задаётся каталогом.
- Сохранять в permit полный набор scopes и версий.
- При смене egress-мapping не позволять использовать ранее выданное несовместимое разрешение.
- Материализовать недостающие budgets через явный sync, а не неявное создание в HTTP hot path.

### Миграции

- Добавить версионируемую привязку source-group, если она нужна конкретной площадке.
- Добавить версию сетевой идентичности маршрута либо эквивалентный fingerprint для проверки permit.
- Новые scopes размещать в существующей таблице бюджетов, без второго координатора.

### Приёмка

- Два route с одинаковым `egress_id` делят egress-квоту.
- Независимые выходы имеют отдельные локальные лимиты, но общий source/origin-потолок.
- Одновременные запросы не приводят к частичному списанию бюджетов.
- Сохраняется канонический порядок блокировок.

## PR D: часовые квоты

**Цель:** поддержать именно «не больше N запросов за последние 60 минут», а не только среднюю скорость.

Сейчас rolling-hour подсчёт реализован специально для `status_refresh` и учитывает авторизованные permit, а также действующие резервации. Общей настраиваемой часовой квоты всех отправок в этом пути нет. [quotaRetry](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkPermitSqlHelper.php)

### Предлагаемая реализация

Добавить **компактный журнал списаний квоты**, отдельный от долговременного журнала observations. Предлагаемое название — `prc_network_quota_charges`.

Минимальные поля:

- `budget_id`.
- `physical_request_id`.
- `charged_at`.
- Тип учитываемой квоты, если потребуется несколько окон.
- Уникальность списания для запроса и бюджета.

### Алгоритм

1. Заблокировать все применимые бюджеты.
2. Проверить GCRA, cooldown и параллелизм.
3. Проверить число списаний в действующем окне.
4. При исчерпании определить время освобождения квоты.
5. При разрешении атомарно выполнить send claim и записать списания.
6. После commit разрешить вызов транспорта.

Резервирование будущего слота не должно гарантировать наличие часовой квоты: окончательная проверка остаётся в `claimSend()`.

### Приёмка

- При конкуренции последний доступный запрос получает только один владелец.
- Retry и redirect расходуют квоту отдельно.
- Повторный вызов claim не списывает её второй раз.
- Неоднозначный сбой после авторизации не возвращает квоту автоматически.
- Очистка не удаляет списания внутри активного окна.
- Расширение окна запрещено без достаточной истории либо сопровождается консервативным прогревом.

**Это журнал ограниченного горизонта, а не бесконечное логирование каждого запроса.**

## PR F: планирование и defer

**Цель:** защищать свежий listing и не держать воркеры занятыми длительным ожиданием.

Сейчас gate может ждать до 20 секунд, а ожидающие demand продлеваются короткими интервалами; выбор следующего demand основан на FIFO. Простое уменьшение ожидания без изменения справедливости может привести к постоянной отмене и повторной регистрации tickets. [ScheduledAttemptGate](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Network/ScheduledAttemptGate.php), [NetworkPermitRepository](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkPermitRepository.php)

### Изменения

- Ввести взвешенное обслуживание классов с заимствованием свободной мощности.
- Защитить минимальный прогресс свежего listing.
- Обеспечить ненулевой прогресс detail.
- Ограничить archive, recovery и diagnostic.
- Сохранять FIFO внутри одного класса.
- Сохранять возраст ожидания и планировочный долг при defer; новая попытка не должна терять всю позицию.
- Применять предварительный backpressure до массового допуска работ к воркерам.
- Использовать существующий Process для durable defer, а не новую очередь исполнения.

Предлагаемые новые компоненты: `NetworkSchedulingPolicy` и репозиторий состояния справедливого обслуживания. **Это предлагаемые имена, не существующие классы.**

### Время продолжения

Предлагаю вычислять `next_eligible_at` как наиболее позднее из применимых ограничений:

- Доступный временной слот.
- Освобождение часовой квоты.
- Cooldown.
- Восстановление маршрута.
- Backoff конкретной работы.

Jitter добавляется только после этого времени.

### Приёмка

- Большой detail backlog не останавливает свежий listing.
- Непрерывный listing не вызывает бесконечного голодания detail.
- При пустом одном классе его мощность используют остальные.
- Архивное заполнение пустой базы не получает приоритет свежего поиска.
- Число пробуждений не растёт пропорционально всему backlog каждую секунду.
- Очередь не становится вторым владельцем работы: lease и финализация остаются в Process.

## PR G: блокировки и ответы

**Цель:** отделить сетевую достижимость от доступности данных и права продолжать запросы.

Изменяемые точки: `RequestClassifier`, `HealthRepository`, `RetryPolicy`, предметная оценка в адаптерах и `AcquisitionValidation`. В текущем executor HTTP-результат сначала записывается через gate, затем передаётся вызывающему слою. [OutboundExecutor](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Network/OutboundExecutor.php)

### Политика результата

| Результат | Предлагаемое действие |
|---|---|
| `429` | Общий cooldown, defer, отсутствие немедленной смены IP |
| `403` | Отдельная классификация отказа в доступе, ограниченная диагностика, соответствующий hold |
| `200` с challenge | Предметная ошибка, без завершения карточки/listing |
| `502/503/504` | Ограниченный транспортный retry |
| Proxy auth / `407` | Credential hold конкретной версии |
| TLS failure | Configuration hold, без ослабления TLS |
| Неизвестная структура | Инцидент адаптера |
| Подтверждённое отсутствие объекта | Предметный терминальный результат |

### Дополнительные изменения

- Не позволять `403` автоматически подтверждать восстановление предметной доступности.
- Оставить отдельный факт «HTTP-ответ получен».
- Для слишком большого `Retry-After` сохранять общий безопасный hold, а не только блокировать одну работу.
- Обработать `Retry-After: 0` без немедленной лавины.
- Не укорачивать валидный срок ожидания сервера.
- Подтвердить, что повторное применение результата не продлевает cooldown от нового времени обработки.

Последний граничный случай важен: сейчас значение `Retry-After` свыше суток возвращает `null`, а `HealthRepository` при таком результате выдаёт `PolicyReview` без обновления origin cooldown. Это точка для целевого regression-теста. [RetryPolicy](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Network/RetryPolicy.php), [HealthRepository](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/HealthRepository.php)

## PR H: восстановление работ

**Цель:** догонять пропуски без бесконечных повторов и без повторной загрузки уже полученного.

Основа уже есть: listing выполняет ограниченную страницу за одну работу, непригодный ответ не продвигает cursor; detail сохраняет части и выполняет контрольную перепроверку согласованности. Эти гарантии нужно сохранить. [ListingHandler](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Acquisition/ListingHandler.php), [DetailHandler](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Acquisition/DetailHandler.php)

### Изменения

- Развести счётчики defer, физических отправок, транспортных ошибок и предметных отказов.
- Для каждой retryable-причины определить backoff и горизонт автоматического восстановления.
- Ожидание лимита не расходует предметные попытки.
- Использовать отдельный recovery-бюджет внутри общей квоты.
- Не запускать сразу весь backlog после закрытия breaker.
- После исчерпания горизонта переводить работу в видимое операторское состояние.
- Массовый ручной retry проводить через тот же бюджет.
- Сохранить checkpoint и исходную идентичность при переносах.

### Особенность detail

Не стоит ради экономии запросов удалять контрольный запрос первой части: сейчас он участвует в проверке согласованности собранной карточки. Оптимизировать его можно только с сохранением эквивалентной гарантии, например при наличии подходящей ревизии источника. [DetailHandler](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Services/Procurement/Acquisition/DetailHandler.php)

### Приёмка

- Полученные части не загружаются повторно без предусмотренной причины.
- Падение воркера не теряет незавершённую работу.
- Повторная доставка не приводит к повторной предметной финализации.
- Истёкший автоматический recovery не исчезает из наблюдаемости.
- После восстановления свежие данные и догоняющая обработка получают предсказуемые доли.

## PR I: очистка

**Цель:** ограничить рост служебных таблиц без потери квот и доказательств.

Здесь нельзя просто добавить `DELETE ... WHERE created_at < ...`: request attempts ссылаются на demands, observations — на attempts, applications — на observations; permit scopes имеют собственные связи. Кроме того, текущий status budget читает историю permit за час. [Схема наблюдений](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/database/migrations/2026_10_25_100001_create_prc_request_observation_tables.php), [Схема сети](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/database/migrations/2026_10_25_100000_create_prc_process_network_tables.php), [Status quota](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/app/Repositories/Procurement/Network/NetworkPermitSqlHelper.php)

### Разделить хранение

| Данные | Предлагаемая политика |
|---|---|
| GCRA/cooldown | Компактное текущее состояние, без сброса при очистке |
| Активные demand/permit | До завершения или безопасного истечения |
| Списания квоты | Максимальное поддерживаемое окно плюс защитный запас |
| Метрики | Агрегаты с укрупнением старых интервалов |
| Audit/evidence | Отдельная архивная политика с учётом зависимостей |
| Незавершённые работы | До завершения или явного решения оператора |

### Изменения

- Перевести часовой контроль на компактный журнал до очистки старых permit.
- Начать с безопасной очистки терминальных demand, не имеющих зависимых доказательств.
- Для связанных audit-записей сделать отдельный согласованный архивный процесс.
- Выполнять очистку небольшими пакетами вне транзакции отправки.
- Добавить dry-run, защитные проверки и метрики задержки очистки.
- Не включать каскадное удаление через всю цепочку ради удобства.

### Приёмка

- Очистка не открывает дополнительную квоту.
- Активные владельцы и расследуемые работы не затрагиваются.
- Повторный запуск безопасен.
- Ошибка архивирования не приводит к удалению оригинала.
- Длительность очистки и число обработанных строк наблюдаемы.

## PR J: операторский контур

**Цель:** оператор понимает не только «есть 403», но и что остановлено, почему и когда продолжится.

### Экран источника

Предлагаю показывать:

- Настроенную и действующую скорость.
- Расход часовой квоты.
- Inflight по origin и выходам.
- Очередь и возраст работ по классам.
- Состояние маршрутов, target и адаптера.
- Причину cooldown/hold и срок следующего действия.
- Backlog восстановления.
- Последнее успешное получение listing и detail.

### Экран работы

Предлагаемое объяснение:

> Карточка ожидает общего бюджета источника. Маршрут доступен. Повторная отправка ещё не выполнялась. Прогресс сохранён.

### Алерты

- Нет прогресса при непустой очереди.
- Растёт возраст свежего listing.
- Detail перестал получать гарантированную долю.
- Повторяются ограничения после восстановления.
- Зависли разрешения или владельцы.
- Отстаёт очистка.
- Действующая политика отличается от ожидаемой.

В метрики не следует помещать URL и идентификаторы каждой закупки как labels; детальная связь должна оставаться в журнале событий.

## PR K: адаптация скорости

**Цель:** автоматически снижать рабочую скорость при подтверждённых ограничениях и осторожно восстанавливать её.

Предлагаю включать эту часть только после предыдущих PR:

- Рабочая скорость всегда ниже или равна административному потолку.
- При подтверждённом rate-limit она снижается.
- После устойчивых успехов повышается постепенно.
- Credentials, TLS и parser failure не считаются доказательством превышения частоты.
- После cold start не накапливается разрешённый burst за время простоя.
- У каждого автоматического изменения есть причина и история.
- Отключение адаптации не отключает жёсткие лимиты.

**Не предлагаю автоматический поиск максимально допустимой нагрузки методом провоцирования блокировок.**

## Проверки и rollout

В репозитории уже есть целевые тесты `GcraConcurrencyTest`, `ClaimSendFenceTest`, `BoundedFifoDemandTest`, `StatusCapacityQuotaTest`, `NetworkDemandRecoveryTest`, `RouteHealthTest` и другие сетевые проверки. Их нужно расширять, а не заменять новой изолированной тестовой системой. [Существующий suite](https://github.com/axiomasoft/agelto/tree/e1123ae7c056051d32eababcc05b4e3599cd1046/tests/Feature/ProcessCore/Network)

### Обязательные сценарии

| Сценарий | Ожидаемый результат |
|---|---|
| Один прокси, много воркеров | Общая скорость не растёт |
| Несколько прокси | Origin/source quota не умножается |
| Разные route, один egress | Общий egress-бюджет |
| Пустая база | Большой backlog без стартового всплеска |
| Непрерывный detail | Fresh listing получает долю |
| Непрерывный listing | Detail продолжает продвигаться |
| Retry и redirect | Каждая отправка отдельно авторизована |
| `429` | Общий cooldown, без лавины |
| `403` или challenge | Нет ложного завершения данных |
| Crash после claim | Нет двойного списания и бесконтрольного повторения |
| Недоступна БД | Отправка запрещена |
| Изменена политика | Старое несовместимое разрешение не используется |
| Очистка во время работы | Квоты и active evidence сохранены |
| Восстановление источника | Backlog разгребается постепенно |

### Порядок выкладки

1. Добавить диагностику без изменения политики отправки.
2. Выполнить добавочные миграции и совместимое чтение старых snapshot.
3. Материализовать новые scopes и проверить полноту каталога.
4. Включить ограничения на одном контролируемом профиле с консервативным потолком.
5. Проверить fairness, recovery и отсутствие лишних пробуждений.
6. Включить retention после проверки новой схемы часовых квот.
7. Адаптивную скорость включать отдельно.

При откате нельзя сбрасывать `tat`, `send_tat`, cooldown и журнал действующей квоты. Если предыдущая версия не умеет безопасно читать новую конфигурацию, корректный rollback — pause затронутых работ, а не их выполнение с упрощёнными ограничениями.

### Требования репозитория

Проверки следует проводить в изолированном `agelto_core_test`, без live crawling и без сброса общей БД; для изменённых отслеживаемых файлов нужно синхронизировать manifest/runtime hashes и проверить архитектурные ограничения. Это прямо закреплено в [AGENTS.md](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/AGENTS.md).

Для этой серии изменений применимы `make core-quality`, suites network, concurrency, acquisition, platforms и observability, затем regression; соответствующие команды перечислены в [cheatsheet](https://github.com/axiomasoft/agelto/blob/e1123ae7c056051d32eababcc05b4e3599cd1046/.ai/guidelines/cheatsheet.md).

**Первый практический шаг — PR A: проверить действующие бюджеты и связать разрешения с фактическими стартами транспорта. Затем — исправление классификации отказов и развитие существующего gate; Redis и переписывание process engine в этот план не нужны.**
