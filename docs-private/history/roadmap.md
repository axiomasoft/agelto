# ТЗ v2 · 06 — Дорожная карта реализации

> Порядок срезов и критерии приёмки. Каждая фаза — вертикальный срез, доводимый до зелёных тестов (Docker test-gate). Ссылки на разделы: `docs/03_Dev/database.md`–`docs/03_Dev/admin-panel.md`.

## Принципы дорожной карты

- Вертикальные срезы (tracer bullets), не горизонтальные слои: каждая фаза даёт работающий сквозной кусок.
- База данных — фундамент, идёт первой; дальше — сбор → документы → извлечение → провайдеры/eval → админка.
- Заимствование из v1 — точечное (heartbeat/курсор, ценовое дробление, context caching, промпты из БД, «схема как код»), не копирование целиком.

## Фаза 0 — Каркас

- Новый репозиторий; стек: PHP 8.4+, Laravel 12, Postgres 17, Redis/Horizon, object storage (MinIO), Node-сервис рендеринга (отдельный контейнер, задел).
- Docker-окружение (app/horizon/scheduler/postgres/redis/minio/browser) по канону docker-скиллов; тестовая БД `*_test`, изоляция.
- **Приёмка**: `make test-preflight` зелёный, `/up` healthy, пустая миграция ядра применяется.

## Фаза 1 — Схема БД и ядро закупок

- Миграции всей схемы `docs/03_Dev/database.md`: справочники, `prc_procurements` + `prc_revisions` + `prc_events`, `plt_status_mappings`, lots/items, документы/версии, сметы, краулинг, LLM-конфиг; партиционирование `*_events`/`*_revisions`/`ai_llm_calls`/`crw_fetches` + premake-команда.
- Модели, репозитории (read/store split), инжест-процессор (закупка → ревизия + события), сервис статус-маппинга.
- **Приёмка**: чек-лист сценариев схемы (`docs/03_Dev/database.md` §11) покрыт тестами — новая закупка, новая редакция, смена статуса/цены, состояние на дату, неизвестный статус → `unknown`+алерт.

## Фаза 2 — Сбор (CSV/HTTP, fresh)

- Source-абстракция + `CsvSourceMethod`; профили/прогоны (heartbeat, курсор, one-active); `crw_fetches`; детект «тихого cap»; вежливый темп + прокси-пул.
- Fresh-режим по расписанию (44-ФЗ + 223-ФЗ): скан по убыванию обновления до известного блока; инжест в ядро; нормализация способа закупки и статусов.
- **Приёмка**: реальный fresh-скан двух реестров наполняет `prc_procurements`/ревизии/события; повтор идемпотентен (нет дублей); дедуп и стоп-детект работают.

## Фаза 3 — Детальная карточка + документы

- Стадия детального анализа карточки (HTTP-first, `docs/03_Dev/crawling-pipeline.md` §5): вкладки common-info/documents/event-journal/supplier-results → `prc_procurements`+`prc_eis_details`, `prc_items`, `prc_financing`, `org_organizations`+`org_procurement_parties`, `prc_events` (из журнала ЕИС), `prc_protocols`/`prc_bids`/`prc_awards`/`prc_clarifications`/`prc_cancellations`.
- Классификаторы (`ref_*`) — загрузчик справочников; резолв кодов позиций.
- Индексация вложений в `doc_documents`; скачивание версий с дедупом по `content_hash`; сырьё в object storage.
- **Приёмка**: по закупке снят полный детальный слой; журнал событий ЕИС наполняет `prc_events`; организация в нескольких ролях резолвится в один `org_organizations`; итоги завершённой закупки → `prc_awards`/`prc_bids`; замена файла → новая версия + событие.

## Фаза 3b — Архив (перекачка истории)

- Archive-режим: по дням + рекурсивное ценовое дробление до выборки ≤ лимита; возобновление с курсора.
- **Приёмка**: перекачка выбранного периода без слепых зон сверх допуска.

## Фаза 4 — Подготовка + скрининг

- Стратегии подготовки: архивы → дочерние записи (`parent_version_id`), Excel→PDF, пометка изображений; защита от zip-бомб.
- Скрининг через `LlmProvider` (дешёвый провайдер): классификация типа, ветвление estimate/иное/unknown; очереди Horizon, lease, retry.
- **Приёмка**: архив со сметой внутри доходит до кандидата; не-смета сохраняет тип без полного разбора; `unknown` отсекается; идемпотентность стадий.

## Фаза 5 — Полное извлечение смет

- Оркестратор многошагового разбора (паспорт → построчные диапазоны → итоги), context caching, structured output, `temperature=0`.
- Merge + детерминированная валидация полноты в коде; маппинг в нормализованные `est_estimates`/sections/items/resources/totals; сырой ответ в object storage.
- **Приёмка**: смета на сотни строк извлекается с контролем полноты; расхождение → ревизия/re-run диапазона; повтор не плодит дублей (unique `(version, step)`).

## Фаза 6 — Провайдеры, eval, shadow

- Матрица роутинга (`ai_routes`) + резолвер с fallback; CRUD context-кэшей; учёт стоимости.
- Golden-датасет + eval-раннер (field/row-метрики) + CI-гейт; shadow-режим для сравнения провайдеров.
- Контракт локальной LLM (OpenAI-совместимый адаптер) — подключаемость без правки домена.
- **Приёмка**: смена провайдера шага через админку без деплоя; eval-отчёт по голдену; shadow-прогон пишет сравнительные метрики.

## Фаза 7 — Админка и наблюдаемость

- Filament-ресурсы (`docs/03_Dev/admin-panel.md`): краулеры/прогоны, реестр закупок с таймлайном событий и редакциями, документы/сметы, промпты, роутинг, датасет/eval, настройки (spatie-settings).
- Метрики, дэшборды, алерты; health-checks; операторский аудит.
- **Приёмка**: оператор управляет краулерами и промптами, видит путь закупки и полноту смет, получает алерты; smoke-контроль источника активен.

## Фаза 8 — Запасной backend и будущее (по потребности)

- Node-сервис рендеринга (job-API, пул, изоляция падений, shared volume) — для будущих площадок с клиентским рендерингом; для ЕИС не на критическом пути.
- Задел: `api`-метод (официальные каналы), публичный API/витрина, awards/contracts (итоги/победители), новые типы документов и их обработчики.
- **Приёмка** (когда актуально): новая площадка добавляется адаптером без миграций ядра.
