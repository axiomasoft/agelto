## 2. Схема кодов (D13)

Код эталона — **идентификатор, а не описание**: он уезжает в путь хранилища
(`<CODE>/source.<ext>`, D17), в `estimates/manifest.json` (D20) и в имена `*.gold.json` (D1).
Поэтому он латинский, верхнего регистра, без пробелов и точек, и переживает пересмотр
формулировок таксономии.

```text
<КЛАСС>-<ФОРМАТ>-<ФОРМА>-<NNN>
^(EST|NEG)-(XLSX|XLS|PDF|GSFX|DOCX|JPG)-[A-Z0-9]{2,10}-[0-9]{3}$
```

| Часть | Значения | Откуда берётся |
|:--|:--|:--|
| `КЛАСС` | `EST` — смета, эталон extraction · `NEG` — не-смета, эталон скрининга | D5: корпус двухсоставный |
| `ФОРМАТ` | `XLSX` · `XLS` · `PDF` · `GSFX` · `DOCX` · `JPG` | расширение исходного файла (все семь расширений корпуса, кроме мусорного `ini`) |
| `ФОРМА` | латинский код формы из таксономии P1.2 — §2.1 ниже | кластер, а не имя файла (P1.2 §3: имя файла форму не определяет) |
| `NNN` | трёхзначный порядковый, независимый в пределах тройки `КЛАСС+ФОРМАТ+ФОРМА` | порядок появления в этом документе |

Примеры: `EST-XLSX-KS2-001` (акт по Методике 2020 на бланке КС-2) · `EST-GSFX-LSR-001`
(контейнер ГрандСметы) · `NEG-DOCX-CONTRACT-001` (проект контракта).

### 2.1 Словарь кодов формы

Одиннадцать кодов на 23 кластера — коды формы намеренно **более общие, чем кластеры**:
Code Guidance требует при сомнении брать более общий код, а не изобретать трёхбуквенный на
один файл. Разные кластеры одной формы разводятся форматом и порядковым номером, а не новым
кодом: `EST-XLSX-KS2-001/002` (`CL-01`) и `EST-XLSX-KS2-003` (`CL-11`) — один код формы,
разные кластеры.

| Код формы | Что называет | Кластеры |
|:--|:--|:--|
| `KS2` | акт о приёмке выполненных работ (форма КС-2, в т.ч. по Методике 2020) | `CL-01`, `CL-11`, `CL-13` |
| `KS3` | справка о стоимости выполненных работ и затрат (форма КС-3) | `CL-03` |
| `LSR` | локальный сметный расчёт (любого генератора и метода расчёта) | `CL-05`, `CL-10`, `CL-14`, `CL-15` |
| `VOR` | ведомость объёмов работ на сметном бланке | `CL-12` |
| `SCAN` | скан-PDF сметы без текстового слоя | `CL-16` |
| `DRAWING` | чертёж / схема обмера | `CL-02`, `CL-22` |
| `VOLUME` | расчёт объёмов работ (папки «Объемы») | `CL-04`, `CL-18`, `CL-19` |
| `AOSR` | акт освидетельствования скрытых работ | `CL-06`, `CL-17` |
| `SPEC` | спецификация материалов и оборудования | `CL-07` |
| `JOURNAL` | кабельный журнал | `CL-08` |
| `PHOTO` | фотография с объекта | `CL-09` |
| `NMCK` | закупочный расчёт цены контракта по 44-ФЗ (НМЦК, сумма цен единиц работ) | `CL-20`, `CL-21` |
| `CONTRACT` | проект контракта | `CL-23` |

Три кода из примеров Implementation Rules не использованы: `RESCALC` — потому что ресурсный
метод у `.gsfx` является свойством РАСЧЁТА, а не формы (форма — ЛСР, метод виден в
`Properties.txt`, квирк `RESOURCE_METHOD`), и разводить формы по методу значило бы поставить в
идентификатор величину, которая меняется от сметы к смете.

**Цена схемы названа явно.** Пересмотр таксономии двигает код, а код — путь в хранилище: пока
P2 не исполнена, переименование бесплатно, после — стоит переноса файлов и правки манифеста.
Это ровно тот баланс, который зафиксировал D13.

## 4. Как построен отбор

Порядок — от жёстких обязательств к добровольным добавкам; каждый шаг проверяется машинно
(`check_shortlist.py`), кроме последнего.

1. **Крайние случаи §2 разведки** — семь строк таблицы, обязательны к включению. Они покрывают
   ПУТИ КОДА, а не формы: оконный путь и границу `unprocessable` (132-МБ скан),
   детерминированный gold (`.gsfx`), старый бинарный формат (`.xls` КС-2), многосметность
   (`ЛСР.xlsx`, `СМЕТА.xlsx`), ложное срабатывание скрининга (НМЦК), негативы (контракт, фото,
   чертёж) и пограничные табличные документы (кабельный журнал, акты скрытых работ).
2. **Представитель каждого кластера P1.2** — 23 файла. Одиннадцать из них совпали с крайними
   случаями шага 1: разведка называла ровно те документы, которые таксономия потом выделила в
   отдельные кластеры-одиночки. Совпадение не случайно и снимает вопрос «а не разошлись ли
   слои» — сверка машинная (§8, команда 3).
3. **Внутрикластерные вариации** — одна добавка (§4.1).
4. Ничего сверх этого не добавлено: рост шорт-листа стоит времени владельца на ручную
   проверку каждого эталона, а F1 на дублях одного шаблона неинформативен (D4).

### 4.1 Единственная добавка сверх «по представителю на кластер»

`EST-XLSX-KS2-002` — второй файл кластера `CL-01`. Он взят не «для полноты», а потому что
представитель `CL-01` не показывает ни одну из трёх вариаций, которые внутри кластера реальны
(P1.2 §5) и которые ломают ровно тот код, который будет писать P5.2:

| Вариация | У представителя `EST-XLSX-KS2-001` | У `EST-XLSX-KS2-002` | Чем опасна |
|:--|:--|:--|:--|
| Смещение шапки | строки 25/27 | строки 25/28 | резолвер сетки, зашитый на номер строки, молча съедет на строку данных |
| Ресурсные строки позиции | есть (`ОТ(ЗТ)`/`ЭМ`/`ОТм(ЗТм)`) | свёрнуты (`NO_RESOURCE_ROWS`, 7 файлов корпуса) | «нет ресурсов» прочитается как дефект разбора, а не как свойство документа |
| Дробные номера материалов | есть (`9.1`, `9.2`) | нет | привязка `row_index` к дробному номеру не универсальна даже внутри одного кластера |

Три вариации нашлись в ОДНОМ файле — поэтому добавка одна, а не три. Номера строк шапки сняты
зондом §8 команда 5.

## 5. Что в шорт-лист НЕ попало и почему

**Непокрытых кластеров нет: 23 из 23.** Раздел оставлен намеренно — при пересмотре отбора сюда
попадает каждый кластер, оставшийся без эталона, с поимённой причиной. Сейчас он пуст по факту,
а не по умолчанию: `check_shortlist.py` ищет ID непокрытого кластера ИМЕННО В ЭТОМ разделе
(якорь — текст заголовка «НЕ попало», не его номер) и роняет прогон, если не находит. Упоминание
кластера где-нибудь ещё по документу — например, в словаре кодов формы §2.1 — за объяснение не
засчитывается.

**Непокрытый квирк ровно один — `BYTE_DUPLICATE` (23 из 24).** Это единственный квирк словаря,
который является свойством КОРПУСА, а не документа: три файла
(`ЛСР 02-01-06 (Система водоотведения).xlsx` и две его копии `(1)`/`(2)`) дают один sha256.
Включить их значило бы завести три кода эталона на один хеш — реестр `prc_ai_fixtures` и
манифест хранят sha256 как идентичность содержимого (D6/D20), и три записи с одним хешем
превратили бы `ai:fixtures:verify` в проверку, которая не может отличить «дубль по замыслу» от
«ошибки импорта». Дедупликация — задача импорта P2.3, а не состава эталонов; квирк остаётся в
словаре P1.2 и адресован именно P2.

**Рабочие итерации (`WORKING_ITERATION`, 54 файла) не отсеяны и не размножены.** Пять эталонов
шорт-листа несут этот маркер — они попали как представители своих кластеров, а маркер в имени
(`!`, `+`, `ВКЛ_`) на содержание документа не влияет (P1.2 §7). Брать дополнительно «чистую»
версию того же документа смысла нет: форма та же.

**`.gsfx`-вложения (`Attachments/`) отдельными эталонами не заводятся.** Контейнер эталонируется
целиком: распаковка и разбор вложений — предмет P3, а не состава корпуса.

## 6. Черновик метаданных реестра

`artifacts/fixture-shortlist.json` — прямой вход P2.3 (генератор манифеста → `ai:fixtures:import`
→ `prc_ai_fixtures`). Запись:

| Ключ | Тип | Откуда | Примечание |
|:--|:--|:--|:--|
| `code` | строка по регекспу D13 | решение этого item'а | становится каталогом хранилища `<CODE>/source.<ext>` (D17) |
| `source_path` | путь относительно `estimates/files` | инвентарь P1.1 | вход импорта; после P2 живёт только в манифесте как происхождение |
| `sha256`, `size_bytes` | из инвентаря P1.1 | не пересчитываются здесь | верификатор сверяет байт-в-байт с инвентарём |
| `class`, `format`, `form` | разбор кода | дубль полей кода | хранятся отдельно, чтобы реестр не парсил строку кода |
| `generator`, `cluster_id`, `quirks` | таксономия P1.2 | не переписываются | верификатор сверяет с привязкой файла |
| `expected_estimates` | целое ≥ 1 у `EST`, `0` у `NEG`, `null` — см. ниже | таксономия + структура книги | ожидание, против которого P5 проверит собранный gold |
| `expected_rows` | всегда `null` | — | реальное число строк считает P5; здесь его знать неоткуда (ТЗ) |
| `gold_source` | `deterministic` \| `llm_assisted` \| `none` | D2/D5 | путь получения эталона, не его состояние |
| `is_verified` | всегда `false` | — | флаг «проверено человеком» ставит ТОЛЬКО P8.3 (D43) |
| `selection_reason` | одна содержательная фраза | этот документ | почему именно этот файл, а не «представитель кластера» |

**`expected_estimates: null` — ровно одна запись, `EST-PDF-SCAN-001`.** Число смет внутри
132-МБ скана машинно не установлено и до OCR (P3.7) установлено быть не может: текстового слоя
нет, а гадать по имени файла запрещено Code Guidance. Разведка §2 фиксирует «множество смет
подряд» — то есть заведомо > 1, но конкретное N неизвестно. Поставить `1` значило бы завести
заведомо ложное ожидание, против которого P5 проверит gold; поэтому здесь `null` в том же
смысле, в каком P1.2 оставила `null` у признаков `CL-16`: «не установлено», а не «нет».
Верификатор такой `null` пропускает только у `EST` и только если код записи назван в этом файле
поимённо — молча `null` не проходит.

### 7.1 `CL-12` — класс `EST` (делегированное решение)

Это единственный файл корпуса, который по форме смета (бланк акта, обоснования расценок ФСНБ,
номера позиций по смете, единицы измерения, количества), а по содержанию — ведомость объёмов:
стоимостного блока нет вовсе (`NO_PRICE_COLUMNS`). Класс определяет, какой gold он получит:
`EST` — полный разбор строк без цен, `NEG` — однобитный вердикт «это НЕ смета».

Принят `EST` (`EST-XLSX-VOR-001`). Три довода, по возрастанию веса:

1. **Как негатив он ничего не добавляет.** Жанр «табличный документ без сметных цен» в
   негативах уже покрыт трижды и с разных сторон: `NEG-PDF-JOURNAL-001` (кабельный журнал),
   `NEG-XLSX-VOLUME-001` и `NEG-XLSX-VOLUME-002` (расчёты объёмов). Четвёртая точка того же
   жанра — потраченный слот эталона.
2. **Как эталон extraction он покрывает то, чего не покрывает никто.** Это единственный файл
   с распознаваемой сеткой, у которого цены отсутствуют структурно, — то есть единственный
   дешёвый (`deterministic`) способ прогнать через весь контракт §8.2 путь «позиции есть,
   `price` пуст». Схема к этому обязана быть готова и без него (D32: не всякая величина
   получает колонку), но проверить это будет нечем.
3. **Ошибка в эту сторону дешевле.** D5 фиксирует асимметрию «ложное срабатывание скрининга
   дороже пропуска», и она верна для чертежей, фотографий и контрактов — документов, которые
   сметной программой не порождались вовсе. Здесь асимметрия переворачивается: пометив этот
   файл негативом, мы учим скрининг признаку «нет колонки цены → не смета», а он ложен для
   реальных смет (ресурсный метод, обрыв стоимостного блока на границе листа). Цена такого
   обобщения — молча пропущенные сметы прода, то есть невидимая потеря; цена обратной ошибки —
   один лишний вызов извлечения, который видно в логе.

Граница решения названа явно: это классификация ОДНОГО файла в составе корпуса, а не правило
скрининга. Формулировку правила «что считать сметой» пишет P7.1 по текстам промтов, и она
обязана опираться на состав документа, а не на этот прецедент.

Генератор `artifacts/fixture-shortlist.json` приведён ниже целиком: артефактом плана он не
является (`Files` item'а — три файла), но без него состав JSON невоспроизводим. Решением
является ТОЛЬКО таблица `SELECTION`; всё остальное (`sha256`, `size_bytes`, `generator`,
`cluster_id`, `quirks`) читается из P1.1/P1.2 и потому проверяемо верификатором.

```python
# -*- coding: utf-8 -*-
"""Генератор artifacts/fixture-shortlist.json (P1.3). Запуск из корня репозитория."""
import json, collections

INV = "plans/2026.07.26-EST-TRAIN/findings/P1-corpus-inventory.json"
CLU = "plans/2026.07.26-EST-TRAIN/artifacts/corpus-clusters.json"
OUT = "plans/2026.07.26-EST-TRAIN/artifacts/fixture-shortlist.json"

# (код, путь либо None = представитель кластера, кластер, ожидаемое число смет, источник gold, почему)
# Тексты `selection_reason` и пути — колонки таблицы §3 этого документа.
SELECTION = [
    ("EST-XLSX-KS2-001", None, "CL-01", 1, "deterministic", "…"),
    ("EST-XLSX-KS2-002",
     "1 (3)/1.кровля/02-01-01 Кровля - Акт по Методике 2020 (PИМ) с титулом КС-2+.xlsx",
     "CL-01", 1, "deterministic", "…"),
    # … остальные 22 записи — по одной строке §3, порядок тот же
]

def main():
    inv = {f["path"]: f for f in json.load(open(INV, encoding="utf-8"))["files"]}
    clu = json.load(open(CLU, encoding="utf-8"))
    clusters = {c["id"]: c for c in clu["clusters"]}
    asg = clu["assignments"]
    out, seen = [], collections.Counter()
    for code, path, cid, n_est, gold, reason in SELECTION:
        path = path or clusters[cid]["representative"]
        f, a = inv[path], asg[path]
        assert a["cluster"] == cid, (path, a["cluster"], cid)
        seen[code] += 1
        out.append({
            "code": code, "source_path": path, "sha256": f["sha256"], "size_bytes": f["size"],
            "class": code.split("-")[0], "format": code.split("-")[1], "form": code.split("-")[2],
            "generator": clusters[cid]["generator"], "cluster_id": cid, "quirks": sorted(a["quirks"]),
            "expected_estimates": n_est, "expected_rows": None, "gold_source": gold,
            "is_verified": False, "selection_reason": reason,
        })
    assert all(v == 1 for v in seen.values()), seen
    with open(OUT, "w", encoding="utf-8") as fh:
        json.dump(out, fh, ensure_ascii=False, indent=2, sort_keys=True)
        fh.write("\n")
    print(f"written: {OUT} — {len(out)} записей")

main()
```
