## 1. Context

EST-AI (закрыт 2026-07-09, 🟠) построил пайплайн разбора смет: подготовка → скрининг →
извлечение, LLM-слой за фасадом `LlmProvider`, промты как файлы + сид, gold-датасет
(`prc_ai_dataset_examples`), eval-раннер с field-level F1, экспорт SFT. Его последняя запись в
§1 прямо называет следующий шаг: «другая модель будет парсить папку эталонных смет и наполнять
промты». Этот план — тот самый шаг, только шире: инфраструктура есть, а **эталонов, конвертеров
под реальные форматы, решения по токен-оптимальному входу, боевых текстов промтов и петли
«прогнал → увидел расхождение → улучшил промт» — нет**.

Вход: папка `estimates/files` — 157 файлов, 155 МБ, реальный хаос сметного документооборота
(`xlsx`/`xls`/`pdf`-текст/`pdf`-скан/`gsfx`/`docx`), включая 132-МБ PDF со сканами нескольких
смет подряд и контейнер ГрандСметы с машинно-читаемым XML. Разведка — `findings/corpus-recon-2026-07-26.md`.

Цель плана: превратить эту папку в **работающий обучающий контур** — курированный эталонный
корпус в хранилище с кодами и реестром в БД, детерминированный gold там, где формат это
позволяет, фабрика представлений документа (включая форматы, которых пайплайн сегодня не
понимает), измеренное решение по формату входа, боевые тексты промтов, отчёт расхождений
против эталона с предложениями по промту, и админка, где смету можно загрузить, прогнать,
сравнить с эталоном и пометить проверенной. Всё это одновременно — материал для будущей
локальной LLM (EST-AI D15/D16): датасет копится с первого дня.

Схема БД **сознательно считается подвижной**: боевой парсинг не запускался, данных нет,
`migrate:fresh` дёшев. Правки схемы централизованы в P4 (по фактам всего корпуса), точечные
правки в других фазах допускаются только с отдельным D#.

## 2. Execution Rules

- Один item за раз; статус обновляется В ПЛАНЕ (phase-файл + Status Board) до завершения работы.
- Статусы — 6 канонических строк байт-в-байт (`plan-protocol` §6).
- План разошёлся с кодом → не импровизировать, эскалировать (`plan-protocol` §10) + handoff.
- После закрытия item/фазы — перезаписать `plans/2026.07.26-EST-TRAIN/handoff.md` целиком.
- Тесты: Pest, `test('<интент по-русски>')`, БД `agelto_test`, запуск
  `docker compose exec app php artisan test --filter=<Subject>`; стиль
  `docker compose exec app ./vendor/bin/pint --dirty --test`. Один `--filter` за прогон.
- LLM-вызовы в тестах — только `tests/Support/Doubles/FakeLlmProvider`; реальный вызов в тесте —
  блокирующее замечание (`.claude/rules/agelto-reviewer-overrides.md`).
- Персистентность — только через `app/Repositories/Procurement/*StoreRepository`; сервисы
  `final readonly`, конструкторная инъекция, именованные аргументы, `declare(strict_types=1)`.
- Домен не вызывает Prism/SDK напрямую — только через `Contracts\LlmProvider` и его
  `SupportsFileUpload`/`SupportsContextCaching`.
- Промты правятся ТОЛЬКО в `resources/ai/prompts/**` + `ai:prompts:sync`; правка
  `is_protected`-промта в БД/сидере в обход файла — блокирующее.
- Файлы корпуса НЕ коммитятся в git (D1): в репозитории — только манифест и `*.gold.json`.
- `composer require` / `pint --dirty` автофикс / `vendor:publish` — с ХОСТА, не из контейнера.

## Обсуждение

### 1 — Чем распознавать сканы (OCR-движок)

- **(рекоменд.) Вариант A. Tesseract в worker-образе.** Плюсы: бесплатно, offline, есть
  русская модель, предсказуемый ресурс. Минусы: на сложных сметных таблицах ломает структуру
  колонок — годится как источник текстового слоя, не как парсер таблиц.
- **Вариант B. Только vision-путь провайдера.** Плюсы: ноль инфраструктуры, встроенный OCR
  Gemini не тарифицируется отдельно (258 ток./стр.). Минусы: локальная LLM в будущем такого
  качества vision не даст — обучающий контур останется без текстового представления сканов.
- **Вариант C. OCR-движок с распознаванием структуры таблиц.** Плюсы: лучший вход и для
  бенчмарка, и для локальной модели. Минусы: тяжёлая зависимость, требует отдельной оценки.

**Статус:** Resolved → D22 (выбран вариант A — Tesseract + `rus`/`eng` + OCRmyPDF в единый образ;
P3.7 не выбирает движок, а замеряет его потолок числом. Вариант C не отвергнут по существу: вход
в него — измеренная доля восстановленных строк, а не вкус)

### 2 — Как хранить двухуровневую цену смет (базовая/текущая), индексы и виды работ

- **(рекоменд.) Вариант A. Нормализовать в схеме.** Отдельные колонки базовой/текущей цены на
  позиции и ресурсе + справочник видов работ (носитель НР/СП). Плюсы: арифметическая
  валидация и витрина работают на SQL; эталон сравнивается по полям. Минусы: миграция +
  правка контрактов DTO и промтов.
- **Вариант B. Оставить `attributes jsonb`.** Плюсы: ноль миграций. Минусы: eval не умеет
  сравнивать поля внутри произвольного jsonb — обучающий контур слепнет ровно на тех
  величинах, ради которых смета и разбирается.

**Статус:** Resolved → D32 (2026-07-26, ответ владельца — выбран гибрид по критерию: колонками
то, что подтверждено корпусом И участвует в арифметике/сравнении с эталоном, остальное — ключи
`attributes` с ЗАФИКСИРОВАННОЙ контрактом схемой, чтобы eval сравнивал по путям, а не слеп на
произвольном json. Вариант B в исходной формулировке («оставить jsonb как есть») отвергнут, но
его дешевизна частично взята: не всё уезжает в колонки. Конкретный список величин выводит P4.2 из
фактов корпуса под гейтом владельца)

### 3 — Кто наполняет нормализованные поля: расширять ли контракт ответа LLM

- **(рекоменд.) Вариант A. Расширить ровно под схему.** Поле, попавшее в схему, попадает и в

- **Вариант B. Минимально — только двухуровневая цена.** Индексы, коэффициенты и трудозатраты
  заполняет только детерминированный парсер `.gsfx`. Плюсы: дешевле по токенам. Минусы: на сканах
  и xlsx поля пустые — eval меряет их лишь на структурных эталонах.
- **Вариант C. Не расширять.** Плюсы: ноль правок контракта. Минусы: нормализация оправдана только

### 4 — Носитель видов работ (`Vid_Rab`/`VidRab_Group`, нормативы НР/СП)

- **(рекоменд.) Вариант A. Отдельная таблица с иерархией.** `parent_id` + ссылка с раздела/
