# P7 — Боевые промты, diff-отчёт и петля тюнинга

## Phase Context

Фаза отвечает за КАЧЕСТВО разбора: тексты системных инструкций и механику их улучшения. Исходное
состояние — не пустота: восемь файлов `resources/ai/prompts/**` уже несут тексты, перенесённые
EST-AI из v1 (правила чистки чисел, JSON-only, нормативные базы, буфер `incomplete_items`, блок
защиты от indirect prompt injection), RAG:— (repo-grounded: `resources/ai/prompts/global/0-global.md`,
`extraction-global/0-extraction-global.md`, `extraction-rows/0-extraction-rows.md`). Задача фазы —
не написать с нуля, а ДОВЕСТИ их против реального корпуса и против расширенного контракта ответа
(P4.5, D33): каждое правило получает свидетеля-эталон, словари синонимов пополняются фактическими
формулировками корпуса (носитель — `#[Alias]`-атрибуты и §2 спеки, не `.md`, D58).

Вторая половина фазы — петля улучшения. Сначала ДЕТЕРМИНИРОВАННЫЙ diff-отчёт «gold vs
предсказание» (какие поля, какие строки, где не сходится арифметика) поверх расширенного
`EvalMetrics` — фаза единственный владелец extraction-метрики (D38/D44/D55). Затем дешёвый
LLM-критик читает diff + текущий композированный промт и кладёт предложение в очередь
`prc_ai_prompt_suggestions` — патч файла промта либо переиспользуемый hint (D59/D60). В файл
`resources/ai/prompts/**` предложение попадает ТОЛЬКО через апрув человека и команду применения
(D8); экранная форма того же апрува — P8.4. Замыкает петлю сравнение eval-прогонов между версиями
промтов по критерию и разбиению `tune`/`holdout`, зафиксированным ДО первого патча (D63).

Гейт OQ-3 накрывает фазу НЕ целиком: P7.1–P7.5 детерминированы и исполняются без доступа к
провайдеру (тексты, метрика, diff, очередь и критик — на `FakeLlmProvider`), боевое замыкание
петли вынесено отдельным item'ом P7.6 (D57), который ждёт доступа и денег владельца. При
неразрешённом OQ-3 промты пишутся под БАЗОВУЮ политику представлений (D53), и это записывается в
Pending Work — после ADR P6.3 формулировки перечитываются.

Фаза исполняется В КОНТЕЙНЕРАХ (как P2–P6): `php artisan`, Postgres `agelto_test`, диск эталонов.
Новых composer-зависимостей фаза не вводит; новая таблица ровно одна — очередь предложений (D59).

(11 кодов датасета против 6 в пуле extraction) работает без второго набора списков, а появление
записей датасета у `NEG`-эталонов кладёт их в `tune` автоматически — без запрещённого пересбора.
**Пересбор splits после первого патча запрещён:** файл фиксируется ДО первого
применения предложения; ДОБАВЛЕНИЕ в датасет кодов, которых нет в `holdout`, пересбора не требует
(они попадают в `tune` по дополнению), а перевод кода В `holdout` или ИЗ него — только новым D# с
указанием причины (иначе holdout перестаёт быть holdout'ом). **`prompt_version_set` прогона** собирается из `prc_ai_llm_calls`
вызовов прогона: объединение по всем вызовам; расхождение версий ВНУТРИ одного прогона делает
прогон непригодным для сравнения — `ai:eval:compare` отказывается сравнивать такой прогон с явным
сообщением (та же дисциплина, что D54 для бенчмарка). **`--split`** фильтрует
`prc_ai_dataset_examples` по коду эталона (`fixture_id` → `prc_ai_fixtures.code`); значение по
умолчанию — `all` (сегодняшнее поведение сохраняется байт-в-байт). **`ai:eval:compare {--base= :
id прогона} {--candidate= : id прогона} {--format=json|md} {--out=}`** считает по КАЖДОЙ подвыборке
дельты `overall.f1`, `row_coverage`, `per_field` и по каждому эталону — дельту `f1`, и выносит
вердикт `accept`/`reject` по критерию. **Критерий приёмки патча (задан ТЗ, до данных, D63):** патч
принимается, если ОДНОВРЕМЕННО (а) на `tune` `overall.f1` вырос не менее чем на **0.01**;
(б) на `holdout` `overall.f1` упал не более чем на **0.005**; (в) `row_coverage` ни на одной из
подвыборок не упал более чем на **0.005**; (г) ни один отдельный эталон не потерял более **0.05**
`f1`. Не выполнено хотя бы одно — вердикт `reject`, и предложение откатывается (файл возвращается к
прежней версии, `ai:prompts:sync`, статус предложения `reverted` с причиной). Пороги ПОСЛЕ первого
прогона не двигаются: несогласие с порогом — новый D#, а не правка по месту. **Сравнимость
прогонов:** сравниваются только прогоны с ОДИНАКОВЫМ составом эталонов подвыборки и одним маршрутом
моделей (`provider`/`model` записи `EvalRun`); расхождение — отказ сравнивать, а не сноска
в отчёте. **`research/14-prompt-tuning-protocol.md`** пишется В ЭТОМ item'е и содержит: правило
отбора splits (алгоритм пятью шагами выше) и фактический состав; критерий приёмки дословно; порядок
петли по шагам (базовый
прогон → diff → suggest → апрув → apply → sync → повторный прогон → compare → принятие или откат);
что делает исполнитель при `reject`; **раздел «Ограничения разбиения» — четыре пункта
`research/18-holdout-split-rule.md` §8 своими словами, без смягчения** (`holdout` крупнее `tune` по
