# P1 — Схема БД и ядро закупок

## Phase Context

Реализация полной схемы `docs/specs/v2/01-database.md` (SSOT, не переизобретать
структуру — только транслировать в миграции/модели). Каждый item = один
bounded-context префикс таблиц (см. `01-database.md` §0.1) + миграции + Eloquent-модели
+ (где явно указано) репозитории read/store. Партиционирование — `pg_partman`,
RANGE помесячно, на `prc_events`, `prc_revisions`, `ai_llm_calls`, `crw_fetches`,
`sys_operation_logs` (§0.4). Приёмка фазы — чек-лист сценариев `01-database.md` §11
покрыт тестами (item P1.11).

Общие правила схемы для ВСЕХ items этой фазы (см. `01-database.md` §0, не повторять
per-item, но соблюдать в каждом):
- PK — `bigint GENERATED ALWAYS AS IDENTITY`; на закупках/документах/сметах/организациях
  дополнительно `uuid` (UUIDv7, генерация в приложении — PG17 без нативной `uuidv7()`).
- Партиционированная таблица: PK обязан включать partition key → `(id, <time>)`;
  **никаких FK НА партиционированную таблицу извне** (Postgres не поддерживает FK на
  таблицу без единого uniqueness по id без partition key) — там, где схема ссылается на
  ревизию/событие (напр. `prc_procurements.current_revision_id`), это обычный
  `bigint nullable` БЕЗ FK-constraint, резолв через explicit query `(id, detected_at)`.
- Деньги — `numeric(18,2)` + `currency char(3)`.
- Статусы — закрытый enum ядра (`status`) + сырой `source_status`; маппинг — данные
  (`plt_status_mappings`), не хардкод в коде.
- Таблицы с префиксом, имя без повтора домена (`prc_lots`, не `prc_procurement_lots`).
- Все миграции — `Schema::create` с явными `->comment()` там, где колонка неочевидна
  (см. код-стиль `database`/`code-style-spatie`); именованные аргументы в коде
  (`named-arguments`), `final` классы моделей/репозиториев (`code-style-spatie`).
- Репозитории — read/store split по канону skill `repositories` (Read-репозиторий —
  запросы, Store — мутации; не смешивать в одном классе).
