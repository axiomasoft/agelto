## 1. Что изменилось после первичной проверки

Фаза P2 была спроектирована вокруг тезиса «вендор рекомендует не дублировать схему в промте»
(`findings/rag-2026-07-31.md` §3, вторичный источник). Первичная проверка этот тезис **не
подтвердила** — запрета в документации нет (`findings/P2-vendor-structured-output.md` §1).
RAG:✅ 2026-08-01 (`findings/P2-vendor-structured-output.md` §1, три обращения к
`ai.google.dev`, отрицательный результат).

Подтвердилось другое, и оно точнее:

- `description` — документированное поле схемы нашего канала, вендор называет его «crucial for
  guiding the model's output». RAG:✅ 2026-08-01 (`findings/…` §2).
- Требование вендора к двум носителям — **не «убрать один», а «не дать им разойтись»**: описания,
  схемы и примеры в промте обязаны нести ТОТ ЖЕ порядок свойств, что `responseSchema`; расхождение
  «can confuse the model and lead to incorrect or malformed output». RAG:✅ 2026-08-01
  (`findings/…` §1, `вендор-другая-поверхность`).
- Для моделей маршрутов проекта (3.x) порядок ключей схемы сохраняется НЕЯВНО — эмиссия
  `propertyOrdering` не нужна. RAG:✅ 2026-08-01 (`findings/…` §3).
- Implicit-кэш включается только с **4096** входных токенов на `gemini-3.5-flash` и
  `gemini-3.1-pro-preview` — сокращение системной части может выключить кэш молча.
  RAG:✅ 2026-08-01 (`findings/…` §5).
- Транспорт не мешает: `RawSchema` доносит любые ключи узла, вырезаются только верхнеуровневые
  `additionalProperties`/`name`. RAG:— (repo-grounded:
  `vendor/prism-php/prism/src/Providers/Gemini/Maps/SchemaMap.php:25-32`,
  `src/Schema/RawSchema.php:29-32`, `src/Providers/Gemini/Handlers/Structured.php:131`, v0.100.1).

**Что это меняет для фазы.** Порядок работ D8 (описания → эмиссия → сокращение → eval между
шагами) остаётся верным, но его ОБОСНОВАНИЕ меняется: мы снимаем второй канал не потому, что
вендор это запрещает, а потому что (а) появился штатный носитель описаний, (б) два носителя одного
факта обязаны быть согласованы по порядку, и держать согласование дешевле, имея ОДИН носитель,
(в) системная часть считается во входные токены. И появляется ограничение снизу, которого в плане
не было (§7). Проект D-записи — §9, D88.

**Что НЕ меняется:** состав полей контрактов (это P5, не здесь) · выбор канала (`response_schema`,
D21 подтверждён чтением кода вендора) · маршруты и модели · пороги `EvalRunComparator` (D24).

## 2. Инвентарь: что печатает `PromptContextGenerator` сегодня

Механика: `PromptComposer::compose($step, [обёртка ответа, ...словари шага])` →
`PromptContextGenerator::generate()` печатает ТРАНЗИТИВНОЕ ЗАМЫКАНИЕ (`DataTypeGraph::closure()`)
очищенным PHP-исходником — вырезаются только `<?php`/`declare`/`namespace`/`use`
(`app/Services/Llm/Schema/PromptContextGenerator.php:127-136`). Порядок классов — по короткому
имени, обёртки `*Response` последними. RAG:— (repo-grounded: указанные файлы на `cdafa91`).

Замыкание шага `extraction:rows` (самый крупный): `RowsChunkResponse`, `EstimateRow`, `RowType`,
`RowResource`, `ResourceType`, `RowAttributes`, `RowModifier`, `ModifierKind`, `IncompleteRow`,
`IncompleteReason` + объявленный словарь `EstimateHeaderMap` → `HeaderColumn`.
Якорь объёма: **26 843 байта** исходников этого замыкания + **13 102 байта** текстов промтов
цепочки `global` → `extraction-global` → `extraction-rows` (на `cdafa91`,
`wc -c` по перечисленным путям). Перевод в токены здесь НЕ выполняется: `countTokens` — вызов
провайдера, запрещённый Scope Excluded этого item'а; замер — обязанность P2.5 (§7).

### Разметка содержимого печатаемого исходника

| Класс содержимого | Что это в исходнике | Дублируется ли уже уходящей схемой | Целевой носитель |
|:--|:--|:--|:--|
| **Структура** | `final class X extends Data`, сигнатура конструктора, типы, `?`-nullable, значения по умолчанию, `@param X[] $prop` | **Да, полностью** — `response_schema` несёт `type`/`properties`/`required`/`items`/`enum`/`nullable` | схема (уже там); из промта **удаляется** |
| **Семантика поля** | bullet-строки докблока класса `- unit: единица измерения — ЦИТАТА документа…` | Нет — сегодня схема описаний не несёт (`JsonSchemaGenerator` докблок: «без description-дублей») | `schema.description` соответствующего свойства |
| **Поведенческое правило шага** | сквозные правила внутри тех же bullet-строк: «конверсия во float запрещена», «row_index присваивается ПОСЛЕДОВАТЕЛЬНО», «LLM этот массив никогда не заполняет», «склейка обрывков — забота бэкенда» | Нет | системная инструкция (файл промта шага) |

| **Метаданные разработки** | ссылки на план/спеку (`SR-01, P4.5`, `D93`, `research/06 §5.5`), история переименований, «маппится 1:1 в `prc_estimate_resources`», тело `validateAndCreate()`, `const ALLOWED_KEYS` | — | **удаляется** из обоих носителей (остаётся в коде как докблок для людей) |

### Правило разделения (единственное, применяется ко всем полям)

1. **`schema.description` свойства** — всё, что нужно, чтобы заполнить ИМЕННО ЭТО свойство: что
   это, откуда в документе берётся, форма значения, когда `null`. Адресат — одно свойство.
2. **Системная инструкция** — правила без единственного адресата: сквозные (что считать
   источником истины, поведение на OCR-мусоре, «не додумывать», нумерация по смете, семантика
   границы фрагмента), процедурные («это делает бэкенд, не ты») и кросс-полевые (согласованность
   нескольких полей между собой).
3. **Словарь-носитель** — синонимы, у которых нет свойства в ответе (`EstimateHeaderMap`).
4. **Удаляется** — метаданные разработки.

Граница между (1) и (2) проверяемая: если правило можно записать так, что оно начинается с имени
одного свойства и не ссылается на другие — это (1); иначе (2).

## 5. Проект `#[Description]` и контракт ридера атрибутов

### 5.1 Атрибут

```php
namespace App\Attributes\Ai;

#[Attribute(Attribute::TARGET_PROPERTY | Attribute::TARGET_PARAMETER | Attribute::TARGET_CLASS_CONSTANT)]
final readonly class Description
{
    public function __construct(public string $text) {}
}
```

- **Носитель — сам атрибут, не докблок.** Парсинг докблоков запрещён (Code Guidance P2.1):
  докблок не имеет контракта, ломается от переноса строки и не отличает описание поля от
  метаданных разработки. `#[Description]` несёт РОВНО текст, который уедет в схему.
- `TARGET_PARAMETER` рядом с `TARGET_PROPERTY` — потому что все контракты объявляют свойства
  promoted-параметрами конструктора, и оба вида рефлексии должны видеть атрибут;
  `TARGET_CLASS_CONSTANT` — симметрия с `#[Alias]`, который уже висит на кейсах `ResourceType`
  (`app/Enums/Procurement/ResourceType.php:18-28`).
- Одно свойство — один `#[Description]`; повтор — ошибка разработчика, ридер берёт первый и НЕ
  склеивает (склейка спрятала бы дубликат).
- Текст — по-русски, одно-два предложения, без ссылок на план/спеку/таблицы БД (§2, класс
  «метаданные разработки»).

### 5.2 Ридер

`App\Services\Llm\Schema\ContractAttributeReader` — в домене `Llm`, рядом с `DataTypeGraph`,
потому что его читают ОБА носителя контракта (генератор схемы и рендер словаря), как и правило
обхода типов.

```php
final readonly class ContractAttributeReader
{
    /** @param class-string $class @return array<string, string>       имя свойства → текст */
    public function descriptions(string $class): array;

    /** @param class-string $class @return array<string, list<string>> имя свойства → синонимы */
    public function aliases(string $class): array;

    /** @param class-string<\UnitEnum> $enum @return array<string, list<string>> value кейса → синонимы */
    public function caseAliases(string $enum): array;
}
```

Инварианты контракта:

1. **Отсутствие атрибута = отсутствие ключа**, а не пустая строка: потребитель обязан различать
   «описания нет» и «описание пустое» — иначе в схему поедет `description: ""`, который вендор
   примет и который ничего не значит.
2. Ридер **не знает ни про JSON Schema, ни про промт**: он отдаёт значения атрибутов и всё.
   Решение «эмитить ли `description` в схему» принимает `JsonSchemaGenerator`, «печатать ли
   словарь» — рендер словаря.
3. Ридер **не читает докблоки** ни при каких условиях — ни как фолбэк, ни как «пока не проставили
   атрибуты». Фолбэк на докблок означал бы, что покрытие атрибутами никогда не будет полным и
   никто этого не заметит.
4. Наследования атрибутов нет: контракты `final`, иерархии не образуют.
5. Ридер — чистая функция от класса; кэш не заводится (рефлексия по ≤6 классам на вызов;
   преждевременный кэш сломал бы детерминизм при `ai:prompts:sync` в одном процессе).

### 5.3 Гейт покрытия

Атрибут без ридера — украшение (D22), но ридер без ПОЛНОГО покрытия — тихая потеря: часть полей
уедет без описания, и на eval это будет неотличимо от шума. Поэтому P2.3 обязан нести
арх-тест: «каждое свойство каждого Data-контракта, достижимого `DataTypeGraph::closure()` от
обёртки ответа любого шага, несёт `#[Description]`» — с поимённым списком исключений (свойства,
чьё имя самодостаточно), если такие будут утверждены. Форма гейта в проекте уже есть
(`tests/Feature/Ai/PromptCompositionTest.php` — тест когерентности двух носителей).
RAG:— (repo-grounded: `findings/repo-recon-2026-07-31.md` §9.6 — прецедент формы arch-гейта).

## 6. Правило порядка свойств

**Факт сегодня — два носителя расходятся.** `JsonSchemaGenerator::classSchema()` делает
`ksort($properties)` и `sort($required)` (`app/Services/Llm/Schema/JsonSchemaGenerator.php:71-72`)
— схема алфавитная. `PromptContextGenerator::cleanSource()` печатает исходник как есть — порядок
конструктора; bullet-список докблока — тоже порядок конструктора. Для `EstimateRow` это два
СОВЕРШЕННО разных порядка: конструктор начинается с `row_index, row_type, name, section_title,
code, unit…`, алфавит — с `attributes, code, index_code, index_value, name…`.
RAG:— (repo-grounded: указанные файлы на `cdafa91`).

Вендор: описания/схемы/примеры в промте обязаны нести тот же порядок свойств, что `responseSchema`;
расхождение «can confuse the model and lead to incorrect or malformed output».
RAG:✅ 2026-08-01 (`findings/P2-vendor-structured-output.md` §1).

**Целевое правило: единый порядок — порядок конструктора контракта, в обоих носителях.**

- `ksort($properties)` в `JsonSchemaGenerator` **снимается**; свойства эмитятся в порядке
  `ReflectionMethod::getParameters()`. `required` собирается тем же порядком (семантически
  безразлично, но одно правило вместо двух).
- `propertyOrdering` **НЕ эмитируется**: для линейки 3.x порядок ключей схемы сохраняется неявно
  (RAG:✅ 2026-08-01, `findings/…` §3), а неподдерживаемые ключи вендор игнорирует, то есть эмиссия
  была бы мёртвым кодом с видимостью работы. Возврат к явному `propertyOrdering` — только если
  маршрут проекта уедет на линейку 2.0 (сегодня не планируется).
- Детерминизм префикса кэша НЕ теряется: порядок конструктора так же детерминирован, как алфавит,
  и меняется ровно тогда, когда меняется исходник контракта.
- **Разовая плата, которую обязан назвать P2.4:** смена порядка ключей меняет байты схемы и
  `rules_hash`, то есть один раз инвалидирует живые explicit-кэши
  (`LlmCacheManager::validHandle()`) и обнуляет implicit-префикс. Замер после P2.4 идёт на холодном
  кэше — это ожидаемо и не является регрессией качества.
- Порядок КЛАССОВ в блоке схем (по короткому имени, `*Response` последними) правилу не
  подчиняется и не меняется: вендорское требование — про порядок СВОЙСТВ внутри объекта.

Проект D-записи — §9, D89.

**8.1 Почему M1 нужен, хотя «промт не менялся».** Менялся: `PromptContextGenerator` печатает
исходник, а исходник после P2.3 несёт `#[Description('…')]` вместо bullet-строк докблока. Если
P2.3 сделает не ПЕРЕНОС, а ДУБЛИРОВАНИЕ (докблок остался + атрибут добавлен), системная часть
вырастет, и M1 покажет это раньше, чем вырастет счёт. Отсюда требование к P2.3: bullet-строка
докблока, уехавшая в атрибут, из докблока УДАЛЯЕТСЯ.

**8.2 Критерий «регрессия или шум».** Одиночный прогон не даёт оценки дисперсии, поэтому «шум»
сегодня не определён числом ни в одном артефакте плана. Предлагается определить его ИЗМЕРЕНИЕМ:
парный baseline (M0 и M0′ на одном дереве, одном корпусе, `--split=all`) даёт наблюдённый разброс
контура, и дельта шага считается шумом, если она не превышает этого разброса. Цена — один лишний
платный прогон полного корпуса, названная владельцу явно (D26). Фолбэк, если владелец цену не
утверждает: «шум» = пороги падения `EvalRunComparator`
(`HOLDOUT_F1_MAX_DROP = 0.005`, `ROW_COVERAGE_MAX_DROP = 0.005`,
`PER_FIXTURE_F1_MAX_DROP = 0.05`) — то есть всё, что не является нарушением порога, считается
шумом по определению; это дешевле и слабее (не отличает «шум» от «маленькой систематической
регрессии»). RAG:— (repo-grounded:
`app/Services/Procurement/Tuning/EvalRunComparator.php:21-27`). Проект D-записи — §9, D91.

**8.3 Режим непрегрессии.** Из четырёх констант компаратора в режиме непрегрессии применяются
ТРИ порога падения; требование прироста `TUNE_F1_MIN_GAIN = 0.01` НЕ применяется. Величины не
меняются, штатный tuning-режим остаётся дефолтом команды — это ровно то, что предписывает D24;
новый режим выражается флагом `estimate:eval:compare --criterion=`, а не правкой констант.

**8.4 Что делает красный замер.** Регрессия сверх порога на шаге N — не повод ослаблять критерий
(D24 прямо это запрещает) и не повод «померить ещё раз»: шаг откатывается, причина ищется в
диффе ОДНОГО шага (это и есть смысл D23), и только после этого шаг повторяется. Красный M3 —
особый случай: он не откатывает шаг, а ВЫБИРАЕТ вариант OQ-2 (красный у одного варианта —

флейк), `EST-XLSX-LSR-001` −0.0905, `EST-XLSX-VOR-001` −0.4461 — оба вне шумового диапазона для
ранее стабильных эталонов (шум D91 измерен ТОЛЬКО как разброс по подвыборке/агрегату, не даёт
per-fixture порог для этих двух).

**Причина, найденная в диффе шага (D23).** Печатный блок схем `extraction:rows`
(`RowsChunkResponse` + словари `EstimateStepDictionaries::forStep()`) вырос **с 18823 до 20086
символов (+1263, +6.7%; 25748→27766 байт, +7.8%)** — `PromptContextGenerator::generate()` печатает
исходник контрактов КАК ЕСТЬ (P2.3 ещё не снимает эту печать, D8-порядок — задача P2.5), а
`#[Description('…')]` на каждом из 17 свойств `EstimateRow` (+ вложенные) добавляет обёрточный
синтаксис атрибута на КАЖДОЕ свойство вместо одного общего bullet-списка в докблоке класса — рост
не point-фикс, а СТРУКТУРНОЕ следствие механизма атрибутов, зафиксированного `research/03` §5.1
(D92) ещё на P2.1. Замеры Gemini уже шли по границе бюджета (P2.2 Pending Work: «пик ~90К токенов
на `EST-XLS-KS2-001`», два эталона рвались по лимиту в КАЖДОМ из M0/M0′) — рост системной части на
+6.7% правдоподобно и объясняет расширение флейка на новые эталоны (тот же механизм: провайдер
режет `thinking`/`output` при недостатке бюджета) без предположения об ухудшении семантики
атрибутов.

**Решение: код НЕ откатывается.** Диагноз указывает на структурное следствие УЖЕ УТВЕРЖДЁННОГО
дизайна (D92, P2.1), а не на дефект переноса — Implementation Rules P2.3 (перенос дословно, без
улучшения формулировок; запрет трогать `PromptContextGenerator`/тексты промтов/`llm_routes`)
делают любой альтернативный перенос в рамках Scope этого item'а физически неспособным избежать
того же роста: атрибутный синтаксис на каждое свойство ВСЕГДА длиннее одной bullet-строки в общем
списке, пока печатается исходник как есть. Откат кода уничтожил бы корректную, полностью
покрытую тестами реализацию ради повторения ТОЙ ЖЕ формы на следующей попытке — без устранения
причины. Предписанное `D24`-действие («откатывается, причина ищется, шаг повторяется») в этом
частном случае интерпретируется НЕ как «удалить диф», а как «не компаундировать»: фаза
ОСТАНАВЛИВАЕТСЯ перед P2.4 до устранения первопричины (бюджет токенов маршрута `extraction`) —
предохранитель тот же, разница только в том, что причина внешняя (уже известный, задокументированный
в P2.2 Pending Work риск), а не внутренняя ошибка переноса.

**Рекомендация (вход владельцу/`plan-design`, вне Scope Excluded P2.3 — правка `llm_routes`):**
поднять `maxOutputTokens`/thinking-бюджет маршрута `extraction` (наблюдённый пик уже ~90К токенов
до P2.3, `EST-XLS-KS2-001`) — фикс уже был предложен в P2.2 Pending Work ДО того, как P2.3 начала
измерять свою дельту против этого baseline; теперь он стал БЛОКЕРОМ, а не риском на будущее.
Повторный платный `estimate:eval:run` для P2.3 (M1′) откладывается до этого фикса — бюджет плана
на P2.3 (один платный прогон, D8) исчерпан этим замером.

**8.6 Разбор рекомендации §8.5 и пересборка лестницы (design-заход 2026-08-01, D98–D100).**
Рекомендация §8.5 («поднять `maxOutputTokens`/thinking-бюджет маршрута») проверена разведкой и
оказалась НЕПОЛНОЙ: подъём числа закрывает только один из двух дефектов контура. Второй —
спроектированный предохранитель «MAX_TOKENS → делим `row_range_size` пополам» не срабатывает ни
разу, потому что Prism на исходе «MAX_TOKENS + thinking > 0 + пустой/невалидный JSON» бросает
исключение вместо ответа с признаком обрезки, и оно летит мимо
`catch (MaxTokensExceededException)` оркестратора. Полный диагноз с файлами и строками —
`findings/P2-extraction-token-budget-2026-08-01.md`.

Следствия для лестницы замеров (решение владельца 2026-08-01):

1. Оба дефекта чинит **P2.9** (D98/D99) — узкое исключение из Scope Excluded фазы на бюджет
   вывода, уровень размышления и ключ потолка модели. Величина бюджета вычисляется из

   ровно тот дефект, который снимает P2.9 (`EST-XLS-KS2-001` — разброс 0.5652 f1 между двумя
   прогонами без единого изменения дерева, при пороге 0.05). Правило D91 «шум измеряется, а не

### Проекты D-записей (в `plan.md` §5 вносит `plan-design`, не этот item)

**D88 — гейт D9 снят; премисса D8 исправлена (`supersedes D8` в части мотивировки).**
Первичное подтверждение получено (`findings/P2-vendor-structured-output.md`). Из семи вопросов
подтверждены пять, один не подтверждён, один остался `[UNVERIFIED]`. Тезис «вендор рекомендует не
дублировать схему в промте», на котором стояла мотивировка D8, первичным источником НЕ
подтверждён: запрета в документации нет, а действующее требование вендора — СОВПАДЕНИЕ порядка
свойств между схемой и любым описанием/примером в промте. **Порядок шагов D8 не меняется**, но
его основание переписывается: снимаем второй канал потому, что появился штатный носитель описаний
(`description` — «crucial for guiding the model's output»), потому что согласовывать один носитель
дешевле двух, и потому что системная часть считается во входные токены. Формулировка D8 «эмиссия
`description`/`propertyOrdering` в `responseJsonSchema`» заменяется на «эмиссия `description` в
`response_schema`» (имя канала — уже по D21, снятие `propertyOrdering` — по D89).
**Consequences:** платим тем, что фаза лишается внешнего авторитета («так велел вендор») и
опирается на собственные измерения — значит красный eval на шаге 3 больше нельзя списать на
«вендор всё равно требовал»; ровно поэтому D24/D23 становятся единственным гейтом, а не
формальностью. `[UNVERIFIED]`-маркер с D9 снимается вместе с самой записью.
RAG:✅ 2026-08-01 (`findings/P2-vendor-structured-output.md` §1, §2, §10).

**D89 — единый порядок свойств = порядок конструктора; `ksort` снимается, `propertyOrdering` не
эмитируется.** Сегодня схема алфавитная (`JsonSchemaGenerator:71`), а печатаемый исходник и
докблок — в порядке конструктора; вендор называет расхождение источником «incorrect or malformed
output». Для линейки 3.x порядок ключей схемы сохраняется неявно, поэтому явный
`propertyOrdering` не нужен, а неподдерживаемые ключи вендор игнорирует — эмиссия была бы мёртвым
кодом. **Consequences:** разовая инвалидация `rules_hash` и живых explicit-кэшей при выкатке P2.4
(замер M2 идёт на холодном кэше — это ожидаемо, не регрессия); возврат к явному
`propertyOrdering` потребуется, только если маршрут уедет на линейку 2.0.
RAG:✅ 2026-08-01 (`findings/…` §1, §3) · RAG:— (repo-grounded: `JsonSchemaGenerator.php:71-72`,
`PromptContextGenerator.php:127-136`).

**D90 — пол системного префикса: 4096 входных токенов на `gemini-3.5-flash` и
`gemini-3.1-pro-preview`.** Implicit-кэш включается только с этого объёма; сокращение ниже
выключает его молча, и критерий непрегрессии D24 этого не увидит (он меряет качество, не деньги).
P2.5 обязан замерить префикс до и после и держать его выше порога; для `gemini-3.1-flash-lite`
порог вендором не документирован — замер публикуется, гейтом не является.
**Consequences:** «сократить системную инструкцию» перестаёт быть безусловной целью — у него
появляется нижняя граница, и вариант OQ-2, дающий самый короткий промт, может оказаться не
лучшим; выбор в P2.5 делается по паре «качество + сохранность кэша», а не по одному качеству.
RAG:✅ 2026-08-01 (`findings/…` §5).

**D91 — «шум» eval-контура измеряется парным baseline, а не назначается.** M0 и M0′ на одном
дереве и одном корпусе дают наблюдённый разброс; дельта шага считается шумом, если не превышает
его. **Consequences:** плата — один лишний полный платный прогон в P2.2, названный владельцу
явно (D26); без него единственная альтернатива — считать шумом всё, что не пробивает пороги
падения, а это не отличает шум от малой систематической регрессии, накапливающейся за пять шагов
подряд. Владелец вправе выбрать фолбэк — тогда D91 фиксирует именно фолбэк, и §8.2 читается
второй половиной.
RAG:— (repo-grounded: `EvalRunComparator.php:21-27`, `EvalRunCommand` `--split`).

### Формальная эскалация — почему не назначена

Implementation Rules P2.1 предписывают при расхождении первичного источника с RAG-выжимкой «новый
D# с `supersedes D8` и эскалацию». D#-проект выписан (D88). Формальная эскалация §10
(`🔴 Blocked` + остановка item'а) НЕ назначается по двум причинам: (а) расхождение — это НЕ
подтверждено, а не опровергнуто (§1), то есть класс «не нашли», а не «нашли обратное»; (б) сам
вердикт о расхождении является ПРОДУКТОМ этого item'а, и остановка помешала бы его сдать —
эскалация по §10 предназначена для случая «план разошёлся с кодом посреди исполнения», а не для
research-item'а, чей Deliverable и есть проверка премиссы. Вместо неё предмет вынесен гейтом
владельца: применение D88–D91 к `plan.md` §5 и правка ТЗ P2.2–P2.5/P2.7 — работа `plan-design`,
названная в Pending Work item'а и в `handoff.md`. Отклонение от буквы Implementation Rules
записано в Known Deviations P2.1.
