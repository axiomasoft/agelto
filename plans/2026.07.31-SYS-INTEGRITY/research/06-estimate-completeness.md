**Форма писателя B-1/B-2 (вход P5.5).** Детерминированная функция `unit` → (`unit_base`,
`unit_multiplier`): напечатанный числовой множитель в начале строки отделяется, остаток — база
(`100 м2` → `м2` / `100`; `1000 м3` → `м3` / `1000`); множителя нет — `unit_base = unit`,
`unit_multiplier = 1`. Разобрать не удалось (пустой `unit`, мусор, единица из двух чисел) —
`unit_base = unit`, `unit_multiplier = 1`, исключений не бросается: смета может нести что угодно, и
нормализатор обязан быть тотальным, а не «правильным на чистом входе». `unit` остаётся ЦИТАТОЙ
документа (SR-15 донора) — правило «ровно один носитель» не нарушается: цитата и разбор цитаты —
разные факты, у каждого свой носитель.

**Форма писателя B-5 (вход P5.5).** (1) `PassportResponse::$work_types` пишется деревом в
`prc_estimate_work_types` (`parent_id`, `position`, нормативы НР/СП — заполняются только gsfx-веткой,
исключение из D33 §6 п.3 донора, на боевом LLM-пути остаются `null`). (2) `EstimateRow::$work_type_name`
резолвится в `work_type_id` через `findOrCreate` по паре `(estimate_id, title)`: боевой LLM-ответ
несёт `work_types = []` по построению (докблок `PassportResponse::$work_types`), и резолв «только
при непустом дереве» оставил бы колонку пустой на ВСЁМ боевом потоке — то есть воспроизвёл бы ту
самую дыру, ради которой item заводится. Запись, созданная резолвом, несёт только `title`; нормативы
`null` — это честное «вид работ назван, нормативы документом не напечатаны», а не потеря.

## 5. Строки не-`Item` класса: КС-3, печатные агрегаты позиции, итог раздела — решение владельца

`EstimatePersister::persistRows()` материализует ТОЛЬКО `row_type = item`
(`EstimatePersister.php:154-157` — `continue` для любого другого типа; `prc_estimate_items` колонки
`row_type` не имеет). Из этого следуют три факта, которые P5.1 нашёл по отдельности, а они —
один структурный вопрос:

- три ключа КС-3 `attributes.amount_since_start` / `.amount_since_year_start` /
  `.amount_reporting_period` (SR-14 донора, утверждены и живут в контракте) физически некуда
  записать: они заполняются только строкой `row_type = summary_row`, которая до таблицы не доходит
  (класс A-structural, P5.1 §1);
- печатные агрегаты позиции («Итого прямые затраты», «ФОТ», «НР», «СП», «Всего по позиции» —
  строки 47–51 §3) — тот же класс `subtotal`, тоже не хранятся;
- «итог раздела» — та же строка `subtotal` (P5.1 §3, помечен «НЕ кандидат — без названного
  потребителя»).

**Решение владельца (§12): не материализовать.** Величины живут в `prc_ai_analyses.result` и в
`estimates/gold/*.gold.json` — там же и измеряются eval'ом; арифметическая проверка «ПЗ = ОТ+ЭМ+МАТ»
выполняется `EstimateValidator` по КОНТРАКТУ до персиста, реляционного носителя не требует; ни один
сценарий витрины (фильтр/агрегат по разрезам КС-3 или по итогу раздела) в перечне P5.1 §4 владельцем
не назван. Схема не меняется. Альтернатива, которая была вынесена и отклонена: колонка
`prc_estimate_items.row_type` (`text` + PHP enum `RowType`) плюс снятие `continue` — цена в том, что
КАЖДЫЙ существующий читатель `prc_estimate_items` обязан был бы фильтровать `row_type = 'item'`,
иначе итоговые строки тихо посчитались бы позициями.

Признак дрейфа этого решения — строка C-11 карты следствий.

## 6. Разрешение коллизии носителей: `passport.reference` против `regulatory_base`

Существующий ключ `EstimatePassport::$reference` описан как «обоснование/ссылка на нормативный
документ, если есть в тексте» — формулировка, под которую новая величина `regulatory_base` подходит
буквально. Оставить обе как есть значит получить два носителя одного факта уже на уровне промта:
модель заполнит оба.

**Решение.** `reference` сужается до «основание составления сметы» — то, что форма 421/пр печатает
строкой «Основание» с подписью «(проектная и (или) иная техническая документация)»
(`ЛСР.xlsx` строки 23–24, §3): проектная/техническая документация, задание, договор. Редакция
сметных нормативов уходит в `regulatory_base` и только туда. Правка — докблок `#[Description]`
поля `reference` (носитель семантики на дереве — атрибут, P2.3 закрыта, D43) плюс строка §3.1
спеки; схема и имя поля не меняются. Владелец правки — P5.5 (строка C-2 карты следствий).

## 8. Индексы → сценарий владельца

Правило item'а (Implementation Rules п.3): индекс заводится только под НАЗВАННЫЙ владельцем
сценарий с конкретной формулировкой `WHERE`/`ORDER BY`/`GROUP BY`; индекс «на всякий случай»
оплачивается каждой вставкой боевого разбора.

**Решение: новых индексов — 0.** Перечень P5.1 §4 разобран построчно.

| Кандидат | Сценарий из перечня P5.1 §4 | Вердикт | Почему |
|:--|:--|:--|:--|
| `prc_estimate_items (estimate_id, total_price_base)` · `(estimate_id, unit_price_base)` | сортировка позиций по базисной цене (сравнение уровней) | **не заводится** | Сценарий внутрисметный: отбор уже идёт по `estimate_id`, который проиндексирован при создании таблицы (`2026_07_04_100035` — `foreignId('estimate_id')->index()`); объём после отбора — сотни строк (214 строк на 6 смет реального gold), сортировка идёт по уже прочитанной странице |
| `prc_estimate_items (estimate_id, source_position_number)` | натуральная сортировка по номеру позиции | **не заводится** | То же основание; вдобавок номер дробный (`9.1`) и хранится `text` — «натуральная» сортировка требует не индекса, а правила сравнения |
| `prc_estimate_items (index_code)` | фильтр по применённому индексу пересчёта (SR-03) | **не заводится** | Межсметный сценарий сформулирован как категория («фильтр по `index_code`»), но не как запрос: неизвестно, отбираются сметы или позиции и по равенству или по префиксу. ## 11. Точный вход P5.5 и P5.6 (Deliverables item'а)

**P5.5 — миграции, enum'ы, поля контракта, писатели.**

- Миграции: **одна** — `add_regulatory_base_to_prc_estimates_table` (`text nullable` + `comment`).
  Применённые `create_*` (`2026_07_04_1000{33..37}`, `2026_07_27_100057`) не правятся.
- Enum'ы: **ноль** (§1). Адрес по D44 не применяется.
- Поля контракта ответа LLM: **три** — `PassportResponse::$regulatory_base`,
  `EstimatePassport::$regulatory_amendments`, `EstimatePassport::$index_letter`. Плюс сужение
  докблока `EstimatePassport::$reference` (§6).
- `RowAttributes::ALLOWED_KEYS` — **не меняется** (новых ключей `attributes` нет), снапшот
  `tests/Fixtures/Llm/step-json-schemas.json` пересобирается из-за трёх новых свойств паспорта.
- Писатели: нормализатор `unit` → `unit_base`/`unit_multiplier` на позиции и ресурсе (B-1, B-2);
  запись `prc_estimate_work_types` + резолв `work_type_id` (B-5).
- Модели/фабрики: `Estimate` (`regulatory_base`), `Item`/`Resource` (`unit_base`/`unit_multiplier`
  уже в `$fillable` и `casts` — проверить, что фабрика создаёт непустые значения),

from xml.etree import ElementTree as ET

def dump(path, lo, hi):
    z = zipfile.ZipFile(path)
    shared = []
    if 'xl/sharedStrings.xml' in z.namelist():
        root = ET.fromstring(z.read('xl/sharedStrings.xml'))

            shared.append(''.join(t.text or '' for t in si.iter(f"{{{NS['m']}}}t")))

        if rn > hi: break

        if out: print(rn, ' | '.join(out)[:500])
