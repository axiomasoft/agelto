## 1. Таксономия: три вида использования, четыре точки исхода, четыре кейса `ProxyScope`

**Решение.** В фазе P1 действует ОДИН набор терминов; слово «канал» как счётное существительное
выводится из употребления — оно означало то вид использования (три), то точку исхода (четыре), и
именно это дало расхождение «три канала» / «четвёртый канал» внутри одного абзаца Scope Included
(находка **N3** захода 2 аудита — `phases/P7.md` → `## Audit design — 2026-07-31 (заход 2)`).

| Термин | Слой | Счёт | Кто определяет |
|:--|:--|:--|:--|
| **вид использования прокси** | 0 (бриф) | **3** | владелец, `brief/00-brief.md:28-34` |
| **точка исхода** (call-site) | код | **4** | дерево, `grep -rn "pick(target" app/` + LLM-провайдер |
| **`ProxyScope`** (кейс enum'а) | схема | **4** | этот документ, §4 |

Сопоставление — полное и без остатка:

| # вида (бриф) | Вид использования | Точка исхода (файл:строка на `09e07a5`) | `ProxyScope` |
|:--|:--|:--|:--|
| 1 | Нейросеть | `app/Services/Llm/Providers/PrismGeminiProvider.php:390-395` (`proxy()` → `config('ai.gemini.proxy')`; `pick()` не вызывает) | `llm` |
| 2 | Кроулинг | `app/Services/Procurement/Eis/CsvSourceMethod.php:71` (`pick(target: $endpoint)` — CSV-листинг) | `crawl_listing` |
| 2 | Кроулинг (MCP Playwright) | точки исхода НЕТ — браузерного рантайма в проекте нет | кейса нет (OQ-4, §9.3) |
| 3 | Детальный анализ | `app/Services/Procurement/Eis/CsvSourceMethod.php:160` (`pick(target: $url)` — вкладка карточки) | `crawl_detail` |
| 3 | Детальный анализ | `app/Services/Procurement/DocumentDownloader.php:84` (`pick(target: $url)` — файл документа) | `document_download` |

**Почему так, а не «три скоупа по видам».** Правило Implementation Rules P1.1 («состав `ProxyScope`
выводится из фактических call-site'ов, кейс без названного call-site'а запрещён») и правило P1.6
(«каждый call-site получает СВОЙ скоуп») вместе дают ровно биекцию «точка исхода ↔ кейс». Вид
использования 3 («детальный анализ») распадается на две точки исхода, потому что вкладка карточки и
файл документа — разный трафик: HTML-страница в десятки килобайт против многомегабайтного файла,
разное время удержания соединения и разный риск бана. Держать их одним скоупом значит запретить
оператору выделить под скачивание отдельные узлы.

**Что ломается без этого решения.** Исполнитель P1.2 замораживает состав enum'а МИГРАЦИЕЙ (D4, D18:
правка потребует новой миграции на схеме, которую P3 уже перенесёт). Читая «три канала» в Phase
Context и «четыре канала» в Scope Included, он получает разброс в один кейс — то есть либо лишний
мёртвый кейс, либо склейку скачивания с карточкой, которую потом не разъединить без миграции данных.

RAG:— (repo-grounded: `grep -rn "pick(target" app/` → 3 совпадения, перечислены выше;
`brief/00-brief.md:28-34` — «три разных вида использования прокси», нейросеть первая).

## 3. Целевая модель данных

### 3.1 `prc_proxies` — что добавляется и почему

Существующие колонки на `09e07a5` (`database/migrations/2026_07_04_100040_create_prc_proxies_table.php`):
`service, host, port, username, password, targets(jsonb), is_active, fails_count`.

| Колонка | Тип | Обоснование | Что ломается без неё |
|:--|:--|:--|:--|
| `country` | `char(2)` NULL | ISO 3166-1 alpha-2, верхний регистр. Единственный носитель гео; enum стран не заводится — 250 мёртвых кейсов (правило P1.2) | Требование брифа «не запустить Gemini через российский прокси» нечем выразить (дыра 1) |
| `scopes` | `jsonb` NOT NULL DEFAULT `'[]'` | Список значений `ProxyScope`; типизация — enum-каст модели (`AsEnumCollection::of(ProxyScope::class)`) + мультиселект Filament по enum'у. Заменяет `targets` | Свободная строка возвращает дыру 2: опечатка = пустая выборка |
| `open_until` | `timestamptz` NULL | Момент, до которого узел глобально выведен из выдачи (breaker). NULL/прошлое = узел доступен | Бан на одной площадке снова выключал бы узел глобально и НАВСЕГДА (дыра 7) |
| `open_count` | `smallint` NOT NULL DEFAULT 0 | Сколько раз подряд breaker открывался без успешной пробы — показатель степени экспоненциального cooldown | Cooldown фиксированной длины: битый узел возвращается в выдачу каждые 30 минут вечно |
| `last_failure_reason` | `text` NULL | Значение `ProxyFailureReason` последнего глобального отказа — операторская диагностика в таблице Filament | Оператор видит «узел выключен» без причины и лечит наугад |
| `last_success_at` / `last_failure_at` | `timestamptz` NULL | Отметки исхода; вход операторской диагностики и будущей калибровки порогов на боевом прогоне (P4.7) | Нечем отличить «узел не использовался» от «узел стабильно падает» |
| `targets` | — | **УДАЛЯЕТСЯ** той же миграцией | Второй носитель факта «для чего узел» рядом со `scopes` (D19: две точки истины = рассинхрон) |

**`fails_count` не переименовывается и не удаляется** — его смысл не меняется: серия подряд идущих
глобальных отказов, обнуляемая успехом. Меняется ТОЛЬКО побочный эффект: сегодня
`ProxyPool::reportFailure()` на пороге ставит `is_active=false` (`ProxyPool.php:29-31`), то есть
автоматика правит операторский тумблер. В целевой модели `is_active` — **исключительно ручной
выключатель оператора**, автоматика работает через `open_until` (временно и самозаживляюще).

*Что ломается без этого разделения:* автоматически выключенный узел не возвращается в пул никогда —
его надо включать руками, и оператор не может отличить «я его выключил» от «его выключила система».

**Пустой `scopes` = узел не выдаётся никогда.** Это инверсия текущей семантики (`targets = null`
означает «годится для любой цели», `ProxyPool.php:19`) и она намеренная: fail-open по умолчанию —
ровно тот механизм, из-за которого сегодня запрос уходит мимо прокси. Fail-closed стоит одной
операторской настройки при заведении узла и снимает целый класс тихих отказов.

**Индексы:** GIN по `scopes` (под `@>`, который генерирует `whereJsonContains`) и составной
`(is_active, country)` — оба под единственный горячий запрос §11.

RAG:✅ 2026-07-31 (минимальная сущность узла: provider/server/creds/geo/status + scope отдельным
полем, здоровье не одной колонкой — `findings/rag-2026-07-31.md` §2).
RAG:— (repo-grounded: `app/Models/Procurement/Crawler/Proxy.php`, `ProxyPool.php:15-37`).

**Чего в модели НЕТ и почему** (правило «поля на будущее без названного потребителя запрещены»):
`kind (dc/resi/mobile)`, `asn`, `region`, `city`, `cost`, `supports_sticky`, `sticky_key`,
`max_concurrency`, `block_rate`, `captcha_rate`, `tls_fail_rate`, `ban_score`, `geo_verified_at` —
всё перечисленное источник (`rag` §2) выводит из задачи «антибот-обход коммерческих площадок с
капчей и фингерпринтингом». Agelto решает более узкую: две площадки, CSV и SSR-HTML, капчи нет
(её нечем детектировать — в дереве нет ни одного места, где ответ проверялся бы на challenge),
конкурентность ограничена сверху `PoliteThrottle` и числом воркеров. Каждая такая колонка была бы
мёртвой: её никто не пишет и никто не читает.

### 3.2 `prc_proxy_targets` — носитель per-target здоровья (новая таблица)

Одна строка на пару (узел, цель). **Цель = хост** в канонической форме (§9.1), не URL.

| Колонка | Тип | Смысл |
|:--|:--|:--|
| `proxy_id` | FK → `prc_proxies`, `ON DELETE CASCADE` | Узел |
| `target` | `text` | Канонический хост (`zakupki.gov.ru`, `generativelanguage.googleapis.com`) |
| `success_ratio` | `double precision` NOT NULL DEFAULT 1.0 | EWMA успешности (α из конфига); стартовое значение 1.0 — новый узел получает шанс |
| `latency_ms_avg` | `integer` NULL | EWMA длительности успешного запроса; NULL = замеров не было |
| `consecutive_failures` | `integer` NOT NULL DEFAULT 0 | Серия отказов НА ЭТОЙ цели |
| `open_until` | `timestamptz` NULL | Breaker уровня (узел, цель) |
| `open_count` | `smallint` NOT NULL DEFAULT 0 | Степень экспоненциального cooldown |
| `last_failure_reason` | `text` NULL | Значение `ProxyFailureReason` |
| `last_outcome_at` | `timestamptz` NULL | Отметка последнего учтённого исхода |

Ключи: `UNIQUE (proxy_id, target)` — он же индекс под join горячего запроса; отдельного индекса по
`target` не заводится (селективность даёт первая колонка составного, а запрос всегда идёт с
конкретным `proxy_id`-множеством из того же join'а).

**Почему EWMA, а не окно/агрегат.** Скользящие индикаторы источника (`success_rate_5m/1h`) требуют
либо оконного агрегата по журналу запросов, либо отдельного счётчика по бакетам времени. Первое —
запрещённый агрегат по `prc_fetches` в горячем пути (Implementation Rules P1.1); второе — таблица,
которую нужно чистить. EWMA даёт то же свойство «свежее весит больше» ценой ОДНОГО `UPDATE` на
исход и нуля фоновых задач.

*Что ломается без этой таблицы:* остаётся дыра 7 — узел, забаненный ЕИС, выключается и для Gemini.

RAG:✅ 2026-07-31 («главная названная ошибка — считать прокси мёртвым глобально после блока на одном
сайте; здоровье минимум двухуровневое» — `findings/rag-2026-07-31.md` §2).

### 3.3 `prc_crawlers` — форма связи профиля с прокси

Добавляются ДВЕ колонки:

| Колонка | Тип | Смысл |
|:--|:--|:--|
| `use_proxy` | `boolean` NOT NULL DEFAULT `true` | Прямое требование брифа: «для каждого профиля выбирать, использует он прокси или нет». `false` = прямой запрос — намеренный режим, а не отказ |
| `proxy_country` | `char(2)` NULL | Требуемая страна узла для запросов ЭТОГО профиля. NULL = профиль страну не ограничивает |

Дефолт `use_proxy = true` выбран потому, что D3 объявляет прокси обязательным для боевых прогонов
против ЕИС: профиль, заведённый без явной настройки, обязан попадать в предписанный режим, а не в
исключение.

**Двухслойная гео-политика, без двух владельцев одного факта:**

- **конфиг скоупа задаёт ЗАПРЕТ** (`forbidden_countries`) — это гарантия безопасности, профиль её
  ослабить не может;
- **профиль задаёт ТРЕБОВАНИЕ** (`proxy_country`) — операционное сужение внутри разрешённого.

Пересечение считается фильтром ДО скоринга (§6). Конфликт («профиль требует RU, скоуп запрещает
RU») даёт пустое множество кандидатов и обрабатывается как пустой пул (§10) — не молча.

**Колонки `proxy_scope` на профиле НЕ будет** — обоснование и проект D-записи в §14.1.

## 5. Таксономия причин отказа и уровень реакции

`App\Enums\Procurement\ProxyFailureReason` — backed string. Реакция breaker'а зависит от причины (D7).

| Кейс | Значение | Как детектируется | Уровень | Почему такой уровень |
|:--|:--|:--|:--|:--|
| `NetworkTimeout` | `network_timeout` | `ConnectionException` / cURL timeout | **глобальный** | Узел не отвечает — свойство узла, а не площадки |
| `TlsError` | `tls_error` | `RequestException` с cURL SSL-кодом | **глобальный** | Свойство узла |
| `ConnectFailed` | `connect_failed` | отказ соединения с прокси | **глобальный** | Свойство узла |
| `ProxyAuthFailed` | `proxy_auth_failed` | HTTP 407 | **глобальный** | Креды узла протухли — на всех целях сразу |
| `Http403` | `http_403` | статус 403 от ЦЕЛИ | **целевой** | Площадка забанила ЭТОТ адрес; на других целях узел жив |
| `Http429` | `http_429` | статус 429 от ЦЕЛИ | **целевой**, короткий cooldown | Троттлинг, не бан: узел здоров, ему нужна пауза |
| `EmptyBody` | `empty_body` | 200 при пустом теле | **целевой** | Уже наблюдаемый в дереве сигнал ЕИС (`CsvSourceMethod.php:85-88` — повторный запрос на пустое тело) |
| `Unknown` | `unknown` | всё прочее | **целевой** | Fail-safe: неизвестное не выключает узел глобально |

**HTTP 5xx причиной отказа ПРОКСИ не считается** и в `reportOutcome` уходит как успех транспорта:
пятисотка — состояние площадки, штрафовать за неё узел значит выжигать пул при аварии ЕИС.

**Чего в таксономии нет:** `CAPTCHA`, `BOT_CHALLENGE`, `GEO_MISMATCH` из источника. Причина одна и
та же — в дереве нет детектора: ни одной проверки тела на challenge-страницу, ни одного сервиса
верификации гео. Кейс, который никто не может выставить, — мёртвая ветка в `match` и ложная
уверенность у читателя.

RAG:✅ 2026-07-31 (раздельные причины деградации и зависящая от причины реакция breaker'а —
`findings/rag-2026-07-31.md` §2). RAG:— (repo-grounded: `CsvSourceMethod.php:85-88`).

## 6. Политика выбора: фильтр → score → weighted random внутри top-K

Порядок жёсткий (D5, D6): **гео и breaker — фильтры, НЕ веса.**

```
resolve(scope, target, requirements):
  # 1. ФИЛЬТР (SQL, один запрос, §11)
  candidates = proxies where
        is_active = true
    AND scopes @> [scope]
    AND (open_until IS NULL OR open_until <= now())              # глобальный breaker
    AND country NOT IN policy(scope).forbidden_countries          # ЖЁСТКИЙ гейт (D5)
    AND (policy(scope).forbidden_countries = [] OR country IS NOT NULL)   # неизвестная страна = запрещённая
    AND (requirements.country IS NULL OR country = requirements.country)  # требование профиля
    AND (target_row IS NULL OR target_row.open_until IS NULL
         OR target_row.open_until <= now())                       # per-target breaker
  if candidates = ∅: → §10

  # 2. SCORE (в PHP, над уже отфильтрованным множеством)
  score(p) = w_success * p.target.success_ratio                       # 0..1, старт 1.0
           - w_latency * min(p.target.latency_ms_avg / latency_ref_ms, 1)
           - w_streak  * min(p.fails_count / streak_ref, 1)
           # у узла без строки в prc_proxy_targets: success_ratio = 1.0, latency-штраф = 0
           #   (новый узел получает шанс, иначе пул не разогревается)

  # 3. TOP-K + TIE-BREAK (D6: least-failures ТОЛЬКО как tie-breaker)
  ordered = candidates sorted by (score DESC, fails_count ASC, id ASC)
  pool    = first K of ordered

  # 4. WEIGHTED RANDOM внутри top-K
  weight(p) = max(score(p), epsilon)          # epsilon > 0: даже худший из top-K достижим
  chosen    = randomness.weightedPick(pool, weight)   # источник случайности ИНЪЕКТИРУЕТСЯ
```

Параметры — в `config/crawler.php` с комментарием «почему такое значение», стартовые помечаются
некалиброванными (калибровка — боевой прогон P4.7):

| Параметр | Старт | Смысл |
|:--|:--|:--|
| `w_success` / `w_latency` / `w_streak` | `1.0` / `0.3` / `0.5` | Веса слагаемых score |
| `latency_ref_ms` | `5000` | Задержка, при которой штраф максимален |
| `streak_ref` | `5` | Серия глобальных отказов, при которой штраф максимален |
| `top_k` | `3` | Ширина случайного выбора |
| `ewma_alpha` | `0.3` | Вес свежего исхода в EWMA |
| `epsilon` | `0.01` | Нижняя граница веса |

**Что ломается без этого решения.** Сегодняшний `orderBy('fails_count')->orderBy('id')->first()`
(`ProxyPool.php:20-22`) — strict-best: весь трафик идёт через один узел, пока тот не деградирует,
после чего весь трафик идёт через следующий. Источник называет это выжиганием лучших IP
положительной обратной связью, а бриф независимо просит «рандомным образом черпать» — это одно и то
же требование, снятое с двух сторон.

**Почему источник случайности инъектируется.** Глобальный `rand()` в теле резолвера делает тест
политики недетерминированным, и единственный способ его проверить — тысяча прогонов со
статистикой. С инъекцией фиксированное значение даёт предсказуемый узел (правило Code Guidance P1.4).

RAG:✅ 2026-07-31 (`findings/rag-2026-07-31.md` §2 — фильтр по scope/geo/breaker → score → weighted
random внутри top-K; least-failures только tie-breaker).

## 7. Автомат circuit breaker

Состояние **выводится**, а не хранится третьей колонкой-enum'ом:

| Состояние | Условие |
|:--|:--|
| `closed` | `open_until IS NULL` |
| `open` | `open_until > now()` |
| `half-open` | `open_until <= now()` И `open_count > 0` — узел снова попадает в кандидаты, но первая же выдача забирает **пробу** |

```
# ОТКРЫТИЕ (в reportOutcome, при отказе)
level = reason.level()                     # global → prc_proxies, target → prc_proxy_targets
row.consecutive_failures += 1
if row.consecutive_failures >= threshold(level, reason):
    row.open_count   += 1
    row.open_until    = now() + min(base(level, reason) * 2^(open_count-1), cap)
    row.consecutive_failures = 0

# ПРОБА (half-open) — единственность гарантирует БД, не приложение
UPDATE ... SET open_until = now() + probe_lock
 WHERE id = ? AND open_count > 0 AND (open_until IS NULL OR open_until <= now())
# affectedRows = 1 → эта выдача и есть проба; 0 → пробу забрал другой воркер, узел пропускается

# ЗАКРЫТИЕ (успех)
row.open_until = NULL; row.open_count = 0; row.consecutive_failures = 0
```

| Параметр | Глобальный уровень | Целевой уровень |
|:--|:--|:--|
| `threshold` | 5 подряд | 3 подряд (для `http_429` — 10) |
| `base` cooldown | 30 мин | 15 мин (для `http_429` — 2 мин) |
| `cap` | 6 ч | 6 ч |
| `probe_lock` | 60 с | 60 с |

**Почему единственность пробы делается условным `UPDATE`, а не флагом в приложении.** Воркеров
Horizon несколько, и «проверить состояние → решить, что проба моя → записать» — классическая гонка:
на открытый узел уходит столько проб, сколько воркеров одновременно дошли до выдачи. Условный
`UPDATE` с проверкой `affectedRows` — единственная форма, которая держит инвариант «ровно одна
проба» без блокировок.

**Что происходит при падении воркера с непогашенной пробой.** Узел остаётся заперт на `probe_lock`
(60 с) и после этого снова становится кандидатом на пробу — контур самозаживляется, зависшего
состояния нет.

RAG:✅ 2026-07-31 (автомат `closed → open → half-open → closed` на двух уровнях —
`findings/rag-2026-07-31.md` §2).

## 8. Гейт запрещённых стран для LLM-скоупа

**Формулировка.** Резолвер для скоупа `llm` НЕ возвращает узел, у которого
`country ∈ config('crawler.proxy.policy.llm.forbidden_countries')` **или** `country IS NULL`, ни при
какой конфигурации здоровья, весов и наполнения пула. Гейт реализован как условие SQL-фильтра ВНУТРИ
резолвера, ДО скоринга (D5).

**Неизвестная страна = запрещённая.** Узел без `country` не проходит в скоуп, у которого список
запретов непуст. Иначе «забыл проставить страну» = «прошёл гейт», а это ровно тот исход, ради
предотвращения которого гейт существует.

**Носитель политики** — `config/crawler.php`, один блок на все скоупы, с env-override:

```php
'proxy' => [
    'policy' => [
        ProxyScope::Llm->value            => ['forbidden_countries' => ['RU'], 'required_country' => null],
        ProxyScope::CrawlListing->value   => ['forbidden_countries' => [],     'required_country' => 'RU'],
        ProxyScope::CrawlDetail->value    => ['forbidden_countries' => [],     'required_country' => 'RU'],
        ProxyScope::DocumentDownload->value => ['forbidden_countries' => [],   'required_country' => 'RU'],
    ],
],
```

`config/ai.php` остаётся носителем ТОЛЬКО env-фолбэка (`gemini.proxy`) — политики там нет: домен
`Llm` не знает ни про страны, ни про скоупы (D16).

**Проверяемый критерий приёмки** (вход Validation P1.5): в пуле N ≥ 2 активных узлов, у ВСЕХ
`country = 'RU'`, все со скоупом `llm` и здоровые; `forbidden_countries = ['RU']` → `resolve(Llm, …)`
не возвращает ни один из них ни при одном значении инъектированного источника случайности. Тот же
кейс с узлом без страны (`country IS NULL`). Проверяется на нескольких конфигурациях здоровья, а не
на одной удобной.

**Что ломается без жёсткого фильтра.** Вес в скоринге допускает выбор запрещённого узла при
вырожденном пуле — а вырожденный пул это и есть тот момент, когда ошибка происходит. Гейт обязан
быть гарантией, а не предпочтением (D5).

## 9. Контракт резолвера

### 9.1 Форма

```php
final readonly class ProxyResolver
{
    public function resolve(
        ProxyScope $scope,
        string $target,                       # КАНОНИЧЕСКИЙ ХОСТ, не URL
        ?ProxyRequirements $requirements = null,   # страна профиля, флаг use_proxy
    ): ProxyLease;                            # всегда лиза либо исключение, никогда null

    public function reportOutcome(ProxyLease $lease, ProxyOutcome $outcome): void;
}
```

**`ProxyLease`** — DTO, а не модель Eloquent:

| Поле/метод | Смысл |
|:--|:--|
| `proxyId: ?int` | `null` у direct-лизы; уезжает в `prc_fetches.proxy_id` (P1.6) |
| `server: ?string` | `host:port` — дискретное поле |
| `username` / `password` | дискретные поля |
| `scope`, `target` | контекст, нужный `reportOutcome` |
| `httpOptions(): array` | `['proxy' => 'http://user:pass@host:port']` или `[]` — вход `Http::withOptions()` |
| `isDirect(): bool` | лиза без узла (профиль с `use_proxy = false`) |

**Почему лиза, а не модель `Proxy`:**

1. Модель Eloquent, уехавшая в домен `Llm`, делает сейм D16 фиктивным — порт обязан быть узким.
2. Лиза несёт `scope` и `target`, поэтому вызывающая сторона не может «потерять» контекст перед
   `reportOutcome` — сегодня контекст теряется буквально (`ProxyPool::reportFailure(Proxy)` не знает,
   на какой цели произошёл отказ, отсюда дыра 7).
3. Дискретные поля `server/username/password` — прямая форма опции `proxy` в
   `browser.newContext({ proxy })`, то есть задел под браузерный канал не требует переделки лизы
   (§9.3).

**Direct-лиза вместо `null`.** Профиль с `use_proxy = false` получает `ProxyLease::direct()`:
`httpOptions()` пуст, `reportOutcome` — no-op. Call-site остаётся однообразным (`Http::withOptions
($lease->httpOptions())`), а «прокси не используется» становится ЯВНЫМ состоянием, а не значением
`null`, которое сегодня одинаково означает и «не настроен», и «выборка пуста», и «отключён».

**Канонический хост.** Приведение делает вызывающая сторона ОДИН раз
(`parse_url($url, PHP_URL_HOST)`, нижний регистр, без порта и схемы) и передаёт результат. Резолвер
не разбирает строку догадками. Это и есть починка дыры 8: сегодня в `pick()` уходит
`https://zakupki.gov.ru/epz/order/orderCsvSettings/download.html`, а в `targets` лежит
`zakupki.gov.ru` — `whereJsonContains` не находит ничего и запрос уходит напрямую.

### 9.2 Стык с доменом `Llm`

Порт `App\Services\Llm\Contracts\OutboundProxy` (D16) — один метод, без утечки моделей:

```php
interface OutboundProxy { public function optionsFor(string $host): array; }   # → ['proxy' => …] | []
```

Адаптер `App\Services\Procurement\Proxy\PoolOutboundProxy` зовёт `resolve(ProxyScope::Llm, $host)` и
отдаёт `httpOptions()`. `PrismGeminiProvider` про прокси-слой не знает — он знает про порт
(`withProxy()`, `PrismGeminiProvider.php:178-189`, и клиент Files API, `:382`).

Форма стыка подтверждена и не выбирается заново на месте (правило Implementation Rules P1.5).

### 9.3 Задел под браузерный канал (OQ-4 — не решается здесь)

Проверено первичным источником: прокси в Playwright задаётся **при запуске браузера ЛИБО при
создании контекста** (`browser.newContext({ proxy })`), поля — `server`, `username`, `password`,
`bypass`; **способа сменить прокси уже созданному контексту документация не даёт** — ротация без
рестарта процесса браузера означает НОВЫЙ контекст.
RAG:✅ 2026-07-31 (первичный источник — `playwright.dev/docs/network`, раздел HTTP Proxy: «Proxy can
be either set globally for the entire browser, or for each browser context individually»; утверждение
«у живого контекста не меняется» стоит на ОТСУТСТВИИ такого API в документации, а не на явной фразе
запрета — граница названа сознательно).

Следствие для контракта — и оно единственное: **лиза обязана быть единицей жизни контекста, а не
запроса.** Дискретные поля `server/username/password` (§9.1) ложатся в `newContext({proxy})` без
преобразования; смена узла = новая лиза = новый контекст. Ничего сверх этого фаза не делает: ни
кейса enum'а, ни методов «на будущее», ни описания канала в доках как существующего.

## 10. Поведение при пустом множестве кандидатов

Единое правило: **тихого прямого запроса не существует.**

| Скоуп / условие | Поведение | Почему |
|:--|:--|:--|
| `crawl_*`, `document_download`, профиль `use_proxy = true` | `NoProxyAvailableException` (типизированное, с указанием скоупа, цели и причины пустоты) | D3 объявляет прокси обязательным для прогонов против ЕИС; прямой запрос — нарушение правила плана и раскрытие адреса. Исключение ловит существующий `catch` прогона (`FreshRunProcessor.php:87-91`) и переводит прогон в `failed` — оператор видит отказ, а не «прогон прошёл» |
| те же, профиль `use_proxy = false` | direct-лиза, запрос напрямую | Намеренный режим, выбранный оператором |
| `llm`, пул пуст | Фолбэк на `config('ai.gemini.proxy')` + `Log::warning` с явной пометкой «гейт стран к env-прокси не применён» | Прямое требование брифа: «пока берёт из env единственный прокси — это как бы будет дефолтом, его может и хватить» |
| `llm`, пул пуст И env пуст | `NoProxyAvailableException` | Прямой вызов Gemini бессмыслен: исходящий прокси в проекте существует именно из-за RU-ограничений (`config/ai.php:18-24` — «исходящий прокси (v1-канон, RU-ограничения)»). Тихий прямой вызов дал бы сетевую ошибку без причины в логе |

**Названная плата за env-фолбэк.** Страну env-прокси гейт проверить не может — переменная не несёт
метаданных. Фолбэк остаётся легальным (требование брифа), но каждое срабатывание помечается в логе,
и это единственный путь, которым запрос к Gemini может уйти через узел неизвестной страны.
Закрывается заведением LLM-узлов в пул — тогда фолбэк не срабатывает никогда.

## 11. Цена горячего пути

**Один HTTP-запрос площадки стоит:**

1. **1 SELECT** — кандидаты со здоровьем по цели одним запросом:

```sql
SELECT p.*, t.success_ratio, t.latency_ms_avg, t.open_until AS t_open_until, t.open_count AS t_open_count
  FROM prc_proxies p
  LEFT JOIN prc_proxy_targets t ON t.proxy_id = p.id AND t.target = :target
 WHERE p.is_active
   AND p.scopes @> :scope::jsonb                        -- GIN
   AND (p.open_until IS NULL OR p.open_until <= now())
   AND (t.open_until IS NULL OR t.open_until <= now())
   AND <гео-условия §8>
```

2. **1 UPSERT** в `prc_proxy_targets` на исход (`reportOutcome`) + **1 UPDATE** `prc_proxies` только
   когда меняется глобальное состояние (открытие/закрытие breaker'а, сброс серии) — в норме не
   выполняется.
3. **1 условный UPDATE** дополнительно — только когда узел берёт half-open пробу (редко).

**Итого в норме: 1 SELECT + 1 UPSERT на запрос.** Агрегата по `prc_fetches` нет ни одного — это
жёсткое требование (Implementation Rules P1.1), и оно выполнено конструкцией: всё, что нужно score,
лежит денормализованно в строке пары (узел, цель).

**Перечитывание профиля — 1 SELECT по первичному ключу на ИТЕРАЦИЮ БЛОКА** (не на запрос), §12. На
фоне `PoliteThrottle` (1000–4000 мс между запросами, `config/crawler.php:46-49`) цена обоих запросов
пренебрежима — это доли процента времени итерации.

**Записи здоровья идут через `*StoreRepository`** (правило Execution Rules плана), а не прямыми
`update()` из сервиса.

## 13. Вердикт по происхождению узла (D69)

Мысль брифа §1: «прокси бывают двух происхождений — покупные и личные (поднятые на своих серверах
линуксовой утилитой)».

**Вердикт: отдельный носитель происхождения (колонка `origin` / enum `ProxyOrigin`) НЕ заводится.**

Причина названа поимённо, как требует D69:

1. **Ни один предикат выбора на происхождение не смотрит.** Фильтр (§6, шаг 1) — скоуп, страна,
   breaker; score — успешность, задержка, серия отказов; tie-breaker — число отказов. Происхождение
   не входит ни в один из них и войти не может: узел либо работает, либо нет, и это измеряется
   напрямую, а не выводится из того, кто его поднял.
2. **Операторское различение уже покрыто** существующей колонкой `service` (сегодня в фабрике —
   `webshare`/`brightdata`, `database/factories/Procurement/Crawler/ProxyFactory.php`): личные узлы
   заводятся с собственной меткой сервиса и видны в таблице Filament тем же столбцом.
3. **Колонка без потребителя — мёртвая по правилу этого же item'а** («предлагать поля на будущее без
   названного потребителя запрещено»), и она не бесплатна: её нужно заполнять, показывать,
   поддерживать в фабрике и переносить в P3.

**Условие пересмотра (проверяемое).** Происхождение получает СВОЙ носитель — типизированный, а не
свободный текст `service` — как только появится предикат, который на него опирается. Названные
кандидаты: (а) cost-penalty в score, если покупные узлы станут тарифицироваться по трафику;
(б) разное доверие к ЗАЯВЛЕННОЙ стране (у личного узла страна известна достоверно, у покупного —
со слов вендора) — тогда гейт §8 обязан различать источники факта. Ни того, ни другого в этом плане
нет.

**Операционное соглашение (не схема):** личные узлы заводятся со `service = 'self-hosted'`. Это
конвенция, фиксируемая в доках P1.8, а не ограничение БД.

### 14.1 Проект D-записи A — профиль обхода НЕ несёт колонку скоупа

**Решение.** Связь `prc_crawlers` ↔ прокси состоит из ДВУХ колонок (`use_proxy`, `proxy_country`),
а не из трёх: колонка `proxy_scope` на профиле не заводится. Скоуп — свойство ТОЧКИ ИСХОДА (§1), и
он определяется однозначно: листинг → `crawl_listing`, вкладка → `crawl_detail`, файл →
`document_download`. Формулировки Phase Context P1 и Scope Included P1.2/P1.3 «(использовать/не
использовать, скоуп, страна)» приводятся к «(использовать/не использовать, страна)».

**Почему.** Колонка скоупа на профиле — второй владелец факта «для чего берётся узел» рядом с
call-site'ом. Значения у неё могут быть только из тех же четырёх кейсов, и любое, кроме
соответствующего call-site'у, бессмысленно (профиль, назначивший листингу скоуп `llm`, отправляет
трафик кроулинга в пул нейросети). Это ровно класс дыры 2 — свободно задаваемый скоуп, дающий
молчаливо неверную выборку, — только на уровне выше.

**Что делать вместо этого**, если понадобится «выделенные узлы под конкретный профиль»: связь
профиль ↔ узел (pivot `prc_crawler_proxy`), а не переопределение скоупа. Названного требования на
это сегодня нет, поэтому и pivot не проектируется.

**Consequences:** объём P1.2/P1.3 уменьшается на одну колонку, миграцию и поле формы (P1.7);
формулировки трёх мест приводятся к двум колонкам. Работы ни у одного item'а не прибавляется.

### 14.2 Проект D-записи B — у стадии детального анализа профиля нет; её гео-политика берётся из конфига скоупа

**Факт (проверен на `09e07a5`).** `DetailAnalysisProcessor::run()` принимает `Procurement`, а не
`Crawler` (`app/Services/Procurement/Modes/DetailAnalysisProcessor.php:53`), источник метода берётся
из `config('crawler.detail_source_method')`, а не из профиля (`:61-64`); вызывается стадия командой
`crawler:fetch-details` по due-набору `DetailRefetchSelector`, вне какого-либо прогона
(`app/Console/Commands/Procurement/FetchDetails.php:26-56`). Связи «закупка → профиль» в схеме нет:
`prc_procurements` несёт `registry_id`, но не `crawler_id`
(`grep -n "crawler_id" database/migrations/2026_07_04_*procurements*.php` → пусто).

**Следствие.** Формулировка Scope Included P1.3 «перечитывание настроек профиля на каждой итерации в
`FreshRunProcessor`, `ArchiveWindowScanner` и `DetailAnalysisProcessor`» в третьей позиции
неисполнима как написана: перечитывать нечего — профиля в этой стадии не существует.

**Решение.** Стадия детального анализа (скоупы `crawl_detail` и `document_download`) берёт
гео-требование из политики скоупа `config/crawler.php` (§8), а не из профиля; `use_proxy` для неё
всегда `true` (обходного режима у неё нет — D3). Из Scope Included и Files P1.3 удаляется
`DetailAnalysisProcessor`, из Validation — соответствующая часть; предмет P1.3 сужается до двух
процессоров прогона, что совпадает с его же Why («правка профиля в админке во время СУТОЧНОГО
ПРОГОНА»). Свойство «настройки читаются каждый раз» для детальной стадии выполнено деревом: пул
читается из БД на каждый `resolve()`, кэша нет (`findings/repo-recon-2026-07-31.md` §1, абзац «Про
считывать на каждой итерации»).

**Альтернатива, которая отвергнута:** резолвить профиль по `registry_id` закупки. Профилей на реестр
несколько (fresh + archive, `CrawlerMode`), и выбор «какой из них главный для детальной стадии» —
новое неоднозначное решение ради настройки, у которой уже есть однозначный носитель (политика
скоупа).

**Consequences:** объём P1.3 уменьшается на один файл и один тест-кейс; требование брифа не
теряется — оно закрывается политикой скоупа. Работы ни у одного item'а не прибавляется.

## 15. Что остаётся открытым

Неснятых неоднозначностей внутри документа нет. Открытым остаётся ровно один вопрос, и он уже
заведён: **OQ-4** — нужен ли браузерный рантайм в принципе (решение владельца). Этот документ его не
решает и не предвосхищает: он фиксирует форму лизы, которую `newContext({proxy})` принимает без
переделки (§9.3), и не заводит ни кейса enum'а, ни методов под несуществующий канал.

Новых открытых вопросов фаза P1 не порождает: два расхождения с уже написанными ТЗ (§14.1, §14.2)
имеют вид решения, а не вопроса, и оформлены проектами D-записей.
