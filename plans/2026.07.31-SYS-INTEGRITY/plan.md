## 1. Context

Пайплайн v2 построен: crawling → документы → скрининг → извлечение смет, LLM за фасадом
`LlmProvider`, промты как файлы + сид, gold-контур и eval (`2026.07.26-EST-TRAIN`), архитектура
доменов (`2026.07.28-EST-ARCH`). **Боевой парсинг ни разу не запускался.** Владелец сформулировал
девять требований к системе, сводящихся к одному: «хочу понимать, что система полностью
целостная, надёжная, гибкая, типизированная, тестируемая, предсказуемая» (`brief/00-brief.md`).

Разведка дерева (`findings/repo-recon-2026-07-31.md`) показала, что четыре из девяти пунктов
исходят из «этого нет», и в трёх случаях это неверно: прокси-домен существует, DTO-контракты в
промт передаются (и в более развитом виде, чем в `Old/`), а media library не используется вовсе.
Реальные дыры лежат глубже и точнее: прокси не связан с профилем обхода и не знает про гео;
семантика полей контракта живёт в докблоке, а не в типе, из-за чего схема едет в модель ДВУМЯ
каналами, которые обязаны нести один порядок свойств, а фактически расходятся (первичная проверка
вендора — `findings/P2-vendor-structured-output.md` §1, D88; запрета дублирования у вендора нет,
но два носителя одного факта дороже одного); диск файла не хранится
рядом с путём (кроме одной таблицы, где приём применён верно); в сметной модели восемь пробелов
против состава ЛСР; `app/Enums/Procurement` — 38 файлов плоско при разложенных соседних слоях
(поправка D68/D77: в первой редакции стояло 36).

План закрывает эти дыры и заканчивается ревизией схемы БД. Развилка «одна БД или две» **закрыта
владельцем 2026-07-31: одна БД** (D71), вместе с ней утверждена целевая модель хранения (D72) —
P7.3 не выбирает топологию, а подтверждает решение числами боевого прогона и фиксирует модель как
канон проекта.

Схема БД считается **подвижной**: боевых данных нет, `migrate:fresh` дёшев. Это перестаёт быть
верным после боевого прогона P4 — поэтому P6 (адресация файлов) стоит ДО него.

## 2. Execution Rules

- Один item за раз; статус обновляется В ПЛАНЕ (phase-файл + Status Board) до завершения работы.
- **Порядок исполнения фаз — НЕ нумерация: `P1 → P2 → P3 → P5 → P6 → P4 → P7`** (D63). Нумерация
  фаз — адрес, а не очередь; `roadmap.md` несёт эту очередь как обязательную.
- Статусы — 6 канонических строк байт-в-байт (`plan-protocol` §6).
- **Research-item фазы закрывается первым.** Ни одно проектное решение фазы не принимается до
  его закрытия (D2).
- План разошёлся с кодом → не импровизировать, эскалировать (`plan-protocol` §10) + handoff.
- После закрытия item/фазы — перезаписать `plans/2026.07.31-SYS-INTEGRITY/handoff.md` целиком.
- Тесты: Pest, `test('<интент по-русски>')`, БД `agelto_test`, запуск
  `docker compose exec app php artisan test --filter=<Subject>`; стиль
  `docker compose exec app ./vendor/bin/pint --dirty --test`. Один `--filter` за прогон.
- LLM-вызовы в тестах — только `tests/Support/Doubles/FakeLlmProvider`; реальный вызов в тесте —
  блокирующее замечание (`.claude/rules/agelto-reviewer-overrides.md`).
- Персистентность — только через `app/Repositories/**/*StoreRepository`; сервисы
  `final readonly`, конструкторная инъекция, именованные аргументы, `declare(strict_types=1)`.
- Домен не вызывает Prism/SDK напрямую — только через `Contracts\LlmProvider`.
- Промты правятся ТОЛЬКО в канонических корнях (`resources/ai/prompts/**` +
  `resources/<домен>/ai/prompts/**`, D32 EST-TRAIN) + `ai:prompts:sync`.
- **Сетевые прогоны против ЕИС — только через прокси-скоуп площадки** после закрытия P1 (D3).
- `composer require` / `pint --dirty` автофикс / `vendor:publish` — с ХОСТА, не из контейнера.
- **Незакоммиченный чужой диф — НЕ трогать, не коммитить, не откатывать; называть в отчёте**
  (`plan-protocol` §6). Состав на `09e07a5`: `M .env.example` · untracked `config/cms.php`,
  `database/seeders/User/`, `estimates/gemini-analys.md`, `.swissknife/`. Удаление `Old/**`
  ЗАКОММИЧЕНО (`09e07a5 chore: удалить устаревший каталог Old/`) и чужим дифом больше не является.
  Список — ориентир, а не истина: фактический состав снимается `git status --porcelain` ПЕРЕД
  каждым item-коммитом. Особая осторожность с `database/seeders/User/` — он лежит в каталоге, куда
  пишет P4.5 (`database/seeders/Procurement/*`): коммитятся только поимённые пути из `Files`
  item'а, `git add -A` / `git commit -a` запрещены во всех items (D77).
- **Гейт закрытия item'а — линтер плана** (`plan-protocol` §8, шаги 4–5), инвокация целиком:
  `python3 /home/vostrikov/projects/packages/swissknifeman/packages/task/scripts/plan-lint.py plans/2026.07.31-SYS-INTEGRITY`
  — из корня репозитория, `PYTHONPATH` не требуется; скрипт живёт ВНЕ этого репозитория. Зелёное
  на 2026-07-31: `plan-lint: OK (1 план(ов), 0 ошибок, 0 предупреждений)`; закрывающий item
  называет число НОВЫХ записей от своего диффа. Проверка цитат — `python3
  /home/vostrikov/projects/packages/swissknifeman/plans/verify-citations.py`; в `plans/` ЭТОГО
  репозитория её нет. Скрипт недоступен → так и сказать в Completion Notes, выдуманный «lint
  зелёный» — материальное отклонение (D76).

Вариант B теряет обоснование «взрослого выбора для продажи доступа на чтение» — этот вывод
источника верен для read-serving SQL, а не для API-фасада: клиент Postgres не видит, произвольный

нагрузочный аргумент, и перед ним появляется ступень, которой в этой развилке не было —

rate limit). Поправка 2026-07-31 (D75): «кэш в Postgres» верно лишь частично — docker-контуры уже

**Решение владельца (2026-07-31, D71/D72): вариант A — ОДНА БД.** Разбор в сессии `finish`

### 15 — Объём правок схемы, когда в БД уже лежат боевые данные

- **(рекоменд., выбран владельцем) Вариант A — неразрушающие + гейт на остальное.** Расширение
  точности, индексы `CONCURRENTLY`, недостающие FK и явный `ON DELETE`, `NOT NULL` с backfill;
  сужающее и переименовывающее — перечнем владельцу. Плюсы: данные прогона (и фактура самой
  ревизии) сохраняются, каждая правка обратима по одной. Минусы: часть находок закрывается не в
  этом плане.
- **Вариант B — всё, включая сброс данных смоука (`migrate:fresh`).** Плюсы: схема снова
  подвижна, правки дёшевы. Минусы: ревизия «индексы против фактических запросов» теряет свою
  фактуру, а боевой прогон к ЕИС придётся повторять — то есть плата не в коде, а во внешнем
  ресурсе.
- **Вариант C — всё, включая деструктивное, с backfill-миграциями.** Плюсы: максимальная
  полнота. Минусы: самый рискованный item фазы на единственной боевой БД, и риск берётся ради
  находок, приоритет которых ещё не подтверждён эксплуатацией.

**Статус:** Resolved → D58

### 16 — Что фаза делает с находками аудита процессов

- **(рекоменд., выбран владельцем) Вариант A — дефекты + точечные тесты по гейту.** Чиним
  дефекты контракта процесса (осиротевшая очередь `ai_shadow`, отсутствующие таймауты/ретраи) и
  пишем тесты только на инварианты, названные аудитом критичными. Плюсы: боевой дефект закрыт,
  объём предсказуем, список утверждает владелец. Минусы: покрытие остальных 24 команд остаётся
  открытым вопросом.
- **Вариант B — только документ-аудит.** Плюсы: фаза остаётся исследовательской и короткой.
  Минусы: `ai_shadow` продолжает копиться в Redis, а требование брифа §6 закрывается отчётом о
  том, что оно не выполнено.
- **Вариант C — аудит + сплошное покрытие команд и job'ов тестами.** Плюсы: полное покрытие.
  Минусы: объём сопоставим с отдельной фазой и вытесняет приёмку плана; ценность равномерна не
  для всех 29 команд.

**Статус:** Resolved → D59
