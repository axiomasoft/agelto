  рендер списка диапазонов в `loadSettings.html` (`data-from`/`data-to`, при `totalCount` ≥ 5000 —
  ровно 10 диапазонов `1-500`…`4501-5000`). Три кандидата отвергнуты по отдельности:
  `recordsPerPage` на выгрузку не влияет (четыре значения — байт-в-байт один блок), `totalCount`
  задаёт число диапазонов, а не шаг, набор колонок приходит тем же HTML ДО выбора.
- **Критерий достаточности владельца выполнен:** ссылка на CSV строится из сида детерминированно,
  чистым HTTP. Включая `totalCount` — он есть в SSR-разметке листинга

**Вводная владельца 2026-08-05 (ответы на вопросы закрытия P4.1) — вход P4.2:**

1. **Ценовой потолок — параметр профиля, а не константа.** «Пока смотрим только лакомые сметы по
   этим параметрам, но я в любой момент в админке смогу скорректировать профиль». Следствие для
   P4.2/P4.3: сегодняшняя потеря 8 714 закупок выше `archive.price_ceiling = 1e9` (Р-3) приемлема
   как ТЕКУЩАЯ настройка, но потолок обязан быть полем типизированного фильтра профиля и правиться
   из Filament (P4.4), а не жить константой конфига.
2. **В P4.2 рассматриваются ОБА реестра — 44-ФЗ и 223-ФЗ**; какой запускать на проде, решает
   владелец после синтеза. Значит в объём P4.2 входит и ветка карточки 223-ФЗ
   (`/epz/order/notice/notice223/<вкладка>.html?purchaseNoticeNumber=<N>&noticeGuid=<GUID>`,
   Р-11: GUID в CSV-листинге отсутствует), и блок на 510 строк / 500 уникальных номеров (Р-5).
3. **Playwright в боевой контур НЕ входит** — подтверждено фактурой P4.1: CSV-листинг, SSR-вкладки
   карточки и ссылки `filestore/...` берутся обычным GET, `totalCount` — регуляркой по SSR-разметке
   листинга; шагов, требующих JS-рендера, не осталось. НО сертификат — вопрос БОЕВОГО клиента, а не
   браузера: `ignoreHTTPSErrors` есть только у Playwright, поэтому прод-контейнеру нужен корень
   Минцифры в CA-bundle Guzzle либо явное решение по `verify` (Р-10). Headless-рендеринг
   `02-crawling.md` §7 остаётся запасным backend'ом для площадок с JS — для ЕИС не понадобился.
4. **Дробление остаётся ЦЕНОВЫМ; по часам — невозможно.** Подтверждается разметкой: среди 45
   именованных полей формы расширенного поиска нет ни одного временнóго, формат всех дат —
   `dd.MM.yyyy`. Суточная гранулярность — предел источника, поэтому день обновления на 16 166
   записей (`03.08.2026`) дробится только по `priceFromGeneral`/`priceToGeneral`.
