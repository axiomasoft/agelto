## 3. Два факта, найденных живой приёмкой (Implementation Rules п. 8 — НЕ чинятся этим item'ом)

### 3.1. `prc_events` не покрывает исторические даты реальных карточек — блокирует `markDetailFetched`

Все восемь карточек несут события журнала с РЕАЛЬНЫМИ датами 2025 года (закупки завершены в 2025).
Партиции `prc_events` (pg_partman) существуют только на ближайшие месяцы вперёд от текущей даты
прогона (2026-08) — премейк, не бэкафилл прошлого. `EventJournalProcessor` падает
`SQLSTATE[23514]` («no partition of relation "prc_events" found for row») на КАЖДОЙ из восьми
карточек без исключения (детерминированно, не флейк — так же воспроизвелось у семи из восьми при
первой попытке; восьмая, 36971, разошлась `cURL error 28` — транспортным таймаутом при первой
попытке, а при повторе упала тем же `23514`).

`DetailAnalysisProcessor::run()` ловит исключение как `Throwable` (штатный error-блок), но это
значит: **`markDetailFetched` не достигается ни для одной из восьми карточек** — `detail_fetched_at`
у всех восьми остался от прогона P4.15 (12:26–12:32), `detail_attempts` вырос, `detail_last_error`
несёт этот код. Данные, записанные РАНЕЕ в try-блоке (common-info/items/financing через
`CommonInfoProcessor::process()` — своя транзакция; документы через `DocumentIndexer`/
`DocumentDownloader` — прямая запись), сохраняются: числа §2 честные, не потеряны откатом.

Это дефект `prc_events`-партиционирования (P7.4 уже назван его владельцем в Open risks плана —
«партиции не покрывают тестовые даты»), НЕ дефект транспорта карточки, который чинит P4.16.
Scope Excluded item'а прямо называет: правка парсеров и контура `EventJournalProcessor` — не
предмет этого item'а. Не чинится здесь по Implementation Rules п. 8.

**Эксплуатационное следствие для Pending Work:** пока P7.4 не закрыт, ЛЮБАЯ реальная закупка с
историческими событиями будет повторно уходить в backoff при каждом плановом ре-фетче детального
слоя (детальная стадия никогда не помечается снятой) — источник получит повторные живые запросы на
одну и ту же карточку до тех пор, пока партиции не покроют её дату. Это не гипотеза: воспроизведено
машинно на восьми из восьми карточек этого прогона.

### 3.2. `prc_procurement_parties = 0` на всех восьми карточках — подтверждение, не регрессия

P4.14 отметила [UNVERIFIED]: блок `organizations-block`/`table.parties-table` отсутствовал на
ЕДИНСТВЕННОЙ живой карточке пробы P4.13, и было неясно, типично ли это для потока. Этот прогон
даёт живой вход `PartiesParser` на ВОСЬМИ карточках четырёх типов процедуры (`ea20`×5, `ok20`×1,
`zk20`×1, `ezt20`×1) — блок отсутствует на всех восьми. `PartiesParser` работает корректно (парсер
не тронут этим item'ом, Scope Excluded), возвращает пустой результат честно.

**Вердикт:** [UNVERIFIED] закрывается — на снятой раскладке ЕИС (44-ФЗ, все четыре типа процедуры
корпуса) организационный блок карточки `common-info` в текущей вёрстке ОТСУТСТВУЕТ; роли/организации
приходят из другого источника (не проверено этим item'ом — не его Scope). `prc_procurement_parties
> 0` из Validation item'а НЕ достигнуто — это факт вёрстки источника, не дефект транспорта.

## 4. Материальный остаток

Validation item'а несёт критерий `prc_procurement_parties > 0`, который живой корпус этой выборки
структурно не может удовлетворить (§3.2). Это — материальное отклонение (Validation осталась
неисполненной по ОДНОМУ критерию из восьми), item закрывается `🟠 Done with deviations`.

`detail_fetched_at`/`markDetailFetched` не достигнуты ни на одной из восьми карточек — блокер §3.1,
вне Scope. Контрактному критерию фазы («документный контур доказан числами») это не мешает: он
сформулирован через `prc_documents`/`prc_document_versions`, оба положительны.

## 5. Инфраструктурная поправка окружения (не код, не Scope item'а)

MinIO контейнера `agelto_minio` был поднят с `MINIO_ROOT_PASSWORD`, НЕ совпадающим с
`AWS_SECRET_ACCESS_KEY`/`filesystems.disks.s3.secret` приложения (`placeholder123`) — существующий
Known workaround плана («`MINIO_ROOT_PASSWORD=<любое> docker compose build/up`»,
`handoff.md`/`plan.md` Open risks). Без выравнивания `DocumentDownloader` падал на первой же
проверке существования объекта («Unable to check existence for: …», сигнатура не совпадает).
Применено: `MINIO_ROOT_PASSWORD=placeholder123 docker compose up -d minio` (пересоздание
контейнера с паролем, совпадающим с уже сконфигурированным секретом приложения; том `minio_data`
не тронут). Это выравнивание окружения под уже существующий конфиг приложения, а не правка кода —
без него `Deliverables` item'а (документы со скачиванием) физически недостижимы.
