## 2. Вкладка `documents` — раскладка (предмет правки этого item'а)

Подтверждает `findings/P4-load-baseline.md` §5 Д-5 и `research/10-p4-remediation.md` §3.6 без
расхождений — «ожидалось → снято» = «совпало» по всем пунктам.

- **Селектор блока:** `div.blockFilesTabDocs` (единственный на странице, `section__title` =
  «Прикрепленные файлы»).
- **Селектор строки:** `div.attachment.row` (ровно 6 — по числу ссылок `filestore`).
- **Селектор ссылки:** `span.section__value > a[href^="https://zakupki.gov.ru/44fz/filestore/
  public/1.0/download/"]` — ссылка АБСОЛЮТНАЯ (полный `https://...`), не относительный путь.
- **Имя файла:** атрибут `title` ссылки, С расширением (`"НМЦК размещение информационного
  сообщения на страницах на 2025 год.xls"`); текст ссылки (`$link->text()`) — БЕЗ расширения и
  усечённый по смыслу, не совпадает с `title` — использовать текст ссылки как имя файла означало
  бы терять расширение на каждом документе.
- **`uid` (ключ дедупа `external_id`):** query-параметр `uid` СОХРАНИЛСЯ в новой форме ссылки —
  `?uid=F160E393C87D4C65ACEDF22204D1A9C9` (32-символьный hex, было — та же query-строка форма).
  `externalIdFromHref()` (`parse_url` + `parse_str` по query-строке `uid`) продолжает работать
  БЕЗ ИЗМЕНЕНИЙ — метод агностичен к домену/пути ссылки, только к наличию `?uid=` в query.
  Соседняя ссылка `a[data-modalup]` (просмотр подписи, `.../signview/ep/listModal.html?
  reestrNumber=...&uid=...`) тоже несёт `uid`, но лежит ВНЕ `span.section__value` — селектор
  `span.section__value > a` её не подхватывает, коллизии нет.
- **`kind` (тип документа):** в старой раскладке брался из первой колонки строки 3-колоночной
  таблицы («Извещение о проведении…», «Проект контракта» и т.д.). В НОВОЙ раскладке такой колонки
  нет вовсе: все 6 вложений лежат плоским списком под ОДНИМ заголовком «Прикрепленные файлы» без
  категоризации по типу документа. Источника для `kind` не найдено — поле легитимно приходит
  `null` для всех строк (DTO уже несёт `?string $kind`, ничего не домысливается).
- **Абсолютность ссылки:** `absoluteUrl()` (`DocumentsParser.php:101-109`) уже отдаёт абсолютную
  ссылку как есть при `str_starts_with($href, 'http')` — поведение верно для НОВОЙ раскладки без
  изменений (правка НЕ требуется, `research/10` §3.6 подтверждено чтением кода до пробы).

## 3. Остальные три вкладки — только факты (вход P4.14, диагноз/фикс НЕ этого item'а)

### `event-journal`

Подтверждает `research/10-p4-remediation.md` §3.7 частично, с уточнением тега. Таблица —
`table#event.table.mb-0.displaytagTable` (не `div.event-journal-table`, как искал старый
`EventJournalParser:31` — ноль совпадений там же, где это уже нашла разведка П4.7). Строки —
РЕАЛЬНЫЕ `<tr class="table__row">` (не `div`, как предполагал `research/10` §3.7 — тег другой,
класс совпал); ячейки — РЕАЛЬНЫЕ `<td class="table__cell table__cell-body">` (заголовочные —
`<th class="table__cell table__cell-header table__cell-body">`). Две колонки: «Дата и время»,
«Событие». Пример строки: `23.01.2025 09:29 (МСК+9)` / `Закупка № 0338200009125000001
автоматически переведена на этап «Определение поставщика завершено»…`.

### `common-info`

Структура НЕ совпадает с гипотезой `research/10` §3.7 (`section.common-info-block dt`+`dd`) —
на странице НЕТ ни одного `<dt>`/`<dd>` (`grep -c` = 0). Фактическая раскладка — плоский список
`section.blockInfo__section` внутри нескольких `div.row.blockInfo`, каждая секция —
`span.section__title` (подпись поля) + `span.section__info` (значение), без вложенности
"объект/подобъект"; секции `Финансовое обеспечение закупки (всего)` / `Детализация по кодам видов
расходов` — тоже плоские `section__title`/`section__info` внутри общей раскладки, ОТДЕЛЬНОЙ
`table.financing-table` (как искал `CommonInfoParser:128`) на странице нет — 0 совпадений
`financing-table`/`financing-info-block`/`purchase-items-block`/`items-table`. Тридцать три поля
`section__title` встречены на странице (полный список — сырой HTML), включая «Ответственное
должностное лицо», «Идентификационный код закупки (ИКЗ)», «Способ определения поставщика…»,
«Требуется обеспечение заявки»/«исполнения контракта», «Этап закупки», «Сведения о связи с
позицией плана-графика». Организация-заказчик — секция «Организация, осуществляющая размещение».
Диагноз Д-7 (все поля `prc_eis_details` пустые) этим не ставится — только сырая раскладка.

### `supplier-results`

На ЭТОЙ карточке (закупка признана несостоявшейся) вкладка несёт ДВЕ секции:
«Заказчик(и), с которыми планируется заключить контракт» (`section__title`) и «Основание признания
торгов несостоявшимися». Отдельного явного текста-маркера 404/пусто НЕТ — вкладка ответила `200`
и содержит контент (в отличие от `ea615`/`po615`, где разведка `research/eis-block-win1251`
зафиксировала физический `404` для этой вкладки — см. `artifacts/eis-registry-settings.json`
`_observed`). `PartiesParser` (`section.organizations-block table.parties-table`) не находит
соответствия ни на этой, ни на `common-info` вкладке — 0 совпадений `organizations-block`/
`parties-table` на обеих; похоже, состав сторон закупки на текущей вёрстке слился в `common-info`
(«Организация, осуществляющая размещение») либо не показан на карточках без заключённого
контракта — диагноз оставлен P4.14.
