## §1. Разделение write-heavy парсинга и чистой read-БД (вход P7, OQ-1)

**Запрос:** PostgreSQL 17/18, критерии выбора между (a) одна БД + `pg_partman` + read replica,
(b) read-модель в той же БД, (c) отдельная БД через logical replication, (d) CDC/Debezium;
пороги-триггеры и trade-offs.

**Что подтвердилось:**

- Общая рекомендация — **начинать с одной БД и физически разделять контуры тогда, когда write
  path начинает ломать SLO на чтение**, а не «когда становится медленно».
- Физическое разделение оправдано, когда **одновременно верны минимум два** пункта: WAL
  pressure + заметный replica lag; autovacuum не успевает и bloat растёт; читающие запросы
  конкурируют за shared buffers / CPU / checkpoint I/O с ingestion; нужны РАЗНЫЕ индексы,
  fillfactor, параметры autovacuum или retention для write- и read-контуров; нужно независимо
  масштабировать чтение.
- Ориентиры-пороги (позиционированы источником как rule-of-thumb, не абсолют): bloat > 20% —
  разбираться, но не делить; bloat ≥ 50% — сильный сигнал; dead tuples в миллионах на горячих
  таблицах — тюнить autovacuum, не помогает → выносить чтение; replica lag в **минутах** на
  данных, которые клиент считает свежими — уже архитектурная проблема; read latency растёт
  синхронно с write throughput — признак contention.
- Про вариант (b) прямая оговорка: денормализованная read-модель ускоряет запросы, но
  **write-нагрузка обслуживается тем же storage, тем же autovacuum и тем же checkpointing**,
  поэтому выигрыш ограничен. Это важный контр-аргумент, а не поддержка «read-модели» как
  универсального ответа.
- Вариант (c) назван самым сбалансированным «взрослым» для сценария «продаём доступ на
  чтение»; цена — eventual consistency, дисциплина DDL, не все объекты реплицируются гладко.
- Вариант (d) — избыточен, если нужен только отдельный read-serving SQL endpoint.
- Рекомендованная последовательность: partitioning + жёсткий vacuum-тюнинг + read replica →
  при падении read SLO переходить на отдельную read-БД через logical replication → CDC только
  при нескольких downstream-потребителях.

**Что это меняет для Agelto:**

Вопрос владельца («две БД или нет?») **не имеет ответа из архитектурного мнения** — все
названные критерии измеримые, а боевой парсинг ещё не запускался (`findings/repo-recon-2026-07-31.md` §4:
«стартовые значения калибруются на живых данных»). Шаг (a) в проекте уже сделан:
`setup_pg_partman.php`, `set_pg_partman_retention.php`, `set_hot_partition_autovacuum.php`
(§7 разведки). Значит P7 обязана: (1) снять baseline перечисленных метрик на боевом прогоне
P4, (2) сопоставить с порогами выше, (3) вынести владельцу решение с числами. Ранее этого
решение не принимается — OQ-1.

Отдельно фиксируется: рекомендация НЕ поддерживает вариант (b) как «дешёвую замену» (b) ≠ (c);
предварительный вердикт сессии дизайна («одна БД + read-модель») в этой части **ослаблен**
источником и в план как решение не заносится.

postgresql.org/docs/current/sql-vacuum.html · postgresql.org/docs/current/routine-vacuuming.html ·
red-gate.com/simple-talk/databases/postgresql/uncovering-the-mysteries-of-postgresql-auto-vacuum/

## §2. Архитектура прокси-пула (вход P1)

**Запрос:** модель данных прокси (scope, гео, здоровье), стратегии выбора, health-check и
circuit breaker, sticky sessions, привязка к профилю обхода; proxy per BrowserContext в
Playwright и смена прокси без рестарта браузера.

**Что подтвердилось:**

- Проектировать пул следует **не как список IP, а как слой маршрутизации с состоянием,
  телеметрией и политиками выбора** по домену/сценарию/профилю.
- Минимальная сущность: `id, provider, kind (dc/resi/mobile), server, username, password,
  geo.country, geo.region, geo.city, asn, tags, cost, supports_sticky, sticky_key,
  max_concurrency, status, last_checked_at`. **Scope/purpose держать отдельным полем** — один
  пул не должен одинаково обслуживать разные классы задач.
- Здоровье — **не одна колонка `is_alive`**, а набор скользящих индикаторов:
  `success_rate_5m/1h, p50/p95_latency, block_rate, captcha_rate, tcp_fail_rate,
  tls_fail_rate, ban_score, consecutive_failures, open_circuit_until, cooldown_until,
  geo_verified_at`.
- **Главная названная ошибка: считать прокси мёртвым глобально после блока на одном сайте.**
  Здоровье обязано быть минимум двухуровневым — `global_health` и `per-target health`.
- Стратегии: round-robin годится только для однородного пула; **weighted random практичнее
  как дефолт** (вес из свежей успешности, latency penalty, block penalty, geo match, sticky
  affinity, cost penalty, доменной пригодности); least-failures — **только как tie-breaker**,
  в лоб он выжигает лучшие IP положительной обратной связью. Рабочая схема: фильтр по
  scope/geo/sticky/breaker → score → **weighted random внутри top-K**, не строго top-1.
- Circuit breaker на двух уровнях (proxy+target и target/pool), автомат
  `closed → open → half-open → closed`; причины деградации хранить раздельно
  (`NETWORK_TIMEOUT, TLS_ERROR, HTTP_403, CAPTCHA, EMPTY_BODY, BOT_CHALLENGE, GEO_MISMATCH`),
  реакция breaker'а зависит от причины.
- Health-check трёхуровневый: L0 сетевой (TCP/TLS/timeout), L1 canary URL, L2 целевой домен
  (403 / CAPTCHA / redirect-to-challenge / аномально короткий body).
- Sticky — TTL-окном (ориентир 5–30 мин) или на время `session_id`, не «навсегда». Stateless
  листинги — короткий sticky или без него; stateful flow — жёсткая связка
  proxy ↔ context ↔ cookie jar ↔ fingerprint.
- Прокси не выбирается отдельно от остального профиля: geo должен быть согласован с
  `timezone`, `locale`, `Accept-Language`. Предложенная единица оркестрации — **SessionLease**
  (proxy + context options + evasion profile + TTL + target scope), а не request и не browser.
- **Playwright:** прокси задаётся при `browser.newContext({ proxy })` (поля `server`, `bypass`,
  `username`, `password`; HTTP и SOCKS). Сменить прокси у **уже созданного** контекста
  **нельзя**; ротация без рестарта процесса браузера = создание НОВОГО контекста в живом
  browser process. `browser.newPage()` — convenience API, само создаёт контекст; для
  production рекомендован явный `newContext()` → `newPage()`. **[требует первичного
  подтверждения по playwright.dev при детализации P1]**

**Что это меняет для Agelto:**

Текущий `ProxyPool` (`orderBy fails_count, id` + глобальный `is_active` по счётчику отказов) —
ровно те два антипаттерна, которые источник называет по имени: strict-best выбор и глобальное
выключение по локальному бану. Целевая модель P1 — фильтр(scope, country, breaker) → score →
weighted random top-K, с per-target здоровьем и таксономией причин. Требование брифа «черпать
рандомным образом» совпадает с рекомендацией, и это не совпадение: детерминированный выбор
выжигает узел.

Требование «Gemini не через RU» ложится на фильтр по `country` **до** score — как жёсткий
гейт, а не как вес.

Единица «прокси + профиль» из источника (SessionLease / EvasionProfile) — прямое основание
связывать прокси не с запросом, а с прогоном/профилем обхода, как и просит бриф («все дочерние
элементы подчинены настройкам профиля»).

## §3. Structured output Gemini: схема vs system instruction (вход P2) — ЛОМАЕТ ТЕКУЩЕЕ РЕШЕНИЕ

**Запрос:** Gemini 2.5/3 — `responseSchema`, `propertyOrdering`, влияние `description`-полей;
схема в `responseSchema` vs дублирование в system instruction; ограничения схемы; стабильность
префикса и кэширование.

**Что подтвердилось:**

- **`responseSchema` — главный источник истины по структуре.** Документация вендора
  рекомендует конфигурировать схему на модели, а **не дублировать её в text prompt**: при
  inline-описании схемы в промте модель *not constrained to follow the schema*, и качество
  обычно ниже.
- Рекомендованное разделение: `responseSchema` — типы, обязательность, enum, ограничения,
  порядок свойств; system instruction — **только поведенческие правила**: что считать
  источником истины, как трактовать спорные случаи, что делать при отсутствии данных, политика
  извлечения.
- `description` на поле — полезный сигнал именно для **неоднозначных** полей; жёсткого правила
  «N слов на свойство» нет. Когда описания начинают повторять весь системный промт, выигрыш
  падает, а токены растут. Эвристика: 1 короткое предложение на неочевидное поле; 1–3 полных
  примера **на объект/кейс**, а не мини-пример на каждое поле.
- Ограничения и источники ошибок 400: длинные имена свойств, большие enum, много optional-полей,
  глубокая вложенность, сложные numeric/date constraints. Совет при нестабильности —
  **сначала упрощать схему, потом усиливать промт**.
- `propertyOrdering` поддерживается и важен для стабильного порядка ключей; порядок полей в
  примерах должен совпадать с `propertyOrdering`, иначе вывод становится *rambling or
  unexpected*.
- `responseJsonSchema` (расширенная JSON-Schema-поддержка) — на линейке Gemini 2.5, рекурсивные
  `$ref` ограничены и разворачиваются до конечной глубины; `anyOf` есть, но применять умеренно.
- **Схема считается во входные токены**, изменение схемы или её порядка меняет поведение ⇒
  стабильный префикс и неизменный порядок полей — практическое требование.
- Про точную эффективность implicit/explicit context caching публичная документация жёстких
  эмпирических гарантий не даёт.

**Что это меняет для Agelto — это главная находка сессии:**

Agelto сегодня делает **оба канала одновременно**: `JsonSchemaGenerator` → `responseJsonSchema`
(`PrismGeminiProvider.php:45`) **и** `PromptContextGenerator` → очищенный PHP-исходник
контрактов в системную инструкцию (`PromptComposer.php:30`). Второй канал — ровно то
дублирование, против которого предостерегает вендор.

Но выкидывать его **нельзя механически**, и это ключевой нюанс: докблоки Data-классов несут
**семантику, которой в JSON Schema нет**, потому что нет носителя `description` (`#[Description]`
не существует — разведка §2 дыра 1). Пример: `EstimateRow` печатает 30 строк правил
(«`unit` — ЦИТАТА документа; разбор на базу и множитель делает БЭКЕНД», «`row_index` — сквозной
номер В ПРЕДЕЛАХ СМЕТЫ, включая заголовки разделов»). Убери исходник из промта, не перенеся эти
правила — потеряешь качество, а не дублирование.

⇒ Целевая последовательность P2 (не «убрать блок схем», а **разложить его на два носителя**):

1. Ввести `#[Description]` (и расширить покрытие `#[Alias]`, §2 разведки) как машиночитаемый
   носитель семантики поля.
2. `JsonSchemaGenerator` начинает эмитить `description` (и `propertyOrdering`) в
   `responseJsonSchema` — структура **и** значение уходят одним каналом.
3. Только после этого system instruction сокращается до поведенческих правил, а
   `PromptContextGenerator` перестаёт печатать структуру (либо удаляется, либо остаётся
   исключительно носителем словарей-справочников вроде `EstimateHeaderMap`).
4. Каждый шаг проверяется eval-прогоном против gold (контур существует:
   `prc_ai_dataset_examples`, `prc_ai_eval_runs`) — **порядок именно такой**, иначе регрессия
   не будет отличима от шума.

Побочный эффект в плюс: сокращение системного префикса удешевляет каждый вызов (схема
считается во входные токены), а `propertyOrdering` закрывает риск нестабильности префикса,
ради которого `PromptContextGenerator` и делал детерминированную сортировку.

**Оговорка:** RAG-ответ — вторичный источник, а решение ломает работающий боевой контур.
**[требует первичного подтверждения]** по ai.google.dev (structured output: `responseSchema`,
`responseJsonSchema`, `propertyOrdering`, лимиты) при детализации P2 — через `context7` или
прямое чтение вендорской документации.

**Источники:** blog.google/innovation-and-ai/technology/developers-tools/gemini-api-structured-outputs/ ·
medium.com/google-cloud/structured-output-with-gemini-models-begging-borrowing-and-json-ing-f70ffd60eae6

## §4. ЕИС zakupki.gov.ru: лимиты выгрузки и отслеживание изменений (вход P4)

**Запрос:** лимиты CSV-выгрузки (500/5000), параметры URL-фильтров, надёжное отслеживание
изменённых закупок при нестабильной пагинации, альтернативы (FTP/opendata/XML/API).

**Что подтвердилось:**

- Ограничение выгрузки результатов поиска **до 5000 записей** подтверждается; в справочных
  материалах отдельно встречается порог **500** для отдельных сценариев/интерфейсов. Длинные
  выборки дробят фильтрами.
- Расширенный поиск действительно даёт фильтры «Размещение», «Обновление», мин/макс цена,
  закон, этап, заказчик, ОКПД2 — то есть дробление **по интервалам дат и цен** — штатный приём.
- URL-параметры вида `publishDateFrom, updateDateFrom, priceFromGeneral, recordsPerPage,
  sortBy, af, ca` в выдаче встречаются, но **их стабильность и семантика не документированы**;
  источник прямо советует считать их «деталями текущего фронтенда», а не контрактом API, и не
  строить на них единственную точку интеграции.
- **Ключевой ответ на вопрос брифа про плывущую пагинацию:** полноту обеспечивает **не
  пагинация**, а устойчивый идентификатор. Схема: хранить закупки по реестровому номеру;
  переобходить выдачу **узкими окнами по дате обновления**; для каждого ID хранить **хэш
  значимых полей карточки**; совпал — не трогать, разошёлся — перезагрузить карточку и
  документы. Окна делать **перекрывающимися (запас 1–3 дня)** и дедуплицировать по ID/версии —
  это ловит запоздалую индексацию и ретроактивные правки.
- Рекомендованный режим: nightly full-scan по широкому окну + delta-scan по последним
  суткам/неделе с перекрытием; очередь повторных попыток, журнал причин расхождений,
  антидубликаты по `regNumber`/`noticeId`.
- **Альтернативы:** старый FTP-доступ с XML-выгрузками, по указаниям источников, **закрыт с
  01.01.2025**; вместо него — сервисы отдачи данных и SOAP-интеграция (`int44.zakupki.gov.ru`),
  а также XML-представления карточки (`viewXml.html`). Рекомендация: HTML/поиск — только
  инкрементальный индикатор, **XML/SOAP — источник истины**, локальное хранилище — система
  контроля изменений.

**Что это меняет для Agelto:**

- Механика дробления по цене в проекте уже есть (`config/crawler.php` → `archive.*`,
  `eis.block_size = 500`) — вопрос брифа «учтено ли» закрывается **утвердительно по коду**, но
  калибровка констант на живых данных не проводилась; это работа P4, не переписывание.
- «Надёжный механизм отслеживания», которого владельцу не хватало, из источника получает
  конкретную форму: **хэш значимых полей карточки + перекрывающиеся окна по `updateDate` +
  дедупликация по реестровому номеру**. В проекте уже есть `prc_revisions` и `prc_events` —
  при детализации P4 проверить, покрывают ли они эту роль, или нужен носитель хэша.
- Факт «FTP закрыт с 2025, есть SOAP + `viewXml.html`» — потенциально **меняет источник
  истины пайплайна** (сейчас `SourceMethod::Csv`, а `html`/`api` — «задел контракта, реализация
  вне плана V2-CRAWL», `config/crawler.php`). Это не задача переписывать транспорт в этом
  плане, но **обязательный пункт разведки P4** и кандидат в open questions.
- **[требует первичного подтверждения]** — все три пункта (лимит 5000/500, закрытие FTP,
  доступность `viewXml.html`/SOAP без авторизации) проверяются **живой Playwright-разведкой**
  в P4, как и просил бриф. RAG здесь задаёт гипотезы, а не факты.

**Источники:** ppt.ru (инструкция по сохранению найденных в ЕИС закупок) · habr.com/ru/articles/869934/ ·
ru.stackoverflow.com/questions/773915

## §5. Состав локальной сметы по методике 421/пр (вход P5)

**Запрос:** обязательные графы ЛСР по 421/пр (ресурсно-индексный метод), состав колонок
позиции ФЕР/ТЕР/ГЭСН, НР и СП, коэффициенты, разделы и итоги; отличия ЛСР / ресурсной
ведомости / КС-2 / КС-3 / ССР; что обязано лежать в БД для реконструируемости.

**Что подтвердилось:**

- Табличная часть ЛСР в РИМ — типично **12 колонок**: позиция, шифр нормы, наименование работ,
  единица измерения, объём, ресурсно-расценочная детализация, стоимость, итоговые показатели.
- Позиция в РИМ — **не одна цифра**: внутри неё норма + раскрытие ресурсов + строки
  **неучтённых ресурсов**, если они добавлены отдельно. Хранить следует деревом:
  позиция → норма/состав → ресурсные строки → начисления и коэффициенты.
- Обязательный состав строки позиции: сквозной номер; **шифр нормы**; **тип нормы** (ГЭСН/ФЕР/
  ТЕР/ГЭСНм/ГЭСНр/доп. ресурс/неучтённый); наименование; единица; объём; коэффициенты к норме
  и/или к стоимости; **прямые затраты**; **накладные расходы**; **сметная прибыль**; итог по
  позиции; признак метода расчёта и уровень цен; привязка к разделу/этапу.
- НР и СП нельзя хранить «процентом сверху» без контекста: нужны **норматив, база начисления,
  ставка, правило округления, итоговая сумма**.
- Коэффициенты хранить **по каждому применению**, а не суммарно: к норме / к объёму / к
  стоимости / к оплате труда / к эксплуатации машин / к материалам; плюс метаданные —
  источник, основание (письмо/приложение/таблица), дата, признак «применён автоматически или
  вручную».
- Ресурс внутри позиции: тип (труд/машина/материал/оборудование/перевозка), **код по
  КСР/ФССЦ/ФСЭМ/ТССЦ**, наименование, единица, норма расхода, базисная цена, текущая цена,
  **источник цены**, **признак учтённости нормой или добавления отдельно**.
- Начисления отдельной сущностью: тип (НР, СП, перевозка, заготовительно-складские, зимние,
  временные), **база начисления**, норматив/ставка, сумма, порядок применения, источник нормы.
- Версионность: нормативный документ, номер и дата приказа, таблица/приложение, версия индекса,
  **дата ценового среза**, источник конъюнктурного анализа.
- Разделы и **промежуточные итоги** по разделу обязательны — не только визуально: разделы
  привязаны к конструктивным частям / видам работ / этапам.
- Разграничение форм: **ЛСР** отвечает «из чего сложена стоимость»; **КС-2/КС-3** — «что
  выполнено и сколько к оплате» (КС-3 составляется на основе КС-2); **ССР** — «сколько стоит
  объект целиком», агрегирует по главам.

**Что это меняет для Agelto:**

Сопоставление с фактической схемой (`findings/repo-recon-2026-07-31.md` §5) даёт **восемь
конкретных пробелов**: НР/СП как суммы на позиции; разбивка прямых затрат (ОТ / ЭМ, в т.ч.
ЗПМ / МАТ); тип нормы; признак неучтённого ресурса; источник цены ресурса; база начисления в
`totals`; признак НДС на смете; нормативный документ + дата ценового среза. Плюс из этого же
источника: **метаданные применения коэффициента** (основание, дата, авто/вручную) — сегодня
`RowAttributes.modifiers[]` есть, полноту `RowModifier` надо сверять отдельно.

Важная методологическая оговорка, определяющая ХАРАКТЕР фазы P5: источник описывает **что
обязано быть в смете**, а Agelto **извлекает то, что есть в конкретном файле**. Не всякая
колонка методики присутствует в каждом документе, и добавлять колонку в схему «потому что так
в 421/пр» — путь к полю, которое всегда `null`. Поэтому P5 обязана вести проверку **на
эталонном корпусе** (`prc_ai_fixtures` + gold-контур плана `2026.07.26-EST-TRAIN`): пробел
подтверждается фактом «в фикстурах эта величина есть, а положить её некуда», а не цитатой из
методики.

**[требует первичного подтверждения]** — состав граф и обязательность НР/СП на позиции
сверяются с текстом приказа Минстроя 421/пр и типовой печатной формой ЛСР при детализации P5;
использованные источники вторичны.

## §6. Смена S3-провайдера без даунтайма: диск в записи, dual-read, backfill (вход P6)

**Запрос (2026-07-31, дизайн-сессия P6, две ступени Perplexity):** (1) миграция объектного
хранилища между S3-провайдерами без даунтайма для приложения, хранящего пути файлов в БД —
хранение имени диска/бакета в записи, dual-read с фолбэком, фоновый backfill с верификацией
контрольной суммы, cutover и окно отката; типичные ошибки практики 2024–2026. (2) Laravel
Flysystem: хранить имя диска рядом с путём вместо чтения конфига в момент чтения; ленивая
миграция / promote-on-read; resumable идемпотентная artisan-команда копирования между дисками с
проверкой sha256 — плюсы и минусы.

**Зачем:** раздела по хранилищу в этом файле не было, а `plan.md` D12 на него ссылался — висячая
цитата. Раздел закрывает её первичной фактурой (`plan.md` D49).

### Целевая форма записи

Запись обязана однозначно определять место объекта — не «путь + глобальный конфиг», а явные
поля: носитель (логическое имя диска), ключ объекта, контрольная сумма, размер, момент миграции.
Названная причина: **равенство путей ≠ равенство объектов** — один и тот же ключ в двух бакетах
это два разных объекта, и вывести адрес из глобального префикса нельзя.

Отдельный вердикт по Laravel: «диск в БД» оправдан, когда размещение — **состояние записи**, а не
свойство приложения; если таблица навсегда привязана к одной области хранения, проще держать
выделенный диск и относительный путь. Имена дисков в БД обязаны быть **логическими и
стабильными** (не `s3-eu-west-1-bucket-a`): инфраструктурное имя в строках превращает
переименование диска в `filesystems.php` в миграцию ДАННЫХ. Путь хранится относительным —
`url`/`temporaryUrl`/`exists`/`get`/`copy` определены относительно корня диска.

Отдельно названо: **не выводить место чтения из «текущего диска по умолчанию»** после того, как
файлы уже сохранены — смена конфига делает старые строки двусмысленными; вместо этого — маленькая
доменная абстракция (класса `StoredFileLocator`), чтобы call-site'ы не собирали
`Storage::disk($model->disk)` руками.

### Порядок миграции (canonical flow)

1. Заморозить целевую форму записи (см. выше) — ДО копирования.
2. Создать приёмник: бакет, креды/IAM, lifecycle, шифрование, CORS — до копирования, чтобы код
   уже умел писать в новое место без второй правки схемы.
3. Выкатить dual-read: читать по адресу записи, фолбэк на прежнее место только когда объекта нет
   или он не проходит проверку.
4. Backfill в фоне пакетами; для больших объёмов управляемые batch-инструменты предпочтительнее
   ad-hoc рекурсивных скриптов (ретраи, манифесты, наблюдаемость).
5. Верификация слоями: полнота по манифесту/инвентарю → побайтовая целостность по контрольной
   сумме → выборочное чтение приложением.
6. Переключить ЗАПИСЬ на новый носитель; dual-read остаётся включённым.
7. Держать окно отката: старый бакет read-only и доступен, пока метрики не подтвердят стабильность;
   фолбэк снимается ПЕРЕД удалением источника, а не вместе с ним.

### Ленивая миграция (promote-on-read)

Годится, когда блокирующая массовая миграция недопустима: читаем с текущего диска записи, при
расхождении с целевым — копируем, верифицируем, транзакционно обновляем строку, источник помечаем
на отложенную уборку, НЕ удаляем сразу. Против гонки одновременных промоутов — блокировка строки
или атомарный CAS-апдейт (`update … where disk = :old and path = :old_path`). Цена: первое чтение
холодного объекта платит стоимость миграции — не годится для латентно-чувствительных путей.

### Backfill-команда

Resumable by design: выбирать кандидатов (`disk <> :target` или `migrated_at is null`), чанками,
каждая строка идемпотентна — повторный запуск пропускает уже проверенное и чинит незавершённое.
Алгоритм на строку: заявить/заблокировать → если цель уже совпадает и хэш сходится, пропустить →
если объект на приёмнике есть, хэшировать и сравнить → копировать потоком (не читая файл целиком
в память) → сравнить sha256 обеих сторон → обновить БД ТОЛЬКО после успешной верификации →
источник пометить на отложенное удаление. Колонки состояния миграции (`migration_status`,
`migration_attempted_at`, `migration_error`, `migration_run_id`, `migrated_at`) фреймворком не
требуются, но именно они дают перезапуск и наблюдаемость.

### Названные ошибки (pitfalls)

- **ETag как доказательство целостности** — не работает для multipart, разных схем шифрования и
  провайдер-специфичных реализаций; нужна контрольная сумма.
- **Дрейф метаданных** — копирование без `content-type`, `cache-control`, `content-disposition`,
  пользовательских метаданных, ACL/SSE/класса хранения ломает выдачу файлов downstream.
- **Горячие записи во время backfill** — если источник остаётся writable, нужен либо dual-write,
  либо финальная дельта-синхронизация перед cutover, иначе поздние изменения теряются.
- **Троттлинг и retry-штормы** на массовом копировании — нужен контроль конкурентности и backoff.
- **Расхождение прав** — приёмник принимает копию, но чтение падает на IAM/bucket policy/KMS.
- **Версионирование и lifecycle** — delete-маркеры и noncurrent-версии делают источник «полным»
  при фактически скрытых объектах.
- **Подписанные URL** не переживают cutover; клиенты, кэширующие URL, продолжают падать.
- **Кэши приложения** (CDN, очереди, воркеры) держат ссылки на старый бакет дольше веб-слоя.
- Со стороны Laravel: строка БД может пережить имя диска в конфиге; отсюда — стабильные логические
  псевдонимы и телеметрия на промахи объекта, несовпадения хэша и неудачные промоуты.

**Вердикт для P6:** приём, применённый в проекте один раз (`prc_document_representations.disk`,
`null` = диск по конфигу), совпадает с рекомендованной формой ЧАСТИЧНО: место чтения при `null`
по-прежнему выводится из «текущего конфига» — ровно то, что источник называет ошибкой. Отсюда
инвариант P6: перед сменой конфиг-ключа `null` обязан быть материализован в фактическое имя диска
(`plan.md` D51).

## §7. Как ФАКТИЧЕСКИ снять метрики, которыми решается OQ-1 (вход P7.2, P7.4)

**Запрос (2026-07-31, `perplexity-web/search_advanced`, web):** PostgreSQL 17 — как измерить
bloat % и dead tuples (`pgstattuple` vs оценка по `pg_stat_user_tables`), скорость генерации WAL
(`pg_current_wal_lsn` дельта, `pg_stat_wal`), lock contention и wait events (`pg_stat_activity`,
`pg_locks`), неиспользуемые индексы (`pg_stat_user_indexes.idx_scan`), размеры таблиц/индексов,
отставание autovacuum; что требует `pg_stat_statements` и что невозможно снять без физической
реплики.

**Что подтвердилось:**

- **Bloat.** Строгое значение даёт только расширение `pgstattuple`
  (`CREATE EXTENSION IF NOT EXISTS pgstattuple` — обычное расширение, рестарт НЕ нужен):
  `table_len` / `tuple_len` / `dead_tuple_len` → `dead_pct`. Оценка по
  `pg_stat_user_tables.n_dead_tup / (n_live_tup + n_dead_tup)` — **косвенный сигнал доли мёртвых
  строк, а не bloat**; подавать её как «bloat %» нельзя.
- **Отставание autovacuum.** `pg_stat_user_tables`: `n_dead_tup`, `last_autovacuum`,
  `last_autoanalyze`, `autovacuum_count`, `n_mod_since_analyze`.
- **WAL.** Скорость — ТОЛЬКО дельта между двумя точками:
  `SELECT pg_current_wal_lsn(), clock_timestamp()` в t0 и
  `pg_wal_lsn_diff(pg_current_wal_lsn(), '<lsn_t0>') / elapsed_s` в t1; альтернатива —
  накопительные счётчики `pg_stat_wal` (`wal_records`, `wal_fpi`, `wal_bytes`, `stats_reset`).
  Одиночное значение интерпретировать нельзя.
- **Contention.** `pg_stat_activity` (`wait_event_type`, `wait_event`, `pg_blocking_pids(pid)`) и
  `pg_locks` — **моментальный снимок**: длительность ожиданий по одному запросу из них не
  восстанавливается, нужна серия сэмплов или логирование lock waits.
- **Индексы.** `pg_stat_user_indexes.idx_scan` — фильтр кандидатов на удаление, читается вместе с
  `pg_relation_size(indexrelid)` и **обязательно с `stats_reset`**: «0 за период» и «0 с момента
  reset» — разные утверждения.
- **Размеры.** `pg_total_relation_size` / `pg_relation_size` / `pg_indexes_size`; для решения
  важнее ПРИРОСТ за окно, чем абсолют.
- **`pg_stat_statements`.** Только он даёт per-query `calls`, `total_exec_time`, `wal_bytes`,
  `shared_blks_*`, `plans` — то есть ответ «какой запрос создаёт write pressure и contention».
  Требует `shared_preload_libraries = 'pg_stat_statements'` → **рестарт кластера**;
  `track_planning` по умолчанию выключен. Без него доступны только агрегаты уровня таблиц.
- **Replica lag.** На одиночном primary **не измеряется в принципе** — нужен реально
  применяющий WAL standby. На primary измеряется только объём и интенсивность генерации WAL.

**Что это меняет для Agelto:**

Два критерия §1 на смоук-прогоне P4.7 **структурно неизмеримы**: replica lag (реплики нет) и
per-query contention/write pressure (`pg_stat_statements` в проекте отсутствует, разведка §13).
Остальные — измеримы штатными представлениями, причём часть (bloat, dead tuples, размеры,
`idx_scan`) считывается ПОСЛЕ прогона из каталога, а часть (WAL-скорость, wait events) только
ВО ВРЕМЯ прогона дельтой/сэмплами. Отсюда правило P7.2: метрику, которую нельзя снять
постфактум и которой нет в `findings/P4-load-baseline.md`, item **не реконструирует**, а называет
неснятой. И отсюда же P7.4: инструментовка (`pg_stat_statements` + `pgstattuple` + параметры
Postgres) окупается на следующем окне прогона, а не задним числом.

**Источники:** postgresql.org/docs/current/pgstatstatements.html ·
postgresql.org/docs/current/monitoring-stats.html · postgresql.org/docs/current/pgstattuple.html

## §8. Чеклист ревизии схемы PostgreSQL 17 перед продом (вход P7.1, P7.5)

**Запрос (2026-07-31, `perplexity-web/search_advanced`, web):** приоритезированный чеклист ревизии
схемы — FK-колонки без индекса, выбор `ON DELETE`, точности `numeric` для денег и количеств,
политика `NOT NULL`, ограничения RANGE-партиционирования, `CREATE INDEX CONCURRENTLY` и опасные
`ALTER TABLE` на данных, `jsonb`-мешки vs выделенные колонки; диагностические SQL.

**Что подтвердилось (в порядке приоритета источника):**

- **P0. FK-колонка без индекса** — самый частый источник внезапно дорогих `DELETE`/`UPDATE` по
  родителю: проверка дочерних строк без индекса вырождается в seq scan. Индекс на FK не нужен для
  целостности, но нужен для скорости проверок и каскадов; составной FK — индекс с ТЕХ ЖЕ ведущих
  колонок. Диагностика — джойн `pg_constraint (contype='f')` × `pg_index` по совпадению ведущих
  колонок.
- **P0. Семантика `ON DELETE`.** `NO ACTION` — дефолт, проверка может быть отложена у deferred
  constraint; `RESTRICT` — немедленный запрет без отложенности; `CASCADE` — автоудаление детей.
  Правило ревизии: связь обязана быть ОСОЗНАННОЙ, «оставили дефолт» — находка. Диагностика —
  `pg_constraint.confdeltype` (`a`/`r`/`c`/`n`/`d`).
- **P0. Точности `numeric`.** `numeric` = `decimal`, точный тип, для денег предпочтителен.
  Главный риск — РАЗНЫЕ `precision/scale` для ОДНОГО доменного понятия в одной схеме: неявные
  округления, потеря масштаба, тихие ошибки в вычислениях. Диагностика — группировка
  `information_schema.columns` по `column_name` с `COUNT(DISTINCT precision/scale) > 1`.
- **P1. Миграции без длительной блокировки.** Обычный `CREATE INDEX` блокирует запись;
  `CREATE INDEX CONCURRENTLY` — не блокирует, но дольше и при сбое оставляет **invalid index**
  (диагностика — `pg_index WHERE NOT indisvalid OR NOT indisready`). Часть `ALTER TABLE` берёт
  `AccessExclusiveLock` надолго — проверять отдельно по таблицам с данными.
- **P1. RANGE-партиционирование.** `UNIQUE`/`PRIMARY KEY` партиционированной таблицы **обязан
  включать ключ партиционирования** (типичная ловушка: хочется PK на `id`, приходится `(id, дата)`);
  FK НА партиционированную таблицу упирается в ту же уникальность. Диагностика —
  `pg_get_partkeydef` + сверка `conkey` ограничений с ключом партиционирования.
- **P2. `NOT NULL` и дефолты.** Обязательность, вынесенная в приложение, копит полупустые строки;
  `DEFAULT 0`/`DEFAULT ''` «везде подряд» маскирует отсутствие данных — потом не отличить
  «реально ноль» от «не заполняли».
- **P2. `jsonb` vs колонки.** `jsonb` уместен для редких, слабо структурированных, эволюционирующих
  атрибутов; для горячих бизнес-полей — хуже статистика, дороже фильтрация, TOAST-эффекты. Часто
  фильтруется/сортируется/джойнится → отдельная колонка либо generated-колонка/expression-индекс.

**Что это меняет для Agelto:**

Чеклист становится ФИКСИРОВАННЫМ порядком ревизии P7.1 (и критерием severity, D60), а не свободным
осмотром: сначала FK-без-индекса и `ON DELETE`, затем разъезд точностей, затем партиционирование,
затем миграционная безопасность, затем гигиена (`NOT NULL`, `jsonb`). Разведка §13 уже показывает
попадания по каждому из первых трёх пунктов, включая единственную точность-одиночку
`prc_items.quantity decimal(15,3)` против `decimal(18,6)` у сметных количеств и 28 FK без явного
`onDelete` при нуле `restrictOnDelete`.
