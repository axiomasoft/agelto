# P2 — Диагноз блокера гидрации: OOM `TextGridRenderer` на `EST-XLS-KS2-001` (2026-08-01)

Слой 1 (raw). Диагноз и репро блокера, поднятого эскалацией `plan-run P2.2` 2026-08-01.
Потребляет: P2 (item P2.8 — фикс; P2.2 — гидрация после фикса).

Все числа сняты на дереве `4c3ed4e` в контейнере `agelto_app`; каждая команда приведена целиком и
воспроизводима как есть. Диагноз **repo-grounded** — внешних фактов в нём нет, RAG-ступень не
применялась.

## 1. Что падало

`estimate:gold:import --prepare` → `DocumentPreparer::prepare()` → `SpreadsheetStrategy::process()`
→ `storeTextGrid()` → `TextGridRenderer::render()` → `emptyColumns()`/`cellText()`:

```text
PHP Fatal error: Allowed memory size of 1073741824 bytes exhausted
```

Лимит — жёсткий `ini_set('memory_limit', '1024M')` в `GoldImportCommand.php:47`. Падение
детерминированно и привязано к ОДНОМУ документу корпуса: `EST-XLS-KS2-001`
(`estimates/files/Выполнение 2019.04 АКТ КС-2 01-01-001.xls`, 426 496 байт, легаси BIFF `.xls`,
`tune`-сплит, один из ШЕСТИ обязательных gold-эталонов). После краха процесс останавливается —
оставшиеся коды `--prepare` не обрабатывает, поэтому блокируется гидрация ВСЕГО корпуса.

## 2. Корневая причина — материализация отсутствующих ячеек

`Worksheet::getCell()` **создаёт** объект ячейки, если координаты нет в коллекции — это не
геттер-читатель:

```php
// vendor/phpoffice/phpspreadsheet/src/PhpSpreadsheet/Worksheet/Worksheet.php:1185-1202
public function getCell(CellAddress|string|array $coordinate): Cell
{
    …
    return $cell ?? $sheet->createNewCell($finalCoordinate);
}
```

`TextGridRenderer` обходит лист ПЛОТНО — `emptyColumns()` (`TextGridRenderer.php:149-169`) гоняет
вложенный цикл `1..highestColumn` × `1..highestRow`, вызывая `cellText()`
(`TextGridRenderer.php:133-143`), а тот — `getCell()`. То есть на каждую координату
прямоугольника used-range создаётся объект `Cell`, даже если ячейки в файле нет.

Замер на проблемном файле:

```bash
docker exec agelto_app php -d memory_limit=1024M -r '
require "/var/www/html/vendor/autoload.php";
$ss = (new PhpOffice\PhpSpreadsheet\Reader\Xls)->load("/var/www/html/estimates/files/Выполнение 2019.04 АКТ КС-2 01-01-001.xls");
$s = $ss->getActiveSheet();
echo "highestRow=", $s->getHighestRow(), " highestCol=", $s->getHighestColumn(), PHP_EOL;
echo "existing cells=", count($s->getCellCollection()->getCoordinates()), PHP_EOL;'
```

| Величина | Значение |
|:--|:--|
| `getHighestRow()` | 9 679 |
| `getHighestColumn()` | `IW` (индекс 257) |
| Координат в плотном обходе (`257 × 9679`) | **2 487 503** |
| Реально существующих ячеек в коллекции | **29 464** |
| Реальный максимум колонки среди существующих ячеек | **8** |
| Память после `load()` (до обхода) | 30 МБ |

Разрыв — **84×**. Колонки 9…257 в файле ПУСТЫ (раздутый used range — типовая примета легаси
`.xls`), но плотный обход материализует их целиком: ≈2.46 млн лишних объектов `Cell` при лимите
1 ГБ. Расход не зависит от содержимого документа — только от произведения границ used-range.

**Ключевой вывод:** это не «тяжёлый документ» и не «нехватка лимита» — это квадратичный обход с
побочным эффектом создания. Подъём `memory_limit` сам по себе блок не снимает надёжно (нужен
объём под 2.46 млн объектов), а на документе с большим used-range упадёт снова при любом лимите.

## 3. Size-gate этот класс не ловит

`TextGridRenderer::countRows()` (`:171-177`) и `SpreadsheetStrategy::withinToolLimits()` (`:96-106`)
считают строки через `listWorksheetInfo()` — метаданные листа без загрузки. Для этого `.xls`
ридер отдаёт:

```bash
docker exec agelto_app php -r '
require "/var/www/html/vendor/autoload.php";
foreach ((new PhpOffice\PhpSpreadsheet\Reader\Xls)->listWorksheetInfo("/var/www/html/estimates/files/Выполнение 2019.04 АКТ КС-2 01-01-001.xls") as $i)
  echo $i["worksheetName"], " rows=", $i["totalRows"], " cols=", $i["totalColumns"], PHP_EOL;'
```

→ `rows=100 cols=8` — против фактических `9679 × 257` после загрузки.

То есть на легаси `.xls` дешёвый гейт **слеп**: 100 строк проходят порог `xlsx_max_rows` (20 000) с
запасом в 200×, а обход после загрузки идёт по 9 679 строкам и 257 колонкам. Гейт по МБ тоже
пропускает — файл 426 КБ при пороге 25 МБ. Ни один существующий предохранитель не стоит на
величине, которая реально определяет расход.

## 4. Прототип разреженного обхода — замер

Обход только существующих координат (`getCellCollection()->getCoordinates()`), затем наложение
merge-диапазонов поверх собранной карты значений; формат вывода не менялся:

```bash
# полный текст прототипа — в Implementation Rules item'а P2.8; здесь только результат
docker exec agelto_app php -d memory_limit=512M -r '…прототип…'
```

| Величина | Плотный обход (сегодня) | Разреженный (прототип) |
|:--|:--|:--|
| Итераций по координатам | 2 487 503 | 29 464 |
| Память | OOM при 1024 МБ | **peak 32 МБ** |
| Время | не завершается | **0.15 с** |
| Результат | — | 88 строк, 11 165 байт текста |

Первые строки вывода прототипа (`## SHEET:` + `row_index`-якорь + повтор merge — формат D3
соблюдён):

```text
## SHEET: Акт приемки выполненных работ
1						Унифицированная форма № КС-2
4							Код
5					Форма по ОКУД	322005	322005	322005
```

Строка 5 показывает работающий повтор merge (`322005` трижды), строки 2–3 присутствуют в полном
выводе, строка с пропуском `row_index` подтверждает, что якорь не пересчитывается.

## 5. Эквивалентность вывода (почему фикс не меняет предмет измерения)

Текущий `cellText()` для координаты вне merge-диапазона и без ячейки в коллекции возвращает `''`
(созданная пустая ячейка → `getCalculatedValue() === null` → `stringify()` → `''`). Значит плотный
обход и разреженный дают ОДИН И ТОТ ЖЕ вывод при трёх условиях:

1. значения существующих ячеек берутся тем же `getCalculatedValue()`;
2. merge накладывается ПОСЛЕ сбора и ПЕРЕЗАПИСЫВАЕТ ячейки диапазона значением якоря — включая
   случай **пустого якоря**: сегодня непустая неякорная ячейка внутри merge-диапазона тоже
   рендерится как `''`, потому что `cellText()` всегда читает якорь;
3. набор непустых колонок и набор непустых строк выводится из той же карты значений.

Пункт 2 — единственное место, где наивная реализация разошлась бы с текущим поведением.

## 6. Что НЕ является причиной (проверено и отброшено)

- **Раздутая merge-карта.** `buildMergeMap()` разворачивает диапазоны в карту координат и на
  патологическом merge (лист целиком) сам съел бы память. На этом файле — 36 диапазонов, 136
  координат суммарно, ни одного крупнее 1000 ячеек. К падению отношения не имеет, но как класс
  риска остаётся (см. бюджет ячеек в ТЗ P2.8).
- **Накопление памяти между документами.** Изолированный прогон
  `--code=EST-XLS-KS2-001 --prepare` падает немедленно (эскалация `plan-run`, воспроизведено
  дважды) — крах привязан к самому документу.
- **`EST-XLSX-KS2-001` из `config/ai.php:479`** (token-limit харнесса `pdf_alt`) — ДРУГОЙ код
  (лишний `X`), к делу не относится.
- **`fixtures:import`.** Прошёл чисто, 24/24, 0 отклонено — проблема строго в `--prepare`.

## 7. Второй документ в статусе `downloaded`

На момент остановки в `downloaded` (не `prepared`) висели два документа: id 8 `EST-XLS-KS2-001`
(предмет этого диагноза) и id 7 `EST-PDF-SCAN-001`. Второй в число ШЕСТИ обязательных
gold-эталонов **не входит** — его запись манифеста несёт `gold_path: null` (132-МБ скан-PDF на 86
страниц без текстового слоя, единственный представитель оконного пути). Его статус блокером
baseline'а не является; отдельного вердикта этот заход по нему не выносит.

## 8. Фикс (P2.8) — результат

Числа сняты на дереве `b51ce3a` (item-коммит кода/тестов P2.8; findings-коммит идёт следующим,
диффа кода после `b51ce3a` больше нет).

passed (21 assertions)** — семь исходных кейсов не менялись байт-в-байт, три новых присутствуют.
`docker exec agelto_app php artisan test --no-tia --filter=RepresentationContract` → **11 passed
(22 assertions)**, без изменений.

**Регрессионный кейс краснел до фикса — факт проверен.** До правки (код возвращён к дереву `HEAD`
до `b51ce3a` через `git stash`) прогон
`docker exec agelto_app php artisan test --no-tia --filter="регрессия разреженности"` завершился
**exit 255, без вывода сводки тестов** — тот же класс краха, что в §1 (немой OOM: `display_errors`
выключен в CLI SAPI контейнера, поэтому даже `error_log=/dev/stderr` не даёт видимого текста —
подтверждено отдельным репро `php -d memory_limit=16M -r '…'`, который печатает `PHP Fatal error:
Allowed memory size…` при включённом выводе). После восстановления фикса (`git stash pop`) тот же
`--filter` даёт **1 passed за 0.02 с** — детерминированно, без специального терпения к таймауту.

**Сверка эквивалентности.** На момент item'а в БД **0 представлений** `kind=text_grid`
(`docker exec agelto_app php artisan tinker --execute="echo DB::table('prc_document_representations')->where('kind','text_grid')->count();"`
→ `0`) — крах §1 останавливал `--prepare` ДО того, как хоть одно такое представление
сохранилось для xlsx/xls документов корпуса. Сверка вакуальна: **0 сверено, 0 совпало,
расхождений нет** — самостоятельного вывода о байт-в-байт эквивалентности на реальных
представлениях этот заход дать не может за отсутствием предмета сравнения; первое реальное
представление корпуса создаёт следующий пункт (боевое репро) и оно СТАНЕТ материалом для
будущей сверки P2.2.

**Боевое репро.** До прогона: документ id 8 (`EST-XLS-KS2-001`) — статус `downloaded`,
`text_grid`-представлений `0`. Команда
`docker exec agelto_app php artisan estimate:gold:import --code=EST-XLS-KS2-001 --prepare` →
`Готово: документов 0 · версий 0 · записей extraction 1 · записей screening 1 · отклонено 0 ·
unprocessable 0.`, **без fatal error**. После прогона: `text_grid`-представлений **1** (было 0) —
`document_version_id=8`, `size_bytes=11165`, `meta={"rows":88,"tool":"phpspreadsheet","sheets":1}`
— число строк и байт **совпадает день-в-день** с замером прототипа §4 («88 строк, 11 165 байт
текста»), что подтверждает: фикс на боевом документе даёт ТОТ ЖЕ результат, что и измеренный
прототип диагноза.

**Известное отклонение от буквы Validation (не дефект диффа P2.8).** Статус документа id 8 ПОСЛЕ
прогона остался `downloaded` (не изменился) — `last_error` пуст, документ не стал
`unprocessable`, крах не повторился, но и в `prepared` он не перешёл. Причина — код-грепом
подтверждённый факт, НЕ затронутый диффом этого item'а: единственное место, где код проставляет
`DocumentStatus::Prepared`, — `App\Jobs\Procurement\PrepareDocumentJob.php:83`;
`GoldImportCommand` вызывает `DocumentPreparer::prepare()` НАПРЯМУЮ (`GoldImportCommand.php:75`),
минуя этот Job, а `DocumentPreparer::prepare()` (см. его доккомментарий) сам статус меняет ТОЛЬКО
на терминальной ветке `Unprocessable` — переход в `Prepared` в этом вызывающем пути архитектурно
не производится ни до, ни после P2.8. Это предсуществующее поведение команды (Scope Excluded
этого item'а — статус/гидрация принадлежат P2.2), никак не зависящее от разреженности обхода.

`phases/P2.md`.
