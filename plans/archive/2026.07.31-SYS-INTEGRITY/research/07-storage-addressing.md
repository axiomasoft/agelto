## 1. Критерий D50, операционализированный

D50 задаёт критерий словами: колонка нужна ⟺ «(а) запись в БД адресует файл И (б) файл живёт
дольше окна отката смены провайдера». В таком виде он не решает ни одного спорного случая: окно
отката — недели, а самый короткоживущий блоб проекта живёт 90 дней (`ai/llm-calls/`, слой 1 §6),
то есть (б) выполняется у ВСЕХ семи носителей и критерий вырождается в «колонка нужна везде».
Работающий разделитель лежит не в словах критерия, а в его собственном обосновании (D50: «две
таблицы ПАРТИЦИОНИРОВАНЫ… ради артефактов, которые чистит retention»).

Поэтому критерий применяется в проверяемой форме — два вопроса и одна цена:

> **В1. Адресует ли ЗАПИСЬ файл?** У носителя есть колонка с путём И живой писатель, который её
> заполняет. Адрес, выводимый конвенцией (путь из хэша), аргументом команды или флагом, — не
> запись; колонку вешать не на что.
>
> **В2. Могут ли строки ОДНОГО носителя одновременно указывать в РАЗНЫЕ поколения диска?**
> Это и есть смысл «переживает окно отката»: пара «строка + файл» должна дожить до момента,
> когда у носителя появится второе поколение. Носитель, чья строка или чей файл гарантированно
> умирает раньше (retention партиции, ILM-правило), второго поколения не увидит.
>
> **Колонка нужна ⟺ В1 ∧ В2.**
>
> **Цена (не свойство).** Если носитель партиционирован и создан сырым SQL, колонка требует
> правки партиционированной схемы. Цена не отменяет вердикт сама по себе — она называется
> отдельной строкой рядом с ним, чтобы вердикт «не нужна» не выглядел следствием лени.

Такая форма даёт разные ответы на разных носителях (проверка на невырожденность: три «нужна»,
пять «не нужна») и воспроизводима третьим лицом по фактам слоя 1.

## 3. Проект колонки и правил её заполнения

**Форма.** По прецеденту `100055:33`: `$table->text('<имя>')->nullable()->comment('<null = диск
по config(<ТОЧНЫЙ ключ>)>')`. Без `default`, без индекса, без enum и без ссылки на справочник.

| Таблица | Имя колонки | Конфиг-ключ в комментарии |
|:--|:--|:--|
| `prc_document_versions` | `disk` | `crawler.documents_disk` |
| `prc_ai_fixtures` | `disk` | `ai.fixtures.disk` |
| `prc_estimates` | `raw_result_disk` | `crawler.raw_disk` |

Имя `raw_result_disk`, а не `disk`: колонка пути на этой таблице называется `raw_result_ref`,
и одинокий `disk` на таблице сметы читался бы как «диск сметы», которого не существует. Пара
«путь + его диск» обязана читаться как пара.

**Почему без `default`.** Дефолт замаскировал бы «писатель не записал диск»: строка выглядела
бы корректной, а диагностика P6.3 (`disk IS NULL` у новой записи = дефект писателя) исчезла бы.

**Почему без индекса.** Селективность нулевая до появления второго поколения; единственный
потребитель — команда backfill, которая идёт чанками по первичному ключу.

**Правила заполнения (инвариант D51).**

1. **Новая запись пишет ФАКТИЧЕСКОЕ имя диска — всегда.** `null` у новой записи — дефект
   писателя, а не «фолбэк сработает».
2. **`null` — исключительно историческая семантика:** «диск по конфиг-ключу НА МОМЕНТ ЧТЕНИЯ».
   Это значение НЕ переживает смену конфига, поэтому оно обязано быть материализовано до неё.
3. **Имя берётся из ключа, адресующего ИМЕННО этот носитель.** У эталонов — `ai.fixtures.disk`,
   не «диск документов». Универсальный «диск документов» в комментарии колонки эталонов — ложь.

## 4. Контракт резолвера адреса

### 4.1 `FileLocation` — объект-значение

```php
namespace App\Services\Storage;

final readonly class FileLocation
{
    public function __construct(
        public string $disk,
        public string $path,
    ) {}
}
```

Ничего больше. `exists()`, `get()`, `url()` в нём НЕ заводятся: VO с файловыми операциями
превращается в фасад Flysystem, а именно от фасада эта фаза и уходит.

### 4.2 `FileLocationResolver` — сигнатуры

```php
namespace App\Services\Storage;

final readonly class FileLocationResolver
{
    // ЧТЕНИЕ: «по записи дай диск и путь». Метод на класс носителя — полиморфизм через
    // сигнатуру, без `resolve(mixed $record)` со `match` по типу.
    public function forDocumentVersion(DocumentVersion $version): FileLocation;
    public function forRepresentation(DocumentRepresentation $representation): FileLocation;
    public function forFixture(Fixture $fixture): FileLocation;

    // ЗАПИСЬ: «на какой диск класть НОВЫЙ объект этого носителя» — единственный легальный
    // читатель конфиг-ключей диска в проекте (гейт-тест ниже).
    public function currentDocumentsDisk(): string;   // config('crawler.documents_disk')
    public function currentFixturesDisk(): string;    // config('ai.fixtures.disk')
    public function currentRawDisk(): string;         // config('crawler.raw_disk')
}
```

Каждый read-метод возвращает `new FileLocation(disk: $record-><колонка диска> ?? $this-><ключ
носителя>(), path: $record-><колонка пути>)`. Фолбэк на конфиг при `null` сохраняется — его
снимает не код, а материализация P6.5.

**Метода `forEstimateRawResult()` НЕ существует.** У `prc_estimates.raw_result_ref` нет
читателя в дереве (слой 1 §3.3): P6.2 заводит колонку, P6.3 учит писателя писать имя через
`currentRawDisk()`, а метод чтения появится вместе с первым читателем. Резолвер не растёт под
гипотетического потребителя.

### 4.3 Что резолвер НЕ делает

- **Не оборачивает файловые операции.** `get`/`put`/`delete`/`readStream`/`writeStream`
  вызываются на call-site'е: `Storage::disk($location->disk)->get($location->path)`. Резолвер
  отвечает на вопрос «где», а не «как прочитать».
- **Не проверяет существование публично.** `exists()` нужен автомату фолбэка (§5) и живёт там
  приватным методом. Публичный `exists()` на резолвере — первый шаг к фасаду.
- **Не выдаёт временных URL.** `temporaryUrl()` — операция диска, вызывается на call-site'е.
  Отдельно: подписанные URL смену провайдера не переживают (`rag` §6, pitfalls) — это факт для
  runbook'а, а не повод заводить метод.
- **Не кэширует.** Запись уже в памяти; кэш дал бы рассинхрон сразу после backfill'а.
- **Не пишет и не копирует.** Резолвер read-only относительно хранилища.

### 4.4 Стык с существующим `RepresentationResolver`

`RepresentationResolver::forLlm()` (`app/Services/Procurement/Prepare/`) остаётся на месте и
сохраняет внешнюю форму `array{storagePath, disk, extension, mime}` — переписывать четырёх
потребителей (`ExtractionOrchestrator:109`, `ScreeningProcessor:87`, `RerunRangeAction:173`,
`FormatBenchRunner:199`) эта фаза не обязана. Меняется ТОЛЬКО источник диска внутри: вместо
`config('crawler.documents_disk')` (`:33`) и двух `?? $documentsDisk` (`:44`, `:56`) — вызовы
`FileLocationResolver::forRepresentation()`/`forDocumentVersion()`.

**Пятый потребитель, найденный слоем 1 (§3.4):** `DatasetInputBuilder:95` повторяет фолбэк
`$representation->disk ?? config('crawler.documents_disk')` В ОБХОД `RepresentationResolver`.
Он переводится на `FileLocationResolver::forRepresentation()` в том же item'е — иначе гейт-тест
либо покраснеет на нём, либо будет ложно-зелёным из-за записи в allowlist.

### 4.5 Гейт-тест (P6.3)

Запрещает прямое чтение конфиг-ключей `crawler.documents_disk`, `ai.fixtures.disk`,
`crawler.raw_disk` вне `app/Services/Storage/**`.

- Форма — Finder/grep по дереву (тот же приём, что `DomainLayoutTest`), не `pest-plugin-arch`:
  предмет проверки — строка вызова, а не граф `uses`.
- Allowlist — **поимённый, со строкой-причиной на каждый файл**. Легальные исключения на
  сегодня: `LlmCallRecorder`, `LlmPayloadReader`, `CsvBlockIngestor`, `CsvSourceMethod`,
  `DatasetExportCommand` — все обслуживают носители с вердиктом «колонка не нужна» (§2), их
  адресация конфигом законна.
- **Обязательна проверка на ложно-зелёный:** временно вернуть
  `Storage::disk((string) config('crawler.documents_disk'))` в `RepresentationResolver` и
  убедиться, что гейт КРАСНЕЕТ; факт проверки — в Completion Notes P6.3 (форма гейта в проекте
  имеет доказанные ложно-зелёные варианты, §9.6 разведки P3).
- Чинить красный гейт расширением allowlist'а без причины в комментарии — запрещено.

## 5. Автомат фолбэка на окно cutover (P6.4)

**Цепочка — ДАННЫЕ, не ветка в коде.** Конфиг-ключи рядом с существующими, значение — список
логических имён от НОВЫХ поколений к старым, дефолт `[]`:

| Ключ диска | Ключ цепочки |
|:--|:--|
| `crawler.documents_disk` | `crawler.documents_fallback_disks` |
| `ai.fixtures.disk` | `ai.fixtures.fallback_disks` |
| `crawler.raw_disk` | `crawler.raw_fallback_disks` (нужен, если принят D114) |

Пустая цепочка по умолчанию означает: на сегодняшнем дереве поведение не меняется байт-в-байт,
ко второму диску обращения нет вовсе.

**Автомат (чтение одного носителя):**

```
resolve(record) → location(disk_записи, path)
если Storage::disk(location.disk)->exists(path):      # ровно один exists() на диск
    вернуть location
иначе для disk_i в цепочке(носителя):                  # порядок: новые поколения → старые
    если Storage::disk(disk_i)->exists(path):
        log.warning(носитель, id записи, disk_записи, disk_i)   # промах — сигнал владельцу
        вернуть FileLocation(disk_i, path)
вернуть location                                       # нигде нет: адрес записи, ошибку
                                                       # поднимает call-site при чтении
```

Инварианты:

- **Фолбэк срабатывает только на ОТСУТСТВИЕ объекта.** Исключение драйвера (сеть, IAM, KMS) —
  не «нет объекта»: оно пробрасывается. Иначе сетевой сбой S3 молча уводит чтение на чужое
  поколение — а у дисков проекта стоит `'throw' => false`, то есть различать `exists() === false`
  и исключение придётся явно.
- **Проверка существования — `exists()`, без чтения содержимого.**
- **Копирование, запись и обновление строки на пути чтения ЗАПРЕЩЕНЫ** (D52): резолвер
  read-only, promote-on-read не пишется. Синхронное копирование в request-path — названная
  источником причина latency spikes.
- **Промах логируется на уровне `warning`** с носителем, id записи и обоими дисками. Это
  единственный сигнал, по которому владелец решает, можно ли снимать фолбэк; без него шаг
  «снятие фолбэка» в runbook'е делается вслепую.
- Число дисков в цепочке кодом не ограничено, но каждый лишний диск — лишний `exists()` на
  промахе.

## 6. Команда backfill (P6.5)

`storage:disk-backfill <носитель> [--materialize-only] [--to=<disk>] [--from-id=<id>] [--dry-run]`

Носители — только те, у кого есть колонка диска: `document-versions`, `fixtures`,
`estimate-raw-results` (последний — при принятии D114).

### 6.1 Режим материализации (`--materialize-only`)

Объекты НЕ трогает вообще. Для каждой строки с `disk IS NULL` проставляет имя, которое ПРЯМО
СЕЙЧАС вернул бы резолвер для этого носителя (`currentDocumentsDisk()` и т.д.). Отсюда жёсткое
условие: **команда обязана запускаться ДО флипа конфига** — после флипа она проставит новое имя
историческим строкам, чьи объекты лежат на старом диске, и оборвёт адресацию окончательно.
Условие пишется в help-тексте команды и печатается в шапке отчёта.

### 6.2 Режим переноса (`--to=<disk>`) — порядок на строку неизменен

```
для чанка строк по возрастанию первичного ключа, начиная с --from-id:
  для строки:
    location ← резолвер(строка)
    если location.disk == target:
        если sha256(target, path) совпадает с эталоном строки → пропустить («уже перенесена»)
        иначе → пометить расхождением, НЕ трогать
    если объект есть на target:
        сравнить sha256 и размер с эталоном
        совпало → обновить строку (disk ← target); не совпало → пометить расхождением
    иначе:
        скопировать ПОТОКОМ (readStream → writeStream), файл целиком в память не читается
        сравнить sha256 И размер обеих сторон
        совпало → ТОЛЬКО ТЕПЕРЬ обновить строку (disk ← target)
        не совпало → пометить расхождением, строку НЕ обновлять
  напечатать курсор последнего обработанного id
источник НЕ удаляется никогда — уборка отдельная операция после окна отката
```

- **Обновление записи ДО верификации — материальное отклонение**, а не стилистика: строка,
  указывающая на непроверенную копию, хуже строки, указывающей на старый диск.
- **Эталон хэша** берётся из самой записи там, где он есть (`prc_document_versions.content_hash`,
  `prc_ai_fixtures.sha256`); у `prc_estimates.raw_result_ref` колонки хэша нет — эталоном
  служит sha256, посчитанный с ИСТОЧНИКА перед копированием (сравнение источник↔приёмник).
- **ETag доказательством не является** (multipart, разные схемы шифрования, провайдерские
  реализации) — только контрольная сумма.
- **Идемпотентность и возобновление — без колонок состояния.** `migration_status`/`migrated_at`
  не заводятся: возобновление даёт курсор `--from-id`, идемпотентность — контент-адресация и
  сверка хэша. Лишние колонки пережили бы свою задачу.
- **Расхождение хэша не валит прогон:** строка попадает в отчёт, прогон продолжается, итоговый
  код возврата ненулевой.
- **Запрещено:** `--force`, пропускающий верификацию; удаление источника; параллельные воркеры;
  тихое приведение несовпадающего хэша к «ок».

### 6.3 Отчёт

Таблица в stdout + счётчики: обработано / скопировано / пропущено (уже на месте) / расхождений /
курсор для продолжения. JSON не требуется.

## 7. Соглашение об именовании дисков (D53)

> Имя диска в БД — **логическое, стабильное, поколенческое**: `<роль>_v<N>` —
> `documents_v1`, `fixtures_v1`, `raw_v1`. В имени НЕТ драйвера (`s3`, `local`), провайдера
> (`minio`, `aws`), региона (`eu-west-1`) и бакета: инфраструктурное имя в строках превращает
> переименование диска в `filesystems.php` в миграцию ДАННЫХ.

Смена провайдера увеличивает `N` (`documents_v1` → `documents_v2`), а не меняет роль.

**Сегодняшние имена конвенции НЕ соответствуют** и в этом плане не переименовываются (D53):
`s3`, `estimates`, `estimates_s3` (последнее — прямое нарушение: драйвер внутри имени).
Переименование — шаг 0 процедуры cutover (§8), и порядок здесь неочевиден и важен:

> **Переименование обязано пройти ДО материализации `null`, а не после.** Материализация
> записывает в колонки имя, которое конфиг несёт В ТОТ МОМЕНТ. Материализуем при `s3` —
> получаем `s3` в тысячах строк, и последующее переименование ключа в `documents_v1` делает
> ровно то, от чего конвенция защищает: миграцию данных.

Гейт-теста конвенции (P6.6) достаточно в форме: имя, попадающее в колонку диска, входит в
реестр разрешённых логических имён и не матчит запрещённые подстроки (`s3`, `minio`, `aws`,
`bucket`, `-\d`, регионы). Сегодняшние `s3`/`estimates`/`estimates_s3` держатся в реестре
grandfather'ов **со строкой-причиной и датой снятия — шагом 0 cutover'а**; пустой реестр
grandfather'ов = конвенция соблюдена целиком.

## 8. Процедура смены S3-провайдера (источник текста runbook'а P6.6)

**Десять** шагов, а не восемь: скелет P6.6 не учитывал ни шаг 0 (переименование, §7), ни
дельта-синк (шаг 5) — а без него горячие записи, сделанные во время backfill'а, теряются
(`rag` §6, pitfalls). У каждого шага — проверка и точка отката.

| # | Шаг | Проверка | Точка отката |
|:-:|:--|:--|:--|
| 0 | **Переименовать логические имена дисков** в `filesystems.php` на поколенческие (`s3` → `documents_v1`, `estimates` → `fixtures_v1`), синхронно — `config/crawler.php`, `config/ai.php`, `.env.example`, тесты. Бакеты и данные НЕ трогаются: меняется только логическое имя | полный сюит зелёный; `grep` не находит старых имён вне реестра grandfather'ов | откат правки конфигов (данных не касалось) |
| 1 | **Создать приёмник:** бакет, креды/IAM, шифрование, CORS, lifecycle — ДО копирования, чтобы код умел писать в новое место без второй правки схемы | `mc ls` на новом бакете; пробная запись/чтение приложением | удалить бакет |
| 2 | **Материализовать `null`** — `storage:disk-backfill <носитель> --materialize-only` по каждому носителю с колонкой | `SELECT count(*) WHERE disk IS NULL` = 0 на всех трёх носителях | `UPDATE … SET disk = NULL` (значение вычислимо, потерь нет) |
| 3 | **Включить фолбэк-цепочку** — прописать текущее поколение в `*_fallback_disks` | тест фолбэка зелёный; в логах нет промахов (объекты ещё на диске записи) | очистить цепочку |
| 4 | **Backfill с верификацией** — `storage:disk-backfill <носитель> --to=<новый диск>`, чанками, в фоне | нулевой код возврата, ноль расхождений в отчёте; выборочное чтение приложением | строки не обновлялись у нескопированного; уже обновлённые указывают на проверенную копию |
| 5 | **Дельта-синк** — повторить шаг 4 (идемпотентен): забирает объекты, записанные во время шага 4 | второй прогон печатает ноль скопированных | тот же, что у шага 4 |
| 6 | **Флип конфига записи** — `documents_disk`/`fixtures.disk`/`raw_disk` на новое поколение; старое поколение остаётся в `*_fallback_disks` | новые записи получают новое имя диска в колонке; чтение исторических идёт без промахов | вернуть конфиг на прежнее поколение — исторические строки указывают на проверенные копии, читаются обоими путями |
| 7 | **Окно наблюдения** — старый бакет **read-only** и доступен; следим за `warning`-промахами фолбэка и ошибками чтения | промахов нет N дней подряд (N назначает владелец) | вернуть шаг 6 |
| 8 | **Снять фолбэк-цепочку** — очистить `*_fallback_disks` | сюит зелёный; в логах промахов нет | вернуть цепочку |
| 9 | **Уборка источника** — удалить объекты старого бакета | — | **точки отката нет** — поэтому шаг отделён от шага 8 окном наблюдения |

**Инварианты порядка, нарушать которые запрещено:**

- Шаг 0 **до** шага 2 (§7): иначе конвенция имён нарушается данными.
- Шаг 2 **до** шага 6 (D51): флип конфига до материализации обрывает адресацию ВСЕХ исторических
  записей — колонка есть, а строки всё равно рвутся.
- Шаг 8 **до** шага 9 и **не вместе с ним** (`rag` §6, шаг 7 канонического порядка): фолбэк
  снимается ПЕРЕД удалением источника, между ними — окно наблюдения. Слияние шагов 8 и 9
  уничтожает единственную страховку.

**Чеклист ловушек, применимых к проекту** (из `rag` §6, отфильтровано по фактам дерева):

- **ETag не доказательство** — верификация только sha256 + размер (§6.2).
- **Дрейф метаданных** — при копировании сохранять `content-type`; проект пишет объекты без
  пользовательских метаданных и ACL, поэтому остальная часть ловушки не применима.
- **Горячие записи во время backfill** — закрыты шагом 5 (дельта-синк); dual-write не вводится.
- **Троттлинг и retry-штормы** — команда однопоточная и чанковая по построению (§6.2).
- **Расхождение прав** — шаг 1 требует пробного чтения ПРИЛОЖЕНИЕМ, а не только `mc`.
- **Версионирование и lifecycle** — delete-маркеры делают источник «полным» при скрытых
  объектах; проверка полноты идёт по строкам БД, не по листингу бакета.
- **Подписанные URL** cutover не переживают; проект их сегодня не выдаёт — ловушка станет
  применимой, когда появится публичная выдача файлов.
- **Кэши воркеров** — Horizon-воркеры держат конфиг в памяти: после шагов 3, 6 и 8 воркеры
  перезапускаются, иначе фолбэк/флип доедет до них позже веб-слоя.

## 9. «До боевого прогона P4.7» и «после» — это две разные процедуры

Различие обязательно к явной записи (D12): фаза исполняется ДО прогона.

| | **Сейчас (до P4.7)** | **После P4.7** |
|:--|:--|:--|
| Данные | `prc_document_versions` пуста или содержит только рабочие копии эталонов; `prc_ai_fixtures` — курируемый корпус (десятки файлов); `prc_estimates.raw_result_ref` — единицы | тысячи документов закупок, боевые сметы |

| Шаг 2 процедуры (материализация) | пробегает пустую/крошечную таблицу за секунды | полноценный чанковый прогон |

| Цена ошибки | `migrate:fresh` | восстановление из бэкапа |

Отсюда — обязанность фазы: команда backfill и фолбэк пишутся и тестируются СЕЙЧАС, на
`Storage::fake`, пока цена ошибки равна нулю; их первая реальная работа (материализация `null`)
случится всё равно, потому что `null` в колонке представлений уже есть на дереве.

## 11. Факты, названные явно и оставленные вне scope

- **`GoldCorpusBuilder:162` вызывает `Storage::disk($disk)->path(...)`** — метода `path()` у
  S3-драйвера нет. Диск `estimates` имеет драйвер `local`, поэтому gold строится; **перевод
  корпуса эталонов на S3 (`estimates_s3`) сломает построение gold НЕЗАВИСИМО от адресации**.
  Решение о переводе корпуса — вне этого плана (Phase Context P6). Практическое следствие для
  процедуры: шаг 0 переименовывает `estimates` → `fixtures_v1`, оставляя драйвер `local`;
  смена драйвера — отдельная работа с отдельным решением.
- **Диск `estimates_s3` объявлен, но ни одним конфиг-ключом не адресуется** (слой 1 §5): на
  него никто не пишет и не читает. Мёртвое объявление — кандидат на удаление или на роль
  приёмника при cutover корпуса; в этом плане не трогается.
- **`FixtureRegistrar::import()` принимает диск АРГУМЕНТОМ** (слой 1 §7): один и тот же корпус
  технически импортируется на разные диски, и до P6.2 запись об этом не сохраняется. После P6.2
  колонка это фиксирует — отдельного решения не требует.
- **Адрес новых классов (D65):** P3.2/P3.3 закрыты, но `research/04-domain-layout.md` §2.5
  называет исход прямо — сервисы хранилища остаются на технической оси `app/Services/Storage/`
  и инвариантами I1/I3 не судятся. Гейт `DomainLayoutTest` судит четыре слоя
  (`Enums`/`Exceptions`/`Dto`/`Repositories` домена `Procurement`), `App\Services\**` и
  `App\Console\**` в периметр не входят (слой 1 §7). `app/Console/Commands/Storage/` —
  та же техническая ось; адреса из ТЗ P6.3/P6.5 остаются в силе без правки.
