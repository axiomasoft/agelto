## 1. Context

Контур crawling → детальный разбор → пайплайн документов у нас уже работает: есть режимы
прогона (`fresh`/`archive`/`delta`/`backlog`), возобновляемый курсор, единственность прогона
на уровне частичного unique-индекса, пул прокси со скорингом и circuit breaker'ом, вежливая
пауза, анти-дубли job'ов, backoff/dead-letter и наблюдаемость пайплайна
(`findings/repo-recon-2026-08-06.md`). Форматы документов (xls/doc/odf/pdf/скан/архив/gsfx)
и схема сметы с подэлементами тоже закрыты.

План закрывает то, чего в этом контуре НЕТ и что владелец назвал условием выхода на прод:
фильтр по ОКПД2 «как на ЕИС» (нам нужна только стройка `43.*`), пер-профильные и пер-стадийные
настройки обхода с общим бюджетом запросов к площадке, операторское управление прогонами из
админки (запуск/стоп/продолжить + история), режим «только актуальные данные», ежедневный
healthcheck «вёрстка ЕИС не поменялась» с уведомлением, доменное событие «закупка завершена»
как точка подписки для будущей рассылки поставщикам, витрина золотых смет в админке,
схлопывание 81 миграции в компактную схему (прода нет, `migrate:fresh` штатен) и слияние
`docs`/`docs-private` в одно дерево с диаграммами.

Изначальный порядок был жёстким в одном месте: схлопывание схемы (P8) шло после всех
запланированных колонок, документация (P9) — после финального состояния того исполнения.
Post-audit P10 легально правит baseline migrations, потому что прода нет и штатный путь —
`migrate:fresh`; затем P10.7 обязан повторно синхронизировать живые docs. P10 не меняет решений
Swissknifeman/Layout migration: владелец оставил их upstream и заказал только product code.

## 2. Execution Rules

- Один item за раз; статус обновляется В ПЛАНЕ до завершения работы.
- Статусы — 6 канонических строк байт-в-байт (см. `plan-protocol` §5).
- План разошёлся с кодом → не импровизировать, эскалировать (§10 протокола).
- После закрытия item/фазы — перезаписать `plans/archive/2026.08.06-CRAWL-HARDEN/handoff.md`.
- **Проектные правила репозитория обязательны** и приоритетнее общих: `CLAUDE.md`
  (доменная раскладка, канон имён, transaction/jobs policy), `.claude/rules/*`,
  скиллы `testing-rules`, `pest-testing`, `procurement-pipeline-dev`.
- **Тесты — только `test('<интент по-русски>', fn)`**, без `it()`; персистентные модели —
  через фабрики; LLM-вызовы — только `Tests\Support\Doubles\FakeLlmProvider`.
- **Ни одного живого запроса к zakupki.gov.ru из тестов.** Разведка (P1) — отдельный
  ручной прогон, её результат фиксируется файлом-артефактом, а тесты работают по фикстурам.
- **Несущие внешние факты несут RAG-маркер** (`RAG:✅ <дата/суть>` / `RAG:— (repo-grounded: <файл>)`
  / `[UNVERIFIED]`). Параметр ЕИС без подтверждённого замера в код не уезжает.
- **Рост `phpstan-baseline.neon`** сверх легальных рычагов — только с D-записью
  (`.claude/rules/agelto-reviewer-overrides.md`).
- Прода нет: ломающие изменения схемы легальны, `migrate:fresh` — штатный путь.
- **Приёмка полного прогона — ДЕЛЬТА против именованного baseline (D112), а не «зелено»**:
  дерево несёт предсуществующие 18 failed (baseline `8728723e`), к плану отношения не имеющие.
  Публикуются оба числа и Δ; зелено = 0 новых красных, объяснимых диффом item'а. Мера одна на
  весь план — буквальный текст строки «полный прогон — зелено» в `Validation` items читается
  по ней. Тихо ослабить порог по своему усмотрению по-прежнему нельзя (`plan-protocol` §6).
- **Модельный маршрут Codex:** `economy` = `gpt-5.6-luna`, `implementation` =
  `gpt-5.6-terra`, `frontier` = `gpt-5.6-sol`; effort из §3 Routing не меняется. Исторические
  упоминания Claude-моделей в журнале и аудитах — провенанс, не инструкция к запуску.
- **Переходное правило Layout v2:** закрытие пункта фиксируется записью в `journal.jsonl`, находкой или решением при необходимости и регенерацией видов; поля исхода в файле ТЗ запрещены и ловятся линтером. До v2-aware rollout Swissknifeman все P10 items исполняются вручную, без `task:*` и v1 carriers (D131).

Фаза P2 батчей не несёт: items связаны по данным последовательно (карта → фильтр → билдер →
форма), а половина из них — `manual`, то есть общей сессии всё равно не получилось бы.

Фаза P3 батчей не несёт по той же причине: цепочка последовательна по данным (сортировка →
контур исполнения → стоп-условие → кнопки → сиды → витрина), первые три item'а — `manual`, а
`Inputs` каждого следующего ссылаются на `Deliverables` предыдущего (`research/04-p3-runs-design.md`
§7). Три item'а реопена (D111) батча тоже не образуют: P3.8 по данным ждёт P3.7 (его приёмка
«архивный профиль проходит все пять действий» включает «Остановить», которая до P3.7 ничего не
останавливает), а P3.9 хоть и независим, но несовместим с обоими по `Model/effort` и `Exec`
(`implementation/medium · plan-exec` против `implementation/high · manual`) — критерий слияния в
батч (`plan-protocol` §9) не выполняется ни одной парой. Оркестрацию фаза не заявляет по тому же
факту: три item'а есть, но независимость scope не держится (D34 в силе). Item реопена D115
(P3.10) — тоже solo: он единственный открытый в фазе, сливать не с чем.

Фаза P4 батчей не несёт: цепочка начинается с follow-up P4.7 (execution lane), затем идёт
носитель настроек → привязка прокси → авто-дизейбл → бюджет → checkpoint P4.9 → подача пачками →
журналы; семь items из девяти — `manual`, а `Inputs`
каждого следующего ссылаются на `Deliverables` предыдущего (`research/05-p4-reliability-design.md` §6).

Фаза P5 батчей не несёт: носители (P5.1) — вход всех остальных, зонд (P5.2) — вход пассивных проб
(P5.3), вердикты обеих групп проб — вход события (P5.5); четыре item'а из шести — `manual`
(`research/06-p5-health-design.md` §6).

Фаза P6 батчей не несёт: цепочка последовательна по данным (канон статусов → продюсер `Awarded`
→ модуль истории → витрина → событие), четыре item'а из пяти — `manual`, а `Inputs` каждого
следующего ссылаются на `Deliverables` предыдущего (`research/07-p6-history-design.md` §4).

Фаза P7 — единственная в плане, несущая оркестрацию, но её периметр СУЖЕН D100 до P7.1–P7.3.
Исходное обоснование D79 («критерий §7 срабатывает: P7.1, P7.4, P7.5 независимы») столкнулось с
колонкой `Exec`: у P7.4 и P7.5 она `manual`, а канон §9 запрещает исполнять manual-item командой —
запуск через `Workflow({scriptPath})` этот гейт лишь обходит, а не снимает. Поэтому оба среза
выведены из `SLICES` скрипта `workflows/wf-crawl-harden-p7.js` в ручные запуски
(`/task:plan-run <ID> P7.4`, `… P7.5`), а скрипт остаётся носителем автономной цепочки трёх
`plan-exec`-срезов одного тира (`implementation/medium`), связанных по данным: рендер золота
(P7.1) → его потребитель (P7.2) → ссылки на обе страницы (P7.3). Батчей фаза при этом НЕ несёт, и
это не противоречие: критерий слияния в батч (`plan-protocol` §9) требует НИЗКОЙ связности внутри
группы, а у P7.1–P7.3 связность как раз высокая. Оркестрация здесь даёт автономность цепочки, а не
слияние подфаз в одну сессию.

Батч `B1` — три item'а живой разведки (P1.1, P1.2, P1.4) одной сессией: канал (RU-прокси +
контекст с `ignoreHTTPSErrors`) поднимается один раз, порядок внутри батча последовательный,
закрытие КАЖДОГО item'а — полный протокол `plan-protocol` §8. Inputs ни одного из трёх не ждут
Deliverables другого. P1.3 идёт solo: ему нужен не Playwright, а RAG-ступень; P1.5 — тоже solo,
по объёму запросов (см. строку Routing).

Фаза P8 батчей не несёт: цепочка последовательна по данным (ревизия и карта поглощения → закупочный
контур → AI-контур → пост-аудит), а единственная пара, которую формально хотелось бы слить
(P8.2/P8.3 — один тир, один `Exec`, одна глубина ревью), связана как раз сильнее всех остальных:
обе поглощают КРОСС-КОНТУРНЫЕ миграции `…100069`/`…100070`, и удалить их файлы может только тот,
кто забрал последнюю строку (`research/09-p8-schema-design.md` §7).

Батч `B2` — два items P9 (P9.6 и P9.7) одной сессией: связности между ними нет (`Inputs` одного не
ссылаются на `Deliverables` другого — контуры разные), тир, `Exec` и глубина ревью совпадают, а
входное состояние дерева у обоих одно и то же (после P9.5). Закрытие КАЖДОГО — полный протокол
`plan-protocol` §8. Остальные items фазы идут solo: цепочка последовательна по данным (карта →
гейт → слияние → роспуск 00–07 → роспуск 08 → диаграммы → навигация), и три из восьми — `manual`
(`research/10-p9-docs-design.md` §6).

Фаза P10 батчей и оркестрации не несёт: P10.1 создаёт run ownership и PostgreSQL concurrency
probe; P10.2 меняет общий cursor lifecycle; P10.3 переиспользует probe и меняет ingest transaction;
P10.4 потребляет этот ingest event contract; P10.5 касается результата P10.2 и того же
`CsvBlockIngestor`; P10.6 переиспользует lock/probe; P10.7 потребляет всё. Общие baseline
migrations, test DB и mutable carriers исключают независимый fan-out. Все items manual по
Layout-v2 bridge; P10.7 поднят до frontier/xhigh не для реализации, а для независимого финального
adversarial verdict (D131).
