# P4.9 — дизайн control-flow при исчерпании request budget

**Дата:** 2026-08-08
**Сырьё:** `findings/P4.9-budget-checkpoint-control-flow-2026-08-08.md`
**Адресат:** `phases/P4.md` item P4.9

## Целевой контракт

`ArchiveWindowScanner::scan()` возвращает enum `ArchiveWindowScanResult`:

- `Drained` — текущий день и ценовой стек полностью дренированы; только этот исход разрешает
  вызывающей обёртке увеличить `cursor.day`;
- `Checkpointed` — `PlatformBudgetExhaustedException` пойман, курсор остаётся на текущем дне,
  `CrawlerRunManager::recordCheckpoint()` увеличивает наблюдаемый счётчик, статус остаётся
  `Running`;
- `Stopped` — применён операторский pause/cancel; курсор не двигается, фактический статус уже
  записан `RunStopGate`/`CrawlerRunManager`.

`RAG:— (repo-grounded: findings/P4.9-budget-checkpoint-control-flow-2026-08-08.md §Наблюдения 1–4)`

Три вызывающие обёртки используют одно правило: `result !== Drained` означает немедленный выход
без продвижения дня и без `complete()`. Дальнейший носитель зависит от уже существующего entrypoint:
archive продолжает `CrawlRunJob`, delta — следующий cron, backlog — следующий sweep. Новый job,
retry-loop или sleep в обёртках не вводится.

## Разобранные альтернативы

1. **Ловить исключение в каждой из трёх обёрток — отвергнуто.** Это размножает одну семантику
   checkpoint и оставляет четвёртому потребителю возможность снова ошибочно трактовать исход.
2. **Использовать исключение как нормальный сигнал до обёрток — отвергнуто.** В двух местах уже
   есть широкий `catch (Throwable)` с переводом в `Failed`; нормальный control-flow снова зависит
   от порядка catch-блоков.
3. **Вернуть `bool` — отвергнуто.** Двух состояний недостаточно для честной диагностики
   `Checkpointed` против `Stopped`, а расширение bool-контракта потребует ломающей смены сигнатуры.

## Инварианты реализации

- `PlatformBudgetExhaustedException` ловится отдельно; неизвестный `Throwable` не превращается в
  checkpoint и сохраняет текущий failure-path.
- На `Checkpointed` не меняются `cursor.day`, `priceStack`, `blockFrom`, `RunStatus`,
  `last_error` и `finished_at`; меняется только наблюдаемость checkpoint.
- Backlog не пишет `backlog_rescanned_at`, пока окно не дренировано полностью.
- Операторский stop также не продвигает день: новый результат закрывает существующую щель P3.7,
  где проверка статуса выполнялась уже после записи следующего дня.
- `Http::preventStrayRequests()` остаётся глобальным fail-closed guard; запрещено возвращать
  literal URL-grep или разрешать сеть через `allowStrayRequests()`.

## Проверяемые сценарии

1. Budget exhaustion на первом блоке archive оставляет день/ценовой стек без продвижения,
   run — `Running`, checkpoint — записан, `CrawlRunJob` ставит continuation в тот же lane.
2. Delta на exhaustion возвращает `Running` без command failure и продолжает с того же дня на
   следующем cron.
3. Backlog на exhaustion возвращает `processed = 0`, не помечает fresh-run rescanned и
   продолжает с того же дня на следующем sweep.
4. Pause/cancel внутри дня не продвигает курсор.
5. Не-budget исключение по-прежнему приводит archive/backlog к их прежнему failure-path.
6. Shared test bootstrap содержит `Http::preventStrayRequests()`, целевой и полный Pest не
   совершают незамокированных HTTP-запросов.
