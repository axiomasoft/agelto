### P1.5 — Инвентарь вкладок и полей по шести видам процедур

**Intent:** Снять полный инвентарь того, ЧТО вообще бывает в карточке ЕИС: для каждого из шести
типов процедур, которые знает справочник площадки (`ea20`/`zk20`/`ok20`/`ezt20`/`ea615`/`po615`), —
фактический перечень вкладок (включая те, о которых наш справочник не знает) и перечень подписей
полей на каждой вкладке, сверенный с тем, куда мы это кладём сегодня (колонка `prc_procurements`,
доменная таблица, jsonb `attributes` или «носителя нет»).
**Why:** Прямое требование владельца 2026-08-06, дословно приведённое в
`brief/01-refinements.md` (блок P6, п. 5): «в госзакупках есть довольно много вкладок… надо
проанализировать разные виды закупок, чтобы понять максимальный весь объём того, что может быть
внутри… возможно, всплывут данные, которые нужно хранить в базе в каких-то столбцах, а не
динамически». Сегодня наш справочник знает РОВНО четыре вкладки на все шесть типов, и единственная
зафиксированная вариативность — явный `null` у `supplier-results` для `ea615`/`po615`
(«вкладки нет по природе»). `RAG:— (repo-grounded:
database/seeders/Procurement/EisPlatformSeeder.php:83-136;
app/Services/Procurement/Eis/EisCardUrlBuilder.php:45-61)`. Существуют ли вкладки СВЕРХ этих
четырёх и какие поля лежат на них у разных типов процедур — не проверялось ни разу
(`findings/eis-params-carryover.md` §3). Цена незнания несимметрична и уже реализовалась однажды:
парсер `supplier-results` разошёлся с площадкой и МОЛЧА возвращал пустоту, потому что фактуры не
было (`research/07-p6-history-design.md` §2.5). Отдельно инвентарь — единственный честный вход
решения «какие поля заслуживают колонки, а какие остаются в jsonb», которое принимается в P8, где
схема пересобирается: принять его без матрицы — значит гадать, а править схему дважды дороже.
**Scope Included:** (1) отбор кандидатов: по CSV-выгрузке на широком окне дат набрать по ОДНОЙ
закупке на каждый из шести типов процедур (сопоставление «дословный способ определения поставщика →
сегмент URL» берётся из сида, не сочиняется); типы, для которых кандидат не нашёлся, помечаются
исходом `не установлено` с описанием, что искали; (2) по каждому кандидату — фактическая навигация
карточки: перечень ВСЕХ вкладок, которые площадка показывает на странице (текст пункта + href), и
HTTP-код каждой из четырёх вкладок нашего справочника; (3) по каждой доступной вкладке — перечень
ПОДПИСЕЙ полей (`span.section__title` и заголовки таблиц `table.tableBlock`) с признаком типа
значения (`дата`/`сумма`/`строка`/`ссылка`/`таблица`) — БЕЗ самих значений; (4) сверка каждой
подписи с нашим носителем: колонка `prc_procurements`, доменная таблица (`prc_items`,
`prc_protocols`, `prc_awards`, `prc_documents`, …), ключ jsonb `attributes` или `нет носителя`;
(5) фиксация: `artifacts/eis-card-inventory.json` (машинная матрица) + `findings/P1-card-inventory.md`
(разбор: чего нет в справочнике вкладок, какие поля без носителя, какие из них просятся в колонку и
почему). Потолок вежливости item'а — **не более 60 запросов** к zakupki.gov.ru, пауза ≥1.5 с.
**Scope Excluded:** ЛЮБАЯ правка кода, схемы, сида справочника вкладок, фикстур и тестов — item
производит факты, справочник `card_url_templates` правит та фаза, что принимает решение;
РЕШЕНИЕ «какое поле получает колонку, какое остаётся в jsonb» (Q16 — владелец, при детализации P8);
починка парсеров (P6.2 и чужие фазы); сохранение сырого HTML карточек (его снимает P1.4 по одной
success-карточке; здесь нужна СТРУКТУРА, а не разметка); значения полей (только подписи и тип —
поэтому обезличивать нечего); ветки 223-ФЗ и любые типы процедур вне шести известных справочнику;
перебор нескольких карточек одного типа ради статистики.

**Implementation Rules:** 1) **Egress-проверка RU-прокси — ПЕРВЫМ запросом сессии**
(`ipinfo.io/json` → `country: RU`); замер без неё недействителен и переснимается (скилл §1.1).
2) Пауза между запросами ≥1.5 с, потолок 60; потолок достигнут — остаток типов помечается
`не установлено`, а не досниматься «быстренько без пауз». 3) **Снимаются ПОДПИСИ, а не значения**:
в артефакт не попадает ни одного фактического значения поля — только текст подписи и класс типа.
Это и защита от персональных данных (обезличивать нечего), и защита от соблазна «заодно проверить
парсер». 4) Перечень вкладок берётся из НАВИГАЦИИ живой страницы, а не из нашего справочника:
смысл item'а — найти то, чего мы не знаем; сверка со справочником делается ПОСЛЕ и записывается как
расхождение. 5) Каждый тип процедуры несёт метку исхода (`снят` / `не найден кандидат` /
`недоступен`) — «шесть строк в артефакте» без меток исхода не считаются инвентарём. 6) Столбец
«наш носитель» заполняется по ФАКТУ чтения миграции и DTO, а не по памяти; сомнение выражается
значением `неясно`, а не догадкой. 7) Рекомендация «просится в колонку» аргументируется одним
признаком из трёх: по полю фильтруют/сортируют, оно обязательно у всех типов, оно участвует в
доменном правиле; иначе рекомендация — `jsonb`. 8) Ни одного изменённого файла вне `plans/`.
**Code Guidance:** Артефакт — машинно-проверяемый JSON:
`{channel{egress_ip,egress_country,checked_at}, requests_total,
procedure_types[{raw, url_type, reg_number, outcome, tabs[{tab, url, http_status, present,
in_our_catalog}]}], fields[{url_type, tab, label, value_kind, our_carrier, recommendation}]}`.
Проза, разбор и рекомендации живут в `.md`, числа и матрица — в JSON; один факт — один носитель.
