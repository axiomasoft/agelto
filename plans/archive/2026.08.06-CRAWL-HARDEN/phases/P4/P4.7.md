### P4.7 — Длинный execution lane для датированного archive-профиля

**Intent:** Развести стандартный и длинный lease одной `CrawlRunJob` по профилю: обычные
профили сохраняют пятиминутный контур, временный архив 2025 с явными датами автоматически идёт в
часовой `long`-контур и при self-dispatch не возвращается в стандартную очередь.
**Why:** Третий аудит P3 верно обнаружил технический конфликт, но двусмысленно назвал его
«бюджетом длинного обхода». Общий crawl не имеет продуктового/денежного лимита: archive скачивает
CSV-листинг и сохраняет карту, а детальные карточки/сметы разбираются отдельными job. Реальный
дефект уже: `CrawlRunJob` жёстко маршрутизируется в `crawl`, где Horizon завершает job через 300
секунд; archive-процессор не читает fresh-checkpoint 240 секунд и может не вернуться к строке
self-dispatch. Владелец принял P3 `🟠` и выбрал отдельный большой конечный lease для конкретного
датированного профиля (D117). Боевой замер 194 CSV-блоков даёт около 23 минут сетевой части при
текущем throttle, поэтому час — наблюдаемый запас >2×, а не произвольный месяц.

**Scope Included:** (1) enum `App\Enums\Procurement\Crawler\CrawlerExecutionLane` со значениями
`Standard='standard'`, `Long='long'`; (2) миграция `prc_crawlers.execution_lane` — text,
`default('standard')`, индекс не нужен; `Crawler` получает fillable/cast/property; фабрика по

меняется (`retry_after=360`); (4) Horizon supervisor `supervisor-crawl-long`:
`connection=redis_crawl_long`, `queue=['crawl_long']`, `timeout=3600`, `tries=1`,
`maxProcesses=1`, `maxTime=0`, `maxJobs=0`; существующий `supervisor-crawl` остаётся 300 секунд;
(5) значения long параметризуются `.env.example` как `CRAWL_LONG_TIMEOUT=3600` и

`timeout < retry_after`; (6) Docker Horizon `stop_grace_period=4200s` в dev и production default,

из docblock `ArchiveWindowScanner`: дневные обёртки уже перечитывают статус после P3.7; вместо него
честно назвать отсутствие секундного checkpoint у archive; (11) dev/operator docs описывают две
очереди, resume с курсора и калибровку long только по фактической длительности; (12) тесты

**Implementation Rules:** 1) Единственный SSOT выбора — `$crawler->execution_lane`; UI/команды не
передают произвольные connection/queue names. 2) Route-map должна возвращать сразу ПАРУ
connection+queue; запрещено резолвить их двумя независимыми `match`, способными разойтись.
3) `CrawlRunJob` сериализует lane как enum/value и маршрутизируется в constructor ДО dispatch;
self-dispatch обязан явно передать `$this->executionLane`. 4) `redis_crawl_long` копирует все
параметры `redis`, кроме queue/retry_after; использует тот же `REDIS_QUEUE_CONNECTION`.
5) Инварианты отдельны: standard `240 < 300 < 360`; long `3600 < 3900 < 4200`; long не должен
поднимать `retry_after` всех остальных supervisor'ов. 6) **Номер миграции — следующий свободный В
МОМЕНТ исполнения** (D35). `down()` удаляет только колонку. 7) Existing profiles получают
`standard` через DB default; миграция не меняет их пакетно PHP-циклом. 8) `long` не означает
`is_active`/schedule: сид остаётся без cron и не получает новый автозапуск. 9) Документация не
называет час гарантией завершения; это первичная калибровка lease, курсор — гарантия resume.
10) Изменение дефолтов 3600/3900/4200 требует D-записи с фактическим замером.
**Code Guidance:** Enum — строковый и без инфраструктурных секунд. `CrawlQueueRoute` — маленький
immutable VO (`connection`, `queue`) с одним `for(CrawlerExecutionLane)`; допустимо поместить
factory в enum только если connection/queue остаются единственной инфраструктурной обязанностью
enum. В job named arguments сохраняются. Конфиги комментируют две разные цепочки инвариантов, а
не утверждают, что все supervisor'ы делят один retry_after. Form helperText использует
пользовательские слова «время одной job», не «бюджет crawl».
