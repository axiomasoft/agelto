### P5.7 — Ремедиация RED-аудита healthcheck

**Intent:** Закрыть продуктовые находки первого аудита P5 одним атомарным срезом: вернуть полный
зелёный прогон, сделать два пассивных сигнала фактическими, считать сетевые запросы честно и
подчинить ежедневную проверку флагу отключения.
**Why:** Audit P5 воспроизвёл не архитектурный развал, а пять узких дефектов на швах уже готового
контура: stale acceptance после четвёртой пробы, отсутствие limit последних смет, пустой
`key_fields`, счётчик до сетевой границы и неиспользуемый disable-флаг. Они связаны одним
failure scenario — healthcheck либо ложно зелёный, либо продолжает активность после отключения —
и должны пройти общей интеграционной приёмкой. `RAG:— (repo-grounded: этот файл, блок
Audit P5 — 2026-08-08 (заход 1); tests/Feature/Health; app/Services/Procurement/Health)`.
**Scope Included:** (1) команда по умолчанию пишет четыре результата и её тест отражает финальный
состав; (2) `EstimateFieldsCheck` берёт из baseline `min_sample`, сортирует по `updated_at desc` и
анализирует не более этого числа последних смет в окне; (3) versioned baseline перечисляет
доступные поля `DetailAnalysisProcessor` для `common-info`/`documents`/`event-journal`, чтобы
`key_fields_expected > 0` и кейс «якоря есть, все поля пусты» становился плохим; (4)
`ListingFilterCheck.requests_used` равен реально начатым HTTP-попыткам: budget/proxy отказ до HTTP
не увеличивает счёт, connection failure начатого запроса увеличивает; (5) при
`crawler.health.enabled=false` команда не читает baseline, не пишет историю и не ходит в сеть,
расписание не регистрирует healthcheck; (6) тесты на каждый failure scenario; (7) восстановление
карты item→commit и числовых git-якорей P5 в плане/handoff.
**Scope Excluded:** калибровка `0.05/0.20/0.032`; изменение формулы overlap; правка пяти парсеров
вкладок; новый транспорт уведомлений; миграции/схема; P6 и последующие фазы; общая переработка
`CsvSourceMethod`; устранение чужого baseline полного suite.

**Implementation Rules:** 1) Не менять пороги ради зелёного теста; тесты создают данные, на которых
старый код воспроизводимо врёт. 2) `min_sample` — и гейт достаточности, и верхняя граница последних
смет; число читается из baseline, не дублируется в коде. 3) `key_fields` называют только ключи,
которые уже присутствуют в `keyFieldValues` процессора; новый парсинг не добавляется. 4) Счётчик
увеличивается на той границе, где HTTP уже начат: budget/proxy fail = 0 для первого запроса,
`ConnectionException` первого запроса = 1. 5) Disable path fail-closed до чтения baseline и до
любого запроса. 6) Исправление stale assertion на `4` обязательно сопровождается проверкой видов,
а не только числа. `RAG:— (repo-grounded: app/Services/Procurement/Health;
resources/crawler/health/eis-baseline.json; tests/Feature/Health)`.
**Code Guidance:** Сохранить узкие классы и текущие public-контракты. Для limit выделить приватный
ридер порога или переиспользовать типизированную проверку без нового repository. Для request-count
различать pre-request exceptions и `ConnectionException` явно, не вводить callback/глобальный
счётчик. Тесты — `test('<русский intent>', fn)`, данные фабриками, время заморожено штатным Pest
bootstrap. **Анти-самообман:** кейс последних смет содержит старую здоровую и новую сломанную;
без `limit(1)` старый код должен дать другой вердикт. **Анти-подгонка:** не удалять активную пробу
из default command ради возврата числа 3. **if-then:** если точный request-start нельзя выразить
без расширения `CsvSourceMethod`, остановиться и вынести носитель в D-запись; молча назвать
completed call «запросом» нельзя.
