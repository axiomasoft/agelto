# P4.2 — факты дерева под контракт источника расхода (recon, 2026-07-30)

Слой 1 (`plan-protocol` §16). Разведка репозитория перед детализацией item'а P4.2. **Якорь — `d171bfd`**
(коммит закрытия P4.1; он же будущий `<base>` P4.2, если P4.2 пойдёт следующим). Все команды ниже
воспроизводимы на этом дереве. Назначение файла — снять из ТЗ P4.2 плейсхолдеры «по итогу P3.2»,
«по итогу D31/P3.5», «на `8ec018e` — …», которые к моменту исполнения стали фактами, и назвать
расхождения ТЗ с деревом ДО того, как их найдёт исполнитель.

## 2. Что именно отдаёт `LlmCallReadRepository` (P4.1 + P3.2)

Четыре метода, ни один не даёт разреза ПО ДНЯМ:

| Метод | Возврат | Кто зовёт |
|:--|:--|:--|
| `usageSummary(int $analysisId, array $purposes): array{prompt_tokens,…,cost_micros}` | типизированный массив (докблок `@var object{…}` вместо записи в baseline) | `UsageSnapshotRecorder` (P4.1) |
| `spendByProviderModelPurpose(CarbonInterface $since): Collection<LlmCall>` | модели с `selectRaw`-агрегатами как ДИНАМИЧЕСКИМИ свойствами | `LlmSpendReporter::report()` |
| `forAnalysesSince(array $analysisIds, CarbonInterface $since): Collection<LlmCall>` | вызовы прогона | eval-раннеры |
| `resolvePromptVersionSet(array, CarbonInterface): ?array` | версии промтов прогона | eval-раннеры |

**Два разных приёма типизации в одном файле** — важен для баланса baseline (§5): `usageSummary()`
аннотирует форму строки докблоком `@var object{…}` и записей в baseline НЕ порождает;
`spendByProviderModelPurpose()` возвращает `Collection<LlmCall>`, и обращения к её динамическим
свойствам в `LlmSpendReporter` дают РОВНО восемь записей baseline.

## 3. Оси, которые обязан покрыть источник (по фактическому коду трёх потребителей)

| Потребитель | Окно | Оси группировки | Форма | Статус |
|:--|:--|:--|:--|:--|
| `ai:cost-report --days=N` | СКОЛЬЗЯЩЕЕ `now()-N дн … now()` | `(provider, model, purpose)` | таблица + «Итого» + «Экономия кэша» | существует |
| `LlmSpendCard` (`/pulse`) | СКОЛЬЗЯЩЕЕ `now()-1 дн … now()` | `(purpose)` | таблица + «Итого» | существует |
| Виджет дашборда (P4.3) | период в границах горизонта | `(день, provider, model)` | диаграмма по дням | ещё нет |

Отсюда конфликт, который контракт обязан разрешить ЯВНО: **оба существующих потребителя считают
по СКОЛЬЗЯЩЕМУ окну, а бриф §3 и D38 требуют разреза по КАЛЕНДАРНЫМ дням.** Свёртка календарных
суток не воспроизводит скользящее окно 24ч (два неполных дня), поэтому «источник отвечает только
дневными бакетами» ломает семантику сумм, замороженную D38.

Часовой пояс дневного бакета — `config('app.timezone')` = **`UTC`** (`config/app.php:68`), то есть
сегодня «день» однозначен, но правило обязано быть названо в контракте: смена пояса приложения
иначе молча сдвинет все дневные цифры.

## 4. Горизонт и индексы (D37, Implementation Rule 7)

- Retention: `config/partitioning.php` → `retention.llm_calls = {months: env(AI_RETENTION_LLM_CALLS_MONTHS, 12), keep_table: false}` — партиции ДРОПаются, не детачатся.
- Курс ₽ и прайсинг: `config/ai.php:186-188` → `cost_report.rub_per_usd = env(AI_COST_REPORT_RUB_PER_USD, 90.0)`; экономия кэша считается по `config('ai.capabilities')` в `LlmSpendReporter::cacheSavingsMicros()`.
- Индексы `llm_calls` (`database/migrations/2026_07_04_100026_create_llm_calls_table.php:40-42`):
  `(analysis_id)`, `(analysis_run_id)`, `(purpose, called_at)`; таблица партиционирована RANGE по
  `called_at`. **Вывод:** запрос «сумма по дням за период» идёт по диапазону `called_at` → работает
  партиционный pruning, нового индекса не требует; отдельного индекса `(provider, model)` нет и
  по фактам этого запроса не нужен (группировка после отсечения диапазона). То есть эскалация
  Implementation Rule 7 при штатном исполнении не ожидается.

## 5. `phpstan-baseline.neon` — фактическая вычитающая дельта (D71)

Восемь записей, осиротеющих при уводе агрегата с динамических свойств `LlmCall`, лежат **не по
пути `CostReportCommand`** (как утверждало ТЗ до этой разведки), а по пути
`app/Services/Llm/LlmSpendReporter.php` — их туда переселил P3.2:

```bash
$ grep -c "path: app/Services/Llm/LlmSpendReporter.php" phpstan-baseline.neon
8
```

Все восемь — `identifier: property.notFound`, `count: 1`, на свойствах `LlmCall::$cached_tokens`,
`$calls`, `$completion_tokens`, `$cost_micros`, `$model`, `$prompt_tokens`, `$provider`, `$purpose`
(строки 436–483 на `d171bfd`).

Три величины гейта D58 на `d171bfd`:

| Величина | Команда | Значение |
|:--|:--|:--|
| записей | `grep -c "message:" phpstan-baseline.neon` | **249** |
| сумма `count:` | `awk '/count:/{gsub(/[^0-9]/,"",$2); s+=$2} END{print s}' phpstan-baseline.neon` | **318** |
| гистограмма `identifier:` (топ) | `grep -o "identifier: .*" phpstan-baseline.neon \| sort \| uniq -c \| sort -rn` | `property.notFound` 212 · `argument.type` 12 · `nullsafe.neverNull` 7 · `return.type` 3 · `larastan.noUnnecessaryCollectionCall` 2 · `class.notFound` 2 · `arrayValues.list` 2 · остальные по 1 |

**Развилка, определяющая знак дельты.** Записи осиротеют (чистое вычитание, форма D71) только если
новая реализация источника НЕ обращается к динамическим свойствам `LlmCall` в СВОЁМ файле — то есть
если репозиторий отдаёт типизированную строку (приём `usageSummary()`: `->toBase()` + докблок
`@var object{…}`, либо DTO). Если же маппинг динамических свойств просто ПЕРЕЕЗЖАЕТ в файл
источника, восемь записей не исчезнут, а сменят путь — это ПЕРЕМЕЩЕНИЕ (случай D58), а P4.2 в число
пяти items с правом регенерации baseline не входит.

## 6. Livewire и инъекция в Pulse-карточку — жёсткий факт

`vendor/livewire/livewire/src/Factory/Factory.php:21-32` — `create()` делает **`$component = new
$class;`**, без контейнера:

```php
public function create($name, $id = null): Component
{
    [$name, $class] = $this->resolveComponentNameAndClass($name);
    $component = new $class;
```

Рендер вызывается как `wrap($component)->render()`
(`vendor/livewire/livewire/src/Mechanisms/HandleComponents/HandleComponents.php:450`) — без аргументов.

**Следствие для P4.2:** конструкторная инъекция источника в `LlmSpendCard` НЕВОЗМОЖНА (Livewire
создаст карточку `new` и упадёт на обязательном аргументе), инъекция в `render()` — тоже (аргументы
не передаются). Единственный механизм — резолв из контейнера ВНУТРИ `render()`. Это не «сервис-локатор
из лени», а граница фреймворка; существующий тест (`new LlmSpendCard`) при таком решении остаётся
рабочим.

## 7. Тесты потребителей: что заморожено, а что подвижно

- `tests/Feature/Ai/CostReportTest.php` — 4 теста, ожидания по ВЫВОДУ (`expectsOutputToContain`):
  `extract_rows`, `$0.0173`, `не найдено`, `0.2700`, `gemini-2.5-flash-lite`. D38 запрещает правку
  числовых ожиданий. В файле есть предупреждение о механике `expectsOutputToContain` (несколько
  ожиданий на ОДНУ строку вывода «съедают» друг друга) — при добавлении дневной секции это
  ограничение остаётся в силе.
- `tests/Feature/Observability/PulseCardsTest.php` — тест `LlmSpendCard` создаёт карточку через
  `new LlmSpendCard`, читает `$view->getData()['rows']` и обращается к свойствам СТРОКИ
  (`->calls`, `->prompt_tokens`, `->cost_micros`) плюс `$data['totalCostMicros']`. Числа (2 вызова,
  1500 prompt-токенов, 750 микро-долларов) — поведенческие и меняться не должны; ФОРМА строки
  (stdClass → DTO) подвижна, D38 её не морозит (он про `ai:cost-report`).
