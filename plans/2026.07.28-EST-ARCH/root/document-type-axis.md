# document-type-axis — контракт оси типа документа и составного ключа «тип + шаг»

**Контракт P1.2 плана `2026.07.28-EST-ARCH`.** Замораживается утверждением владельца (строка
в `plan.md` → `## 6. Update Log`). После заморозки правится ТОЛЬКО новой D-записью со ссылкой
`supersedes` — правка «по ходу» исполнения любой фазы запрещена (`plan-protocol` §11).

**Что этот документ решает:** как решения владельца D16 (SSOT типа документа — enum + реестр
анализаторов в коде), D17 (check-constraint по enum'у) и D18 (`prc_ai_fixtures` = ядро +
`type_profile jsonb`) выглядят В СХЕМЕ — потаблично, по колонкам, ключам и ограничениям.
Вход для P1.4 (миграции), P1.5 (переезд транспорта), P1.8 (оси подсказок) и P2 (реестр
анализаторов, валидация шага).

**Якорь фактов:** все числа, перечни и цитаты кода получены на `dc0815c` командами, названными
рядом с утверждением либо в разделе «Как проверены факты схемы».

**Имена таблиц транспорта — ЦЕЛЕВЫЕ** (`llm_routes`, `llm_prompts`) по D22 и карте
`root/naming-canon.md`: контракт читают исполнители уже после переезда. Сегодняшние имена —
`prc_ai_routes`, `prc_ai_prompts`.

## 1. Пространство значений оси и её носитель

### 1.1. Значения типа документа

SSOT — enum `App\Enums\Procurement\AiDocumentType` (D16). Пять значений на `dc0815c`:
`estimate`, `tech_spec`, `contract_draft`, `protocol`, `unknown`
(`grep -c "case " app/Enums/Procurement/AiDocumentType.php` = 5).

Мёртвый реестр `prc_document_types` сносится тем же D16 — таблица перестаёт существовать, а
значит перестаёт существовать и «code из реестра» как источник значения. Единственный источник —
enum.

### 1.2. Носитель кросс-документного назначения — РЕШЕНИЕ

Сегодня «маршрут годится для любого типа документа» выражено голым литералом `'any'` в
`text`-колонке: он лежит в данных (`AiRoutingSeeder` — три строки из одиннадцати), приезжает
аргументом в резолвер (`ScreeningProcessor:138`, `ScreeningOutcomeHandler:95`, `PromptCritic:70`,
`EvalRunCommand:196`) и участвует в фолбэке чтения
(`AiRouteReadRepository:32` — `where document_type = ? or document_type = 'any'`, точное
совпадение раньше по `orderByRaw`).

**Решение: остаётся НЕНУЛЕВОЙ СЕНТИНЕЛ со значением `'any'`, но перестаёт быть голым литералом —
получает именованный носитель в коде.**

- Носитель — новый enum `App\Enums\Llm\DocumentTypeScope` с единственным кейсом
  `Any = 'any'`. Каталог `app/Enums/Llm/` заводится этим решением; перенос в него `LlmPurpose`
  и `PromptStep` контрактом НЕ предрешается — это предмет P2/P3.5.
- В `AiDocumentType` кейс `any` НЕ добавляется (Implementation Rule 2 item'а): этот enum —
  вердикт скрининга «что за документ», служебное значение протащило бы себя в ответ LLM и в
  `ScreeningResult`.
- Колонки, где сентинел допустим, остаются `NOT NULL`; форма unique-ключа НЕ меняется из-за
  ловушки NULL, потому что NULL'ов в ключе нет.
- Столкновение сентинела с будущим типом документа закрывается тестом (см. §7, P1.4): ни одно
  значение `AiDocumentType` не равно `DocumentTypeScope::Any->value`.

**Отвергнутая альтернатива — NULL как носитель кросс-документного назначения.** Ловушка Postgres
здесь снимаема: образ БД — `agelto_postgres:17-partman` (`docker-compose.yml:127`), то есть
Postgres 17, и `UNIQUE NULLS NOT DISTINCT` (доступно с 15) вернуло бы ключу способность ловить
дубли. Отвергнуто не по ловушке, а по смыслу: «маршрут годится для любого типа» — это
УТВЕРЖДЕНИЕ, а не отсутствие данных, и класть его на NULL значит завести второй безымянный
дискриминатор ровно того сорта, который этот же план вычищает решением D24 («явная ось
происхождения вместо `procurement_id IS NULL`; два факта на одном условии»). Плюс `?AiDocumentType`
в сигнатурах не отличает «кросс-документный маршрут» от «тип ещё не определён» — а `prc_ai_analyses`
несёт ровно второй смысл в NULL (§3.1).

**Отвергнутая альтернатива — оставить голый строковый литерал.** Это сегодняшнее состояние:
опечатка `'anу'` (кириллическая `у`) даёт молчаливый фолбэк-маршрут, а не ошибку — прямое
противоречие брифу §6.

### 1.3. Форма check-constraint (D17)

На каждой колонке типа документа — именованный `CHECK`, добавляемый в ту же create-миграцию
(D20 — правки вносятся в исходные миграции, не ALTER'ами):

```
ALTER TABLE <таблица>
    ADD CONSTRAINT <таблица>_<колонка>_check
    CHECK (<колонка> IN (<значения>))            -- NOT NULL-колонка
    CHECK (<колонка> IS NULL OR <колонка> IN (…)) -- nullable-колонка
```

Правила формы, обязательные для P1.4/P1.8:

1. Список значений НЕ пишется восемью копиями литералов. Единственный носитель —
   `AiDocumentType::values(): list<string>` (статический хелпер, заводится этим же item'ом);
   колонки с сентинелом складывают `[...AiDocumentType::values(), DocumentTypeScope::Any->value]`.
   Проверяется числом: `grep -rc "'estimate', 'tech_spec'" database/migrations/` = 0.
2. Имя constraint'а задаётся явно (не отдаётся автогенерации Postgres) — иначе `down()` и
   последующие правки не могут на него сослаться.
3. Кастование в enum на границе записи (`casts()` модели) — дополнение к check'у, а не замена:
   сидеры, фабрики и прямые `INSERT` идут мимо моделей.
4. Цена, принятая D17 явно: новый тип документа требует правки миграции (`migrate:fresh` в dev,
   одна строка `ALTER … DROP/ADD CONSTRAINT` в проде).

## 3. Разбор по таблицам: что именно меняется

### 3.1. `prc_ai_analyses` — NULL остаётся, и это законно

Колонка заведена как `text nullable` с комментарием «code из prc_document_types, без строгого FK»
(`2026_07_04_100025:27`). Смысл NULL здесь — **скрининг ещё не отработал**, тип неизвестен. Это
подлинное отсутствие данных, а не замаскированное утверждение, поэтому NULL сохраняется, а
сентинел на этой колонке запрещён: анализ всегда про КОНКРЕТНЫЙ документ.

Новый комментарий колонки (§8) и check по §1.3. Больше на этой таблице ничего не меняется:
partial unique `prc_ai_analyses_active_version_step_unique` (`:72-76`) — инвариант перепрогонов и
теневых прогонов, D25 его прямо не трогает.

### 3.2. `prc_ai_corrections` — `NOT NULL`

Сегодня `nullable` (`2026_07_09_100052:31`). Но правка оператора всегда висит на `analysis_id`
(`NOT NULL`, `cascadeOnDelete`), а соседняя колонка `is_reusable` документирована как «применять
ко всем документам ЭТОГО `document_type`» (`:36`) — при NULL это правило не определено вовсе.
Значит колонка обязана быть заполненной: `NOT NULL`, значение берётся из анализа на границе
записи.

Периметр вынужденной правки кода (P1.4): `PromptPatchApplier::applyHint()` создаёт `Correction`
с `'document_type' => $suggestion->document_type` (`:70`) — после §3.3 источник тоже `NOT NULL`,
цепочка сходится без дополнительной ветки.

### 3.3. `prc_ai_prompt_suggestions` — две оси предмета (D21)

`kind` остаётся ФОРМОЙ предложения (`prompt_patch` / `correction_hint`) — на ней стоит ветвление
`PromptPatchApplier` (`:42`, `:56`), и расширение множества `kind` предметом сломало бы его.
Предмет несут две отдельные оси:

- `document_type` — `NOT NULL`, заполняется для ВСЕХ форм (сегодня `nullable` с комментарием
  «для correction_hint», `2026_07_28_100058:52`). Для патча кросс-документного промта (`global`,
  `screening:*`, `prompt:critic`) значение — сентинел §1.2.
- `analysis_step` — новая колонка на существующем enum `AnalysisStep` (`screening`/`extraction`),
  `nullable`. NULL означает **предложение не привязано к одной стадии** — так выглядит патч
  кросс-стадийного промта `global`. Это отсутствие привязки, а не утверждение «годится для обеих»,
  поэтому сентинел здесь не заводится.

Существующая колонка `prompt_step` (`:48`) с новой осью не сливается и не переименовывается: она
означает «шаг ТОГО промта, который патчится», и заполнена только у формы `prompt_patch`.

Исполнитель — P1.8 (его Intent — «оси предмета в `prc_ai_prompt_suggestions`»).

### 3.4. `prc_ai_eval_runs` — обе оси заводятся с нуля

Прогон оценки сегодня неявно сметный: в таблице нет ни типа документа, ни задачи
(`2026_07_04_100031:16-27`). При этом команда УЖЕ различает задачи —
`ai:eval:run --task=extraction|screening` (`EvalRunCommand:52`, валидация `:80`), но значение
опции в строку прогона не пишется (`EvalRun::$fillable` — восемь полей, ни `task`, ни
`document_type`, `app/Models/Procurement/Ai/EvalRun.php:24-32`). Два прогона разных задач в
таблице неотличимы — сравнивать их метрики нельзя, а именно это делает `ai:eval:compare`.

Обе колонки `NOT NULL`. Сентинел на `document_type` ДОПУСКАЕТСЯ: прогон скрининга гоняет
кросс-документный маршрут `(any, screening)` по всему корпусу, включая негативы чужих типов —
приписать такому прогону один конкретный тип было бы ложью.

### 3.5. `prc_ai_dataset_examples` — ось типа заводится, `task` получает check

Ось `task` (`screening`/`extraction`) есть с первого дня (`2026_07_04_100030:23`), оси типа
документа нет. Эталон всегда про конкретный документ (`document_version_id NOT NULL`), поэтому
`document_type NOT NULL` без сентинела.

Check на `task` — сверх буквы D17 (он про колонки типа документа), по тому же критерию:
колонка `text` с перечислением в комментарии и без ограничения ловит опечатку только глазами.
Значения берутся из `AnalysisStep`, а не из нового литерала.

## 4. Составной ключ «тип + шаг» (D7)

### 4.1. `llm_prompts`: `(key, version)` → `(document_type, key, version)`

Сегодня уникальность промта — `unique(key, version)` (`2026_07_04_100029:27`), а разделение
сметного и кросс-документного держится соглашением о префиксе внутри строки: на `dc0815c` во всех
девяти файлах `resources/ai/prompts/**/*.md` `key` дословно равен `step`
(`grep -h "^key:\|^step:" resources/ai/prompts/*/*.md`), то есть ключом фактически служит имя шага.
Второй тип документа со своим шагом `extraction:rows` немедленно столкнётся с существующей
строкой сметы.

Ключ становится `(document_type, key, version)`. `step` в ключ НЕ входит: он свойство промта
(в какую системную часть тот композируется), а не его идентичность; два промта с одним `key` и
разными `step` — повреждённые данные, а не легальный случай.

Вынужденная синхронизация, исполнитель P1.4:

- front-matter файлов промтов получает обязательное поле `document_type` (девять файлов);
  `PromptSeeder::parseFile()` добавляет его в список обязательных (`:104`) и валидирует так же
  жёстко, как сегодня валидирует `step` (`PromptStep::from()`, `:111`);
- `PromptSeeder::run()` upsert'ит по тройке вместо пары (`:33-34`), деактивация протухших версий
  группируется по `(document_type, key)`, а не по `key` (`:45-46`);
- `PromptResource` в админке — форма несёт `step` свободным `Textarea`
  (`Prompts/Schemas/PromptForm.php:24`); ось типа документа обязана попасть в форму как `Select`
  по `AiDocumentType` + сентинел, иначе check-constraint будет ловить оператора отказом БД.

Композиция промтов по типу документа (`PromptReadRepository::activeForSteps()` — выбирает по
шагам, о типе не знает) — предмет P2 (§5): пока тип один, выборка по шагу совпадает с выборкой по
паре, регресса нет; но и «сделано» это не.

### 4.2. `llm_routes`: `(document_type, purpose, priority)` → `+ shadow`

Ключ уже составной (`2026_07_04_100028:33`), ось типа уже есть — по D7 меняется только
целостность (§1.3) и носитель кросс-документного назначения (§1.2).

Отдельная находка, чинится тем же item'ом: в ключ не входит `shadow`, хотя теневой маршрут — это
самостоятельное подмножество, выбираемое отдельным запросом (`AiRouteReadRepository:45-57`), и
`AiRouteFactory`/`seedShadowRoute` заводят его с тем же `priority = 0`, что и основной
(`tests/Feature/Llm/ShadowDispatchTest.php:44-45`). На засеянной БД теневой маршрут для уже
существующей пары `(тип, purpose)` не создастся вовсе — упрётся в unique. Ключ становится
`(document_type, purpose, priority, shadow)`.

## 5. Пространство значений `step`/`purpose` и МЕСТО валидации

Разложение по природе шага (D7) — контракт фиксирует состав, реализацию делает P2:

| Носитель | Кросс-документное (остаётся общим enum'ом) | Объявляет анализатор типа (для сметы) |
|:--|:--|:--|
| `PromptStep` — колонка шага промта | `global`, `screening:global`, `screening:classify`, `prompt:critic` | `extraction:global`, `extraction:discovery`, `extraction:passport`, `extraction:rows`, `extraction:totals` |
| `LlmPurpose` — колонка назначения маршрута | `screening`, `eval`, `shadow`, `prompt_critic` | `discovery`, `extract_passport`, `extract_rows`, `extract_totals` |

**Сейм валидации — граница записи. Их сегодня ЧЕТЫРЕ, а не «репозиторий + сидер»:**

1. `PromptSeeder` (`database/seeders/PromptSeeder.php:33`) — пишет `Prompt` напрямую моделью;
2. `AiRoutingSeeder` (`database/seeders/AiRoutingSeeder.php:52`) — пишет `AiRoute` напрямую;
3. Filament-формы `PromptForm` (`step` — свободный `Textarea`, `:24`) и `AiRouteForm`
   (`document_type` — свободный `Textarea`, `:19`; `purpose` — `Select` по `LlmPurpose`, `:22-23`);
4. фабрики `PromptFactory`/`AiRouteFactory` — в тестах.

Store-репозитория ни у промтов, ни у маршрутов НЕ существует: в `app/Repositories/Procurement/`
есть только `PromptReadRepository` и `AiRouteReadRepository`
(`ls app/Repositories/Procurement/` — 13 файлов, `*StoreRepository` для промтов и маршрутов среди
них нет). Формулировка Implementation Rule 5 item'а («граница записи репозиториев промтов/маршрутов
+ сидеры») описывает целевое, а не текущее состояние — расхождение зафиксировано, а не подогнано.

**Что закрывает какой этап:**

- **P1.4** — check-constraint закрывает ось `document_type` на ВСЕХ четырёх путях сразу, включая
  Filament: это ограничение БД, обойти его формой нельзя.
- **P2** — валидация значения `step`/`purpose` по реестру типа; там же типизация сигнатур
  резолвера на `AiDocumentType|DocumentTypeScope`.
- **Между P1 и P2 `step` машинно не проверяется.** Это НЕ регресс — сегодня он тоже не
  проверяется (единственная проверка — `PromptStep::from()` в сидере, то есть только для файлового
  канона и только на общем enum'е). Но и «сделано» это не: строка `step`, записанная админкой или
  фабрикой, до P2 остаётся непроверенной.

## 6. `prc_ai_fixtures`: две оси и состав `type_profile` (D18)

### 6.1. Две оси — почему одной мало

Колонка `doc_type` сегодня несёт **ожидаемый вердикт скрининга для негативов**
(`2026_07_27_100053:30` — комментарий «ожидаемый вердикт скрининга, для негативов D5»), а
читается это в `ScreeningGoldBuilder:30-40`: у `class = neg` вердикт берётся из реестра, у
`class = est` захардкожен `AiDocumentType::Estimate`.

Карта имён P1.1 переименовывает колонку в `document_type` — со СВОИМ смыслом, который совпадает
с соседями: в `prc_ai_analyses.document_type` тоже лежит «какой это документ». Но реестру нужен
второй факт, которого сегодня нет вовсе: **чей это эталон**. Негатив в сметном корпусе — это файл
типа `tech_spec`, лежащий в корпусе типа `estimate`, чтобы проверять сметный скрининг-гейт. Один
столбец два эти факта не несёт.

| Колонка | Смысл | Форма |
|:--|:--|:--|
| `document_type` (переименование `doc_type`) | фактический тип файла = ожидаемый вердикт скрининга | `NOT NULL`, check по 5 значениям |
| `owner_document_type` (новая) | тип, чей анализатор владеет корпусом и валидирует `type_profile` | `NOT NULL`, check по 5 значениям |

У позитива обе колонки равны (`estimate`/`estimate`); у негатива расходятся
(`tech_spec`/`estimate`).

`document_type` становится `NOT NULL` (сегодня `nullable`) — заполняется и для позитивов. Это
снимает ветку «негатив без `doc_type` → rejected» (`ScreeningGoldBuilder:31-37`) и хардкод
`AiDocumentType::Estimate` (`:48`): вердикт для ЛЮБОГО класса — `$fixture->document_type`.
Альтернатива «оставить `nullable`, NULL = совпадает с owner» отвергнута по §1.2: это снова факт,
спрятанный в отсутствии значения.

Вынужденная синхронизация (P1.4): `FixtureManifestEntry::$doc_type` → `$document_type` и новое
поле `$owner_document_type`; `estimates/manifest.json` регенерируется (24 вхождения ключа
`doc_type`, `grep -c '"doc_type"' estimates/manifest.json`), позитивы получают
`document_type = owner_document_type = estimate`.

реестр — P2). Переезжают РОВНО пять колонок, названных D18:

| Поле профиля | Тип | Кто читает сегодня | Фильтруется в админке? | Форма доступа после переезда |
|:--|:--|:--|:--|:--|
| `class` | `est`/`neg` (`FixtureClass`) | `ScreeningGoldBuilder:30`, `GoldBuildCommand:200` — ветвление в PHP после выборки | нет — экрана реестра не существует | `type_profile->>'class'` |
| `form` | строка (`KS2`, …) | `EvalRunCommand:512` — `orderBy('form')` + группировка пула холдаута | нет — экрана реестра не существует | `type_profile->>'form'` |

`notes` и обе оси §6.1. Правило чтения списка D18: перечень переезжающих полей ИСЧЕРПЫВАЮЩИЙ
(пять названных), перечень ядра — иллюстративный («общее ядро»), поэтому файловые метаданные и
провенанс остаются на месте.

### 6.3. Название и описание эталона: заводится колонка `title` (D90, supersedes D42)

D42 толковал требование владельца «загружаем документ, пишем описание, код, коммент» как «ложится
на существующие `code` и `notes`, отдельная колонка не нужна». Владелец толкование ОТВЕРГ
(2026-07-29, гейт этого item'а): «название и описание — это просто для удобства поиска… чтобы
потом самим искать нужные сметы проще и смотреть описание, что в них… по логике почти ни на что
не влияет, просто чтение». Технический код `EST-XLSX-KS2-001` названием не является — искать по
нему можно, читать нельзя.

| Колонка | Роль | Форма |
|:--|:--|:--|
| `code` | технический идентификатор, контракт `Fixture::CODE_PATTERN` | без изменений (`text unique`) |
| `title` | человекочитаемое название эталона — для поиска и понимания «что внутри» | новая, `text NOT NULL` |
| `notes` | описание/комментарий, свободный текст | без изменений (`text nullable`) |

Обе колонки — ЧИСТО ЧИТАТЕЛЬСКИЕ: ни один шаг пайплайна, эталона или оценки качества на них не
ветвится. Проверка после P1.4: `grep -rn "->title\b" app/Services/ app/Jobs/` — пустой вывод.

`NOT NULL` — потому что название, которое можно не заполнить, не выполняет своей единственной
работы (поиск). Бэкфилл 24 существующих записей при регенерации манифеста (P1.4) —
`original_filename` без расширения; дальше значение задаёт оператор в форме загрузки (P5.1).
Периметр вынужденной правки: `FixtureManifestEntry` получает `$title`, `estimates/manifest.json`
регенерируется тем же проходом, что и переименование `doc_type` (§6.1).

Индекс под поиск не заводится по §6.4.

### 6.4. Индексы — не заводятся, и это решение, а не умолчание

**Ни одного expression- или GIN-индекса по `type_profile` контракт не предписывает.**

Основание — размер отношения: одна строка реестра = один эталонный ФАЙЛ корпуса, сегодня их 24
(`grep -c '"doc_type"' estimates/manifest.json` = 24 — по записи на эталон). На таблице такого
порядка seq scan дешевле любого индексного доступа, а три expression-индекса — это три объекта,
которые надо поддерживать при каждой правке формы профиля.

Порог пересмотра назван числом, чтобы решение было проверяемым: индексы заводятся, когда
`select count(*) from prc_ai_fixtures` превысит 10 000 строк, ЛИБО когда фильтр по полю профиля
попадёт в запрос, выполняемый в HTTP-цикле не оператором (сегодня оба предиката — консольные:
`EvalRunCommand`).

Что это значит для P5.1 (фильтры реестра в админке) и `Fixture::nextCodeFor()` (следующий
свободный номер в тройке «класс/формат/форма»): они пишутся на выражениях `type_profile->>'…'`
из таблицы §6.2 БЕЗ индексов, и это не «недоделка», которую P5.1 вправе починить миграцией —
схему закрыл P1.

**Отвергнутая альтернатива — GIN-индекс на всём `type_profile`.** Он окупается на запросах
вхождения (`@>`) и существования ключа; ни одного такого запроса ни сегодня, ни в ТЗ P5.1 нет —
там равенство по одному полю.

**Отвергнутая альтернатива — оставить `class` и `gold_source` в ядре.** Оба читаются как
кросс-документные (у корпуса любого типа есть позитивы, негативы и способ получения эталона), и
`class` вдобавок гейтит смысл ядерной колонки `document_type` (§6.1), а `gold_source` — носитель
единственного SQL-предиката из пяти. Отвергнуто, потому что D18 назвал обе поимённо среди
переезжающих; пересмотр — новая D-запись со `supersedes D18`. Цена, если пересматривать позже:
ALTER-миграция + правка `EvalRunCommand::writeSplits()`, `FixtureManifestEntry`, фабрики и формы
P5.1.

## 7. Тест на столкновение сентинела (P1.4)

Сентинел `'any'` живёт в том же пространстве значений, что и типы документа, поэтому его
неконфликтность обязана быть машинной, а не подразумеваемой:

```
test('сентинел кросс-документного назначения не совпадает ни с одним типом документа', function (): void {
    expect(AiDocumentType::values())->not->toContain(DocumentTypeScope::Any->value);
});
```

Красный исход достижим: добавление в `AiDocumentType` кейса со значением `any` — ровно тот
сценарий, который Implementation Rule 2 item'а запрещает, и тест ловит его при первом же прогоне.
