# usage-source-contract — контракт источника расхода LLM

**Контракт P4.2 плана `2026.07.28-EST-ARCH`.** Замораживается утверждением владельца (строка
в `plan.md` → `## 6. Update Log`). После заморозки правится ТОЛЬКО новой D-записью со ссылкой
`supersedes` — правка «по ходу» исполнения любой фазы запрещена (`plan-protocol` §11).

**Что этот документ решает:** какие запросы принимает источник расхода, в какой форме отвечает,
как подписывает каждую цифру (идентификатор источника, лаг, горизонт, момент актуальности), по
какому правилу режет календарный день, что отвечает за пределом горизонта хранения и где — ТЕКСТОМ,
а не пустым классом — лежит место второй реализации «биллинг провайдера». Вход для P4.3 (виджет
дашборда) и P4.4 (процедура сверки).

**Якорь фактов:** код читан на `d171bfd` (ветка `main`, состояние после закрытия P4.1). Все
`файл:строка` ниже сняты на этом коммите; разведка — `findings/P4.2-usage-source-facts-2026-07-30.md`.

**Почему сейм вообще есть.** Не ради гипотетического адаптера: у Gemini нет REST фактического
расхода, программный путь только через экспорт Cloud Billing в BigQuery с лагом ≥24ч, и владелец
решил его не подключать (D34). Сейм оправдан тем, что КАЖДАЯ цифра расхода на экране обязана нести
подпись источника и лага (D10): молчаливое смешение «наших» и «провайдерских» цифр — механизм, по
которому инцидент D126 EST-TRAIN ($2.30 по трекингу против ~$12 по биллингу Google) оставался
невидимым.

## 1. (в1) Какие запросы принимает источник

**Один метод, одна форма ответа на всех трёх потребителей:**

```php
namespace App\Services\Llm\Contracts;

interface UsageSource
{
    public function usage(UsageQuery $query): UsageReport;
}
```

Запрос — полуинтервал времени плюс НАБОР осей группировки:

```php
final readonly class UsageQuery
{
    public function __construct(
        public CarbonInterface $from,      // включительно
        public CarbonInterface $to,        // исключительно
        public bool $byDay = false,
        public bool $byProvider = false,
        public bool $byModel = false,
        public bool $byPurpose = false,
    ) {}
}
```

- **Окно — `[from, to)`**, полуинтервал: `called_at >= from AND called_at < to`. Скользящее окно
  выражается как `[now()-N дн, now())`, календарный день — как `[00:00 дня, 00:00 следующего)`;
  граница не принадлежит двум окнам сразу.
- **Оси — подмножество `{день, провайдер, модель, назначение}`** (D124 в1). Пустой набор осей —
  законный запрос: одна строка-итог за окно. Ось, не выбранная запросом, приходит в строке ответа
  как `null` — «схлопнута», а не «неизвестна».
- **Три сегодняшних потребителя и их запросы:**

| Потребитель | Окно | Оси |
|:--|:--|:--|
| `ai:cost-report --days=N` (существующая таблица) | `[now()-N дн, now())` | провайдер · модель · назначение |
| `ai:cost-report` (НОВАЯ дневная секция) | `[now()-N дн, now())` | день · провайдер · модель |
| `LlmSpendCard` (`/pulse`) | `[now()-1 дн, now())` | назначение |
| виджет дашборда (P4.3) | период в границах горизонта | день · провайдер · модель |

**Отвергнуто:** два метода-вопроса («итоги за окно» и «серия по дням») — второй носитель одного
факта, расходящийся при первой же правке фильтра (D124, отвергнутый вариант «б»).
**Отвергнуто:** источник отвечает ТОЛЬКО дневными бакетами, а потребители складывают сутки — свёртка
календарных суток не воспроизводит скользящее окно 24ч (два неполных дня) и ломает семантику сумм,
замороженную D38 (D124, вариант «а»).

## 2. (в2) Форма ответа и подписи

```php
final readonly class UsageReport
{
    /** @param list<UsageRow> $rows */
    public function __construct(
        public array $rows,
        public UsageSignature $signature,
        public bool $beyondHorizon,
    ) {}
}

final readonly class UsageRow
{
    public function __construct(
        public ?CarbonImmutable $day,   // null, если ось «день» не запрошена
        public ?string $provider,
        public ?string $model,
        public ?string $purpose,
        public int $calls,
        public int $promptTokens,
        public int $cachedTokens,
        public int $completionTokens,
        public int $costMicros,
    ) {}
}

final readonly class UsageSignature
{
    public function __construct(
        public string $sourceId,          // 'tracking'
        public string $label,             // «наш трекинг (llm_calls)»
        public int $lagSeconds,           // 0 у трекинга
        public int $horizonMonths,        // config('partitioning.retention.llm_calls.months')
        public CarbonImmutable $horizonFrom,
        public CarbonImmutable $asOf,
    ) {}
}
```

- **Подпись — ПОЛЕ ответа, а не отдельный вызов.** Получить цифру без подписи нельзя: `UsageReport`
  не конструируется без `UsageSignature`. Разработчик, «забывший вывести подпись», получает не
  неподписанную цифру, а цифру с неотрендеренной подписью — это видно на экране (пустое место), а
  не тихо (цифра без происхождения). Ревью-правило для P4.3/P4.4: экран, показывающий `rows` и не
  показывающий `signature`, — блокирующее замечание.
- **Строка ответа не несёт денег-производных:** ни рублей, ни экономии кэша, ни процентов.
  Токены и `cost_micros` — всё, что источник знает.
- **Значения подписи вычисляются, а не вписываются.** `horizonMonths` — из
  `config('partitioning.retention.llm_calls.months')`; `horizonFrom` = `asOf - horizonMonths мес.`;
  `lagSeconds` = 0 — не «оптимистичная оценка», а следствие механики записи: цена считается и
  пишется в момент самого вызова (`LlmCallRecorder`), между фактом расхода и строкой в `llm_calls`
  нет ни выгрузки, ни пересчёта. Литерал `12` в коде = ложь на экране при смене
  `AI_RETENTION_LLM_CALLS_MONTHS`.
- **`asOf`** — момент, на который собран ответ (`CarbonImmutable::now()`); для трекинга совпадает с
  моментом запроса, для будущего биллинга совпадать не будет (см. §5).

**Отвергнуто:** отдельный метод `signature()` рядом с `usage()` — подпись, которую можно НЕ
запросить, эквивалентна её отсутствию; ровно это и произошло с обоими сегодняшними потребителями,
не несущими подписи вовсе.
**Отвергнуто:** подпись строкой-текстом («наш трекинг, лаг 0, 12 мес.») вместо полей — потребитель
не сможет ни сравнить горизонт с периодом (P4.3), ни отличить лаг для сверки (P4.4).

## 3. (в3) Правило дневного бакета

**День — КАЛЕНДАРНЫЙ, в поясе `config('app.timezone')`** (сегодня `UTC`, `config/app.php:68`).
Бакет строки — `(called_at AT TIME ZONE <app.timezone>)::date`; `called_at` хранится как
`timestamptz` (`database/migrations/2026_07_04_100026_create_llm_calls_table.php:33`), то есть
пояс приложения применяется к моменту времени, а не к «сырой» строке.

Часовой пояс назван ЗДЕСЬ, а не оставлен в коде, потому что он — скрытая зависимость всех дневных
цифр: смена `app.timezone` молча сдвинет каждую дневную сумму, и заметить это можно будет только по
разъезду с биллингом провайдера (у Google — свой пояс отчётности, предмет сверки P4.4).

**Скользящее окно потребителей от этого не ломается** (D124): дневная ось — ОДНА из осей, а не
обязательный режим. Запрос `[now()-1 дн, now())` без оси «день» отвечает ровно тем же итогом, что
и сегодняшний прямой агрегат карточки; календарные сутки в него не вмешиваются.

**Отвергнуто:** резать день по `UTC` жёстко, игнорируя `app.timezone` — при переходе проекта на
московский пояс дневная кривая разъедется с любым другим экраном приложения на три часа.
**Отвергнуто:** отдавать день строкой `YYYY-MM-DD` — потребителю (виджет P4.3) нужен объект даты
для сортировки и заполнения пропусков; строку он всегда получит форматированием.

## 4. (в4) Горизонт и запрос за его пределом

**Горизонт = retention `llm_calls`** — 12 месяцев по умолчанию
(`config/partitioning.php` → `retention.llm_calls.months`, env `AI_RETENTION_LLM_CALLS_MONTHS`),
`keep_table = false` → партиции старше окна **DROP'аются**, а не детачатся (D37). Ежедневный
ролл-ап расхода НЕ заводится.

**Признак «за горизонтом» — ПОЛЕ ответа** `UsageReport::$beyondHorizon`, а не исключение и не
пустая серия:

- `beyondHorizon = $query->from < $signature->horizonFrom` — то есть «часть запрошенного окна
  лежит за пределом хранения»;
- строки за пересечением окна с горизонтом при этом ВОЗВРАЩАЮТСЯ как есть: ответ честен и в части
  «что осталось», и в части «что могло быть удалено»;
- потребитель ОБЯЗАН показать это словами («данных нет — партиции старше retention удалены»), а не
  молча нарисовать провал в начале кривой. Молча пустая серия — дефект того же класса, что инцидент
  D126: цифра, чьё отсутствие невозможно отличить от нуля.

**Отвергнуто:** бросать исключение на запрос за горизонтом — законный запрос («покажи два года»)
превращался бы в ошибку вместо частичного честного ответа.
**Отвергнуто:** молча обрезать `from` до `horizonFrom` — потребитель получил бы окно, которого не
просил, и не узнал бы об этом.

## 5. (в5) Место второй реализации — текстом, а не классом

**Класса-заглушки `ProviderBillingUsageSource` в коде НЕТ и заводить его запрещено** (D34):
пустая вторая реализация — мёртвый код, который никто не снимет, а сейм оправдан не ею, а
обязанностью цифры нести подпись (D10). Место второй реализации описано здесь и проверяется грепом
по этому файлу, а не пустым классом в `app/`.

Когда владелец снимет гейт D34 (новая D-запись со `supersedes D34` + item на адаптер), реализация
`App\Services\Llm\ProviderBillingUsageSource` обязана:

1. **реализовать тот же `UsageSource::usage(UsageQuery): UsageReport`** — без новых методов и без
   расширения интерфейса: потребители (команда, карточка, виджет P4.3, сверка P4.4) не правятся;
2. **отдать подпись со своими значениями:** `sourceId = 'provider-billing'`, `label` с именем
   провайдера и площадки выгрузки, `lagSeconds` ≥ 24ч (лаг биллинга Google — RAG:✅ 2026-07-28,
   `findings/rag-provider-billing-2026-07-28.md`), `horizonMonths` — горизонт хранения экспорта
   BigQuery, `asOf` — момент последней доехавшей выгрузки, а НЕ момент запроса;
3. **лечь на экспорт Cloud Billing в BigQuery** (единственный программный путь к фактическим
   затратам Google) — сегодня требует внешних доступов GCP, отдельной стоимости BigQuery и включения
   экспорта владельцем;
4. **сохранить оси:** день и провайдер выражаются в схеме экспорта напрямую; **модель и назначение —
   нет.** SKU биллинга агрегирует по сервису и SKU, «назначение вызова» (`purpose`) — наше понятие,
   которого у провайдера не существует в принципе. Поэтому вторая реализация вправе вернуть `null`
   в осях `model`/`purpose` даже когда они запрошены, и обязана назвать это в своей подписи;
   потребитель, которому нужен разрез по назначению, остаётся на трекинге;
5. **не подменять трекинг, а стоять рядом:** сверка двух источников — процесс с человеком (P4.4),
   а не автоматический выбор «более правильной» цифры. Две цифры с разными подписями — норма; одна
   цифра без подписи — инцидент.

**Отвергнуто:** завести пустой класс сейчас «чтобы сейм был виден» — D34 прямо запрещает
(мёртвый код).
**Отвергнуто:** конфиг-переключатель источников / фабрика источников при ЕДИНСТВЕННОЙ реализации —
преждевременное обобщение, которое придётся сносить (Code Guidance P4.2).

## 6. Три инварианта, которые контракт удерживает

1. **Скользящее окно обоих существующих потребителей сохраняется, дневной разрез ДОБАВЛЯЕТСЯ**
   (D124/D38). Вывод `ai:cost-report` растёт: старая таблица + «Итого» + «Экономия кэша» остаются
   БАЙТ-В-БАЙТ по семантике, ниже добавляются дневная секция и строка подписи. Замена старой
   таблицы дневной = изменение поведения, замороженного D38.
2. **Деньги-производные остаются у потребителя.** Источник отдаёт токены и `cost_micros`; экономия
   explicit-кэша (`cached × (input − cached)` по `config('ai.capabilities')`) и курс ₽
   (`config('ai.cost_report.rub_per_usd')`) считаются в `LlmSpendReporter`/команде, как и сегодня.
   Перенос их в источник переоткрыл бы D38 через заднюю дверь и втащил прайсинг в слой, который про
   деньги-производные ничего не знает.
3. **Источник не подменяет и не читает слепок расхода на анализе (P4.1).** Слепок отвечает на
   вопрос «сколько стоил ЭТОТ документ» — вечно, потому что анализы не дропаются. Источник отвечает
   на вопрос «сколько мы тратили в эти дни» — в пределах retention. Обратного пересчёта нет ни в
   одну сторону: иначе P4.4 начала бы сверять биллинг с цифрой, у которой два разных происхождения.

## 7. Что источник НЕ делает (названо, а не умолчано)

- **не ходит в БД сам:** чтение — только через `App\Repositories\Llm\LlmCallReadRepository`,
  собственный `selectRaw` в источнике запрещён (`root/service-layer-map.md` §0: агрегаты своей
  таблицы — обязанность репозитория);
- **не печатает и не форматирует:** ни валют, ни таблиц, ни дат — это слой команды/виджета;
- **не фильтрует по успешности вызова:** отказы входят в отчёт с нулевой ценой, как и сегодня —
  «сколько потрачено» и «сколько попыток» остаются разными вопросами к одним строкам;
- **не заводит ролл-ап и таблицу суточных агрегатов** (D37): третий носитель одного факта рядом с
  вызовами и слепками не появляется, пока нет потребности глубже retention;
- **не кэширует ответ:** запрос идёт по диапазону `called_at` с партиционным pruning
  (индексы `llm_calls` — `(analysis_id)`, `(analysis_run_id)`, `(purpose, called_at)`, партиции
  RANGE по `called_at`), нового индекса разрез по дням не требует.
