### P6.4 — Витрина истории изменений в карточке закупки

**Intent:** Показать оператору историю закупки там, где он на неё смотрит: вкладки «События» и
«Редакции» в карточке `ProcurementResource`, секция длительностей и действие «Сравнить с предыдущей
редакцией» с человекочитаемым списком изменений — всё строго read-only.
**Why:** Витрина — прямое требование брифа («Должно быть заметно, какие изменения были в закупке»)
и выбор владельца по глубине: таймлайн + редакции + diff + длительности
(`brief/01-refinements.md` блок P6 п. 4, D66). Место для неё уже назначено самим кодом: докблок
`ProcurementResource` говорит «Карточка с таб-ами (события/редакции/позиции/протоколы/результаты) —
фаза 2», то есть каркас сознательно оставлен незаполненным.
`RAG:— (repo-grounded: app/Filament/Resources/Procurement/Procurements/ProcurementResource.php:17-21)`.
Реестр закупок при этом read-only по конструкции («оператор ревизует, не редактирует») — и это
инвариант, а не стиль: relation-manager со штатными действиями создания/правки тихо превратил бы
витрину продукта пайплайна в редактор (ловушка 8). Образец relation-manager'а в проекте есть —
`Estimates/RelationManagers/ItemsRelationManager` с табличным фильтром.
`RAG:— (repo-grounded: app/Filament/Resources/Procurement/Estimates/RelationManagers/ItemsRelationManager.php:16-27)`.
**Scope Included:** (1) `EventsRelationManager` — лента `prc_events`: время, тип (бейдж с
человекочитаемой подписью из словаря P6.3), поле, старое/новое значение, номер редакции; фильтры по
типу события и по окну дат, сортировка по `occurred_at` убыв.; (2) `RevisionsRelationManager` —
список `prc_revisions`: номер, `detected_at`, `source_updated_at`, причина, действие «Сравнить с
предыдущей» → модалка со списком изменённых полей (`RevisionDiffService` P6.3); (3) секция
инфолиста «Длительности»: когда обнаружена, когда опубликована, текущий/терминальный статус,
сколько идёт или сколько шла, время в каждом статусе; незавершённая закупка показывает «идёт», а не
прочерк; (4) регистрация обоих relation-manager'ов в `ProcurementResource::getRelations()`;
(5) read-only гарантии: ни одного действия создания/правки/удаления, форма relation-manager'а не
заводится; (6) окно по умолчанию — последние `N` дней с явным переключателем «за всё время», чтобы
запрос по умолчанию нёс границу (ловушка 4); (7) тесты Livewire: обе вкладки рендерятся и показывают
записи закупки; действие сравнения показывает изменённые поля; страница не содержит действий
мутации; закупка без истории рендерится без ошибки.
**Scope Excluded:** любые вычисления истории (всё считает P6.3 — витрина только показывает);
графики и агрегаты; вкладки «позиции»/«протоколы»/«результаты» из докблока (другой скоуп);
экспорт истории; правка `ProcurementsTable` и инфолиста сверх секции длительностей; собственный
словарь подписей (переиспользуется словарь P6.3); события и колонка `succeeded_at` (P6.5).

**Implementation Rules:** 1) **Витрина ничего не считает**: длительности и diff приходят готовыми из
сервисов P6.3; повторная логика в Filament запрещена — иначе два ответа на один вопрос разойдутся.
2) **Read-only структурно**: relation-manager'ы не объявляют формы и не регистрируют действия
создания/правки/удаления; проверяется тестом и grep-гейтом. 3) Запрос по умолчанию несёт временную
границу; «за всё время» — явный выбор оператора, а не поведение по умолчанию (ловушка 4). 4)
Eager-load всего, что показано в колонках; N+1 на партиционированных таблицах — это не «медленно»,
а десятки запросов на страницу. 5) Подписи типов событий и полей берутся из словаря P6.3; локальный
массив подписей в Filament — дефект (ловушка «второй словарь»). 6) Diff показывается СПИСКОМ
изменённых полей («было → стало»), а не двумя jsonb рядом (ловушка 7).
**Code Guidance:** Стиль — как в существующих ресурсах домена; каждый relation-manager несёт
докблок, объясняющий, почему он заведён (по образцу `ItemsRelationManager`) и почему он read-only.
Модалка сравнения — штатное `Action` с `modalContent`, без своего Blade-компонента, если хватает
штатных средств. Тесты — только `test('<интент по-русски>', fn)`, Livewire-тесты по образцу
`EstimateResourceTest`; данные — фабриками (`ProcurementEventFactory`, `ProcurementRevisionFactory`).
