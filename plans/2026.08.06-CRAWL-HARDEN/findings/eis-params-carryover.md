# FINDING (слой 1) — параметры ЕИС: что подтверждено и что предстоит снять

**Снято:** 2026-08-06 · **Как:** перенос из артефакта живой разведки предыдущего плана
`plans/archive/2026.07.31-SYS-INTEGRITY/artifacts/eis-filter-params.json` (Playwright MCP,
zakupki.gov.ru через RU-прокси, замер 2026-08-04 20:33–21:00 UTC).
**Зачем:** брейн-дамп требует ОКПД2-фильтр «как на ЕИС» и сортировку по дате обновления/размещения.
Часть нужных параметров уже подтверждена боевым замером, часть помечена «не установлено» —
именно она и есть скоуп разведки P1.

`RAG:✅ 2026-08-04 (живая разведка zakupki.gov.ru, Playwright MCP; артефакт
plans/archive/2026.07.31-SYS-INTEGRITY/artifacts/eis-filter-params.json)` — для строк со
статусом «подтверждено». Строки «не установлено» несут `[UNVERIFIED]` и обязаны быть
перепроверены живым прогоном P1.

## 1. Что нужно брейн-дампу и УЖЕ подтверждено

| Параметр | Значение | Для какого требования |
|:--|:--|:--|
| `sortBy` | `UPDATE_DATE` \| `PUBLISH_DATE` \| `PRICE` \| `RELEVANCE` | блок 2: «сортируем по дате обновления, по убыванию» / «по дате возрастанию» |
| `sortDirection` | `false` — по убыванию, `true` — по возрастанию | там же |
| `publishDateFrom` / `publishDateTo` | `dd.MM.yyyy`, границы включительно | архивный профиль: «за последний год» |
| `updateDateFrom` / `updateDateTo` | `dd.MM.yyyy`, границы включительно | актуальный профиль: окно обновления |
| `pc` | этап «Закупка завершена» | архивный профиль: «статус — закупка завершена» |
| `af` / `ca` / `pa` | подача заявок / работа комиссии / отменена | фильтры этапов |
| `priceFromGeneral` / `priceToGeneral` | интервал НМЦК, границы включительные | актуальный профиль: «определённые цены» |
| `fz44` / `fz223` / `ppRf615` | флаги закона; тот же endpoint выгрузки | «парсер начинать с 44-ФЗ» |
| `from` | номер первой записи блока; округляется ВНИЗ к границе 500 | пагинация |
| `to` | **фактически игнорируется**, влияет только на имя файла | — |
| cap глубины листинга | **5 000 записей на запрос** (`from=5001` возвращает `dedupSignature` блока `from=4501`) | ограничение окна, уже учтено `FreshRunProcessor::handleCapHit()` |
| `totalCount` без браузера | регуляркой `/downloadCsv\('[^']*',\s*'(\d+)'\)/` из SSR-разметки `extendedsearch/results.html` | решение «дробить окно или нет» |
| `scopeOkpd2Csv` | флаг колонки «Классификация по ОКПД2» в CSV | пост-фильтр по ОКПД2, если серверный фильтр не подойдёт |

Endpoint выгрузки: `https://zakupki.gov.ru/epz/order/orderCsvSettings/download.html`,
ответ `windows-1251`, сессия не требуется.
SSR-листинг: `https://zakupki.gov.ru/epz/order/extendedsearch/results.html`.

## 2. Что нужно брейн-дампу и НЕ подтверждено — скоуп разведки P1

| Параметр | Записанное назначение | Статус |
|:--|:--|:--|
| `okpd2Ids` | внутренние id справочника ОКПД2 | `[UNVERIFIED]` |
| `okpd2IdsCodes` | коды ОКПД2 (пример из артефакта: `41.20`) | `[UNVERIFIED]` |
| `okpd2IdsWithNested` | «с учётом вложенных» — ровно та «звёздочка `43.*`», которую просит владелец | `[UNVERIFIED]` |
| `okpd2IdsSeveral` | «несколько ОКПД2» | `[UNVERIFIED]` |

**Ключевые неизвестные, которые обязана снять разведка P1:**

1. Действует ли ОКПД2-фильтр на **CSV-выгрузке** (`download.html`), а не только на SSR-листинге.
   Проект забирает данные именно CSV-методом (`CsvSourceMethod`), поэтому «работает в UI, но не
   в выгрузке» = фильтр бесполезен как серверный и нужен пост-фильтр по колонке `scopeOkpd2Csv`.
2. Что именно принимает `okpd2Ids` — внутренний id справочника ЕИС или код. Если внутренний id,
   нужна карта «код ОКПД2 → id ЕИС», и это отдельный источник данных, которого у нас нет.
3. Как ведёт себя `okpd2IdsWithNested`: включает ли выбор `43` все `43.xx.xx` автоматически,
   или требуется перечислить листья.
4. Совместимость ОКПД2-фильтра с `sortBy=UPDATE_DATE` и c cap'ом 5 000 (сужает ли фильтр
   выборку настолько, что дробление окон можно упростить).

## 3. Прочее, требующее живой проверки в P1

- **Полный перечень этапов/статусов закупки 44-ФЗ на карточке** — брейн-дамп требует событие
  «закупка перешла в положительный терминальный статус». В артефакте есть только 4 флага
  фильтра (`af`/`ca`/`pc`/`pa`); соответствие им статусов НА КАРТОЧКЕ и состав
  `prc_status_mappings` против живого ЕИС не сверялись.
- **Структурные якоря вкладок карточки** (`common-info`, `documents`, `event-journal`,
  `supplier-results`) — база для healthcheck вёрстки (блок 4). Парсеры существуют
  (`Services/Procurement/Eis/Card/*`), но набора «эталонных якорей, чьё исчезновение = поломка»
  нигде не зафиксировано.
- **Версия фронтенда ЕИС** — в разметке номер релиза не найден при замере 2026-08-04; старая
  разведка снималась на `hotfix/16.2.1.25` от 02.07.2026. Значит, детект «вёрстка поменялась»
  нельзя строить на номере версии — только на структурных якорях.
