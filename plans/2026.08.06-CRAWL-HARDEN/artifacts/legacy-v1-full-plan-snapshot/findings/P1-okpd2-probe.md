## 1. Главный вердикт

**Серверный фильтр по ОКПД2 существует, работает и доезжает до CSV-выгрузки.**
Рабочая форма — ровно одна:

```
okpd2Ids=<внутренний id НСИ>[,<id>…]&okpd2IdsWithNested=on
```

**Пост-фильтр по колонке CSV невозможен** — колонка «Классификация по ОКПД2» приходит пустой
(§4). Развилка Q1 тем самым разрешается принудительно: вариант B физически нереализуем.

## 2. Что делает каждый из четырёх параметров

| Параметр | Что делает на самом деле | Исход |
|:--|:--|:--|
| `okpd2Ids` | **фильтрует**; принимает ВНУТРЕННИЙ id справочника НСИ, не код. Несколько — через запятую | подтверждено |
| `okpd2IdsWithNested` | **обязателен**: без него выдача пуста | подтверждено |
| `okpd2IdsCodes` | подпись тега в UI; **на выдачу не влияет** | подтверждено (влияния нет) |
| `okpd2IdsSeveral` | **другой фильтр** — «Закупка содержит несколько ОКПД2». Presence-based: срабатывает на любое значение, включая `false` | подтверждено |

Ловушка, стоившая отдельной пробы: `okpd2IdsSeveral` выглядит как часть механики выбора кодов,
но ею не является. Любая его форма (`=true`, `=false`, с кодами, без кодов) даёт один и тот же
`totalCount` 9732 — то есть он просто отбирает многокодовые закупки.

Вторая ловушка: **ЕИС молча игнорирует неизвестные и неприменимые ключи**, возвращая 200.
`okpd2IdsCodes=99.99.99` даёт базовые 22761 — ровно как отсутствие параметра. Поэтому
«параметр принялся» ничего не доказывает; доказывает только сдвиг `totalCount`.

## 3. Измерения (окно `fz44=on`, `publishDate` 01.08–05.08.2026)

| Запрос | totalCount |
|:--|--:|
| без фильтра ОКПД2 | 22 761 |
| `okpd2Ids=8873921` (код 43) — **без** `withNested` | не извлекается (выдача пуста) |
| `okpd2Ids=8873921` + `withNested=on` | **1 233** |
| `okpd2Ids=8873866` (раздел F) + `withNested=on` | **2 484** |
| `okpd2Ids=8873919,8873920,8873921` (41+42+43) + `withNested=on` | **2 484** |
| `okpd2IdsSeveral` (любое значение) | 9 732 |

**Перекрёстная сверка:** раздел `F` = `41+42+43` (2484 = 2484). Независимое подтверждение,
что сервер раскрывает вложенность корректно, а не считает что-то своё.

Почему без `withNested` пусто: закупки ссылаются на ЛИСТОВЫЕ коды (`43.21.10.140` и т.п.),
а не на группу `43`. Точное совпадение с узлом группы не даёт ничего. Практическое следствие:
**«маска `43.*`» — это не удобство, а единственный рабочий режим фильтра.**

## 4. CSV-выгрузка

Endpoint `/epz/order/orderCsvSettings/download.html`. Фильтр доезжает — три независимых
доказательства:

1. Query, который **ЕИС формирует сам** для кнопки выгрузки, содержит `okpd2Ids` и
   `okpd2IdsWithNested` (снято из `downloadCsv('…')` в SSR-разметке).
2. Пересечение реестровых номеров: блок 1 с фильтром `43` против блока 1 без фильтра —
   **16 из 500**.
3. Размер ответа при одном наборе колонок: без фильтра 48 271 B, фильтр `43` — 90 710 B,
   фильтр `41` — 116 637 B.

**Колонка «Классификация по ОКПД2» — пустая.** Запрошены все 25 флагов колонок; колонка
присутствует (индекс 14), но **0 непустых значений на 500 строк**. То же у соседних
классификаторных колонок (ОКДП, ОКПД, «Код позиции»). Сырая строка показывает подряд идущие
пустые поля: `…;RUB;0;;;;;;"КРАЕВОЕ ГОСУДАРСТВЕННОЕ БЮДЖЕТНОЕ УЧРЕЖДЕНИЕ…`.

Спот-проверка осмысленности: первая строка выгрузки с фильтром `43` —
«Выполнение работ по монтажу системы оповещения и управления эвакуацией», что соответствует
`43.21` (электромонтажные работы). Фильтр отбирает то, что нужно.

## 5. Как получать внутренние id

- Модалка: `/epz/nsi/okpd2/openModal.html?…&selectedCodes=<коды>`; дерево — `jquery.dynatree`
  в `#tree`, узел несёт `data.key` (id) и `data.title` (`«43: Работы строительные
  специализированные»`).
- Обход без UI: **`GET /epz/api/nsi/okpd2/children.html?parentId=<id>`** — дети узла.
  Корневой уровень даёт 21 раздел `A…U`.

Снятые id, нужные проекту:

| Код | id НСИ | Наименование |
|:--|--:|:--|
| `F` (раздел) | 8873866 | СООРУЖЕНИЯ И СТРОИТЕЛЬНЫЕ РАБОТЫ |
| `41` | 8873919 | Здания и работы по возведению зданий |
| `42` | 8873920 | Сооружения и строительные работы в области гражданского строительства |
| `43` | 8873921 | Работы строительные специализированные |

Полный список разделов верхнего уровня — в `artifacts/eis-okpd2-probe.json`.

## 6. Что осталось «не установлено»

1. **Стабильность внутренних id во времени** — переживают ли они обновление справочника НСИ.
   Это несущий риск: id зашивается в профиль обхода. Митигация — хранить в профиле КОД,
   а id резолвить по карте, которую можно пересобрать (`children.html`).
2. Поведение фильтра на ветке 223-ФЗ (`fz223=on`) — не проверялось.
3. Предел на число id в `okpd2Ids` — проверено только 3 значения.
4. Бывает ли колонка ОКПД2 в CSV непустой в принципе — проверено одно окно дат, 500 строк.

## 7. Побочные наблюдения (пригодятся P5)

- ЕИС не отвечает на прямые запросы без RU-прокси: соединение виснет до таймаута, без ошибки.
- Chromium не проверяет сертификат ЕИС дефолтным набором корней (цепочка Минцифры);
  разведка велась в контексте с `ignoreHTTPSErrors`. Launcher `scripts/playwright-mcp.sh`
  исправлен в тот же ход, рецепт вынесен в скилл `eis-recon`.
- Структурные якоря, годные под healthcheck (P5), уже видны: `#okpd2IdsAnchor`, `#tree`,
  `#btn-primary.okpd2SelectButton`, регулярка `downloadCsv\('…',\s*'(\d+)'\)`, заголовок CSV
  `Реестровый номер закупки;…`.
