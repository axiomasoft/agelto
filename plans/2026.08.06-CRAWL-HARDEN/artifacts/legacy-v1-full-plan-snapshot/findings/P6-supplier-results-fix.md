# P6.2 — разрыв между живой success-фактурой и контрактом award

## Источник

- Дерево: `a8ffaae0`.
- HTML: `artifacts/eis-card-html-success/supplier-results.html`, карточка
  `0356500001426005498`, снято 2026-08-07.
- Инвентарь: `artifacts/eis-card-inventory.json`, вкладка `supplier-results` для 44-ФЗ.

## Факт

Живая вкладка использует ожидаемый паттерн `section.blockInfo__section` /
`span.section__title` + `span.section__info` / `table.tableBlock`. На ней есть:

- протокол подведения итогов от 07.08.2026 №ИЭОК;
- строка участника с идентификатором `2`, рангом `1 - Победитель` и предложением
  `10 000 000,00`;
- заглушка «Сведения о контракте из реестра контрактов отсутствуют».

На вкладке нет наименования, ИНН или ОГРН победителя. Таблица
«Заказчик(и), с которыми планируется заключить контракт» описывает покупателя и не может быть
использована как поставщик. Проверка:

```bash
grep -Ec 'ИНН|ОГРН' plans/2026.08.06-CRAWL-HARDEN/artifacts/eis-card-html-success/supplier-results.html
# 0
grep -Ec '1 - Победитель' plans/2026.08.06-CRAWL-HARDEN/artifacts/eis-card-html-success/supplier-results.html
# 1
grep -Ec 'Сведения о контракте из реестра контрактов отсутствуют' plans/2026.08.06-CRAWL-HARDEN/artifacts/eis-card-html-success/supplier-results.html
# 1
```

Инвентарь P1.5 подтверждает ту же форму для `zk20`, `ok20` и `ezt20`: идентификатор участника,
порядковый номер/ранг и цена, без поля с реквизитами организации.

## Почему P6.2 нельзя исполнить по текущему ТЗ

`AwardData` требует `OrganizationData $winner`, а `SupplierResultsProcessor` создаёт
`prc_awards` только при наличии `AwardData`. Подстановка покупателя или вымышленной организации
нарушит анти-подгонку и склеит разные организации; частичный разбор только протокола/заявки не
выполнит acceptance «победитель и award доезжают до `prc_awards`». Расширение DTO и правка
processor одновременно запрещены `Scope Excluded`.

## Варианты редизайна

1. Добавить отдельное обогащение победителя из страницы протокола либо реестра контрактов;
   потребуется явно спроектировать сетевой маршрут, бюджет запросов и момент повторной попытки,
   когда контракт ещё отсутствует.
2. Разрешить анонимный award по идентификатору/рангу участника с последующим обогащением;
   это меняет DTO, processor и, вероятно, схему/доменный контракт.
3. Сузить P6.2 до протокола и анонимных bids, а продюсер `Awarded` перенести в отдельный item,
   который владеет разрешением личности победителя.

Нужен `plan-design`, потому что выбор меняет acceptance и границы текущего item'а.
