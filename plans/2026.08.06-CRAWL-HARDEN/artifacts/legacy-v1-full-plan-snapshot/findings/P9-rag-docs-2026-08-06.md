## 1. Какие типы mermaid-диаграмм безопасны для нашего дерева

**Запрос:** «Mermaid diagram types supported by GitHub markdown rendering and Obsidian in 2026:
flowchart, sequenceDiagram, stateDiagram-v2, erDiagram, C4Context, architecture-beta, timeline,
gantt — which are stable and which are experimental; known rendering pitfalls GitHub vs Obsidian».

**Вердикт:** `RAG:✅ 2026-08-06 (perplexity-web; источники — docs.github.com «Creating diagrams»,
obsibrain.com «Mermaid diagram — diagrams as code in 2026», forum.obsidian.md/t/107464,
unmesh.dev/post/obsidian_mermaid)`.

| Тип | GitHub | Obsidian | Наш вердикт |
|:--|:--|:--|:--|
| `flowchart` / `graph` | стабилен | стабилен | **разрешён** |
| `sequenceDiagram` | стабилен | стабилен | **разрешён** |
| `stateDiagram-v2` | стабилен | стабилен | **разрешён** (уже используется — Д1) |
| `erDiagram` | стабилен | стабилен | **разрешён** |
| `gantt`, `timeline` | стабильны | стабильны, но чаще обрезаются по ширине панели | разрешены, но нам не нужны |
| `C4Context` | экспериментальный | часто ломается | **запрещён** |
| `architecture-beta` | экспериментальный | часто ломается | **запрещён** |

Практические ловушки, значимые именно для нас (оба зеркала — GitHub и Obsidian-vault Brain):

1. **Версия mermaid у обеих площадок отстаёт от документации mermaid.** Синтаксис из свежих
   примеров может «молча» не отрисоваться («No diagram type detected»). Отсюда правило: только
   типы из разрешённого списка выше, никаких новых директив ради красоты.
2. **Широкие диаграммы обрезаются** (Obsidian) или получают горизонтальный скролл (GitHub).
   Отсюда правило: одна диаграмма = один вопрос; большой контур разбивается на несколько.
3. **HTML и markdown внутри подписей узлов не рендерятся** и могут сломать парсинг блока целиком.
4. Кастомный CSS/темы недоступны на GitHub — оформление только штатное (`classDef`).

Совпадает с уже записанным каноном репозитория: «Mermaid — инлайн в markdown-файле (рендерится и
GitHub, и Obsidian), отдельные файлы только для диаграмм с двумя и более использованиями»
(`RAG:— (repo-grounded: docs/meta/editing.md §Диаграммы)`), плюс известный локальный gotcha:
`stateDiagram-v2` не парсит `::` в некавычечной edge-метке.

## 2. Гейт документации: что вообще принято проверять машиной

**Вердикт:** `RAG:— (repo-grounded)` — внешняя ступень для этого не понадобилась: практика
docs-as-code уже зафиксирована в собственном research'е проекта («markdown в git, doc-обновление в
Definition of Done, **линк-чекер**» — `plans/archive/2026.07.07-EST-AI/research/H-docs-structure.md`
§Выжимка п. 2), а требование к содержимому — в `.ai/guidelines/docs-pr-checklist.md`:
frontmatter `audience:`/`type:` и «внутренние ссылки не сломаны». Оба требования сегодня НЕ
проверяются ничем — гейта в дереве нет (`grep -rl "docs/" tests/` даёт только три теста
AI-контура, ни один не про дерево доков).

Проверяемый минимум, вытекающий из этих двух источников:

- frontmatter присутствует и несёт `audience:`/`type:` из закрытых словарей;
- каждая относительная markdown-ссылка резолвится в существующий файл;
- каждый файл достижим из навигации (`docs/index.md` → `_index.md` раздела) — иначе документ
  существует, но его никто не найдёт.

Форма гейта выбрана по идиоме репозитория, а не по внешней практике: `Symfony\Component\Finder`
поверх дерева в unit-тесте — ровно так уже устроен `tests/Unit/Architecture/DomainLayoutTest.php`
(«предмет проверки — путь и строка, а не граф `uses`»).
