### 1.1. Ключевое наблюдение: 39 из 53 падений — это ОДИН дефолт фабрики

`CrawlerFactory::definition()` отдаёт `'filter' => null`, а после D18 такая модель для реестра

## 2. Скрытая флакость: `RegistryFactory` отдаёт код случайно

`RegistryFactory::definition()` ставит `'code' => fake()->randomElement(['fz44', 'fz223'])`, а
`config('crawler.filters')` знает ровно один код — `fz44`. Отсюда два следствия, оба измерены:

1. **Гейт срабатывает через раз.** `DeltaScanTest` и `ChangeTrackingWindowTest` в списке §1
   ОТСУТСТВУЮТ, хотя заводят краулеры ровно так же (`Crawler::factory()->create([...])`) — в этом
   прогоне их реестрам выпал `fz223`, для которого требование скоупа не объявлено. Прошлый замер
   (handoff от 2026-08-07, подмножество из шести путей) оба файла в падающих НАЗЫВАЛ.
   `RAG:— (repo-grounded: tests/Feature/Crawler/DeltaScanTest.php:73-74 Registry::factory()->create()
   без кода; database/factories/Procurement/Platform/RegistryFactory.php:22)`.
2. **Дефолт фильтра в `CrawlerFactory` без пиннинга кода опасен в обратную сторону:** краулер с
   непустым фильтром на реестре `fz223` падает в `RuntimeException` `resolveFilter()` («не
   настроен класс фильтра»), а не в гейт. Две правки обязаны ехать ВМЕСТЕ.
   `RAG:— (repo-grounded: app/Services/Procurement/CrawlerFilterFactory.php:28-32;
   app/Models/Procurement/Crawler/Crawler.php resolveFilter())`.

Пиннинг `'code' => 'fz44'` ничего не отнимает: тесты, которым нужен другой реестр, задают код
ЯВНО и сегодня (`CrawlerFilterContractTest:75`, `StatusMappingSeederTest:60`,
`EisCsvRowMapperTest:61` — все три с явным `fz223`).

## 3. Почему форма обязана получить поле в P2.2, а не в P2.4

Оба падения `CrawlerFormTest` — не «тест устарел», а мёртвый операторский путь:

- **`сохранение профиля формой …`** — `fillForm(['filter' => ['stageCompleted' => true,
  'okpd2Codes' => ['43']]])` отбрасывает ключ `okpd2Codes`: компоненты `filter.okpd2Codes` в
  `CrawlerForm::filterFields()` нет, а Filament дегидрирует только объявленные компоненты.
  Сохранение падает на гейте.
- **`обязательные колонки нельзя снять …`** — страница редактирования дегидрирует секцию фильтра
  из СВОИХ компонент, поэтому `okpd2Codes` существующей записи теряется при любом `save()`, даже
  если оператор трогал только колонки. Это единственный тест мутации формы в файле; выбросить его
  ради зелёного — снять покрытие с механики `MANDATORY_COLUMN_FLAGS`.

`RAG:— (repo-grounded: app/Filament/Resources/Procurement/Crawler/Crawlers/Schemas/CrawlerForm.php
filterFields() ветка EisSearchFilter::class — десять компонент, ни одной для okpd2Codes;
tests/Feature/Filament/CrawlerFormTest.php тесты 1 и 2)`.

То есть между P2.2 и P2.4 оператор не может завести НИ ОДИН профиль ЕИС и не может отредактировать
существующий. Это ровно тот класс, ради которого Implementation Rules P2.2 п. 6 уже требует чинить
сид ТЕМ ЖЕ коммитом («разнос по двум item'ам оставит дерево в нерабочем состоянии»), — правило
существовало, но применялось только к сиду.

**Материал для минимального поля уже есть:** P2.1 закрыт, `Okpd2NodeReadRepository::selectableNodes(int $platformId)`
отдаёт узлы площадки, упорядоченные по коду. Площадка достаётся из выбранного реестра
(`Registry::find($registryId)->platform_id`) — форма уже резолвит реестр этим путём в
`resolveFilterClass()` и `previewUrl()`.
`RAG:— (repo-grounded: app/Repositories/Procurement/Platform/Okpd2NodeReadRepository.php:33-41;
CrawlerForm::resolveFilterClass())`.

Поэтому расщепление «минимальный рабочий мультиселект в P2.2 → сгруппированный поисковый в P2.4»
не создаёт выброшенной работы: это ОДНА компонента, которой P2.4 добавляет `->searchable()`,
группировку `groupBy('parent_code')`, два `helperText` и `Placeholder` пустой карты.

## 5. Что из этого НЕ решается этим заходом

- Загрязнение батч-прогона (`EisSeedersTest`, `StatusMappingSeederTest` видят чужие реестры) —
  дефект тестового контура, существующий на baseline; ни один item плана его не адресует. Назван
  в Open risks handoff'а как долг, отдельного item'а этим заходом не заводится (анти-скоуп: заход
  открыт под редизайн ТЗ P2.2, а не под починку тестового контура).
- Строка «полный прогон — зелено» стоит в Validation и у остальных 45 незакрытых items — D110
  меняет её только у P2.2; остальные правит тот, кто их будет исполнять или следующий
  `plan-design`. Долг назван в D110 явно.
