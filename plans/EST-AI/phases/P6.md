# P6 — Полное извлечение смет

## Phase Context

Фаза 5 роадмапа, ТЗ 03 §3.5 + 04 §4 + спека 08 (P1.2). Многошаговый разбор (D3): (1) паспорт/границы — число строк, разделы, шапка, список смет в документе (в одном файле может быть НЕСКОЛЬКО смет, рвущихся на разных страницах — v1-поле `state`); (2) строки построчными диапазонами (row-range, calibrate 20–50 строк) по кэшированному документу, temperature=0, structured output, каждый ответ несёт буфер `incomplete_items`; (3) итоги/начисления отдельным шагом; (4) merge + stitcher + детерминированная арифметическая валидация в коде; (5) точечный re-run аномального диапазона. **Два пути (D29/D30):** основной row-range по целому документу — когда файл в лимитах маршрута (Gemini: 50МБ/1000стр.); оконный трёхстадийный (P6.4: discovery-сегментация смет → per-estimate окна → totals) — для гигантских/мульти-сметных документов сверх лимитов; выбор — `preflight` в P6.1 ДО загрузки; необрабатываемое — `unprocessable` с reason (D32). **Стабильность на объёме (D31):** длинный разбор = цепочка коротких self-requeue запусков job'а по `analysis.progress`, resume не переизвлекает готовое, ни один шаг не выпадает за токены/таймаут. Персист: `prc_estimates` + sections/items/resources/totals, сырьё в `raw_result`/`raw_result_ref`, качество в `rows_expected/rows_extracted/validation_status`. Всё на контрактах P2 и LLM-слое P3, очередь ai_extraction из P4.1. Тесты — только FakeLlmProvider + JSON-фикстуры чанков.

### P6.4 — Оконный путь: трёхстадийный разбор гигантских/мульти-сметных документов

**Status:** ⬜ Not started
**Intent:** `WindowedExtractionStrategy` — путь для документов, не влезающих в лимиты маршрута (выбран preflight'ом P6.1, D29) ИЛИ превышающих порог страниц (config). Собственный трёхстадийный алгоритм (D30, спека 08 §fallback), т.к. паспорт P6.1 требует целого документа в контексте, а его тут нет: **(1) discovery-проход** — резка PDF на окна по K страниц (default 3, overlap 1, qpdf-слайсер P5.1), дешёвой моделью (screening-класс) по каждому окну извлекаются МАРКЕРЫ границ смет (`DiscoveryResponse`: estimate_start/estimate_end/continuation, page, title?) → бэкенд детерминированно склеивает сегменты «смета k = страницы a..b» и собирает `PassportResponse`-эквивалент БЕЗ единого LLM-вызова; **(2) per-estimate извлечение** — rows-окна внутри страничного сегмента каждой сметы тем же rows-контрактом (page-маркеры в user-части, incomplete-буфер); **(3) totals** — по последним страницам сегмента. Сборка — тот же Stitcher (P6.2), персист — тот же Persister (P6.3).
**Why:** Вводная владельца (research/L finding 17): документ 2–200 МБ, сотни страниц-сканов, несколько ПЕРЕМЕШАННЫХ смет, упор в 50МБ/1000стр. Files API. Row-range по целому документу тут невозможен; discovery-проход даёт паспорт и сегментацию смет, не держа документ в контексте — единственный стабильный путь для гигантов.
**Scope Included:** стратегия за интерфейсом `ChunkSource` (row-range vs windowed — обе реализации, выбор в P6.1 по preflight); `SegmentAssembler` (discovery-маркеры → сегменты смет детерминированно, с эвристикой «continuation склеивает сегмент через границу окна»); переиспользование PdfPageSlicer/Stitcher/Validator/Persister без изменений; интеграция с checkpoint-requeue P6.1 (окна — единица чекпоинта); тесты на FakeLlmProvider: (а) 2 сметы в одном документе, границы на середине окон → корректная сегментация; (б) смета, продолжающаяся через несколько окон (continuation); (в) искусственный разрыв строки на стыке окон → склейка stitcher'ом; (г) сегментация детерминирована (тот же discovery-вход → тот же паспорт).
**Scope Excluded:** контракт `DiscoveryResponse` — создаётся в P2.2 (здесь используется); калибровка порогов/размера окна (на реальных сметах — Pending Work до датасета P7.4); параллелизм окон.
