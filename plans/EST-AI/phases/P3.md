# P3 — LLM-слой: контракт, Gemini-адаптер, резолверы, валидация

## Phase Context

Реализует ТЗ `docs/specs/v2/04-llm-providers.md`: домен зависит от собственного контракта `LlmProvider`, транспорт — Prism (D8), всё в `app/Services/Llm/`. Схема БД готова: `prc_ai_providers`, `prc_ai_routes`, `prc_ai_prompts`, `prc_ai_llm_calls` (партиционирована), `prc_ai_analyses` — см. `plans/EST-AI/research/D-v2-state.md` §Схема. Ключевые требования research/E: finishReason-гейт (MAX_TOKENS → брак до parse), учёт usage включая cached_tokens, стабильный системный префикс в начале запроса, retry «repair — синтаксис, re-ask — семантика». Фаза завершена: скрининг-подобный вызов через фейковый провайдер проходит весь путь резолвер→промт→вызов→валидация→запись LlmCall под тестами; реальный Gemini-адаптер написан, но живьём не вызывается (smoke — вручную владельцем).

### P3.2 — Gemini-адаптер (Prism): вызовы, Files API, usage

**Status:** ⬜ Not started
**Intent:** `composer require prism-php/prism`; адаптер `app/Services/Llm/Providers/PrismGeminiProvider.php`, реализующий все три контракта: structured вызовы с `responseJsonSchema`, upload PDF через Files API (48ч TTL, реальный mime!), explicit context cache CRUD, маппинг usage/finishReason; плюс `LlmCallRecorder` — запись каждого вызова в `prc_ai_llm_calls` (tokens, cached_tokens, cost_micros, duration_ms, prompt_version_set, request/response refs в object storage) через store-репозиторий.
**Why:** Единственная точка контакта с Gemini; сюда стягиваются все уроки v1 (учёт токенов, rules_hash, прокси) и research/E (finishReason, cached_tokens, files 48h).

### P3.4 — Валидационный каскад и политика ретраев

**Status:** ⬜ Not started
**Intent:** `StructuredResponseValidator`: каскад finishReason-гейт → `json_validate()`/`json_decode(JSON_THROW_ON_ERROR)` → гидрация Data-класса → доменные проверки; `ReaskPolicy`: до 2 re-ask с текстом ошибки валидатора и прошлым выводом, затем эскалация маршрутом (следующий priority, обычно модель классом выше) либо фейл в error-блок.
**Why:** Research/E §2/§6: structured output НЕ гарантирует валидность при обрезании; «repair — синтаксис, re-ask — семантика, escalate — неопределённость» — иначе пайплайн будет тихо писать мусор в prc_estimate_*.
**Scope Included:** оба сервиса в `app/Services/Llm/Validation/`; результат — sealed-подобный `ValidationOutcome` (ok(data) / retryable(reason) / fatal(reason)); MAX_TOKENS всегда retryable с рекомендацией «уменьшить окно» (наверх, оркестратору P6.1); юнит-тесты всех ветвей на FakeLlmProvider.
**Scope Excluded:** арифметическая сверка сумм сметы (P6.2 — доменная, не транспортная); backoff очередей (P4.1 — на уровне Job).
**Inputs:** паттерн Instructor (re-ask с ошибкой) — research/E §6; FakeLlmProvider (P3.1).
**Files:** app/Services/Llm/Validation/{StructuredResponseValidator,ReaskPolicy,ValidationOutcome}.php · tests/Unit/Llm/StructuredResponseValidatorTest.php · tests/Unit/Llm/ReaskPolicyTest.php
**Required Reads:** 1) plans/EST-AI/research/E-gemini-research.md §2,§6 2) app/Services/Llm/Contracts/ (P3.1) 3) docs/specs/v2/03-document-pipeline.md §3.5 п.4
**Implementation Rules:** никакого «дописывания скобок» в невалидный JSON (repair-библиотеки не подключаем — гейт finishReason должен ловить обрезание раньше); каждый re-ask — новый LlmCall со своей записью; счётчик re-ask ≤ 2.
**Code Guidance:** сообщение re-ask строится шаблоном: «Предыдущий ответ не прошёл валидацию: {ошибки}. Верни исправленный JSON той же схемы, ничего не поясняй»; доменные проверки на этом уровне — только структурные (row_index монотонен внутри чанка, дубликаты row_index); тест: MAX_TOKENS не доходит до json_decode.
