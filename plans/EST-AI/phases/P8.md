# P8 — Промт-система: сиды, protected, базовые тексты

## Phase Context

Реализует D5+D17: промты — файлы `resources/ai/prompts/**` под git (источник истины), в БД `prc_ai_prompts` их доставляет `PromptSeeder` через обычный `php artisan db:seed` (upsert по кодовому полю `key` + `version`, id не используется). Сидовые промты защищены флагом `is_protected` — из админки они read-only, операторы могут только создавать дополнительные корректирующие записи (не-protected). Базовые тексты закладываются здесь: слоёная структура по шагам (global → step-global → step, канон композиции P3.3) — несколько промтов, постепенно раскрывающих шаги парсинга, а не один монолит. Это точка входа следующего шага владельца: другая модель будет итерировать тексты по папке эталонных смет с обратной связью через `ai:eval:run` (P7.4). Фаза завершена: `migrate:fresh --seed` даёт рабочий набор промтов, protected-поведение под тестами.

### P8.2 — is_protected: миграция и поведение админки

> 🔴 ESCALATION P8.2: Implementation Rules item'а требует «запрет на уровне Policy (не только
> UI) — API/консоль тоже не должны править protected» и Intent требует «edit/delete заблокированы
> политикой» в Filament-ресурсе Prompts. Это структурно недостижимо plain-`Gate::policy()`-подходом
> в ТЕКУЩЕЙ конфигурации AzGuard, уже подключённого в проект: `config/az-guard-filament.php` несёт
> `'source' => 'enum'`, `'enforce' => true`, `'exclude' => ['resources' => []]` (PromptResource НЕ
> исключён из RBAC-дискавери) → `AzGuard\Filament\AzGuardFilamentServiceProvider::boot()`
> регистрирует `Gate::before` через `ResourceGate::check()` (`packages/filament/src/Permissions/
> ResourceGate.php`), который для `update`/`delete` на ЛЮБОЙ обнаруженной Filament-модели отвечает
> `(bool) $user->hasPermission(...)` БЕЗ учёта записи — Laravel `Gate::before`, вернувший
> non-null, полностью замещает результат любой позже зарегистрированной `Gate::policy()` (моя
> `PromptPolicy` при обычном `Gate::allows('update', $prompt)`/`$resource::canEdit($record)` вообще
> не вызывается). Подтверждено эмпирически через tinker на этой ветке: `OperatorRole`
> (`app/Guards/Admin/Roles/OperatorRole.php`) УЖЕ несёт полный CRUD на `PromptPermission`
> (`...$this->crud(PromptPermission::class)`, `Update`+`Delete` включены) — пользователь с этой
> ролью (штатной для «промпты» по её же докблоку) получает `Gate::allows('update', $protectedPrompt)
> === true` и `('delete', ...) === true` НЕЗАВИСИМО от `is_protected`, т.к. `ResourceGate` коротко
> замыкает Gate ДО вызова `PromptPolicy::update()/delete()`. Т.е. любой штатный оператор с ролью
> `OperatorRole` может отредактировать/удалить protected-промт через Filament UI, что прямо
> противоречит цели item'а (D17 — «канон из git» read-only в админке). Scope Excluded этого же
> item'а прямо пишет «RBAC-роли (Azguard-фаза, вне плана)» — но исправление конфликта требует
> именно RBAC-решения (одно из: убрать Update/Delete у `PromptPermission` из `OperatorRole`;
> завести отдельный `#[GuardPolicy]`/`#[GateAbility]`-паттерн для Prompt по примеру
> `policy-gateability.php`-сниппета AzGuard, который работает только при `source => 'policy'`;
> кастомный `Gate::after`/приоритет между `ResourceGate` и `PromptPolicy`; исключить PromptResource
> из discovery). Любой из вариантов — архитектурное решение вне текущего Scope Included: план
> расходится сам с собой (Scope Included требует Policy-enforcement, Scope Excluded запрещает
> трогать RBAC, а RBAC уже структурно исключает Policy-enforcement для этой модели) →
> trigger: конфликт правил | нужен: plan-design.
**Status:** 🔴 Blocked
**Intent:** Поведение админки для `is_protected` (колонка создана в P8.1): Filament-ресурс Prompts — protected-записи read-only (edit/delete заблокированы политикой и спрятаны из таблицы действий), создание новых записей оператором всегда `is_protected=false`; подсказка в форме «канонические промты меняются через git + db:seed».
