# P8 — Промт-система: сиды, protected, базовые тексты

## Phase Context

Реализует D5+D17: промты — файлы `resources/ai/prompts/**` под git (источник истины), в БД `prc_ai_prompts` их доставляет `PromptSeeder` через обычный `php artisan db:seed` (upsert по кодовому полю `key` + `version`, id не используется). Сидовые промты защищены флагом `is_protected` — из админки они read-only, операторы могут только создавать дополнительные корректирующие записи (не-protected). Базовые тексты закладываются здесь: слоёная структура по шагам (global → step-global → step, канон композиции P3.3) — несколько промтов, постепенно раскрывающих шаги парсинга, а не один монолит. Это точка входа следующего шага владельца: другая модель будет итерировать тексты по папке эталонных смет с обратной связью через `ai:eval:run` (P7.4). Фаза завершена: `migrate:fresh --seed` даёт рабочий набор промтов, protected-поведение под тестами.

### P8.2 — is_protected: миграция и поведение админки

> **Разрешение эскалации (plan-design, 2026-07-09, D44):** эскалация от 2026-07-09 закрыта.
> Корень (подтверждён чтением исходников `packages/azguard`, доступного в этом воркспейсе):
> `AzGuardFilamentServiceProvider::boot()` регистрирует `Gate::before` через `ResourceGate::check()`
> (`packages/filament/src/AzGuardFilamentServiceProvider.php:75-81`) ТОЛЬКО для моделей, попавших в
> карту `FilamentDiscovery::subjects($panelId)` (`packages/filament/src/Permissions/
> ResourceGate.php:31-57`) — для остальных моделей `check()` возвращает `null` (defers), и Laravel
> «`Gate::before`, вернувший non-null» не срабатывает, обычный `Gate::policy()` резолвится штатно.
> `FilamentDiscovery::subjects()` пропускает любой Filament-ресурс из
> `config('az-guard-filament.exclude.resources')` (`packages/filament/src/Permissions/
> FilamentDiscovery.php:46-49,129-132`) — **сравнение идёт по классу Resource, не модели**.
> Решение: **исключить `PromptResource::class` из `exclude.resources`** (снимает enum-RBAC
> короткое замыкание ИМЕННО для `Prompt`, остальной admin-панели не касается) + написать
> обычную AzGuard-политику `PromptPolicy` с `#[GuardPolicy(model: Prompt::class)]` +
> `#[GateAbility(permission: PromptPermission::Update/::Delete)]` на методах `update()`/`delete()`
> (канон `docs/best-practices/policies-and-gates.md` пакета: метод сам перепроверяет
> `$user->hasPermission(...)` И накладывает поверх запись-специфичный чек — никакого отдельного
> `Gate::after`/композиции не существует, это ручная композиция внутри метода политики). Ядро
> AzGuard (`AzGuard\PanelProvider::boot()`, `packages/core/src/PanelProvider.php:37-64`) сканирует
> **весь `app/Guards/Admin/**`** (basePath панели — рефлексия расположения
> `AdminGuardPanelProvider`, `app/Guards/Admin/AdminGuardPanelProvider.php:31`) на файлы `*Policy.php`
> РЕКУРСИВНО без требования конкретной подпапки (`packages/core/src/Guard/PolicyDiscovery.php:27`)
> и САМ вызывает `Gate::policy($modelClass, $policyClass)` по `#[GuardPolicy(model:...)]`
> (`PolicyDiscovery::resolveModelClass()`, читает атрибут напрямую — `packages/core/src/Guard/
> PolicyDiscovery.php:49-55`) — ручной `Gate::policy()` в `AppServiceProvider` (как пытался
> черновик) НЕ нужен и conflict-prone (двойная регистрация). Итог: НЕ RBAC-решение (роли/права не
> трогаются, `OperatorRole` остаётся с Update/Delete на `PromptPermission` — коарс-права остаются
> предусловием, `PromptPolicy::update()` их перепроверяет сама) — это добавление ОДНОЙ строки в
> `exclude.resources` + одна политика, ровно то, что Scope Included и просил, без противоречия со
> Scope Excluded «RBAC-роли». D44 фиксирует решение в Decision Log плана.
