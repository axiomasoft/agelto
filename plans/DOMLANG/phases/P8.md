# P8 — Lifecycle-map и state machines единым документом

## Phase Context

> СКЕЛЕТ — не детализирован, разворачивается /task:plan-design DOMLANG P8

Закрывает валидную находку аудита: слова `status`/`stage`/`state`/`step` живут на четырёх уровнях
одновременно. Рефакторинг **не нужен** — оси уже разделены в коде; не хватает одного сводного
документа.

Четыре независимые машины состояний: `ProcurementStatus` (8 кейсов, жизненный цикл закупки) ·
`DocumentStatus` (8, пайплайн документа) · `AnalysisStatus` (5) + `AnalysisStep` (2) ·
`RunStatus` (5, прогон краулера). Плюс `PipelineStage` (3) — стадия, не статус.

Второй Deliverable — `entity-lifecycle-map`: кто создаёт сущность впервые, какая стадия вправе её
мутировать, какая только добавляет дочерние, что считается **повтором** vs **новой ревизией**
(`prc_revisions`) vs **новой версией документа** (`prc_document_versions.content_hash`). Аудит
верно указал, что путаница revision ⇄ document version — реальный риск для следующего исполнителя.

Частичные диаграммы уже есть (`docs/03_Dev/document-pipeline.md` Д1/Д2/Д4) — не дублировать,
ссылаться.

**Ловушка:** mermaid `stateDiagram` не парсит `Class::method()` — использовать `Class.method()`
(workaround зафиксирован в `plans/EST-AI/handoff.md`).

**Scope Included:** `docs/03_Dev/state-machines.md` (4 FSM) + `entity-lifecycle-map`.
**Scope Excluded:** изменение самих enum'ов (кроме уже решённого в P2.1); дублирование Д1/Д2/Д4.
