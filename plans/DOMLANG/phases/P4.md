# P4 — Provenance: тонкий срез по конфликтным полям

## Phase Context

Фаза с **легальным отрицательным исходом**. Сначала доказать, потом кодить.

ADR-0008 (`docs/03_Dev/adr/0008-thin-provenance-slice.md`, решение D4) материализует fact-level
provenance **только** для полей, приходящих из ≥2 слоёв **с расхождением значений**;
пятиуровневая схема `*-derived` из внешнего аудита отклонена. Правило взято из
`RAG:✅ 2026-07-10 «data provenance/lineage: W3C PROV vs прагматичные колонки»`: fine-grained
происхождение окупается, только если ответ должен пережить дедупликацию или согласование
источников. Coarse-lineage в проекте уже есть (`prc_revisions.crawler_run_id`,
`prc_fetches.artifact_ref`, `prc_ai_analyses.{provider,model,rules_hash}`, `prc_estimates.raw_result`,
`prc_documents.source_url`) и покрывает вопрос «кто произвёл запись».

Наличие конфликтных полей — **предмет доказательства, а не предпосылка** (D13, D15). Гипотезы
черновика (`status`, НМЦК, сроки подачи заявок) не подтверждены кодом и подлежат проверке, а не
вере. Классификация кандидатов детерминирована правилами **R1/R2/R3** (D23): дизайн-разведка —
`findings/P4-write-site-map.md` (лид, не вердикт).

`P4.1` (research, кода не пишет) выдаёт proof-таблицу и вердикт. `P4.2` материализует **только**
поля класса R1 с названным потребителем. Ноль полей R1 → оба item'а и фаза закрываются
`⛔ Skipped by decision`, ADR-0008 фиксирует триггер возврата. Это успешный исход, а не провал.

**Scope Included:** research-доказательство конфликтов (proof-таблица, вердикт по правилам R1/R2/R3);
материализация provenance строго для доказанных полей класса R1.
**Scope Excluded:** колонка `provenance` на каждой доменной таблице (прямо запрещено ADR-0008);
дублирование существующего coarse-lineage; пять уровней `*-derived` из аудита; починка дефектов
класса R2/R3 (маршрутизируются в фазу P5, D24); правка `prc_lots`/`prc_cancellations`/
`prc_clarifications` (0 write-site'ов — мёртвые таблицы, вне вопроса о происхождении).

### P4.2 — Материализация provenance для доказанных полей

**Status:** ⛔ Skipped by decision
**Intent:** Завести fact-level provenance **ровно для полей класса R1** из вердикта `P4.1` — колонка(и) происхождения, запись через store-репозиторий, чтение названным потребителем, Pest-тест на разрешение расхождения. Вердикт `N = 0` → item закрывается `⛔ Skipped by decision` без единой строки кода.
**Why:** ADR-0008: fine-grained provenance материализуется только там, где ответ должен пережить согласование источников; налог на storage/processing платится за 10–20% полей, а не за все факты (`RAG:✅ 2026-07-10 «W3C PROV vs прагматичные колонки»`). D13: материализация без названного потребителя = мёртвая колонка. D15: колонка, которой нет в `findings/P1-actual-names.md`, — не «забытая», а **незаслуженная**.
**Scope Included:** при `N ≥ 1` — миграция (edit-in-place создающей миграции целевой таблицы, D14), модель/`$fillable`/каст, запись через соответствующий `*StoreRepository`, обновление DTO-снапшота при необходимости, подключение потребителя (Filament infolist или обучающий контур — тот, что назван в proof), Pest-тесты, обновление `findings/P1-actual-names.md` §4 и ADR-0008 (`Status`/`Consequences`). При `N = 0` — только смена статусов, строка в Update Log и фиксация триггера возврата.
**Scope Excluded:** любое поле, не прошедшее R1 в `P4.1`; починка дефектов класса R2/R3 (D24 → P5); forward `alter`-миграции (D14 запрещает, пока нет применённой persistent-среды); пятиуровневая схема `*-derived`; провенанс-колонка «про запас» на таблице без доказанного поля.
**Inputs:** `findings/P4-provenance-proof.md` (вердикт + proof-таблица — **единственный** источник списка полей и имён колонок) · ADR-0008 · `plan.md` D14 (стратегия схемных правок), D23, D24 · `findings/P1-actual-names.md` §1 (канон имён таблиц/колонок).
**Files:** зависят от вердикта. При `N = 0` — только `phases/P4.md`, `plan.md`, `handoff.md`. При `N ≥ 1` — создающая миграция целевой таблицы в `database/migrations/**` (правится на месте), модель в `app/Models/Procurement/**`, соответствующий репозиторий в `app/Repositories/**`, при необходимости `app/Dto/Procurement/ProcurementSnapshotData.php`, потребитель (`app/Filament/Resources/Procurement/Procurements/Schemas/ProcurementInfolist.php`), тесты в `tests/Feature/Procurement/**`, `findings/P1-actual-names.md`, `docs/03_Dev/adr/0008-thin-provenance-slice.md`.
**Required Reads:** (в этом порядке) 1) `plans/DOMLANG/findings/P4-provenance-proof.md` — вердикт и proof-таблица; 2) `plan.md` §5 D14 — edit-in-place + `migrate:fresh`, триггер отката; 3) `docs/03_Dev/adr/0008-thin-provenance-slice.md` — граница решения и «Триггер пересмотра»; 4) `plans/DOMLANG/findings/P1-actual-names.md` §1, §4; 5) `plan.md` §2 Execution Rules — персистентность только через `*StoreRepository`, `final readonly`, именованные аргументы; 6) при `N ≥ 1` — `phases/P3.md` P3.2 Completion Notes как образец атомарной схемной правки.
**Implementation Rules:**
1. **Первый шаг — прочитать вердикт.** `ВЕРДИКТ: 0 полей класса R1` → перевести item и фазу в `⛔ Skipped by decision`, дописать в ADR-0008 `Consequences` факт «P4.1 конфликтов не нашёл (дата, ссылка на proof)», обновить Status Board, перезаписать `handoff.md`, закоммитить документационный диф. Кода не писать. **Это исполнение плана, а не отказ от работы.**
