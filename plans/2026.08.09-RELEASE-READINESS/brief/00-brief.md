# Бриф владельца — 2026-08-09

Ниже исходный запрос владельца переформулирован по темам без потери требований.

## 1. Makefile, Docker и автоматизация

- Полностью перелопатить Makefile; текущий файл использовать как requirements/input, неприкасаемого кода в нём нет.
- Через RAG найти актуальные лучшие практики Makefile и Docker Compose для development и production.
- Сравнить решения в проектах Sova, Vintera/CMS и Dterema/Dterema, взять лучшее и переработать под Agelto.
- Поддержать запуск команд людьми и агентами; отдельно проверить через RAG агентский режим и компактный/надёжный вывод.
- Docker должен быть оптимален: простое изменение PHP-кода не должно приводить к полной пересборке image.
- Архитектура должна учитывать скорое появление frontend и сборки Vite.
- Максимально автоматизировать build, deploy, проверки и документацию.

## 2. Первый deploy на пустой Ubuntu

- Нужна целостная пошаговая инструкция для пустого сервера: подготовка Ubuntu, окружения и пользователя deploy.
- Описать установку Docker/Compose, Git, Make, reverse proxy, firewall, TLS и прочих необходимых компонентов.
- Описать создание SSH-ключей, добавление ключа в Git-хостинг и клонирование private repository.
- После clone основной репозитория инструкция должна довести оператора до работающего production.
- Взять сильные стороны инструкции Vintera/CMS, но пересмотреть устаревшие части.
- Дать точные команды для первого deploy, обычного обновления, обновления зависимостей/image, rollback, backup и проверки.
- Объяснить обязательные сиды, создание первого администратора и другие bootstrap-операции.

## 3. Private package Asgard/AzGuard

- Сейчас private package прилинкован в Composer к внешнему пути.
- В основном репозитории должна существовать пустая директория local/vendors с .gitkeep.
- Сам package не должен находиться в основном Git-репозитории.
- После clone основного проекта оператор заходит в local/vendors и отдельно клонирует private package.
- Только после этого продолжаются Composer/install/bootstrap шаги.
- Инструкция должна дать точный, проверяемый порядок; фактическое имя package/repository и path contract надо сверить с текущим Composer.

## 4. Секреты и preflight

- Нужен скрипт до развёртывания Docker, который генерирует все нужные пароли и ключи для .env и .env.docker*.
- Нужен безопасный механизм хранения и передачи secrets в Docker.
- Секреты не должны утекать в Git, image, логи или историю shell.
- Нужен ранний скрипт проверки перед build/deploy: наличие файлов, корректность переменных, версии инструментов, порты, права и Compose config.
- Процесс должен быть максимально автоматическим, но fail-closed и понятным.

## 5. Laravel Doctor, fresh install и Livewire

- Добавить и настроить laravel/doctor.
- Проверить, что проект нормально разворачивается с нуля, а не только работает в текущем окружении.
- Сейчас в /admin не подключается Livewire:
  http://localhost:8080/livewire-9c644ad8/livewire.js?id=657d57c2 возвращает net::ERR_ABORTED 404.
- Ошибка возникает постоянно; надо установить первопричину.
- Рассмотреть официальный Composer hook для публикации assets, но применять его только после проверки.
- Fresh-install acceptance обязан включать открытие /admin, загрузку Livewire/Filament assets и рабочее взаимодействие.

## 6. Закрытая production-документация

- Документация на production должна быть доступна только администратору или ролям/политикам, которые будут назначены позже.
- Первично изучить реализацию Vintera/CMS: общий route, middleware/admin-auth, контроллер и выдача собранной документации.
- В Vintera/CMS текущий вариант работает наполовину: стили и скрипты загружаются некорректно либо обходят нужную защиту.
- Желательно не хранить production build документации в public.
- Нельзя допустить прямое извлечение документации, обход route/auth или утечку через public/shared cache.
- HTML и чувствительные assets должны проходить через единый обработчик и authorization policy.
- Для CSS/JS можно принять отдельное решение только после анализа содержимого, threat model и RAG лучших практик.
- Нужны корректные MIME types, защита от path traversal, cache headers и тесты guest/non-admin/admin.

## 7. Прокси crawler/parser

- PLAYWRIGHT_MCP_PROXY_SERVER относится к Playwright MCP и понятен; он не должен неявно становиться runtime-прокси приложения.
- Дефолтные прокси crawler/parser сейчас явно не заданы; надо разобраться, как работает код.
- Предпочтительный optional settings carrier — Spatie Settings, если анализ подтвердит уместность.
- Требуемая семантика — три уровня:
  1. если proxy задан в profile, используется он;
  2. иначе, если задан default proxy, используется default;
  3. иначе запрос идёт без proxy.
- Сохранить архитектурные инварианты ProxyResolver/ProxyScope и разделение global/per-target health.

## 8. Флагманское качество кода

- Выполнить проверки паттернов, современного синтаксиса PHP, разных подходов и best practices.
- Сделать проект флагманом по стабильности, чистоте, безопасности, именованию классов/методов/переменных и расширяемости.
- Найти дублирование, мёртвый код, лишние абстракции, небезопасные места и архитектурные нарушения.
- Проверить транзакции, idempotency, race conditions, queue semantics, migrations, config defaults и production-readiness.
- Не ослаблять тесты, guards или security checks ради зелёного результата.
- Сейчас последний безопасный момент для breaking changes; исправлять системно, а не сохранять плохую совместимость.

## 9. Filament UX

- Всё меню Filament должно быть на русском.
- Упорядочить navigation groups и ресурсы так, чтобы предметная логика была понятна.
- AzGuard переместить вниз.
- Дать понятные названия вместо технических/английских.
- Таблицы сейчас сильно разъезжаются по горизонтали.
- UUID-колонки, вероятно, не надо показывать по умолчанию.
- Длинные тексты переносить, ограничивать или раскрывать штатными возможностями Filament.
- Все create/edit/view страницы группировать по Section.
- Непонятные параметры снабдить helper text, подсказками и примерами.
- Пройти все ресурсы, а не только одну страницу.
- Scopes/enum сейчас могут показывать имя класса на английском; использовать Filament label contracts вроде HasLabel там, где они доступны.
- Булевы значения показывать по-человечески: например, Активен 1 → Да.
- Проверить конкретные поверхности:
  /admin/procurement/platform/status-mappings
  /admin/procurement/crawler/proxies/create
  /admin/procurement/ai/prompts/1
- Привязка status mapping к конкретному ФЗ может усложнять фильтр по статусу; спроектировать более гибкую модель.

## 10. Pest 5 и CI

- Разобраться с тестами целиком.
- У Pest 5 есть новый быстрый механизм; через официальные источники установить его форму и использовать возможности максимально уместно.

- Агентский запуск должен быть быстрым и давать компактный, честный результат.

## 11. Архивы и маршрутизация форматов документов

- Создать тест: когда Document является архивом, архив распаковывается.
- Для содержимого создаются file records, ссылающиеся на родительский архив.
- Каждый дочерний файл проходит обычную обработку.
- Архивы надо распаковывать безопасно и идемпотентно.
- Есть конфиг/registry соответствия расширений файлов классам-обработчикам; проверить и довести контракт.
- Поддерживаются изображения JPEG/PNG и другие необходимые графические форматы, Excel, Word, XML-подобные сметные форматы и архивы.
- Названия JSRF/GSRF/GSFX в исходной формулировке могут быть неточными; через RAG и реальный corpus установить канонические форматы.
- Если extension/MIME не соответствует обработчику, файл получает terminal skip/reject status и понятную reason.
- Добавление нового handler/формата должно быть простым, typed и покрытым contract tests.

## 12. Первичный анализ документа

- При первичном анализе документ классифицируется по типу.
- Нужен расширяемый enum типов: смета, техническое задание и другие найденные классы.
- Допустимы unknown/null, если уверенного сопоставления нет.
- Документ может содержать одну, несколько смет или вообще не быть сметой.
- Нужен текстовый краткий summary: что находится в документе.
- Даже если документ не подходит для дальнейшего estimate pipeline, для успешно прочитанного содержимого надо сохранить полезное резюме и причину дальнейшего решения.
- Нейросеть должна возвращать классификацию, summary и структурированный результат.
- Вся цепочка должна поддерживать поля: prompt/schema, DTO, job/action, модель и БД.
- Желательно автоматически формировать tags/anchors для поиска и навигации по документам.
- Через Playwright/RAG/доступный corpus проанализировать теоретические виды закупочных документов и сформировать стартовую taxonomy.
