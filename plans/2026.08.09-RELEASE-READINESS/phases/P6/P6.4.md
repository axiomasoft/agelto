### P6.4 — Создавать child file records со ссылкой на parent archive и dispatch

**Intent:** Материализовать каждый validated archive entry как concurrency-safe child DocumentVersion с явным parent/path lineage и запустить его через обычный PrepareDocumentJob только after commit. RAG:— (repo-grounded: terminal P6.3, D31).
**Why:** Current application lookup не является DB idempotency proof, parent file читается мимо recorded disk, child job не dispatch-ится, а parent archive может ошибочно уйти в screening. RAG:— (repo-grounded: P6 findings and current ArchiveStrategy/PrepareDocumentJob).

**Implementation Rules:** Object-store read/write/hash completes outside DB transaction; Action owns the short rows/event/status transaction and repositories open none. Unique `(parent_version_id, archive_entry_path)` is the concurrency authority; retry returns the same complete child and repairs only a transactionally representable orphan state. Child version stores actual hash/bytes/MIME/current disk and normalized path; parent version is read from resolver-returned disk/path. Dispatch is registered inside Action with `afterCommit`; rollback creates no visible job. Expanded parent never enters ScreeningJob. RAG:— (repo-grounded: D31, layer/database/FileLocationResolver invariants).
**Code Guidance:** Do not encode the only lineage fact in `external_id`, rely on check-then-insert alone, hold a transaction across Storage/process I/O, or dispatch before commit. Use named arguments and existing repositories/actions; no new generic pipeline bus. Tests use factories and assert DB/queue/storage behavior. If PostgreSQL constraint cannot distinguish intended path identity or a concurrent retry can create two children, stop and escalate D31; catching unique violations without proving resulting row completeness is forbidden.
