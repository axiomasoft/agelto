# P8 — Расширяемость platforms и гибкие status mappings

## Phase Context

Фаза выравнивает runtime extension identity с уже существующей парой Platform/Registry: data rows
остаются identity, а crawlable capability регистрируется typed definition по точному platform code.
Это закрывает collision registry codes и не хранит FQCN в БД. Status mapping эволюционирует в
двухуровневое applicability rule: platform default с exact registry override, причём неизвестное
значение всегда материализуется только в exact registry scope. RAG:— (repo-grounded:
`findings/P8-platform-status-extension-recon-2026-08-09.md`, D35–D36).

P0.5/P0.6/P7.6 ещё не терминальны: P8.1 до factory/schema mutation сверяет их official/frozen
products с текущей картой seams и либо сохраняет D35/D36, либо создаёт явную superseding chain.
P8.2–P8.5 образуют strict descriptor→schema→resolver/UI→contract-test цепочку. Audit P8, заход 1,
добавляет только P8.6 repair-forward: один candidate восстанавливает factory baseline и literal
acceptance P8.5, затем возвращает фазу на независимый Audit P8, заход 2; P8.1–P8.5 не
редетализируются. Реальная новая площадка не реализуется; доказательство использует synthetic test
adapter. RAG:— (repo-grounded: `research/10-P8-execution-design.md`,
`research/23-P8-audit-remediation.md`).

> **Контракт фазы (contract-first).** Потребляет: terminal P0.5/P0.6/P7.6, `root/contracts/release-readiness-v1.md`, D5/D35/D36, current Platform/Registry/SourceMethodFactory/CrawlerFilterFactory/EIS/status-mapping/Filament contracts · Производит: exact platform adapter definition registry, migrated factory/form consumers, platform-default+registry-override status schema/backfill/resolver, authorized operator UI, synthetic extension and architecture tests, developer guide · Границы: не реализует реальную новую площадку, не вводит DB-stored FQCN/global raw-status rules/generic predicate engine, не меняет P7 screening semantics, P9 владеет общей Filament IA, P10 — cross-cutting audit, P12 — production rehearsal

## Scope Included

1. Reconcile terminal P0/P7 evidence and freeze exact platform/registry extension seams.
2. Typed platform definition registry for source methods and registry filter DTOs/forms.
3. Platform-default or exact-registry status applicability with deterministic precedence.
4. Data-preserving migration/backfill, partial uniqueness, repositories and race-safe unknown creation.
5. Authorized Filament create/edit/filter surface with human platform/registry labels.
6. Synthetic second-platform, concurrency/migration/architecture tests and developer guide.

## Scope Excluded

- Реальная интеграция новой procurement platform, live crawling нового источника или новый source method.
- FQCN/handler configuration in DB, global raw-stage mapping or free-form JSON predicates/priorities.
- Изменение глобального `ProcurementStatus` codelist без отдельной evidence-backed superseding D.
- Переписывание EIS parser/card/health behavior, P7 screening contract или P9 global Filament IA.
- Общий security/quality audit P10, CI topology P11 и production rehearsal P12.

### Findings

1. **Blocker · confidence high · P8.2/P8.5 · issue · PROMOTE-CANDIDATE.** Закрытая P8 внесла product-регрессию, а P8.5 ложно назвал её «pre-existing». `ProcurementFactory` теперь всегда строит `Registry::factory()->eis()` (`database/factories/Procurement/ProcurementFactory.php:22`), тогда как `RegistryFactory::eis()` переиспользует одну EIS platform и возвращает для каждого registry тот же code `fz44` (`database/factories/Procurement/Platform/RegistryFactory.php:30`). Item-owned carrier на `2d97a78d` дал focused **24 passed / 113 assertions**, затем full no-TIA **196 failed / 1348 passed / 5879 assertions**, exit 2; типовой сбой — unique collision `(platform_id, code)=(eis, fz44)`. Непосредственно перед P8 terminal P7.6 фиксировал full **1526 passed / 6679 assertions** (`journal.jsonl:307`), поэтому запись P8.5 (`phases/P8/P8.5.state.md:15`, `journal.jsonl:329`) не выдерживает baseline comparison. Failure scenario: обычный тест, создающий несколько procurement/registry, падает на уникальном индексе; release gate и downstream CI не могут принять фазу. Блок подтверждён независимым reviewer и reducer.

2. **Major · confidence high · P8.5 · issue.** Item-owned carrier не реализует собственное поле Validation. ТЗ требует terminal P8.4, negative fixtures, migration rollback/reapply/refusal, docs-link/obsolete scan, Task/citation/diff gates и полный quality-контур (`phases/P8/P8.5.md:12`), но скрипт содержит только focused suite, config cycle, full suite, Pint и PHPStan (`docker/tests/platform-extension-contract.sh:8`). Из-за `set -e` он останавливается на full suite и до Pint/PHPStan не доходит; отдельные прогоны дали Pint **8** style failures и PHPStan **34** errors. Failure scenario: carrier может не проверить prerequisite, plan carriers, citations, docs и negative contract, а его раннее падение скрывает остальные красные гейты.

3. **Major · confidence high · P8.5 · issue.** Architecture proof и developer guide существенно уже обязательного deliverable. Architecture test просматривает только шесть вручную перечисленных файлов и ищет лишь `Eis|fz44` (`tests/Unit/Architecture/PlatformExtensionContractTest.php:6`), хотя ТЗ требует exact-path/namespace allowlist с deliberate forbidden-core fixture (`phases/P8/P8.5.md:10`). Guide даёт четыре общих шага и две краткие failure/rollback заметки (`docs/03_Dev/platform-extension.md:13`), но не называет каждый файл, команду, failure mode, test template, rollback и observability. Failure scenario: новая source-specific branch в любом не перечисленном core-файле пройдёт architecture gate, а cold-start разработчик не сможет воспроизвести extension/rollback procedure.

4. **Major · confidence high · P8.2 · issue.** Commit topology не соответствует стабильному `Files`, но item закрыт `🟢`. Product-коммит `b27a5c09` добавил `app/Contracts/Procurement/Crawler/CrawlerPlatformForm.php` и `app/Filament/Resources/Procurement/Crawler/Crawlers/Schemas/EisCrawlerPlatformForm.php`, которых нет в перечне `Files` (`phases/P8/P8.2.md:8`); это не carve-out plan bookkeeping. Failure scenario: recovery/audit не может восстановить границу item-коммита, а material scope drift скрыт зелёным статусом. Исправление требует узко изменить стабильную ownership/Files-топологию либо вернуть реализацию в объявленную границу — поэтому successor законно идёт через `plan-design`, а не через произвольный reopen.
