# Универсальная схема данных закупок: OCDS, ЕИС и подходы агрегаторов

## 1. OCDS: модель release/record, версионирование, статусы, сущности

### Releases vs Records

OCDS моделирует закупочный процесс как **неизменяемый поток релизов** (releases), привязанных к единому идентификатору `ocid` (Open Contracting ID):

- **Release** — JSON-документ, публикуемый при каждом изменении. Содержит `ocid`, уникальный `id`, `date` и `tag` (тип события: `planning`, `tender`, `tenderUpdate`, `award`, `contract` и т.д.). Релизы **иммутабельны** — правка невозможна, только новый релиз с новым `id`/`date`.
- **Record** — агрегирующий документ по одному `ocid`:
  - `releases[]` — индекс/массив всех релизов (хронология);
  - `compiledRelease` — «снапшот» текущего состояния (последнее значение по каждому полю);
  - `versionedRelease` (опционально) — история изменений каждого поля с метаданными (`releaseDate`, `releaseID`).

Источники: [standard.open-contracting.org/schema/reference](https://standard.open-contracting.org/latest/en/schema/reference/), [standard.open-contracting.org/primer/releases_and_records](https://standard.open-contracting.org/latest/en/primer/releases_and_records/)

### Механика слияния (merge) и версионирования

Правила описаны в OCDS-документации и реализованы в референсной библиотеке `ocds-merge` (github.com/open-contracting/ocds-merge):

- Скалярные поля (`tender.value.amount`) — берётся значение из **последнего** релиза, где поле присутствует.
- Массивы с идентификаторами (`tender.items`, `awards`, `contracts`) — merge по `id` элемента, поля внутри объединяются по тому же принципу «последнее значение побеждает».
- **Пропуск поля** в новом релизе = «без изменений», сохраняется предыдущее значение.
- **Явный `null`** = «очистить поле» — в compiledRelease поле обнуляется.

### Амендменты

Амендменты (изменения тендера/контракта) — это **новые релизы** с соответствующим тегом (`tenderUpdate`, `awardUpdate`, `contractUpdate`), а не редактирование прошлых данных. Прежние значения остаются в старых релизах — это и есть аудиторский след. Это прямо релевантно вашему домену: изменение НМЦК, сроков, предмета закупки — типовые амендменты 44-ФЗ/223-ФЗ.

### tender.status и жизненный цикл

`tender.status` — поле с **закрытым codelist** (напр. `planning`, `active`, `complete`, `cancelled`, `unsuccessful`). Отдельно от статуса — `release.tag`, который описывает **тип события**, а не состояние. Стадии обычно реконструируются комбинацией `release.tag` + `tender.status` + `awards[*].status` + `contracts[*].status` + `milestones`.

Важная деталь по лотам (актуализировано отдельным запросом): начиная с **OCDS 1.1** модель лотов (`tender.lots`) стала **core-расширением**, встроенным в дистрибутив стандарта (раньше — отдельное community-расширение). `Lot.status` использует **тот же закрытый codelist `tenderStatus`**, что и `tender.status`, отдельного `lotStatus` не существует. Правила агрегации:
- если хотя бы один лот `active` → `tender.status = active`;
- иначе если есть `complete` → `complete`;
- иначе если есть `unsuccessful` → `unsuccessful`;
- иначе (все `cancelled`) → `cancelled`.

У `tender.items` отдельного статус-поля в core OCDS нет — статус трекается на уровне тендера/лота/award/contract.

Источники: [standard.open-contracting.org/history/changelog](https://standard.open-contracting.org/latest/en/history/changelog/), [extensions.open-contracting.org/extensions/lots](https://extensions.open-contracting.org/en/extensions/lots/v1.1.5/), [github.com/open-contracting/standard/issues/1160](https://github.com/open-contracting/standard/issues/1160)

### Основные сущности OCDS

| Блок | Назначение | Ключевые поля |
|---|---|---|
| `parties[]` | Все организации-участники (buyer, procuringEntity, tenderers, suppliers), с 1.1 — «party-centric» модель, ссылки по `id` вместо дублирования | `id`, `name`, `identifier`, `address`, `contactPoint`, `roles[]` |
| `buyer` | Ссылка на party, чей бюджет платит | `id` |
| `planning` | Обоснование, бюджет, документы до объявления | `budget`, `milestones`, `documents` |
| `tender` | Само извещение/процедура | `id`, `status`, `value`, `items[]`, `lots[]`, `documents[]`, `milestones[]` |
| `awards[]` | Итоги — кто выиграл что и по какой цене | `id`, `status`, `value`, `suppliers[]`, `items[]`, `documents[]` |
| `contracts[]` | Формальный контракт по award | `id`, `awardID`, `status`, `value`, `period`, `items[]`, `documents[]`, `milestones[]` |
| `milestones` | Плановые/фактические вехи (есть в planning, tender, contracts) | `id`, `title`, `type`, `dueDate`, `dateMet`, `status` |
| `documents` | Файлы на каждом этапе | `id`, `documentType`, `title`, `url`, `datePublished` |

### Актуальная версия стандарта

На середину 2026 стабильная линия — **OCDS 1.1.5** (последняя фиксация в официальном changelog, релиз 1.1 — май 2017, далее патч-версии 1.1.x). Публично изданной версии **1.2 нет** — есть только упоминания о планируемом «следующем minor-релизе», без опубликованного changelog. Для проектирования ядра БД стоит ориентироваться на **1.1.x** как baseline и на реестр официальных расширений.

Источник: [standard.open-contracting.org/history/changelog](https://standard.open-contracting.org/latest/en/history/changelog/)

### Реестр официальных расширений

Каталог: `github.com/open-contracting/extension_registry` (CSV `extensions.csv`) + UI-обёртка [extensions.open-contracting.org](https://extensions.open-contracting.org/en/extensions/). Организация `open-contracting-extensions` на GitHub — 74+ репозитория, включая `lots` (теперь core), `location`, `participationFee`, профили EU/eForms/PPP/GPA (со своими codelist'ами метода закупки и классификаторами вроде CPV). Не подтверждено: точное число активных extension-репозиториев на дату запроса (варьируется, называлась цифра «74+», не проверял по актуальному API).

Источники: [github.com/open-contracting/extension_registry](https://github.com/open-contracting/extension_registry), [standard.open-contracting.org/extensions](https://standard.open-contracting.org/latest/en/extensions/)

## 2. Маппинг закупок РФ на OCDS: что реально существует

**Полноценного официального национального OCDS-издателя в России нет.** Найдены два релевантных факта:

1. **`data.open-contracting.org/ru/publication/94`** — в реестре OCP (Open Contracting Partnership) зарегистрирован датасет-публикация под номером 94, помеченный как данные zakupki.gov.ru, приведённые к OCDS (третьей стороной/в рамках коллаборативного проекта, не официальный госиздатель). Доступны выгрузки в JSON/Excel (например `2023.xlsx`) через OCP Data Registry. Это **аналитический слой**, не заменяющий официальный формат ЕИС.
2. **Проект `btbroot/ocds-ru` на GitHub** — «An attempt of mapping the raw data published on zakupki.gov.ru into OCDS publisher». Использует **XSLT** (87.9% кода) поверх сырых XML-выгрузок ЕИС по FTP. Даёт стартовое соответствие типов документов ЕИС → сущности OCDS:
   - `fcsNotificationZK` (`placingWay.code='ZK44'`) → `tender`;
   - `fcsPurchaseDocument` (`docType.code='P'`) → `tender.documents`;
   - `contract` (`foundation.fcsOrder.placing=9`) → `award`+`contract`;
   - `contractProcedure` → частично `implementation`.
   Проект охватывает в основном 44-ФЗ (запросы котировок, конкурсы, аукционы), поля plangraphs/sketchplans не замаплены.

Счётная палата РФ в аналитических/исследовательских работах рассматривала идею применения открытых стандартов (включая OCDS) для международно-сопоставимого анализа эффективности закупок, но **системной официальной публикации не подтверждено** — это не удалось верифицировать как реализованный факт, только как обсуждаемое направление.

**ЕИС отдаёт первичные данные по FTP** в виде XML, разложенных по директориям: `notifications` (извещения), `protocols` (протоколы), `contracts` (контракты и исполнение), `purchasedocs` (документация), `plangraphs`/`sketchplans` (планы-графики, частично неструктурированные). Плюс справочники НСИ (бюджеты, причины расторжения, организации).

Источники: [data.open-contracting.org/ru/publication/94](https://data.open-contracting.org/ru/publication/94), [data.open-contracting.org/ru](https://data.open-contracting.org/ru/), [github.com/btbroot/ocds-ru](https://github.com/btbroot/ocds-ru) (найден через поиск, не открывал напрямую — рекомендую проверить актуальность/активность репозитория перед использованием как референса, он может быть заброшен).

## 3. Статусные модели: 44-ФЗ vs 223-ФЗ

### 44-ФЗ — относительно жёсткая модель

Закон не даёт закрытого списка текстовых статусов (это регламенты ЕИС/ЭТП), но стадии стандартизированы и мало варьируются между площадками:

| Стадия | Типичные статусы извещения |
|---|---|
| Планирование | (до появления извещения, план-график) |
| Размещение | «Размещено» / «Опубликовано» |
| Приём заявок | «Подача заявок» / «Приём заявок» / «Идёт подача заявок» |
| Рассмотрение | «Работа комиссии» / «Рассмотрение заявок» / «Рассмотрение первых частей заявок» |
| Торги/оценка | «Проведение аукциона» / «Идут торги» / «Оценка и сопоставление заявок» |
| Итоги | «Подведение итогов» |
| Контракт | «Заключение контракта» → «Контракт заключён» / «Размещение завершено» |
| Исполнение | «Исполняется» / «Исполнен» / «Расторгнут» (в реестре контрактов, отдельно от статуса извещения) |
| Нештатные исходы | «Отменена» / «Признана несостоявшейся» / «Признана недействительной» |

### 223-ФЗ — конфигурируемая модель

Ключевое архитектурное отличие: **закон задаёт только рамки** (открытость, недискриминация, эффективность), а конкретные этапы, статусы и основания отмены/несостоявшейся закупки определяются **Положением о закупке** каждого заказчика. Это означает:

- Базовая абстрактная цепочка похожа: планирование → инициирование → публикация → приём заявок → рассмотрение/торги → итоги → договор → исполнение → завершение.
- Но набор способов закупки, промежуточные фазы (например, «переторжка», «переговоры» в запросе предложений), основания для «не состоялась»/«отменена» — **варьируются по заказчику**.
- В отличие от 44-ФЗ, где итог — государственный контракт по жёстким правилам, по 223-ФЗ заключается **гражданско-правовой договор** на более гибких условиях.
- Типичные публичные статусы: «Размещено»/«Подача заявок», «Подача заявок завершена», «Идёт рассмотрение заявок»/«Оценка заявок», «Закупка завершена»/«состоялась», «Закупка не состоялась», «Закупка отменена».

**Архитектурный вывод для вашего ядра**: под 44-ФЗ можно проектировать сравнительно унифицированную жёсткую процессную модель. Под 223-ФЗ — закладывать **конфигурируемость жизненного цикла на уровне заказчика** (описание этапов/переходов как данные, а не хардкод enum'ов).

Источники: [enradm.gosuslugi.ru — текст 44-ФЗ](https://enradm.gosuslugi.ru/netcat_files/393/5723/3_Federal_nyy_zakon_ot_05.04.2013_N_44_FZ_red._ot_28.12.2025_1_.pdf), [bicotender.ru/faq/razlichiya-44-fz-i-223-fz](https://www.bicotender.ru/faq/razlichiya-44-fz-i-223-fz.html), [saby.ru/articles/tenders/otlichiya_44_fz_i_223_fz](https://saby.ru/articles/tenders/otlichiya_44_fz_i_223_fz), [store.onlinecontract.ru — методичка по 223-ФЗ](https://store.onlinecontract.ru/files/fz223/UG_USP_publishing_procurement_information.pdf). *Не подтверждено машинным парсингом*: закрытый перечень статусов именно в терминах ЕИС API/XSD — модель собрана из вторичных источников (методички, коммерческие площадки), не из первоисточника-XSD ЕИС.

## 4. Подход коммерческих агрегаторов (Tenderplan, Контур.Закупки, Bicotender)

Общая архитектура мультиплощадочных агрегаторов (обобщено, конкретные внутренние детали компаний не публикуются, поэтому многое — по описанию их публичных материалов):

- **Масштаб источников**: Bicotender заявляет 7500+ источников (ЕИС, федеральные ЭТП, коммерческие площадки, региональные порталы); Tenderplan и Контур.Закупки — сотни источников.
- **Слой сбора**: там где есть официальный API/выгрузка (ЕИС, часть ЭТП) — интеграция через API/XML/FTP; там где нет — HTML-скрейпинг по расписанию (крон/очереди), с ретраями и инкрементальными обновлениями (отслеживание версий извещений, изменений НМЦК/сроков).
- **Нормализация**: приведение полей к единой схеме — идентификаторы закупки, заказчик, предмет, лоты, сроки, НМЦК, регион, ОКПД2/КТРУ. Иерархия «источник → закупка → лоты → заявки/протоколы» + справочники (заказчики, поставщики, регионы).
- **Хранилище**: реляционная БД + полнотекстовый индекс (Elasticsearch/OpenSearch/Sphinx) для поиска по документации.
- **Продуктовый слой**: сохранённые поисковые профили («ключи»), уведомления, аналитика благонадёжности заказчика/поставщика, интеграции с CRM.

Практический вывод для дизайна ядра: реестр источников с метаданными (тип площадки, применимый ФЗ, формат данных, лимиты частоты, расписание) + воркер/микросервис на источник или группу источников — стандартный паттерн, к которому стоит стремиться и вам, если ядро задумано под будущие площадки помимо ЕИС.

Источники: [tendercorp.ru/blog](https://tendercorp.ru/blog/agregatory-poiska-tenderov-chto-eto-i-kakimi-polzuemsya-my/), [bicotender.ru](https://www.bicotender.ru/). *Пометка о достоверности*: детали внутренней архитектуры конкурентов не публикуются официально, часть выводов — маркетинговые описания, а не техдокументация; трактовать как ориентир, не как точный факт устройства конкретных систем.

## 5. Универсальные поля извещения vs специфичные для ЕИС

### Универсальное ядро (актуально для любой площадки/ФЗ)

- Идентификатор закупки (ИКЗ / регистрационный номер / номер в реестре);
- реквизиты заказчика (наименование, ИНН/КПП, ОГРН, адрес, контакты);
- способ определения поставщика (аукцион/конкурс/запрос котировок/ЕП и т.д.);
- ссылка/идентификатор площадки (код ЭТП, URL);
- предмет закупки: наименование, описание, позиции (наименование/классификатор/количество/единица измерения);
- НМЦК + валюта;
- источник финансирования (в обобщённом виде);
- сроки: начало/окончание подачи заявок, дата подведения итогов, сроки поставки/исполнения;
- обеспечение заявки/контракта (флаг + сумма + тип);
- документы (ТЗ, проект контракта, протоколы) как отдельные вложения со ссылками.

### Специфично для ЕИС / 44-ФЗ (не переносится «как есть» на любую площадку)

- ИКЗ как обязательный реквизит именно 44-ФЗ (по 223-ФЗ такого жёсткого требования нет);
- ОКПД2/КТРУ как обязательный классификатор именно для госзакупок РФ (другие юрисдикции используют CPV и т.п. — релевантно, если ядро когда-то станет мультиюрисдикционным);
- жёсткая привязка к плану-графику (номер в плане-графике) — специфика контрактной системы 44-ФЗ;
- типовая форма извещения (обязательна с 03.02.2022, приложение к ПП РФ №60) — регуляторная специфика, не универсальный паттерн;
- статусный словарь и его жёсткость (44-ФЗ) vs гибкость через Положение (223-ФЗ) — см. раздел 3.

Источники: [v1a.ru — про извещение по 44-ФЗ](https://www.v1a.ru/sovety/analiticheskie-stati/vse-chto-nuzhno-znat-ob-izveshchenii-v-goszakupkakh-po-44-fz-/), [zakupki.gov.ru — расширенный поиск](https://zakupki.gov.ru/epz/order/extendedsearch/search.html), [minfin.gov.ru — письмо об описании объекта закупки](https://minfin.gov.ru/ru/document?id_4=303927-pismo_minfina_rossii_ot_25.09.2023__24-03-0990944_o_razmeshchenii_opisaniya_obekta_zakupki_v_edinoi_informatsionnoi_sisteme_v_sfere_zakupok). *Не подтверждено*: точные имена XML-элементов (`<NoticeId>`, `<IKZ>` и т.п.) в отчёте — это реконструкция по практике интеграций, а не выдержка из официального опубликованного XSD ЕИС; перед реализацией парсера нужно свериться с реальными XSD-схемами ЕИС (FTP-выгрузка/интеграционный интерфейс).

## Рекомендации для ТЗ

1. **Брать OCDS как словарь терминов и структурную референс-модель, НЕ как буквальную схему БД.** Полное соответствие OCDS не нужно (нет требования публиковать OCDS вовне), но модель `release → compiledRelease` очень хорошо ложится на ваш domain: `Link`/извещение = аналог `tender`-релиза, амендменты (изменение НМЦК/сроков) = новые релизы, а не мутация исходной записи. Рекомендация: **проектировать таблицы с append-only историей изменений извещения** (по аналогии release/amendment), а «текущее состояние» — как материализованный/вычисляемый снапшот (аналог compiledRelease), а не единственный источник истины.

2. **Заимствовать сущностную декомпозицию OCDS напрямую**: `parties` (заказчик/участники/поставщики как единый реестр организаций со ссылками, а не дублирование), `tender`/`lots`/`items`, `documents` (переиспользуемая сущность на разных стадиях, что уже соответствует вашему `LinkAttachment`), `awards`, `contracts`, `milestones`. Это совпадает с вашей текущей терминологией (`Order`/`Lot`/`PurchaseObject`) — стоит явно сверить `PurchaseObject` с `tender.items` и решить, нужна ли отдельная сущность `Lot.status` по аналогии с OCDS (переиспользовать closed codelist статуса тендера для лота, не городить отдельный enum).

4. **Не полагаться на официальный госиздатель OCDS для РФ** — его нет. `ocds-ru` (GitHub) и `publication/94` (OCP registry) можно использовать только как **вдохновение для маппинга полей ЕИС XML → доменные сущности**, не как готовую интеграцию — оба нужно верифицировать на актуальность (репозиторий может быть заброшен, датасет — устаревшим/неполным). Первоисточник для реального парсинга — **сырые XML-выгрузки ЕИС по FTP** (`notifications`, `protocols`, `contracts`, `purchasedocs`) плюс справочники НСИ, а не сторонние OCDS-конвертеры.
