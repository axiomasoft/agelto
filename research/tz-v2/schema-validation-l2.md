# Валидация схемы БД госзакупок РФ — второе мнение (веб-исследование)

## 1. Конвенция префиксов таблиц (`plt_`/`prc_`/`doc_`) vs Postgres-схемы

**Вывод: при 30–50+ таблицах префиксы — не основной инструмент модульности; Postgres-схемы (namespaces) дают больше рычагов.** Источник: обсуждение best practices naming в PostgreSQL mailing list и профильные материалы ([postgresql.org](https://www.postgresql.org/message-id/75D418E7-2D14-4C5E-82E2-5836AE87D1F4@foursource.pt)).

Ключевые аргументы:

| Подход | За | Против |
|---|---|---|
| **Префиксы** (`plt_products`, `doc_documents`) | Просто заводится, не требует настройки `search_path`/ORM; удобно, если инструментарий (миграции nwidart/laravel-modules) плохо работает с несколькими Postgres-схемами | Не первоклассная единица — нельзя `GRANT` на «все `prc_`-таблицы» без кастомной автоматизации; переименование модуля = переименование всех таблиц; имена раздуваются (`prc_price_list_items` вместо `price_list_items`) |
| **Postgres schemas** (`pricing.price_lists`) | Естественная граница прав (`GRANT ... ON SCHEMA`), удобный дамп/аудит по домену, чище имена внутри домена | Более многословный SQL без настройки `search_path`; не все ORM/ инструменты миграций из коробки удобно работают с multi-schema (актуально для nwidart/laravel-modules — пакет модульность реализует на уровне файлов и миграций, а не БД-namespace) |

Практическая рекомендация из источников — **гибрид**: 3–6 схем на крупные bounded contexts + чистые имена внутри, префиксы оставить только для нетабличных объектов (`v_...`, `mv_...`, `t_...`) ([devart.com](https://www.devart.com/blog/database-design-best-practices.html), [dbschema.com](https://dbschema.com/blog/design/database-design-mistakes/)).

Для конкретно Laravel/nwidart-модулей отдельный поиск дал более узкое, применимое к вашему стеку правило ([nwidart.com docs](https://nwidart.com/laravel-modules/v6/introduction), пример конвенции: [gist.github.com/ilzrv](https://gist.github.com/ilzrv/bc2c0a2a96580d2d04ce2910751b4cb9)):
- nwidart/laravel-modules **не навязывает** префиксы таблиц — модульность у него на уровне файловой структуры и миграций, а не БД;
- правило: **префикс — только для неоднозначных generic-имён**, которые могут коллизировать между модулями (`settings`, `logs`, `documents`, `templates`); **не префиксовать** уникальные бизнес-существительные (`users`, `notices`, `contracts`);
- избегать смешения стратегий внутри одного модуля — либо все таблицы модуля с префиксом, либо ни одной.

Учитывая, что у вас уже есть `plt_*` (Platform) и вероятно `Modules/Eis` без явного префикса — стоит явно зафиксировать в `docs/dev/architecture.md`, что префикс = имя bounded context (`plt_`, `eis_`), а не технический маркер, и что таблицы классификаторов/справочников, скорее всего, стоит вынести **без префикса** в общий слой (они не принадлежат ни Platform, ни Eis как домену, а являются shared reference data).

## 2. Типичные ошибки в модели «закупка с историей редакций + событийный журнал»

Источники: обзоры типичных ошибок проектирования БД ([chartdb.io](https://chartdb.io/blog/common-database-design-mistakes), [devart.com](https://www.devart.com/blog/database-design-best-practices.html), [dbschema.com](https://dbschema.com/blog/design/database-design-mistakes/)) + прикладной разбор под тендерный домен.

Базовая модель, которую советуют аналитики: **три слоя** — событийный лог (факты) → снапшоты текущего состояния → аналитические/BI-представления. Типичные упущения:

1. **Смешение гранулярности** — хранение атрибутов лота, заявки и контракта в одной «мега-таблице» с кучей nullable-полей вместо разделения по сущностям.
2. **Хранится только «последняя» версия** извещения без реальной истории редакций — при этом аудит по 44-ФЗ/223-ФЗ требует восстанавливать «что было опубликовано на дату X».
3. **`updated_at`/`updated_by` вместо полноценной версионной таблицы** — этого достаточно для «кто последний менял», но недостаточно, чтобы восстановить состояние на произвольный момент.
4. **Версии не привязаны к событию-причине** — теряется «почему» изменилось (продление сроков, изменение НМЦК, техническая правка агрегатора).
5. **Не различаются «технические» и «бизнес» события** в одном event-логе — потом аналитика по бизнес-действиям засоряется техническими (ETL sync, heartbeat).
6. **JSON как единственный носитель события/версии** без выделенных колонок для часто фильтруемых атрибутов (`status`, `nmck_total`, `application_deadline`) — на практике это то, что специально предлагается **не** прятать в `raw_payload`, а поднимать в колонки версии.
7. **Отсутствие FK-целостности у событий** (event ссылается на сущность по текстовому ID) → осиротевшие события, сложный replay.
8. **Денормализация делается в транзакционные таблицы напрямую**, а не в отдельные представления/materialized views с понятной стратегией обновления — рекомендуется денормализовывать только в производные структуры (`current_tender` как MV), не трогая ядро 3NF.
9. **Полнотекстовый поиск как афтерсоут** — заводят `tsvector` прямо на транзакционных таблицах вместо отдельной поисковой таблицы/MV с `GIN`-индексом и языковой конфигурацией (`russian`), из-за чего тяжёлые джойны на каждый запрос поиска.
10. **Классификаторы (ОКПД2 и т.п.) хранятся строками/именами**, а не FK на код — теряется стабильность связей и возможность дедупликации/иерархических срезов.
11. **Организации-участники моделируются жёсткими FK-колонками** (`customer_org_id`, `supplier_org_id`, `platform_org_id` на одной таблице) вместо связки many-to-many «организация ↔ роль в закупке» — не масштабируется, когда у закупки много участников с разными ролями (см. п.4 ниже).

Готовый DDL-паттерн версионирования, который явно рекомендован как рабочий (не готовое решение «под копирку», но валидный каркас):

```sql
CREATE TABLE tender ( id BIGSERIAL PRIMARY KEY, external_id TEXT, created_at TIMESTAMPTZ NOT NULL );

CREATE TABLE tender_version (
  tender_id BIGINT NOT NULL REFERENCES tender(id),
  version_no INT NOT NULL,
  status TEXT NOT NULL,
  customer_id BIGINT NOT NULL,
  procedure_type TEXT NOT NULL,
  publication_date DATE,
  closing_date DATE,
  total_amount NUMERIC(18,2),
  change_reason TEXT,
  source_system TEXT,
  valid_from TIMESTAMPTZ NOT NULL,
  valid_to TIMESTAMPTZ,
  PRIMARY KEY (tender_id, version_no)
);
```

плюс отдельный `tender_event` (append-only, `entity_type`/`entity_id`/`event_type`/`occurred_at`/`payload jsonb`/`actor`/`source_system`) как источник истины, из которого версии/снапшоты строятся или дополняются.

## 3. Классификаторы (ОКПД2, КТРУ, ОКВЭД2, КБК): справочником или кодом в закупке

**Однозначный ответ из исследования: хранить справочниками, ссылаться по коду (FK), а не хранить только «сырую строку» в закупке.** Но с важной оговоркой про регуляторику.

Аргументы за нормализованные справочники:
- **Обновляемость**: классификаторы официально обновляются (Росстат, Минэкономразвития), новые версии/редакции публикуются регулярно; справочник обновляется пакетно без миграции истории закупок ([71.rosstat.gov.ru](https://71.rosstat.gov.ru/folder/37949)).
- **Нормализация**: один код фигурирует в тысячах позиций — дублирование расшифровок раздувает БД.
- **Иерархия и аналитика**: срезы по разделам/группам ОКПД2 требуют `parent_code`/`level` в отдельной таблице.
- **Версионность классификаторов**: коды устаревают/объединяются — нужны `valid_from`/`valid_to` в самом справочнике, а исторические закупки должны быть привязаны к версии, действовавшей на дату размещения.

Но: **в самой записи закупки нужно хранить код «как есть» из ЕИС** (строкой) параллельно с FK на нормализованный справочник — это критично для регуляторного аудита по 44-ФЗ/223-ФЗ, где важно зафиксировать именно то, что было указано в документации на момент публикации, даже если справочник потом это значение «исправил» или устарел.

Рекомендуемая связь между классификаторами:
- ОКПД2 ↔ КТРУ — один-ко-многим;
- ОКПД2 ↔ позиция закупки — один-ко-многим;
- ОКВЭД2 ↔ организация — многие-ко-многим (через pivot, у организации несколько видов деятельности);
- КБК ↔ закупка — один-ко-многим (важно для бюджетных заказчиков).

Практика открытых парсеров ЕИС это подтверждает: в реальных open-source схемах (см. п.6) `okpd2_code`/`ktru_code` в `lot_items` — это просто `VARCHAR`, ссылающийся (неявно или явно через FK) на отдельные справочные таблицы, при этом `notices.okpd2_codes TEXT[]` также используется как денормализованный массив с `GIN`-индексом для быстрого поиска — то есть **на практике комбинируют** нормализованный справочник + денормализованный массив-дубль для скорости фильтрации.

## 4. Организации-роли: единый реестр `parties` + pivot ролей (OCDS-подход) vs плоские FK

**OCDS явно и однозначно рекомендует единый реестр организаций + pivot ролей**, это специально спроектировано под ваш кейс (много ролей у одной организации: заказчик → потом участник другой закупки → потом победитель третьей). Источник: официальная схема OCDS ([standard.open-contracting.org/latest/en/schema/reference](https://standard.open-contracting.org/latest/en/schema/reference/), EU-профиль: [standard.open-contracting.org/profiles/eu](https://standard.open-contracting.org/profiles/eu/latest/en/reference/schema/)).

Ключевая идея OCDS: массив `parties` — канонический список всех организаций/участников контрактного процесса; остальные секции (tender, awards, contracts) ссылаются на них через `OrganizationReference` (`id` + `name`), **не дублируя** реквизиты. Роль хранится как **массив строк из открытого codelist** на самой party-записи внутри процесса — то есть многоролевость заложена в стандарт по умолчанию.

Рекомендуемый реляционный паттерн (адаптация под Postgres):

```
party(id, canonical_identifier /* ИНН/ОГРН */, name, ...)              -- единый реестр организаций
process_party(process_id, party_id, source_release_id, ...)            -- участие организации в конкретной закупке
process_party_role(process_party_id, role_code, valid_from, valid_to)  -- роли, multiplicity, опционально темпорально
```

Это даёт:
- одну переиспользуемую master-запись организации;
- одну запись «участия» на пару (организация, закупка);
- произвольное число ролей на участие, расширяемое без ALTER TABLE (`CUSTOMER`, `AUTHORIZED_BODY`, `PLATFORM_OPERATOR`, `SUPPLIER_WINNER`, `SUPPLIER_PARTICIPANT`, `BANK_GUARANTOR` и т.д. — согласуется с канонными терминами вашего глоссария `Order`/`Lot`/`Platform`);
- разрешение референсов: OCDS явно требует валидировать, что каждый `OrganizationReference.id` резолвится в `parties`, иначе это data quality issue — стоит завести такую проверку и в вашем импорте.

Отдельно источник советует **двухслойную модель** для агрегаторов, которые вычитывают внешние данные (ваш случай — вы парсите ЕИС, не являетесь source-of-truth):
1. **Ingest-слой**: хранить party/роли «как заявлено» в каждой версии извещения (faithful to source) — то есть привязка ролей к `notice_version`, а не только к `notice`.
2. **Canonical-слой**: резолвить организации по ИНН/ОГРН в единую master-запись поверх версий (entity resolution), для аналитики «все закупки поставщика X».

Это прямо стыкуется с найденным по вашему домену паттерном (независимый поиск про ЕИС-агрегаторы предложил похожую `notice_party(lot_id, organization_id, role, contract_id, bid_id)` — то есть two convergent recommendations на единый `organization`-реестр + pivot по ролям).

## 5. Что критично заложить сейчас, чтобы не переделывать на десятках млн записей

Источник: практический чек-лист по масштабированию Postgres OLTP-схем ([the-practical-developer.online](https://the-practical-developer.online/posts/postgres-uuid-vs-bigint-keys/), [medium.com/adyen — repartitioning](https://medium.com/adyen/efficiently-repartitioning-large-tables-in-postgresql-4d170139b7b8), [dev.to partitioning strategies](https://dev.to/jssica_coelho/postgresql-partitioning-strategies-for-massive-databases-part-1-43hh)).

| Решение | Почему критично зафиксировать СЕЙЧАС |
|---|---|
| **Тип PK** | `bigint` дешевле по I/O и даёт лучшую page-locality при вставке, чем случайный `UUID v4`; миграция типа PK на большой таблице = full rewrite + переиндексация всех FK — очень дорого постфактум. Если нужен «непрозрачный» внешний ID — держите его отдельной колонкой (`public_id uuid`/ULID) поверх `bigint` PK, не меняя PK. |
| **Партиционирование** | Решение о ключе партиционирования нужно принять на старте для таблиц, которые дорастут до десятков млн строк (`notices`, `contracts`, `notice_events`, вложения). Для append-only событийных/исторических таблиц — `PARTITION BY RANGE` по времени (`placement_date`/`occurred_at`), помесячно/поквартально. Ретеншн и архивация тогда становится `DETACH/DROP PARTITION`, а не тяжёлый `DELETE`. Ретрофит партиционирования на уже выросшей таблице возможен (batch-миграция через переименование + attach), но кратно дороже, чем заложить сразу. |
| **Индексы** | Не переиндексировать всё подряд заранее — но продумать composite-индексы под реальные фильтры (`WHERE customer_id = ? AND placement_date >= ? ORDER BY ...`), и не тащить широкий `UUID` как leading column в множестве вторичных индексов. |
| **Классификаторы + версии** | См. п.3 — codes с `valid_from/valid_to`, привязка исторической закупки к версии классификатора, действовавшей на дату. Забыть это на старте = невозможность корректно интерпретировать старые записи после переиздания ОКПД2. |
| **Party/roles реестр** | См. п.4 — если вместо этого сейчас плоские FK-колонки на `notice` (`customer_org_id`, `winner_org_id`), при добавлении новых ролей (уполномоченный орган, оператор СМП-площадки, банк-гарант) потребуется рефакторинг схемы и данных задним числом. |
| **Полнотекстовый поиск** | Отдельная поисковая таблица/MV с `tsvector`+`GIN`, `russian`-конфигурацией, а не ad-hoc `LIKE` по транзакционным таблицам — на объёме in-place `LIKE`-поиск деградирует первым. |
| **Адресный слой (ГАР, не КЛАДР/ФИАС)** | Отдельный найденный, но важный факт: ФНС официально вывела формат ФИАС из эксплуатации (2021), КЛАДР — тоже выводится; актуальный формат — **ГАР** (XML, `OBJECTID`/GUID как ключи объекта адреса) ([fias.nalog.ru](https://fias.nalog.ru/News/Viewer?newsId=52), разбор структуры: [hflabs.ru](https://hflabs.ru/blog/poleznoe/poka-fias-rasskazyvaiem-kak-ustroien-adriesnyi-spravochnik-gar), [cartetika.ru](https://cartetika.ru/tpost/rs04cektx1-kladr-fias-i-gar-chto-eto-i-s-chem-eto-e)). Если планируете детальный слой по адресам заказчика/местам поставки — закладывайте иерархию region → municipal_district → settlement → locality → street → address_object с ключом на `OBJECTID` ГАР, плюс денормализованный `region_code` на заказчике/контракте для быстрой региональной аналитики, плюс fallback `region_code_from_source` на случай нераспознанного адреса. Не проектируйте новую систему поверх КЛАДР — легаси. |
| **raw_payload / raw_xml** | В реальных open-source парсерах ЕИС (см. ниже) везде хранится сырой XML/JSON рядом с разобранными полями — оправданно, поскольку XSD-схема ЕИС менялась несколько раз, и без raw-копии переразбор невозможен без повторного скачивания с FTP. Стоит зафиксировать это в `notice_version`/`document_analysis` сразу, а не добавлять потом. |
| **Различение номера в ЕИС и номера на ЭТП** | Для 223-ФЗ часто два разных номера (ЕИС и площадка) — если ключ выбран неверно (площадочный вместо ЕИС), дедупликация/сверка ломается. Источник: [wiki.gosplan.info/purchases](https://wiki.gosplan.info/+show/+1560f3cb75834982b238879990b86ba0/docs/purchases). |
| **Явное разделение терминов "версия"** | В интеграционных схемах путают `apiVersion` (версия вашего API), `sourceEdition` (редакция/тираж источника) и `documentVersion` (версия конкретного извещения/протокола) — держите их разными полями, не сводите к одному `version`. |

## 6. Референс: реальные open-source схемы под ЕИС

Найдены существующие парсеры с готовыми PostgreSQL-схемами, полезные как sanity-check вашей модели:
- [ForwardMoth/zakupki.gov](https://github.com/ForwardMoth/zakupki.gov) — Python, FTP XML → PostgreSQL, 223-ФЗ, >2 млн закупок по Москве.
- [ruzhnikov/gov-purchases-crawler](https://github.com/ruzhnikov/gov-purchases-crawler) — парсинг ftp.zakupki.gov.ru, протоколы + извещения, Python 3.6+/PostgreSQL.
- [shalimski/zakupkiNsi](https://github.com/shalimski/zakupkiNsi) — загрузка НСИ (справочник организаций) в PostgreSQL JSONB.

Их общая схема (organizations/notices/lots/lot_items/contracts/protocols) структурно совпадает с рекомендациями выше: `okpd2_codes TEXT[]` с GIN-индексом как денормализация поверх нормализованного `lot_items.okpd2_code`, `raw_xml` в `notices` для переразбора, партиционирование `notices`/`contracts` по `placement_date` рекомендовано явно при >10M строк.

## Рекомендации для ТЗ (второй детальный слой)

1. **Схемы vs префиксы**: зафиксировать в `docs/dev/architecture.md`, что `plt_`/`eis_`-префиксы = bounded context, а не техническая метка; классификаторы и party-реестр — в общий (unprefixed или отдельный `ref_`/`org_`) слой, не привязанный к Platform/Eis.
2. **Ввести `notice_event`** (append-only, `entity_type`/`entity_id`/`event_type`/`occurred_at`/`payload jsonb`/`source_system`) как источник истины поверх/рядом с уже вероятно существующим версионированием — если сейчас версии фиксируются только как снапшоты без событийной причины, добавить `change_reason`/ссылку на событие.
3. **Вынести классификаторы (ОКПД2, КТРУ, ОКВЭД2, КБК) отдельными справочными таблицами** с `parent_code`, `level`, `valid_from/valid_to`; в позициях закупки хранить одновременно `*_code_raw` (как в источнике) и FK на справочник.
4. **Ввести единый реестр `organization`/`party` + pivot `notice_party(notice_id/lot_id, organization_id, role, valid_from_version, valid_to_version)`** вместо (если сейчас так) плоских `customer_id`/`winner_id` колонок — критично перед добавлением детального слоя карточки, где ролей участников станет больше (уполномоченный орган, оператор ЭТП, банк-гарант, члены комиссии).
5. **Партиционирование `notice`/`document`/событийных таблиц по времени** (`placement_date`/`occurred_at`) — заложить `PARTITION BY RANGE` до пересечения отметки в несколько млн строк, не после.
6. **Проверить тип PK** на всех таблицах, которые дорастут до десятков млн (`plt_links`, документы/анализы) — если сейчас UUID v4, оценить миграцию на bigint + отдельный public UUID, пока таблицы небольшие.
7. **Полнотекстовый поиск**: отдельная `*_search` таблица/materialized view с `tsvector('russian', ...)` + GIN, обновляемая по событию новой версии, а не поиск по транзакционным таблицам напрямую.
8. **Адресный слой**: если планируется гео/региональная аналитика — проектировать сразу на структуре ГАР (не КЛАДР/ФИАС), с денормализованным `region_code` на заказчике/месте исполнения для быстрых срезов и fallback-полем на случай нераспознанного адреса.
9. **Различить номер в ЕИС и номер на ЭТП** как отдельные поля с explicit source, не сводить в один "external_id".
10. **Хранить `raw_payload`/`raw_xml`** на уровне версии документа — уже частично есть через AI-анализ документов, но стоит явно предусмотреть и для карточки извещения (не только вложений), так как схема ЕИС нестабильна во времени.
