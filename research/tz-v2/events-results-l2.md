# Жизненный цикл, журнал событий и результаты закупки на ЕИС — исследование для схемы БД

## 1. Журнал событий карточки извещения

На странице извещения ЕИС (zakupki.gov.ru) есть отдельная вкладка **«Журнал событий»**, которая хронологически фиксирует все значимые операции по закупке — от первичной публикации до отмены [fz44.org](https://fz44.org/obuchenie/%D0%B5%D0%B8%D1%81/), [pro-goszakaz.ru](https://s.pro-goszakaz.ru/files/downloadFolder/Article_103025_b6d2784751cbfbff179dff31c2bc3637.pdf).

**Подтверждённые типы событий**, которые ЕИС фиксирует и рассылает подписчикам как уведомления:
- размещение извещения о закупке (первичная публикация, редакция №1);
- размещение изменений извещения / документации (новая редакция);
- размещение разъяснений документации (ответ заказчика на запрос участника);
- размещение протоколов (рассмотрение заявок, подведение итогов, признание закупки несостоявшейся и др.);
- размещение извещения об отказе от определения поставщика (отмена закупки), а также отмена самой отмены.

**Структура записи журнала** (реконструирована по описанию UI и уведомлений, точной публичной JSON/XML-схемы поля «журнал событий» в открытых источниках найти не удалось — это НЕ подтверждённый факт, а обобщение):
- тип события (человекочитаемая метка: «Размещение извещения», «Изменение извещения», «Разъяснение», «Протокол…», «Отмена определения поставщика»);
- дата и время регистрации события в ЕИС;
- идентификаторы — номер извещения/закупки, номер протокола/документа;
- субъект действия — заказчик или оператор электронной площадки (для протоколов ЭТП);
- краткое наименование документа-события («Итоговый протокол рассмотрения и оценки заявок», «Разъяснение положений документации» и т.п.);
- ссылка/вложение на связанный документ.

Важно: журнал событий по сути — это **UI-проекция** над набором дискретных документов (извещение + N редакций + N разъяснений + N протоколов + возможно решение об отмене), а не самостоятельная сущность с независимым хранением. Для парсинга разумнее строить свою модель `procurement_events` как таблицу-агрегатор ссылок на реальные документы-сущности, а не пытаться распарсить HTML именно вкладки «Журнал событий».

## 2. Протоколы: виды, содержание, связь со стадиями

Протоколы жёстко привязаны к способу определения поставщика — под каждый способ закон предписывает свою цепочку.

| Способ закупки (44-ФЗ) | Типовая цепочка протоколов |
|---|---|
| Открытый конкурс в электронной форме | протокол рассмотрения первых частей заявок → протокол рассмотрения вторых частей и оценки → (протокол признания несостоявшимся, если применимо) → протокол подведения итогов |
| Электронный аукцион | протокол рассмотрения первых частей заявок → протокол проведения аукциона (ход торгов, шаг снижения) → протокол рассмотрения вторых частей заявок → (протокол несостоявшимся) → протокол подведения итогов |
| Электронный запрос котировок | протокол рассмотрения заявок → (протокол несостоявшимся) → протокол подведения итогов (часто совмещён с рассмотрением) |
| Запрос предложений | протокол рассмотрения заявок → протокол оценки и сопоставления → протокол подведения итогов → (протокол несостоявшимся) |
| Закупка у единственного поставщика (ст. 93) | протокол обоснования (по основанию п. ч.1 ст.93) → протокол согласования с контрольным органом (для отдельных оснований, напр. п.24-25) → протокол несостоявшейся закупки (по обстоятельствам) |

Источники: [zakupki44fz.ru](https://zakupki44fz.ru/voprosy-otvety/protokol-rassmotreniya-zayavok/), [finaxe.ru](https://finaxe.ru/article/vidy-zakupok-po-44-fz), [goszakupki.tatarstan.ru](https://goszakupki.tatarstan.ru/file/pub/pub_3779356.pdf).

**Обязательное содержание итогового протокола** (ч. 17 ст. 48 44-ФЗ для электронного конкурса, аналогично для других способов):
- общие сведения: заказчик, объект закупки, НМЦК, способ определения поставщика;
- информация по каждой поданной заявке (или части заявки);
- решение по каждой заявке — «соответствует» / «отклонена», с обоснованием (ссылка на нарушенные пункты закона/извещения/документации/заявки);
- результаты оценки по критериям, ранжирование участников, определение победителя и (опционально) участника со следующим по выгодности предложением;
- при признании закупки несостоявшейся — отдельная фиксация оснований (ссылки на ст. 48, 67, 71 44-ФЗ).

Все протоколы подписываются членами комиссии УКЭП и направляются оператором электронной площадки в ЕИС; для протокола рассмотрения — обычно не позднее 2 рабочих дней после окончания подачи заявок (для отдельных спецзакупок — 5 дней) [zakupki44fz.ru](https://zakupki44fz.ru/voprosy-otvety/protokol-rassmotreniya-zayavok/), [base.garant.ru](https://base.garant.ru/77849084/).

### 223-ФЗ: структура протоколов не унифицирована законом

По 223-ФЗ закон **не задаёт** унифицированную форму и перечень протоколов — их состав и структуру определяет собственное **Положение о закупке** заказчика [xn--80aahqcqybgko.xn--p1ai](https://xn--80aahqcqybgko.xn--p1ai/141/1133/39298/45258.html), [cntd.ru](https://docs.cntd.ru/document/767021250). Жёстко закреплены только:
- обязанность размещать в ЕИС протоколы, составляемые в ходе закупки, и итоговый протокол — независимо от результата (даже при нулевом числе заявок);
- срок размещения — не позднее **3 дней** со дня подписания протокола (и для закупки у единственного поставщика, если протокол вообще составляется);
- после заключения договора — внесение сведений в реестр договоров ЕИС в течение 3 рабочих дней.

Практический вывод для схемы: под 223-ФЗ протокол нужно моделировать как **типизированный, но гибкий по составу полей документ** (тип протокола из открытого/расширяемого справочника: рассмотрение/допуск-отказ/подведение итогов/отмена-несостоявшаяся/единственный поставщик), а не жёстко фиксированную схему, как для 44-ФЗ.

## 3. Результаты определения поставщика: что и где публикуется

После размещения итогового протокола в карточке извещения появляется отдельная вкладка **«Результаты определения поставщика (подрядчика, исполнителя)»** [goszakaz.e-dag.ru](https://goszakaz.e-dag.ru/portal/Show/File/1300?ParentItemId=170). Она представляет собой UI-проекцию итогового протокола, а не независимый источник данных — при автоматизации логичнее парсить сам протокол.

Состав данных на вкладке / в протоколе:

**По победителю:**
- наименование участника / ФИО (ИП, физлицо), ИНН, номер записи в ЕРУЗ, идентификатор заявки на площадке;
- итоговая цена контракта (ценовое предложение, ставшее основанием для контракта);
- порядковый номер заявки в итоговом ранжировании (обычно №1 у победителя).

**По всем участникам (включая отклонённых):**
- наименование/идентификатор в ЕРУЗ;
- ID заявки, присвоенный оператором площадки;
- ценовое предложение;
- порядковый номер в итоговом рейтинге;
- статус: допущена / отклонена;
- для отклонённых — мотивированное основание (ссылка на пункт документации/статью 44-ФЗ или 223-ФЗ, включая случаи ограничений по ст. 14 44-ФЗ — национальный режим, требования СТ-1, лицензии, опыт).

**Особый случай — закупка признана несостоявшейся:** если все заявки отклонены или подана только одна (либо не соответствующая условиям), вместо «победителя» на вкладке отображается результат «несостоявшаяся», с соответствующей записью в протоколе.

Источники: [goszakaz.e-dag.ru](https://goszakaz.e-dag.ru/portal/Show/File/1300?ParentItemId=170), [base.garant.ru](https://base.garant.ru/77849084/).

Важная оговорка (неподтверждённый нюанс, стоит перепроверить на реальной карточке): часть персональных данных участников (кроме победителя) сейчас может не выводиться в публичной части ЕИС из-за режима ограниченного раскрытия сведений (актуально для секционных ограничений 2022+), это нужно валидировать эмпирически при парсинге конкретных закупок.

## 4. Редакции извещения: нумерация и семантика

ЕИС ведёт **порядковый номер редакции** извещения — версию опубликованного текста, а не сам номер закупки/реестровый номер [zakupki21.ru](https://zakupki21.ru/downloadppf?uuid=dbfileb5m78680000p5gntosa2nfn71o).

- Первая публикация — редакция №1.
- Каждое изменение (сроков, требований, НМЦК в допустимых пределах и т.д.) публикуется как новая редакция: №2, №3…
- Заказчик не вправе менять наименование объекта закупки и увеличивать размер обеспечения заявок при внесении изменений; изменения подписываются УКЭП.
- Для практики важно ориентироваться на **последнюю опубликованную редакцию** как на действующую версию условий закупки.

Для схемы это прямо ложится на уже предполагаемую `procurement_revisions` — но с явным полем `revision_number` (int, монотонно возрастающий per-извещение) и, желательно, диффом изменённых полей (что именно изменилось — критично для последующего AI-анализа влияния изменений на условия).

## 5. Разъяснения документации — отдельная сущность

Да, разъяснение — это отдельный документ/сообщение в ЕИС, публикуемый **без указания участника**, который направил запрос [gkgz.ru](https://gkgz.ru/po-kakoj-forme-neobhodimo-gotovit-razyasnenie-polozhenij-izveshheniya-o-zakupke/):

- участник направляет запрос через ЭТП, не позднее чем за 3 дня до окончания срока подачи заявок;
- максимум 3 запроса на разъяснение по одной закупке (для электронного конкурса/аукциона);
- заказчик обязан разместить разъяснение в ЕИС в течение 2 дней со дня, следующего за днём получения запроса;
- разъяснение **не должно** менять суть извещения/документации — если требуется содержательное изменение условий, это оформляется отдельно как изменение извещения (новая редакция), а не как разъяснение.

Вывод: разъяснение и изменение извещения — разные по природе документы с разными сроками и разным влиянием на данные (разъяснение не двигает `revision_number`, изменение — двигает).

## 6. Отмена закупки — отдельная сущность жизненного цикла

Отмена оформляется **отдельным документом** «Решение об отмене определения поставщика», публикуемым в ЕИС, а не правкой исходного извещения [pro-goszakaz.ru](https://s.pro-goszakaz.ru/files/art/st_36_44_fz.docx), [ppt.ru](https://ppt.ru/art/zakupki/kak-oformit-reshenie-ob-otmene-zakupki):

- сроки отмены: конкурс/аукцион — не позднее чем за 5 дней до окончания подачи заявок; запрос котировок — до 1 часа до окончания подачи заявок; после этих сроков — только форс-мажор;
- запрос предложений отменить нельзя (ст. 36 44-ФЗ);
- решение размещается в ЕИС в день принятия, с этого момента закупка считается отменённой;
- ЕИС поддерживает и обратный документ — «Отмена извещения об отмене определения поставщика» (отмена отмены), возобновляющий процедуру.

Это отдельная сущность жизненного цикла, логически близкая к протоколу, но со своим набором оснований/сроков — стоит моделировать как `procurement_cancellation` (или тип события в общей таблице документов-событий) со ссылкой на исходное извещение и, опционально, на документ отмены отмены.

## 7. Проекция на OCDS: tender → awards → contracts, amendments, milestones

OCDS моделирует процесс закупки как последовательность **immutable releases**, привязанных к `ocid`, с полями `tag` (`planning`/`tender`/`award`/`contract`/`implementation`) [standard.open-contracting.org](https://standard.open-contracting.org/latest/en/primer/releases_and_records/), [standard.open-contracting.org](https://standard.open-contracting.org/latest/en/schema/reference/):

| OCDS-блок | Назначение | Соответствие ЕИС |
|---|---|---|
| `tender` | объект закупки, суммы, сроки, документы, статус (`active`/`complete`/`cancelled`) | извещение + документация + редакции |
| `tender.amendment` | факт изменения тендера (дата, обоснование) | редакция извещения |
| `awards[]` | решения о присуждении (по лотам), победитель, сумма, статус | итоговый протокол / вкладка «Результаты определения поставщика» |
| `contracts[]` | заключённые контракты, привязка к `awardID` | реестр контрактов (отдельный от извещения объект в ЕИС) |
| `contracts[].implementation.milestones[]` | вехи исполнения контракта (план/факт даты, статус) | нет прямого аналога в текущем скоупе задачи (это уже стадия исполнения контракта, не извещения) |
| `documents[]` (в каждом блоке) | приложенные файлы | LinkAttachment |

**Важный вывод**: OCDS не выделяет «протокол» и «разъяснение» как отдельные типизированные сущности верхнего уровня — это либо документы (`documents[]`) внутри `tender`, либо `amendment`. Российская модель (с обязательными типизированными протоколами и разъяснениями по закону) **детальнее**, чем базовый OCDS, и для полноценного маппинга потребуется либо расширение (custom fields / extension), либо собственная модель, из которой можно *агрегировать* OCDS-представление, а не наоборот.

Готового публичного OCDS-паблишера для zakupki.gov.ru не существует; ближайшие агрегаторы — Минфин (открытые данные) и Clearspending/ГосЗатраты, но оба не публикуют в формате OCDS напрямую — маппинг делается вручную поверх XML/CSV [minfin.gov.ru](https://minfin.gov.ru/OpenData/7710168360-minfin_buy/), [minfin.gov.ru](https://minfin.gov.ru/common/upload/files/20151126/Begtin_clearspending_openfin.pdf), [index.okfn.org](http://index.okfn.org/place/ru/procurement.html).

## Рекомендации для ТЗ

Сущности, которые стоит добавить в универсальную схему сверх `procurement_revisions` / `procurement_events`:

1. **`procurement_protocols`** — типизированный протокол: `type` (enum: рассмотрение_первых_частей / рассмотрение_вторых_частей / проведение_аукциона / оценка / несостоявшаяся / итоговый / обоснование_ед_поставщика / согласование_ед_поставщика / произвольный_223фз), `stage`, `signed_at`, `published_at`, ссылка на извещение, вложение(я)-источник (LinkAttachment), сырой JSON извлечённых полей (комиссия, обоснования). Для 223-ФЗ `type` должен допускать «прочее/по Положению» — не пытаться жёстко типизировать до конца.

2. **`procurement_bids` / `procurement_protocol_participants`** — построчная разбивка по заявкам внутри итогового (или рассмотрения) протокола: участник (наименование, ИНН, ЕРУЗ-номер), ID заявки на площадке, цена предложения, статус (допущена/отклонена/победитель), основание отклонения (текст + по возможности ссылка на норму), итоговый ранг.

3. **`procurement_clarifications`** (разъяснения) — отдельная сущность: запрос (дата поступления, анонимно) + ответ заказчика (дата публикации, текст, вложения), связь с извещением и, опционально, с конкретной редакцией (если разъяснение привело к изменению).

4. **`procurement_revisions`** (уже есть) — усилить полем `revision_number` (монотонный per-notice) и, если возможно, полем «что изменилось» (diff по ключевым полям: сроки, НМЦК, требования) — это отдельный документ-триггер, отличный от разъяснения.

5. **`procurement_cancellations`** — решение об отмене определения поставщика: основание, дата, ссылка на извещение; плюс опциональная связь на «отмену отмены» (тот же тип с обратным флагом или отдельная запись, ссылающаяся на исходную отмену).

6. **`procurement_awards`** (аналог OCDS `awards[]`) — по сути производная от итогового протокола/`procurement_bids`, но как отдельная агрегированная сущность «результат по лоту»: победитель, итоговая цена контракта, статус (`awarded`/`unsuccessful`/`cancelled`), полезна как денормализованная витрина для отчётности и как якорь для будущей связки с реестром контрактов (`contracts`), который в этой задаче отдельно не исследовался, но логически следующий слой по OCDS-модели.

7. **`procurement_events`** (уже есть) — оставить как тонкий агрегатор-«журнал» (тип события + timestamp + ссылка на реальную сущность-документ из п.1–6), не пытаться хранить в нём бизнес-данные напрямую — это должно быть проекцией, а не источником истины.

Отдельно стоит заложить архитектурное различие: **44-ФЗ** даёт закрытый регламентированный набор протоколов по способу закупки (можно жёстко типизировать `type` через enum и even заранее знать обязательные поля per-типу), тогда как **223-ФЗ** требует гибкой модели (open-ended type + произвольный JSON payload), поскольку структура протокола там определяется Положением о закупке конкретного заказчика, а не законом.
