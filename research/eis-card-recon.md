# Разведка детальной карточки закупки ЕИС (живая, 2026-07-03)

Снято вживую через Playwright (HTTP, `credentials: omit` — сессия не нужна). Примеры: `0338300047926000233` (44-ФЗ ЭА ea20, капремонт, отменён), `0891200000626007012` (44-ФЗ запрос котировок zk20, завершён). Дополняет `eis-csv-recon.md` (тот — про листинг; этот — про **детальный слой** карточки).

## 1. URL и типы процедур

Карточка: `/epz/order/notice/<тип>/view/<вкладка>.html?regNumber=<N>`.
- `<тип>` зависит от способа закупки: `ea20` (электронный аукцион), `zk20` (запрос котировок), `ezt20` (закупка у ед. поставщика ч.12 ст.93), и др. **Тип нужно резолвить** — из листинга (ссылка на карточку содержит тип) либо перебором/редиректом.
- Вкладки (`<вкладка>`): `common-info`, `documents`, `event-journal`, `supplier-results` (только у завершённых).
- Все вкладки — **server-side HTML, берутся обычным HTTP** без сессии (подтверждено). Браузер не нужен.

## 2. Вкладки карточки

| Вкладка | URL | Есть когда | Содержимое |
|---|---|---|---|
| Общая информация | `common-info.html` | всегда | все поля извещения (§3) |
| Документы | `documents.html` | всегда | файлы-вложения (`filestore/...`), уже в `eis-csv-recon.md` |
| Журнал событий | `event-journal.html` | всегда | таблица событий от ЕИС (§4) |
| Результаты определения поставщика | `supplier-results.html` | завершённые | победитель, предложения участников, связь с контрактом (§5) |

## 3. Общая информация (`common-info`) — полный набор полей

Снято с реальной карточки ea20. Разделы и поля:

**Блок «Общая информация о закупке»**
- Способ определения поставщика (полная формулировка, напр. «Электронный аукцион на проведение работ… п.8 ч.1 ст.33 Закона №44-ФЗ»)
- Наименование электронной площадки (ЭТП) + адрес ЭТП (URL, напр. roseltorg.ru)
- Размещение осуществляет (роль: Заказчик / Уполномоченный орган) + организация (ссылка `organizationCode`)
- Наименование объекта закупки (текст)
- Этап закупки (сырой статус: «Подача заявок», «Работа комиссии», «Определение поставщика отменено/завершено»…)
- Сведения о связи с позицией плана-графика (номер + ссылка)

**Блок «Контактная информация»**
- Организация, осуществляющая размещение; почтовый адрес; место нахождения; ответственное должностное лицо (ФИО); email; телефон; доп. информация; регион.

**Блок «Информация о процедуре закупки»**
- Дата/время начала подачи заявок; окончания подачи заявок; дата процедуры подачи предложений о цене; дата подведения итогов. (С таймзоной, напр. «МСК+9».)

**Блок «Начальная (максимальная) цена контракта»**
- НМЦК; валюта; размер аванса, %; ИКЗ.

**Блок «Сроки исполнения и источники финансирования»**
- Дата начала исполнения контракта; срок исполнения; признак «за счёт собственных средств»;
- **Финансовое обеспечение по годам** (таблица: На 2026/2027/2028/последующие/Всего, ₽);
- За счёт внебюджетных средств (та же разбивка);
- **Детализация по кодам видов расходов** (КВР + код поступления + суммы по годам);
- Выделено в рамках нацпроектов (КБК/целевая статья + суммы по годам).

**Блок «Информация об объекте закупки»** — таблица позиций:
- Код позиции (**ОКПД2 + КТРУ**, напр. `41.20.40` / `41.20.40.000-00000023`, ссылка на карточку КТРУ);
- Наименование товара/работы/услуги + характеристики (текст, иногда с доп. требованиями);
- Ед. измерения; Количество; Цена за ед., ₽; Стоимость, ₽.

> Важно: у 44-ФЗ «объект закупки» может быть **одной позицией на всю сумму** (как здесь — «условная единица», работы) либо списком товаров. Многолотовые процедуры (конкурсы) дают несколько лотов, каждый со своей таблицей позиций — структуру лотов подтвердить на многолотовом примере при реализации.

## 4. Журнал событий (`event-journal`) — КЛЮЧЕВАЯ находка

ЕИС **сам ведёт журнал событий** карточки — таблица `Дата и время | Событие`. Примеры строк:
- `30.06.2026 08:22 (МСК+9) | Размещен документ «Извещение о проведении электронного аукциона … №…»`
- `30.06.2026 08:22 | Закупка №… автоматически переведена на этап «Подача заявок»`
- `01.07.2026 07:00 | … переведена на этап «Работа комиссии»`
- `03.07.2026 16:38 | Размещен «Протокол подведения итогов … №ИЗК1»`
- `03.07.2026 16:38 | … переведена на этап «Определение поставщика завершено» в связи с размещением протокола…`
- `03.07.2026 20:18 | Размещен документ «Извещение об отмене определения поставщика …»` + перевод на этап «отменено».

**Следствие для схемы:** переходы этапов и факты размещения документов/протоколов не нужно только *реконструировать диффом редакций* — их можно **забирать напрямую из журнала ЕИС** (авторитетный источник, с точными датами). Наш `prc_events` наполняется из этого журнала (парсинг строк → типизированные события), а diff редакций — дополняющий механизм для полей, которых в журнале нет (цена/сроки).

## 5. Результаты определения поставщика (`supplier-results`) — завершённые

Разделы:
- **Результат определения поставщика** (на основании протоколов): заказчик, с которым планируется контракт; идентификационные номера участников; порядковые номера по итогам рассмотрения; **предложения участников, ₽** (таблица — по сути ставки/итоговая цена).
- **Информация о процедуре заключения контракта**.
- **Сведения о контракте из реестра контрактов** (связь с реестром контрактов — итоговый контракт, номер).

## 6. Что из этого нужно в БД сверх текущей схемы (детальный слой)

1. **Финансирование по годам / КБК / КВР / нацпроекты** — таблица источников финансирования закупки (годовая разбивка).
2. **Позиции объекта закупки** — уже есть `purchase_items`, но нужны поля: код КТРУ (отдельно от ОКПД2), характеристики (текст/структура), стоимость. Классификатор — по OCDS-схеме (scheme+code).
3. **Журнал событий ЕИС** — источник наполнения `prc_events` (не только diff редакций); хранить сырой текст события + распарсенный тип.
4. **Протоколы** — тип документа/сущность: протоколы рассмотрения/подведения итогов, связаны с этапом и датой (в журнале видны как «Размещён протокол …»).
5. **Результаты/итоги (awards)** — победитель, участники, их предложения (₽), связь с реестром контрактов. OCDS `awards`/`contracts`.
6. **Связь с планом-графиком** (номер позиции), **ЭТП** (площадка + URL), **аванс %**, **сроки исполнения**, **обеспечение заявки/контракта** — поля извещения (ядро/extension ЕИС).
7. **Контактное лицо** (ФИО/email/телефон) — на стороне заказчика/размещающей организации.

## 7. Стадии сбора: первичный vs детальный (уточнение)

- **Листинг (CSV)** — `eis-csv-recon.md`: reg_number, объект, НМЦК, заказчик, даты, этап. Быстрый индекс.
- **Детальная карточка (HTTP)** — этот файл: полный набор полей + позиции + журнал событий + результаты. Отдельная стадия/job после листинга, HTTP-first, распадается на 4 вкладки.
- **Документы** — файлы из `documents.html`, дальше AI-пайплайн (сметы). Отдельная стадия.

## 8. Не проверено / риски

- Структура **многолотовой** процедуры (конкурс с несколькими лотами) — снять на реальном примере при реализации.
- 223-ФЗ карточка — набор полей и URL (`/epz/order/notice/…` vs иной путь для 223) отличается; снять отдельно.
- Протоколы как отдельные файлы vs записи — уточнить парсинг на завершённых примерах.
- Стабильность вёрстки блоков `common-info` между релизами ЕИС — как и с CSV, нужен smoke-контроль.

## 9. Многолотовые процедуры 44-ФЗ — живая проверка (доп. к §8)

Снято вживую 03.07.2026, Playwright, без сессии.

- Тип URL для конкурсов 44-ФЗ: **`ok20`** (Открытый конкурс в электронной форме). Найден через фильтр листинга «Способ определения поставщика» → группа «Открытый конкурс*» (реальные коды справочника: `OK504,OKP504,OK20,OKP20,OKK504,OKB20,OKA504,OKA20,OKI20,OKB504,EOK504,EOK20,OKI504`).
- Живой пример: `regNumber=0172200002726000086`, `https://zakupki.gov.ru/epz/order/notice/ok20/view/common-info.html?regNumber=0172200002726000086` — «Оказание услуг по организации питания в государственных бюджетных образовательных учреждениях, подведомственных администрации Центрального района Санкт-Петербурга в 2026-2027 годах», НМЦК 37 779 488,40 ₽, организатор — уполномоченный орган (АДМИНИСТРАЦИЯ ЦЕНТРАЛЬНОГО РАЙОНА САНКТ-ПЕТЕРБУРГА).
- Структура «Информация об объекте закупки» на этой карточке: **ОДНА таблица позиций** (6 строк, Итого 37 779 488,40 ₽), явных блоков/заголовков «Лот 1»/«Лот 2» на странице НЕТ.
- При этом в блоке «Начальная (максимальная) цена контрактов» → «Идентификационный код закупки (ИКЗ)» показаны **5 РАЗНЫХ ИКЗ** одновременно, а в «Сведения о связи с позицией плана-графика» — **5 разных ссылок** на позиции плана-графика (5 школ-заказчиков под одним извещением уполномоченного органа). Это структура совместной/консолидированной закупки (несколько ИКЗ/заказчиков под одним НМЦК и одной таблицей позиций), а не классический «лот» с собственной НМЦК/сроками.
- В листинге по тому же организатору и почти тому же наименованию нашлись ЕЩЁ 3 извещения с РАЗНЫМИ reg_number: `0172200002726000087`, `0172200002726000088`, `0172200002726000089` (соседние номера, тот же организатор, тот же способ, та же дата размещения). Похоже, что для этого типа объединённой закупки текущая версия ЕИС публикует то, что раньше могло быть «лотами» одной карточки, как **отдельные извещения (отдельные reg_number)**, а не как разделы внутри одной карточки.
- **Вывод (частично не подтверждён):** классической структуры «одна карточка 44-ФЗ — несколько явных блоков „Лот N“ со своей НМЦК/сроками/таблицей позиций» на проверенном живом примере **не обнаружено**. Гипотеза: после реформы 44-ФЗ 2019 г. (требование вести многолотовые конкурсы как отдельные процедуры на лот) такая монолитная структура для актуальных 44-ФЗ извещений 2026 года неактуальна или крайне редка. Проверен только 1 живой пример открытого конкурса — для строгого вывода нужно больше образцов; статус риска **не закрыт полностью**, но найдено правдоподобное объяснение и рабочая альтернатива (см. §12).

**Подтверждающий пример (доп. проверка 03.07.2026, по ссылке владельца, price-sort ≥1 000 000 ₽, publishDateFrom=2025):** в листинге запросов котировок (`zk20`) встретились названия объекта закупки с явным текстовым «(лот N)»/«(Лот N)» — `regNumber=0345300063925000131` → «Поставка реагентов для иммунохемилюсцентного анализа (лот 4)», `regNumber=0177200000925002221` → «Поставка расходных материалов для лаборатории (Лот 6)». Это **отдельные reg_number**, каждый со своей карточкой `zk20/view/common-info.html`, а «лот N» — просто часть свободного текста наименования объекта закупки, не структурный блок карточки. Это прямо подтверждает гипотезу §9: заказчики нумеруют лоты вручную в названии, публикуя каждый как отдельное извещение — значит парсеру НЕ нужно искать вложенные «Лот N»-блоки внутри одной карточки 44-ФЗ, достаточно обычной одной таблицы позиций на reg_number (что уже заложено в `01-database.md`). Риск можно считать **закрытым для MVP** с этим рабочим выводом.

## 10. 223-ФЗ карточка — URL и структура (закрывает риск §8 по 223-ФЗ)

Снято вживую 03.07.2026, Playwright, без сессии, 3 карточки.

- **URL 223-ФЗ отличается от 44-ФЗ.** Ссылка в листинге ведёт на `https://zakupki.gov.ru/223/purchase/public/purchase/info/common-info.html?regNumber=<N>`, но браузер **редиректит** на `https://zakupki.gov.ru/epz/order/notice/notice223/common-info.html?regNumber=<N>` — тот же движок `epz`, но отдельная ветка `notice223` (а не `<тип44>/view/...`, как у 44-ФЗ).
- Реестровый номер 223-ФЗ — 11 цифр, начинается с `326…` (примеры: `32616177591`, `32616142202`, `32616166679`).
- Вкладки карточки 223-ФЗ (все внутри `/epz/order/notice/notice223/...`): `common-info.html`, **`lot-list.html`** («Список лотов» — отдельная вкладка, у 44-ФЗ такой нет), `documents.html`, `changes-and-explanations.html` («Изменения и разъяснения» — отдельная вкладка, у 44-ФЗ разъяснения не вынесены отдельным табом), `protocols.html` («Протоколы» — тоже отдельная вкладка, у 44-ФЗ протоколы не выделены отдельным табом на карточке), `contract-info.html` («Сведения о договорах»), `event-journal.html`.
- **Почти все вкладки требуют `noticeGuid` в query** (GUID извещения), помимо `purchaseNoticeNumber`/`regNumber`. Проверено: `lot-list.html?purchaseNoticeNumber=<N>` БЕЗ `noticeGuid` → таймаут/ошибка страницы («Превышен лимит времени ожидания»); с `noticeGuid` — 200 OK. **GUID нужно сохранять при парсинге листинга** — он есть в ссылках результатов поиска (`purchaseNoticeGuid=...`) и на самой карточке (в URL вкладки «Общая информация»).
- **Лот 223-ФЗ — отдельная сущность со своей страницей**, не просто раздел внутри карточки: `lot-list.html` — таблица с колонками `Номер, наименование лота | Централизованная закупка | Сведения о цене договора | Классификация по ОКПД2 | Классификация по ОКВЭД2`; каждая строка — ссылка на `/epz/order/notice/notice223/lot/lot-info.html?lotGuid=<uuid>&purchaseNoticeGuid=<uuid>&purchaseNoticeNumber=<N>`, т.е. у каждого лота собственный `lotGuid`.
  - Проверено на 3 живых примерах (`32616177591` — «ГПЭС 2ой очереди», `32616142202` — «Поставка шибера», `32616166679` — «Трансиверы») — во всех трёх найден **ровно 1 лот**. Живой пример с N>1 лотов найти в отведённое время не удалось (не подтверждено), но сам механизм (перебор строк таблицы `lot-list.html`, у каждой — свой `lotGuid` и своя цена/ОКПД2/ОКВЭД2) однозначно рассчитан на произвольное число лотов — можно смело проектировать краулер под N≥1 без дополнительной проверки.
- Набор полей `common-info` 223-ФЗ **заметно отличается** от 44-ФЗ:
  - Есть, чего нет у 44-ФЗ: «Редакция» (номер редакции извещения — явное поле на карточке!), «Дата размещения извещения» отдельно от «Дата размещения текущей редакции извещения», блок «Предоставление документации» (срок/место/порядок предоставления, оплата за документацию), детальный «Порядок проведения процедуры» с подэтапами (Подача заявок → Рассмотрение первых частей заявок → Подача ценовых предложений → Сопоставление ценовых предложений → Рассмотрение вторых частей заявок → Подведение итогов) — это гранулярнее, чем у 44-ФЗ (там только сводные даты без стадии сопоставления цен).
  - Нет того, что есть у 44-ФЗ на common-info: ИКЗ, прямой таблицы ОКПД2-позиций (она переезжает на уровень `lot-info.html`), видимой «Позиция плана-графика» (вместо неё — отдельная кнопка «План закупки», причём с СВОИМ `regNumber`, отличным от закупочного).
  - «Способ осуществления закупки» — свободный текст по положению заказчика (не закрытый enum, как «Способ определения поставщика» у 44-ФЗ) — соответствует ожиданию из `01-database.md` (`procedure_type_raw`).
  - «Контактная информация» называется по-другому: «Контактное лицо» (одна строка ФИО) вместо «Ответственное должностное лицо» у 44-ФЗ; нет факса/региона на этой карточке.
- **Итог:** адаптер для 223-ФЗ должен парсить отдельную ветку `notice223` с ДРУГИМ набором полей common-info и отдельно обходить `lot-list.html` → N × `lot-info.html` за позициями/ОКПД2/ценой (у 44-ФЗ всё это на одной странице common-info).

## 11. lastDateChangeCsv vs event-journal — ЖИВАЯ ПРОВЕРКА (закрывает критичный риск §8 / `02-crawling.md` §9)

Проверено вживую 03.07.2026 (Playwright, `fetch(..., {credentials:'omit'})` внутри страницы, `TextDecoder('windows-1251')` для декодирования CSV), 2 полных примера + 1 подтверждающий по журналу.

1. **Отмена закупки**, `regNumber=0338300047926000233` (44-ФЗ, ea20). `event-journal.html` показывает: `03.07.2026 20:18 (МСК+9) | Размещен документ «Извещение об отмене определения поставщика (подрядчика, исполнителя) от 03.07.2026 №ИО1»` (и тем же временем — перевод на этап «отменено»). Запрос `GET https://zakupki.gov.ru/epz/order/orderCsvSettings/download.html?registryNumberCsv=true&lastDateChangeCsv=true&stepOrderPlacementCsv=true&nameOrderCsv=true&searchString=0338300047926000233&fz44=on&morphology=on&pageNumber=1&sortDirection=false&recordsPerPage=_10&showLotsInfoHidden=false&sortBy=UPDATE_DATE&currencyIdGeneral=-1&from=1&to=500` (200 OK, без сессии) вернул CSV-строку:
   `№0338300047926000233;Проведение капитального ремонта учреждений здравоохранения…;03.07.2026;Определение поставщика отменено`.
   **`lastDateChangeCsv` = 03.07.2026 — совпадает по дню с событием отмены.**
2. **Протокол подведения итогов**, `regNumber=0891200000626007012` (44-ФЗ, zk20, запрос котировок). `event-journal.html`: `03.07.2026 16:38 (МСК+6) | Размещен «Протокол подведения итогов определения поставщика (подрядчика, исполнителя) от 03.07.2026 №ИЗК1»` + перевод на «Определение поставщика завершено» тем же временем. CSV-запрос тем же методом вернул:
   `№0891200000626007012;Поставка расходных материалов для лаборатории (00007490-ЗК);03.07.2026;Закупка завершена`.
   **`lastDateChangeCsv` = 03.07.2026 — тоже совпадает.**
3. Третий пример для перекрёстной проверки паттерна (без отдельного CSV-запроса): `regNumber=0352300011926000062` (zk20) — журнал показывает идентичный паттерн «протокол сегодня → автопереход на завершение сегодня» (`03.07.2026 22:13 (МСК+3)`), т.е. поведение системы (документ → журнал → смена этапа) воспроизводится единообразно на разных карточках.

**Вывод:** `lastDateChangeCsv` **ОБНОВЛЯЕТСЯ** при размещении протокола и при размещении извещения об отмене — день в CSV совпадает с днём события в журнале (CSV даёт точность только до дня, без времени, точнее по минутам сверить нельзя). Значит **штатный fresh-скан по `sortBy=UPDATE_DATE`/`lastDateChangeCsv` реально ловит эти события** — заводить отдельный обязательный триггер пересъёма детального слоя именно на `event-journal` (в дополнение к уже заложенным в `02-crawling.md` §5.2 триггерам) для протоколов/отмен **не обязательно для MVP**.

**Не проверено (осталось открытым):** разъяснение документации («Размещено разъяснение…») — живое событие такого типа среди проверенных карточек не встретилось в отведённое время. Механизм публикации документа в ЕИС для протоколов/отмен идентичен (документ → запись в журнале → в некоторых случаях авто-переход этапа), и разъяснение технически та же операция «разместить документ», поэтому по аналогии ожидаемо тоже двигает `lastDateChangeCsv` — но это **экстраполяция, не прямое наблюдение**. Стоит перепроверить при первой возможности на реальном примере с разъяснением, прежде чем полагаться на это в проде.

## 12. Предлагаемые правки схемы (на решение — `01-database.md` не редактировался)

- **223-ФЗ лоты — отдельная сущность, не денормализация в `prc_procurements`.** Нужна таблица вида `prc_lots` (`id, procurement_id FK, source_lot_number int/text, lot_guid text nullable unique(procurement_id, lot_guid) — заполняется для 223-ФЗ, title, is_centralized bool, price numeric(18,2), currency, okpd2_code, okved_code`). В `01-database.md` §4 у `prc_bids`/`prc_awards` УЖЕ есть `lot_id FK nullable` — модель это предвидела; не хватает только master-таблицы лота (номер/название/цена/ОКПД2/ОКВЭД2/флаг централизации из `lot-list.html`). Для 44-ФЗ `lot_id` естественно остаётся `NULL` (весь объект закупки = единственный виртуальный «лот»).
- **223-ФЗ требует хранить technical `source_guid` (GUID извещения), а для лота — свой `lot_guid`.** Без `noticeGuid` часть вкладок (`lot-list.html`, вероятно и `changes-and-explanations.html`/`protocols.html`/`event-journal.html`) недоступна напрямую (проверено: без гуида — таймаут страницы). Предлагается добавить `source_guid text nullable` в `prc_procurements` (для 44-ФЗ — `null`, там GUID не требуется) и `lot_guid` в предлагаемую `prc_lots`.
- **Явное поле «Редакция» на карточке 223-ФЗ** подтверждает необходимость универсального `revision_number`-механизма (уже заложен в модели ревизий `01-database.md`) — для 223-ФЗ его можно мэпить напрямую с этого поля карточки, а не только реконструировать из diff.
- **`lastDateChangeCsv` подтверждён как достаточный триггер** для протоколов/отмен на живых данных — можно понизить приоритет/срочность соответствующего открытого вопроса в `02-crawling.md` §9 (доп. независимый триггер на event-journal остаётся best-effort защитой, а не обязательным механизмом MVP).
